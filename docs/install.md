## ติดตั้งด้วย Docker

ต้องมี Docker และ Docker Compose v2 (คำสั่ง `docker compose` ไม่ใช่ `docker-compose`)

1. ดาวน์โหลดโค้ดมาไว้ในเครื่อง server แล้วเข้าไปในโฟลเดอร์โปรเจกต์
2. คัดลอกไฟล์ตั้งค่า
   ```bash
   cp .env.example .env
   ```
3. เปิด `.env` แล้วแก้ตามต้องการ (ทุกบรรทัดอธิบายอยู่ในไฟล์ ดูรายการทั้งหมดที่ [ตั้งค่าระบบ](configuration.md))
   - ถ้าใช้แค่ในเครื่องหรือวง LAN ให้ **ลบหรือคอมเมนต์** บรรทัด `COMPOSE_PROFILES=tunnel` (ตัวอย่างเปิด Cloudflare Tunnel ไว้)
   - อยากกำหนดรหัสผ่าน admin เอง ใส่ `ADMIN_PASSWORD=...` ก่อนเริ่มครั้งแรก
4. สร้างและเริ่มระบบ
   ```bash
   docker compose up -d --build
   ```
5. ดูรหัสผ่านที่สุ่มให้ (ถ้าไม่ได้ตั้ง `ADMIN_PASSWORD`)
   ```bash
   docker compose logs file-center
   ```
6. เปิด `http://localhost:3000` (หรือพอร์ตที่ตั้งใน `PORT`) เข้าสู่ระบบด้วยชื่อผู้ใช้ `admin` ระบบบังคับให้เปลี่ยนรหัสผ่านทันที

คำสั่งที่ใช้บ่อย

| ต้องการ | คำสั่ง |
|---|---|
| ดูสถานะ (ดูคอลัมน์ `healthy`) | `docker compose ps` |
| ดู log สด | `docker compose logs -f file-center` |
| เริ่มใหม่ให้อ่าน `.env` ใหม่ | `docker compose up -d` |
| หยุด | `docker compose down` |
| สร้างอิมเมจใหม่ (หลังแก้ Dockerfile หรือรับอัปเดตฐาน) | `docker compose build --pull` แล้ว `docker compose up -d` |

ค่าเริ่มต้นของ `docker-compose.yml` เปิดพอร์ตให้เข้าได้จากเครื่อง server เท่านั้น (`127.0.0.1:3000`) ถ้าต้องการให้เครื่องอื่นในวง LAN เข้าตรงได้ ให้ตั้ง `BIND_ADDRESS=0.0.0.0` ใน `.env`

log ของคอนเทนเนอร์เก็บไม่เกิน 3 ไฟล์ × 10 MB ต่อคอนเทนเนอร์ (ตั้งใน `docker-compose.yml`)

## ข้อมูลอยู่ที่ไหน และถ้าไฟล์ข้อมูลเสีย

ข้อมูลทั้งหมดอยู่ในโฟลเดอร์ `./data` ข้างไฟล์ `docker-compose.yml` เท่านั้น:

- `data/storage/` ไฟล์ที่อัปโหลด
- `data/system/` ผู้ใช้ การตั้งค่า โลโก้ ประวัติ ถังขยะ session และไฟล์อัปโหลดที่ยังไม่เสร็จ (เป็นไฟล์ JSON ธรรมดา ไม่มีฐานข้อมูลแยก)
- `data/backups/` ไฟล์สำรองของระบบ (ค่าเริ่มต้น ควรย้ายไปดิสก์อื่น ดู [คู่มือผู้ดูแล: สำรองและกู้คืนข้อมูล](admin-guide.md#สำรองและกู้คืนข้อมูล))

รายการไฟล์ใน `data/system/` ทั้งหมดอยู่ที่ [ตั้งค่าระบบ: ไฟล์ข้อมูลใน DATA_DIR](configuration.md#ไฟล์ข้อมูลใน-data_dir)

**ความทนทานของไฟล์ข้อมูล (ตั้งแต่ 1.12.1)**

- ไฟล์ JSON เขียนเป็นไฟล์ชั่วคราว → `fsync` → เปลี่ยนชื่อ จึงไม่มีช่วงที่ไฟล์เขียนไม่ครบ
- ถ้าเขียนไม่ได้ (ดิสก์เต็ม ฯลฯ) ระบบลองซ้ำ 3 ครั้งห่างกัน 0.2 / 1 / 3 วินาที บันทึก error `store-write-failed` ส่งการแจ้งเตือนผู้ดูแล (กระดิ่ง และ webhook ถ้าตั้งไว้) แล้วลองใหม่ทุก 30 วินาทีจนสำเร็จ ระหว่างนั้นการเปลี่ยนแปลงล่าสุดอยู่ในหน่วยความจำอย่างเดียว ถ้ารีสตาร์ตจะหาย
- ตอนหยุดระบบ (`docker stop`, รีสตาร์ต) ระบบเขียนไฟล์ข้อมูลที่ค้างอยู่ **ก่อน** รอคำขอที่ยังทำงาน (รอไม่เกิน 3 วินาทีแล้วปิดการเชื่อมต่อที่เหลือ) และเขียนอีกครั้งแบบ synchronous ก่อนออกถ้าเกิน 8 วินาที

**ถ้าไฟล์ข้อมูลเสียหาย:** `users.json`, `settings.json`, `groups.json`, `grants.json`, `shares.json` และ `app-passwords.json` ถ้า JSON อ่านไม่ได้ ระบบ **ไม่เริ่ม** และไม่ล้างเป็นค่าว่างเอง

1. ดู log (`docker compose logs file-center`) จะบอกชื่อไฟล์และวิธีแก้
2. ระบบเก็บสำเนา `<ไฟล์>.broken-<เวลา>` ไว้ข้างไฟล์เดิม
3. เลือกอย่างใดอย่างหนึ่ง: แก้ JSON ให้ถูก · นำไฟล์จากไฟล์สำรองมาวางแทน · ลบไฟล์เพื่อเริ่มจากว่าง

ข้อมูลที่สร้างใหม่ได้ (รายการโปรด/ล่าสุด, session ฯลฯ) ระบบเริ่มใหม่จากว่างและเก็บ `.broken-<เวลา>` ไว้เช่นกัน

## ย้ายไปเครื่องใหม่

1. ที่เครื่องเดิม: `docker compose down` (หยุดก่อน เพื่อให้ไฟล์ข้อมูลนิ่ง)
2. คัดลอก **ทั้งโฟลเดอร์โปรเจกต์** (รวม `data/` และ `.env`) ไปเครื่องใหม่
3. ที่เครื่องใหม่: `docker compose up -d --build`

ไม่ต้องแก้ค่าใด ๆ ผู้ใช้ รหัสผ่าน ไฟล์ ถังขยะ และประวัติจะอยู่ครบ ผู้ที่ login อยู่ยัง login ต่อได้ ข้อมูลไม่มีพาธเครื่องเดิมฝังอยู่ เครื่องใหม่ต้องมี Docker กับ Docker Compose v2 และถ้าใช้ Cloudflare Tunnel เครื่องใหม่ต่อเข้าโดเมนเดิมได้เลยเพราะโทเคนอยู่ใน `.env`

> การคัดลอก `data/` พา `secret.key` (กุญแจ 2FA) ไปด้วย 2FA เดิมจึงใช้ได้ต่อ แต่ถ้าย้ายด้วยการ **กู้คืนจากไฟล์สำรอง** บนระบบที่ติดตั้งใหม่ ไฟล์สำรองไม่มี `secret.key` ดูวิธีรับมือที่ [คู่มือผู้ดูแล: กู้คืนบนเครื่องอื่น](admin-guide.md#กู้คืนบนเครื่องอื่นและ-2fa)

## แอปในคอนเทนเนอร์ไม่ได้รันเป็น root

แอปทำงานเป็นผู้ใช้ `bun` (uid 1000 ของอิมเมจ `oven/bun`) ถ้ามีช่องโหว่ในแอป ผู้โจมตีจะไม่ได้สิทธิ์ root ในคอนเทนเนอร์

- ตอนเริ่ม `scripts/docker-entrypoint.sh` เริ่มเป็น root ก่อน ถ้า `./data` (หรือโฟลเดอร์ชั้นแรกในนั้น) ยังไม่เป็นของ `bun` จะเปลี่ยนเจ้าของให้ (`chown -R`) **ครั้งเดียว** หลังอัปเกรดจากเวอร์ชันที่รันเป็น root (ข้อมูลมากอาจใช้เวลาสักครู่ในการเริ่มครั้งนั้น) แล้วจึงสลับเป็น `bun` และเริ่ม launcher
- การอัปเดตและรีสตาร์ตผ่านหน้าเว็บเขียนเฉพาะใน `/data` จึงใช้ได้ตามเดิม
- บนเครื่อง host ไฟล์ใน `./data` จะเป็นของ uid 1000 (ใช้ `sudo` ถ้าต้องจัดการไฟล์เหล่านั้นด้วยบัญชีอื่น)

**ตรวจบนเครื่อง server หลังอัปเกรด**

```bash
docker compose up -d --build
docker compose top file-center                                  # คอลัมน์ UID ของ bun src/launcher.ts และ src/index.ts ต้องเป็น 1000 (หรือชื่อผู้ใช้ uid 1000 ของเครื่อง host) ไม่ใช่ root
docker compose exec file-center grep -E '^(Uid|Gid)' /proc/1/status   # ต้องเป็น 1000
ls -ln data                                                     # storage และ system เป็นของ 1000
```

แล้วเปิดหน้าเว็บ อัปโหลดไฟล์หนึ่งไฟล์ ดาวน์โหลดกลับ และลบลงถังขยะ ให้ทำได้ตามปกติ

> `docker compose exec file-center id` จะแสดง root เพราะ `exec` เปิดโปรเซสใหม่ด้วยผู้ใช้ตั้งต้นของคอนเทนเนอร์ ซึ่งต้องเป็น root เพื่อเปลี่ยนเจ้าของ `./data` ตอนเริ่ม ไม่ได้บอกว่าแอปรันเป็นใคร ให้ดูจาก `top` หรือ `/proc/1/status` ตามด้านบน

**ทางหนีไฟ:** ถ้ามีปัญหาเรื่องสิทธิ์ไฟล์ (เช่น `./data` อยู่บน NFS ที่ไม่ยอมให้ `chown`) ให้ใส่ `FC_RUN_AS_ROOT=true` ใน `.env` แล้ว `docker compose up -d` แอปจะรันเป็น root เหมือนเดิม

## ตั้งค่าความปลอดภัยของคอนเทนเนอร์

อิมเมจใช้ฐาน `oven/bun:1.4.4-slim` (เล็กกว่าฐานเต็มราว 70 MB ที่ลดคือขนาด ไม่ใช่จำนวนแพ็กเกจ เพราะฐานทั้งสองมีชุดแพ็กเกจ Debian เดียวกัน `dpkg -l | wc -l` นับได้เท่ากันคือ 85 บรรทัด) ไม่ใช้ distroless เพราะ entrypoint ต้องมี shell ทำ `chown` ครั้งเดียวและ `setpriv`

`docker-compose.yml` ของบริการ `file-center` ตั้งไว้ดังนี้ (`scripts/ci-docker.sh` ตรวจทุกข้อกับคอนเทนเนอร์จริง)

| ค่า | ทำอะไร | ถ้า host ใช้ไม่ได้ |
|---|---|---|
| `read_only: true` + `tmpfs: /tmp` | ระบบไฟล์ของอิมเมจเขียนไม่ได้ เขียนได้เฉพาะ `/data` (ข้อมูล และเวอร์ชันที่อัปเดตจากเว็บใน `/data/system/app` จึงอัปเดตได้ตามเดิม) กับ `/tmp` ในหน่วยความจำ 256 MB | ลบสองบรรทัดนี้ (ถ้าเพิ่ม volume ที่แอปต้องเขียน เช่น `BACKUP_DIR=/backups` ก็ต้องเป็น volume ที่เขียนได้อยู่แล้ว) |
| `cap_drop: [ALL]` + `cap_add` | `CHOWN` เปลี่ยนเจ้าของ `./data` ของการติดตั้งเก่า · `SETUID` และ `SETGID` ใช้ใน `setpriv` ลดจาก root เป็น `bun` · `DAC_OVERRIDE` อ่านโฟลเดอร์ใน `./data` ที่เป็นของผู้ใช้อื่นและปิดสิทธิ์ไว้ (และเขียน `./data` ตอน `FC_RUN_AS_ROOT=true`) หลังลดเป็น `bun` แล้วแอปไม่เหลือสิทธิ์ใด (`CapEff` ใน `/proc/1/status` เป็น 0) | ลบ `cap_drop` และ `cap_add` ถ้า host (เช่น NAS บางรุ่น) ไม่รองรับ |
| `security_opt: no-new-privileges:true` | โปรเซสในคอนเทนเนอร์ขอสิทธิ์เพิ่มผ่าน setuid ไม่ได้ | ลบบรรทัดนั้น |
| `mem_limit` / `pids_limit` | จำกัดหน่วยความจำ (ค่าเริ่มต้น 2g) และจำนวนโปรเซส (512) ปรับได้ด้วย `FC_MEMORY_LIMIT` / `FC_PIDS_LIMIT` ใน `.env` | ตั้งให้สูงขึ้นถ้าเก็บไฟล์ใหญ่มากหรือมีผู้ใช้พร้อมกันมาก (แอปถูกฆ่าเมื่อเกิน `mem_limit`) |

**ตรวจบนเครื่อง server**

```bash
docker compose exec file-center touch /app/x                              # ต้องล้มเหลว: Read-only file system
docker compose exec file-center grep -E 'CapEff|NoNewPrivs' /proc/1/status   # ต้องได้ 0000000000000000 กับ 1
```

รายละเอียดด้านความปลอดภัยอื่นของคอนเทนเนอร์และการตรวจช่องโหว่ใน CI อยู่ที่ [ความปลอดภัย](security.md#ความปลอดภัยของคอนเทนเนอร์)

## รันโดยไม่ใช้ Docker

ต้องมี [Bun](https://bun.sh) แนะนำ 1.4.2 ซึ่งเป็นเวอร์ชันที่อิมเมจและ CI ใช้ ทดสอบบน Linux แล้ว การรันด้วย Bun บน Windows โดยตรงยังไม่ได้ทดสอบ (ดู [ข้อจำกัดที่ควรรู้](security.md#ข้อจำกัดที่ควรรู้))

```bash
bun install
bun run build      # คอมไพล์หน้าเว็บ (ถ้าไม่มี Node ในเครื่องให้ใช้: bun --bun run build)
bun start          # เปิดที่ http://localhost:3000
```

- `bun start` รัน `src/launcher.ts` เพื่อให้อัปเดตและกู้คืนข้อมูลจากหน้าเว็บ (รีสตาร์ตเอง) ได้ ถ้ารัน `bun src/index.ts` ตรง ๆ หน้าอัปเดตจะแจ้งว่ารีสตาร์ตตัวเองไม่ได้
- Bun อ่านไฟล์ `.env` ในโฟลเดอร์ที่รันให้เอง
- ข้อมูลอยู่ที่ `./storage` (ไฟล์) และ `./data` (ระบบ) ข้างโค้ด เปลี่ยนได้ด้วย `STORAGE_DIR` และ `DATA_DIR` ไฟล์สำรองอยู่ที่ `./backups`
- ครั้งแรกระบบสร้างบัญชี `admin` ให้และ **แสดงรหัสผ่านที่สุ่มไว้ในหน้าจอ** (บังคับให้เปลี่ยนทันทีที่เข้าสู่ระบบ) หรือกำหนดเองด้วย `ADMIN_PASSWORD=...` ก่อนเริ่มครั้งแรก
- ONLYOFFICE ต้องติดตั้ง document server เองและตั้ง `OFFICE_*` ดู [ONLYOFFICE](#แก้ไขเอกสาร-office-ด้วย-onlyoffice) ส่วนภาพตัวอย่างต้องมี `vipsthumbnail`, `pdftoppm`, `ffmpeg` ในเครื่อง (ดู [เครื่องมือภาพตัวอย่าง](#เครื่องมือภาพตัวอย่างในอิมเมจ))

การพัฒนาแก้โค้ด (`bun run dev`) อยู่ใน [คู่มือนักพัฒนา](development.md)

## ใช้งานผ่านโดเมนด้วย Cloudflare Tunnel

Cloudflare Tunnel ให้คนภายนอกเข้าผ่านโดเมน (เช่น `https://files.example.com`) ได้โดย **ไม่ต้องเปิดพอร์ตที่เราเตอร์และไม่ต้องมี IP จริง** เพราะคอนเทนเนอร์ `cloudflared` เป็นฝ่ายต่อออกไปหา Cloudflare เอง และ Cloudflare ทำ HTTPS ให้

1. **นำโดเมนเข้า Cloudflare** ที่ [dash.cloudflare.com](https://dash.cloudflare.com) เพิ่มโดเมน แล้วเปลี่ยน nameserver ที่ผู้ให้บริการโดเมนเป็นของ Cloudflare รอจนสถานะโดเมนเป็น Active (ไม่กี่นาทีถึงหลายชั่วโมง)
2. **สร้าง tunnel** ที่ Zero Trust (one.dash.cloudflare.com) > Networks > Tunnels > Create a tunnel > เลือก Cloudflared > ตั้งชื่อ เช่น `file-center` หน้าถัดไปเลือก Docker แล้วคัดลอก **โทเคน** (ข้อความยาวหลัง `--token`) ไม่ต้องรันคำสั่งที่หน้านั้นให้
3. **ตั้งค่า `.env`** (คัดลอกจาก `.env.example` ถ้ายังไม่มี) ให้มีค่าเหล่านี้
   ```env
   COMPOSE_PROFILES=tunnel
   TUNNEL_TOKEN=โทเคนที่คัดลอกมา
   SECURE_COOKIE=true
   TRUST_PROXY=cloudflare
   BIND_ADDRESS=127.0.0.1
   ```
   อยากไม่ให้โทเคนโผล่บนจอหรือค้างในประวัติคำสั่ง ใช้สคริปต์นี้แทนการพิมพ์เอง (วางโทเคนได้ทั้งแบบเปล่า ๆ หรือทั้งคำสั่งที่ Cloudflare ให้มา)
   ```bash
   sh scripts/set-tunnel-token.sh
   ```
   สคริปต์เขียน `COMPOSE_PROFILES=tunnel` กับ `TUNNEL_TOKEN` ลง `.env` และตั้งสิทธิ์ไฟล์เป็น `600` (ถ้าเคยตั้ง `COMPOSE_PROFILES=tunnel,office` ให้เติม `office` กลับเอง)
4. **เริ่มระบบ** `docker compose up -d --build` แล้วดูว่า tunnel ในหน้า Zero Trust ขึ้นสถานะ Healthy
5. **ผูกโดเมนกับระบบ** ในหน้า tunnel > Public Hostname (หรือ Published application routes) > Add
   - Subdomain: `files` · Domain: โดเมนของคุณ
   - Service Type: `HTTP` · URL: `file-center:3000` (ชื่อบริการในเครือข่ายของ Docker ไม่ใช่ localhost)

   Cloudflare สร้าง DNS ให้อัตโนมัติ เปิด `https://files.โดเมนของคุณ` ได้ทันที
6. **ตั้งค่าที่แนะนำใน Cloudflare** (หน้าโดเมน)
   - SSL/TLS > Edge Certificates: เปิด Always Use HTTPS และตั้ง Minimum TLS Version เป็น 1.2
   - **ห้ามสร้าง Cache Rule แบบ "Cache Everything"** กับโดเมนนี้ เพราะจะทำให้ไฟล์ส่วนตัวและ API ถูกเก็บไว้ที่ Cloudflare (ระบบตั้ง `Cache-Control` ให้เองแล้ว: ไฟล์หน้าเว็บใน `/assets/` cache ได้ ส่วนไฟล์ที่ดาวน์โหลดและ API ไม่ถูก cache)
   - ถ้าต้องการชั้นป้องกันเพิ่มสำหรับผู้ดูแล ใช้ Cloudflare Access ครอบพาธ `/admin` และ `/api/admin` ได้

**ข้อควรรู้เมื่อใช้ผ่าน Cloudflare**

- Cloudflare แพ็กเกจ Free/Pro รับคำขอได้ไม่เกิน **100 MB ต่อครั้ง** ระบบอัปโหลดแบ่งส่งทีละ 8 MB จึงอัปโหลดไฟล์ใหญ่ได้ตามปกติ (อย่าตั้ง `UPLOAD_CHUNK_SIZE` เกิน 100 MB) แต่ **WebDAV ส่งทั้งไฟล์ในคำขอเดียว** จึงอัปโหลดไฟล์เกิน 100 MB ผ่านโดเมนไม่ได้ (ดู [คู่มือผู้ใช้: WebDAV](user-guide.md#ข้อจำกัดของ-webdav))
- Cloudflare ตัดคำขอที่เซิร์ฟเวอร์ตอบช้ากว่าประมาณ 100 วินาที (หน้าเว็บจะได้ error 524) การบีบอัด/แตก zip ที่ใหญ่มากอาจเจอกรณีนี้ แต่งานยังทำต่อจนเสร็จที่เซิร์ฟเวอร์ รอสักครู่แล้วรีเฟรชหน้า (วัดจริง: บีบอัดไฟล์ 5 GB ใช้ ~24 วินาที แตก ~26 วินาที เพราะไฟล์ใหญ่กว่า 1 MB ที่บีบอัดไม่ลง เช่น วิดีโอ จะถูกเก็บใน zip แบบไม่บีบอัด)
- ข้อกำหนดของ Cloudflare จำกัดการใช้ CDN แบบไม่เสียเงินเพื่อเผยแพร่วิดีโอหรือไฟล์ขนาดใหญ่ในปริมาณมาก ถ้าจะใช้แจกไฟล์ใหญ่จำนวนมาก ควรอ่านข้อกำหนดก่อน
- โทเคนใน `.env` คือกุญแจของ tunnel ใครได้ไปก็ต่อเข้าโดเมนนี้ได้ ห้ามแชร์ ถ้าหลุดให้ Refresh token ในหน้า tunnel
- ถ้าเปิด `BIND_ADDRESS=0.0.0.0` คู่กับ `TRUST_PROXY=cloudflare` คนในวง LAN ที่เข้าตรงจะปลอม IP ของตัวเองได้ (ไม่กระทบสิทธิ์ แต่กระทบการล็อกและประวัติ)
- ตัวแอปไม่เห็น `TUNNEL_TOKEN` (compose ตั้งให้แอปเห็นเป็นค่าว่าง) แม้แต่โค้ดที่อัปเดตจากหน้าเว็บก็อ่านโทเคนนี้ไม่ได้

**reverse proxy อื่น (1Panel/OpenResty, nginx, Caddy):** ทุกคำตอบของ `/api/*` มีหัว `Cache-Control: no-store` (ตั้งแต่ 1.7.1) proxy ที่ทำตามหัวนี้จะไม่เก็บไว้ ถ้าเปิดแคชแบบบังคับใน proxy ให้ยกเว้น `/api/` หรือปิดแคชของไซต์นี้ ไม่อย่างนั้นรายการไฟล์จะไม่อัปเดต (เช่น อัปโหลดโฟลเดอร์แล้วไม่ขึ้นในรายการ) และข้อมูลส่วนตัวของผู้ใช้คนหนึ่งอาจถูกส่งให้อีกคน และตั้ง `TRUST_PROXY=true` (ดูหัวข้อถัดไป)

## ใช้หลัง 1Panel หรือ nginx

ถ้าเปิดแอปตรง ๆ (`http://<เครื่อง>:<PORT>`) เร็วปกติ แต่ผ่านโดเมนแล้วช้า สาเหตุมักอยู่ที่ reverse proxy ไม่ใช่ตัวแอป ค่าเริ่มต้นของ nginx/OpenResty (1Panel) พักทั้งตัวไฟล์ที่ส่งขึ้นและที่ส่งลงไว้ในหน่วยความจำหรือไฟล์ชั่วคราวก่อนส่งต่อ และจำกัดขนาดคำขอไว้ที่ 1 MB

ในหน้าตั้งค่าไซต์ของ 1Panel (เว็บไซต์ > ไซต์ > การตั้งค่า > ไฟล์ตั้งค่า) หรือในไฟล์ `server { }` ของ nginx ให้ตั้งดังนี้

```nginx
client_max_body_size 0;          # ไม่จำกัดขนาด (แอปจำกัดเองด้วย UPLOAD_MAX_SIZE)
location / {
    proxy_pass http://127.0.0.1:<PORT>;
    proxy_http_version 1.1;
    proxy_request_buffering off; # ส่งชิ้นอัปโหลดต่อทันที ไม่พักก่อน
    proxy_buffering off;         # ส่งไฟล์ดาวน์โหลดให้ผู้ใช้ทันที ไม่พักก่อน
    proxy_max_temp_file_size 0;  # ไม่เขียนไฟล์ชั่วคราวลงดิสก์ของ proxy
    proxy_read_timeout 3600s;    # zip ใหญ่และขั้นตอน "ประกอบไฟล์" ใช้เวลานานได้
    proxy_send_timeout 3600s;
}
```

- เปิด **HTTP/2** ที่ไซต์ (ใน 1Panel: ตั้งค่า HTTPS > เปิด HTTP/2) เบราว์เซอร์จะส่งหลายชิ้นพร้อมกันบนการเชื่อมต่อเดียวได้ดีกว่า HTTP/1.1
- **อย่าเพิ่มหัว `Cache-Control` หรือกฎแคชให้ `/api`** แอปตั้งหัวที่ถูกต้องให้เองอยู่แล้ว
- proxy ของคุณเองต้องส่งหัว `X-Forwarded-For` แล้วตั้ง `TRUST_PROXY=true` และ `SECURE_COOKIE=true` (เมื่อใช้ HTTPS) ใน `.env` ระบบใช้ค่า **สุดท้าย** ของ `X-Forwarded-For` (ค่าที่ proxy ของคุณเขียน)
- ตั้งแต่ 1.9.1 แอปรอคำขอที่เงียบได้นานสุด 255 วินาที (เดิม 30 วินาที) การรวมชิ้นส่วนของไฟล์ใหญ่และ zip ขนาดใหญ่จึงไม่ถูกตัดกลางคัน
- **Cloudflare แบบเมฆส้ม (proxied) ทำให้ไฟล์ใหญ่ช้าได้** ทราฟฟิกอาจถูกส่งอ้อมผ่านประเทศอื่นก่อนถึงเครื่องคุณ และแพ็กเกจ Free/Pro รับคำขอได้ไม่เกิน 100 MB ต่อครั้ง ถ้าจะส่งไฟล์ใหญ่บ่อย ๆ ให้ใช้โดเมนที่ตั้งเป็น **เมฆเทา (DNS only)** หรือใช้ Tailscale เข้าเครื่องโดยตรงแทน

## วัดว่าช้าที่ตรงไหน

ลองดาวน์โหลดไฟล์ใหญ่ไฟล์เดียวสามทาง (ไฟล์ในพื้นที่ public ที่ผู้ใช้ guest ดาวน์โหลดได้ หรือใส่คุกกี้ `-b 'fc_sid=...'` ของคุณ) ดูค่าความเร็วเป็นไบต์ต่อวินาที

```bash
# 1) ตัวแอปโดยตรง
curl -o /dev/null -w '%{speed_download}\n' 'http://127.0.0.1:<PORT>/api/download?space=public&path=/<ไฟล์>'

# 2) ผ่าน proxy บนเครื่องเดียวกัน (ไม่ผ่านอินเทอร์เน็ต)
curl -o /dev/null -w '%{speed_download}\n' --resolve <โดเมน>:443:127.0.0.1 'https://<โดเมน>/api/download?space=public&path=/<ไฟล์>'

# 3) ผ่านโดเมนจริง (รวม Cloudflare และเส้นทางอินเทอร์เน็ต)
curl -o /dev/null -w '%{speed_download}\n' 'https://<โดเมน>/api/download?space=public&path=/<ไฟล์>'
```

| ผลที่ได้ | ปัญหาอยู่ที่ |
|---|---|
| ข้อ 1 ช้า | ดิสก์หรือตัวเครื่อง |
| ข้อ 1 เร็ว แต่ข้อ 2 ช้า | การตั้งค่า proxy ด้านบน |
| ข้อ 2 เร็ว แต่ข้อ 3 ช้า | เส้นทางอินเทอร์เน็ตหรือ Cloudflare (ลองเมฆเทา/Tailscale) |

## แก้ไขเอกสาร office ด้วย ONLYOFFICE

เปิดและแก้ไฟล์ `.docx` `.xlsx` `.pptx` `.odt` `.ods` `.odp` `.csv` `.txt` ในเบราว์เซอร์ได้ด้วย ONLYOFFICE Docs (Community Edition ฟรี) ซึ่งรันเป็นคอนเทนเนอร์แยก (`.doc` `.xls` `.ppt` แบบเก่าเปิดดูได้อย่างเดียว) **ปิดไว้โดยค่าเริ่มต้น** จะเปิดเมื่อตั้งค่าครบเท่านั้น ถ้าไม่ได้ตั้งค่า ปุ่มแก้ไขด้วย Office ไม่แสดงและใช้การดูในหน้าเว็บแทน (ดูฝั่งผู้ใช้ที่ [คู่มือผู้ใช้](user-guide.md#แก้ไขด้วย-onlyoffice))

- **ทรัพยากร:** document server ใช้ RAM ราว 2–4 GB (ขั้นต่ำ 2 GB + swap แนะนำ 4 GB) และดิสก์ราว 3 GB สำหรับอิมเมจ ครั้งแรกที่เริ่มใช้เวลา 1–2 นาทีก่อนพร้อมใช้งาน
- **รุ่นฟรีจำกัด 20 การเชื่อมต่อพร้อมกัน** (นับทุกแท็บที่เปิดเอกสารอยู่ ทั้งดูและแก้) เกินนั้นผู้ใช้คนถัดไปจะเปิดเอกสารไม่ได้จนกว่าจะมีคนปิด

**เปิดใช้งาน (Docker)** เพิ่มใน `.env` แล้ว `docker compose up -d`

```env
# ถ้าใช้ tunnel อยู่แล้ว: COMPOSE_PROFILES=tunnel,office
COMPOSE_PROFILES=office
# สร้างด้วย  openssl rand -hex 32  (ไม่ตั้งหรือสั้นกว่า 32 ตัวอักษร = ปิด)
OFFICE_JWT_SECRET=ค่าที่สร้างได้
# ที่อยู่ของ document server ที่ "เบราว์เซอร์" เปิดได้
OFFICE_URL=http://localhost:8080
# ที่อยู่ที่ document server ใช้เรียก File Center (ชื่อคอนเทนเนอร์ ไม่ใช่ localhost)
OFFICE_INTERNAL_URL=http://file-center:3000
# ที่อยู่ที่ File Center ใช้ดาวน์โหลดไฟล์ที่บันทึก (ไม่ตั้ง = OFFICE_URL)
OFFICE_SERVER_INTERNAL_URL=http://onlyoffice
```

- `OFFICE_URL` ต้องเป็น `https://` (ยกเว้น `http://localhost` / `127.0.0.1` ใช้ในเครื่องเดียว) ค่าไม่ถูกต้องระบบยังเปิดได้ แต่จะเตือนใน log และปิดการแก้ไขเอกสารไว้
- คอนเทนเนอร์ `onlyoffice` (อิมเมจ `onlyoffice/documentserver:9.4.0`) เปิดพอร์ตที่ `127.0.0.1:8080` เท่านั้น (เปลี่ยนด้วย `OFFICE_PORT`) และได้ `JWT_SECRET` จาก `OFFICE_JWT_SECRET` เดียวกันอัตโนมัติ compose ตั้ง `ALLOW_PRIVATE_IP_ADDRESS` ให้ เพราะ document server ดาวน์โหลดไฟล์จาก `http://file-center:3000` ซึ่งเป็น IP ภายในของ Docker
- **ผ่าน Cloudflare Tunnel ต้องมี hostname ที่สอง** เพราะเบราว์เซอร์ของผู้ใช้โหลดโปรแกรมแก้ไขจาก document server โดยตรง: ในหน้า tunnel > Public Hostname > Add Subdomain `office` · Service `HTTP` · URL `onlyoffice:80` แล้วตั้ง `OFFICE_URL=https://office.โดเมนของคุณ` (ไม่ต้องเปิดพอร์ตเพิ่ม)
- รันด้วย bun โดยตรง (ไม่ใช้ Docker): ติดตั้ง document server เอง เปิด JWT ด้วยความลับเดียวกัน และตั้ง `OFFICE_INTERNAL_URL` เป็นที่อยู่ที่เครื่องนั้นเรียกถึง File Center ได้

กลไกและความปลอดภัยของการเชื่อมต่อ (โทเคนของลิงก์ JWT การบันทึกเป็นเวอร์ชัน CSP) อยู่ที่ [ความปลอดภัย: ONLYOFFICE](security.md#onlyoffice) และ API ที่ [คู่มือนักพัฒนา](development.md#onlyoffice)

## เครื่องมือภาพตัวอย่างในอิมเมจ

หน้ารายการไฟล์แสดงภาพเล็กของรูป หน้าแรกของ PDF และเฟรมหนึ่งของวิดีโอแทนไอคอนได้ สร้างโดย **เครื่องมือของระบบในอิมเมจ Docker** (ไม่ใช่ไลบรารีในแอป)

| ชนิด | นามสกุล | เครื่องมือ (แพ็กเกจ Debian) |
|---|---|---|
| รูป | jpg jpeg png webp gif (เฟรมแรก) bmp tif tiff และ heic heif avif ถ้า libvips ในเครื่องอ่านได้ | `vipsthumbnail` + `vipsheader` (`libvips-tools`) |
| PDF | pdf (หน้าแรก) | `pdftoppm` (`poppler-utils`) |
| วิดีโอ | mp4 m4v mov 3gp webm mkv avi mpg mpeg wmv flv (เฟรมที่ 1 วินาที ถ้าคลิปสั้นกว่านั้นใช้เฟรมแรก) | `ffmpeg` |

- `docker compose build` ใช้ฐาน Debian และลงเครื่องมือด้วย `apt-get` (ปิดทั้งหมดได้ด้วย `--build-arg THUMB_TOOLS=false` เฉพาะเครื่องที่เข้า mirror ของ Debian ไม่ได้)
- **ขนาดอิมเมจ:** เครื่องมือทั้งหมดเพิ่มพื้นที่ราว 500 MB (ประมาณ: libvips-tools + poppler-utils + ฟอนต์ ≈ 155 MB, ffmpeg ≈ 350 MB) ถ้าไม่ต้องการภาพตัวอย่างของวิดีโอ ตั้ง `THUMB_VIDEO=false` ใน `.env` แล้ว `docker compose up -d --build` อิมเมจจะไม่มี ffmpeg
- ถ้าไม่มีเครื่องมือ (หรืออิมเมจเก่า) ระบบไม่พัง หน้าเว็บแค่แสดงไอคอนเหมือนเดิม ตรวจได้ที่ `GET /api/thumbs/status` (ต้องเข้าสู่ระบบ) ได้ `{ "image": true, "pdf": true, "video": false }`
- `THUMBNAILS=off` ปิดการสร้างภาพตัวอย่างทั้งหมด แคชอยู่ที่ `DATA_DIR/thumbs` ตัดให้ไม่เกิน `THUMB_CACHE_MAX_MB`

**ทำไมใช้โปรแกรมของระบบ ไม่ใช้ไลบรารี `sharp`:** `sharp` ใช้งานได้ใน Bun (วัดแล้ว: jpg 4000×3000 → 256 px ใน ~60 ms, ติดตั้ง ~19 MB) แต่เป็น native addon ที่ต้องอยู่ใน `node_modules` ของอิมเมจ ขณะที่การอัปเดตจากหน้าเว็บส่งแต่ `server.js` ที่รวมไลบรารีไว้แล้ว addon จึงไม่ถูกส่งไปด้วยและโหลดไม่ได้หลังอัปเดต ส่วน `vipsthumbnail` เป็นโพรเซสแยก (ถ้าไฟล์ทำให้มันค้างหรือพัง กระทบแค่โพรเซสนั้น และฆ่าทิ้งเมื่อหมดเวลาได้) เร็วใกล้เคียงกัน (~120–200 ms ต่อรูป jpg 4000×3000) และถ้าไม่มีก็แค่ปิดภาพตัวอย่างโดยแอปไม่พัง

ฝั่งผู้ใช้ดูที่ [คู่มือผู้ใช้: ภาพตัวอย่าง แกลเลอรี และดูไฟล์ zip](user-guide.md#ภาพตัวอย่าง-แกลเลอรี-และดูไฟล์-zip) ส่วนข้อกำหนดความปลอดภัยของเครื่องมือ (ไม่ผ่าน shell, timeout 10 วินาที, คิว) อยู่ที่ [ความปลอดภัย](security.md#ภาพตัวอย่างและดูไฟล์-zip)

## เมื่อไรต้อง build อิมเมจใหม่

การอัปเดตจากหน้าเว็บ (**ระบบ → อัปเดตระบบ**) ส่งเฉพาะโค้ดของแอป (`server.js` กับหน้าเว็บ) **ไม่ส่งโปรแกรมของระบบ ไม่ส่ง launcher และไม่ส่ง Dockerfile** ดังนั้น

| เหตุการณ์ | ต้องทำ |
|---|---|
| อัปเดตโค้ดแอปธรรมดา | อัปเดตจากหน้าเว็บอย่างเดียว ไม่ต้องทำอะไรเพิ่ม |
| **ครั้งแรกที่เปิดใช้การอัปเดตจากหน้าเว็บ** (อิมเมจเก่าที่ยังไม่มี launcher) | `docker compose up -d --build` หนึ่งครั้ง เพื่อให้มี launcher หลังจากนั้นอัปเดตผ่านเว็บได้ตลอด |
| **รุ่นที่เพิ่มเครื่องมือของระบบ** เช่น 1.11 ที่เพิ่มเครื่องมือภาพตัวอย่าง (vips, poppler, ffmpeg) | `docker compose up -d --build` หนึ่งครั้งหลังอัปเดต ไม่งั้นหน้าเว็บแสดงไอคอนเหมือนเดิม |
| รุ่นที่แก้ `Dockerfile`, `scripts/docker-entrypoint.sh` หรือ `src/launcher.ts` | `docker compose up -d --build` |
| แก้เฉพาะ `docker-compose.yml` หรือ `.env` | `docker compose up -d` (ไม่ต้อง `--build`) |
| อยากได้อัปเดตความปลอดภัยของ Debian ฐาน | `docker compose build --pull` แล้ว `docker compose up -d` เป็นระยะ |

หมายเหตุ

- เวอร์ชันที่ติดตั้งผ่านเว็บเก็บใน `data/system/app/` (อยู่ใน volume จึงรอดการรีสตาร์ตคอนเทนเนอร์) ถ้าภายหลังสร้างอิมเมจใหม่แล้ว เวอร์ชันในอิมเมจ **ใหม่กว่า** เวอร์ชันที่อัปเดตไว้ ระบบจะใช้เวอร์ชันในอิมเมจ
- `launcher` (`src/launcher.ts`) อยู่ในอิมเมจและอัปเดตผ่านเว็บไม่ได้ ถ้าต้องแก้ส่วนนี้ต้อง build อิมเมจใหม่
- วิธีใช้หน้าอัปเดตอยู่ที่ [คู่มือผู้ดูแล: อัปเดตระบบ](admin-guide.md#อัปเดตระบบ)

## สร้างและเผยแพร่อัปเดตของคุณเอง

ส่วนนี้สำหรับคนที่แก้โค้ดหรือทำ fork ของตัวเอง ถ้าใช้รุ่นทางการ ไม่ต้องอ่านส่วนนี้ (ระบบติดตั้งรุ่นทางการที่เซ็นแล้วได้ทันที ไม่ต้องตั้งอะไร)

### กุญแจเซ็นแพ็กเกจ

**ระบบติดตั้งเฉพาะแพ็กเกจที่เซ็นแล้ว** (ทั้งไฟล์ที่อัปโหลดและที่ดึงจาก `UPDATE_SOURCE`) ถ้าไม่เซ็น ใครที่ได้ทั้ง session ของ admin และรหัสผ่าน admin ไปก็ติดตั้งโค้ดอะไรก็ได้ แต่เมื่อบังคับลายเซ็น แม้บัญชี admin ถูกยึดไปก็ติดตั้งโค้ดอื่นไม่ได้

ระบบฝังกุญแจสาธารณะของ File Center ไว้ใน `src/update-key.ts` กุญแจส่วนตัวของรุ่นทางการไม่อยู่ใน repository ถ้าสร้างแพ็กเกจเอง ต้องมีกุญแจของคุณเอง

1. **สร้างกุญแจครั้งเดียว** บนเครื่องที่ใช้สร้างแพ็กเกจ (ไม่ใช่เครื่อง server)
   ```bash
   bun run package --gen-key ~/file-center-keys
   ```
   ได้ไฟล์กุญแจส่วนตัว `~/file-center-keys/update-signing.key` (อ่านได้เฉพาะเจ้าของ) และ public key หนึ่งบรรทัดที่แสดงบนหน้าจอ ระบบไม่เขียนทับไฟล์กุญแจที่มีอยู่แล้ว
2. **เก็บกุญแจส่วนตัวไว้นอก server** ห้ามวางในโฟลเดอร์โปรเจกต์บน server ห้าม commit และควรสำรองไว้ที่ปลอดภัย ถ้ากุญแจหายต้องสร้างใหม่แล้วเปลี่ยน `UPDATE_PUBLIC_KEY` (ต้องเข้าเครื่อง server) ถ้ากุญแจหลุด ให้สร้างใหม่และเปลี่ยนทันที
3. **ตั้งค่าบน server** ใส่ public key ใน `.env` แล้วรีสตาร์ต (`docker compose up -d`)
   ```env
   UPDATE_PUBLIC_KEY=MCowBQYDK2VwAyEA...
   ```
   ถ้าค่าผิด ระบบยังเปิดใช้งานได้ตามปกติ แต่จะแจ้งใน log และไม่รับแพ็กเกจใด ๆ จนกว่าจะแก้ค่า กุญแจนี้ **ใช้แทน** กุญแจที่ฝังมา (แพ็กเกจรุ่นทางการจะถูกปฏิเสธ)
4. **สร้างแพ็กเกจแบบเซ็น** ทุกครั้งที่อัปเดต (ดูหัวข้อถัดไป)

ปิดการบังคับ: `UPDATE_ALLOW_UNSIGNED=true` รับแพ็กเกจที่ไม่เซ็นด้วย (แพ็กเกจที่เซ็นมายังต้องตรวจผ่าน) **เสี่ยง** ใครที่ได้ session และรหัสผ่านของ admin จะติดตั้งโค้ดของตัวเองบนเซิร์ฟเวอร์ได้ ระบบจะเตือนตอนเริ่มระบบ ในหน้าภาพรวมและหน้าอัปเดต และบันทึกการติดตั้งแพ็กเกจที่ไม่เซ็นเป็น `update-apply-unsigned`

### สร้างแพ็กเกจ

บนเครื่องที่มีโค้ด

1. เพิ่มเลข `version` ใน `package.json` (ระบบรับเฉพาะเวอร์ชันที่ใหม่กว่าที่ใช้อยู่)
2. สร้างแพ็กเกจแบบเซ็น
   ```bash
   bun run package --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน"
   ```
   ได้ `dist-update/file-center-<version>.zip` (ราว 1 MB) มี `manifest.json` (ขนาดและ SHA-256 ของทุกไฟล์) กับ `manifest.sig` (ลายเซ็นของ `manifest.json`) ไม่ใส่ `--sign` จะได้แพ็กเกจที่ไม่เซ็น ซึ่งระบบไม่รับ (เว้นแต่ `UPDATE_ALLOW_UNSIGNED=true`)
3. ติดตั้ง: ที่หน้า **ระบบ → อัปเดตระบบ** ลากไฟล์ `.zip` มาวาง (ดู [คู่มือผู้ดูแล](admin-guide.md#อัปเดตระบบ))

ตัวเลือกอื่นของ `bun run package` (มีในหัวไฟล์ `scripts/package.ts`): `--version 1.2.0` (กำหนดเวอร์ชันเอง ปกติใช้ใน `package.json`) และ `--skip-web` (ใช้ `web/dist` ที่ build ไว้แล้ว)

ระบบตรวจลายเซ็นตอนอัปโหลดและตรวจซ้ำตอนติดตั้ง แพ็กเกจที่ไม่มีลายเซ็น เซ็นด้วยกุญแจอื่น หรือถูกแก้หลังเซ็น จะถูกปฏิเสธ

### เผยแพร่ใน git และให้ server ตรวจหาเอง

**เผยแพร่** (บนเครื่องที่มีโค้ด ทุกครั้งที่ออกเวอร์ชันใหม่)

1. เพิ่ม `version` ใน `package.json` แล้ว commit ให้เรียบร้อย
2. สั่ง
   ```bash
   bun run release --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน" --push
   ```

ผลของคำสั่ง

- สร้างแพ็กเกจด้วย `scripts/package.ts` แล้ว commit ลง branch `updates` (branch ที่มีแต่แพ็กเกจ ไม่มีโค้ด สร้างให้เองถ้ายังไม่มี) พร้อม `SHA256SUMS`, แถวใหม่ในตารางของ `README.md` และ `latest.json` (เวอร์ชันล่าสุด ที่ server อ่าน)
- ไม่ยอมทำงานถ้ามีไฟล์ที่ยังไม่ได้ commit (แพ็กเกจต้องตรงกับ commit ที่ระบุ) หรือ version ไม่ใหม่กว่าทุกเวอร์ชันที่มีใน `updates` แล้ว
- ไม่ใส่ `--sign` ระบบไม่ยอมเผยแพร่ ต้องใส่ `--unsigned` ให้ชัดเจนเท่านั้น (เฉพาะ server ที่ตั้ง `UPDATE_ALLOW_UNSIGNED=true` จึงจะรับ)
- ไม่ใส่ `--push` = commit ไว้ในเครื่องเท่านั้น ตรวจแล้วค่อย `git push origin updates` เอง ใช้ `--skip-web` ถ้า build หน้าเว็บไว้แล้ว
- branch ปัจจุบันที่ทำงานอยู่ไม่ถูกแตะต้อง (ทำใน git worktree ชั่วคราวแล้วลบทิ้งเสมอ)

**ตั้งค่า server ให้ตรวจหาอัปเดตจากที่ของคุณ**

`.env.example` ใส่ `UPDATE_SOURCE` ของรุ่นทางการไว้ให้แล้ว ถ้าไม่มีบรรทัดนี้ server ก็ใช้รุ่นทางการที่ `https://raw.githubusercontent.com/RockZa27/file-center/updates` ปลอดภัยเพราะติดตั้งได้เฉพาะแพ็กเกจที่เซ็นด้วยกุญแจของ File Center ถ้าออกรุ่นเอง ให้ชี้ไปที่ branch `updates` ของคุณ ถ้าไม่ต้องการให้ server ติดต่อ GitHub เลย ให้ตั้ง `off` แล้วรีสตาร์ต (`docker compose up -d`)

```env
UPDATE_SOURCE=https://raw.githubusercontent.com/<owner>/<repo>/updates
# หรือปิด
UPDATE_SOURCE=off
```

- ใช้ได้กับ **repo สาธารณะ** เท่านั้น (server ดาวน์โหลดโดยไม่มีรหัสผ่านหรือ token) repo ส่วนตัวให้ดาวน์โหลดไฟล์ .zip เองแล้วลากมาวางแทน
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) และไม่ตามการ redirect ค่าอื่นระบบยังเปิดได้ แต่จะเตือนใน log และปิดการตรวจหาอัปเดตไว้
- **ลายเซ็นบังคับ:** server จะติดตั้งโค้ดที่ดึงมาจากอินเทอร์เน็ต SHA-256 ใน `latest.json` บอกได้แค่ว่าไฟล์ไม่เสียระหว่างทาง แต่บอกไม่ได้ว่าใครสร้าง ใครที่แก้ branch `updates` ได้ (หรือบัญชี GitHub ถูกยึด) ก็เปลี่ยนทั้งแพ็กเกจและ `latest.json` ได้ มีแต่ลายเซ็นที่กันกรณีนี้ จึงต้องตั้ง `UPDATE_PUBLIC_KEY` เป็นกุญแจของคุณคู่กับ `UPDATE_SOURCE` ของคุณ
- เมื่อตั้งแล้ว หน้า **ระบบ → อัปเดตระบบ** ตรวจหาเวอร์ชันใหม่ได้ และตรวจเองเบื้องหลังวันละครั้ง ดูวิธีใช้ที่ [คู่มือผู้ดูแล](admin-guide.md#อัปเดตจากหน้าเว็บในปุ่มเดียว)

#### ช่องทางเบตา (เวอร์ชัน x.y.z-beta.N)

เบตาคือเวอร์ชันทดลองที่ออกก่อนรุ่นปกติ (เช่น `1.9.0-beta.1` < `1.9.0-beta.2` < `1.9.0` ตามลำดับ semver) ตั้งแต่ 1.8.0

- **เผยแพร่:** ตั้ง `version` เป็น `x.y.z-beta.N` แล้วสั่ง `bun run release --beta --sign <กุญแจ> [--push]` ได้ไฟล์ `latest-beta.json` (รูปแบบเดียวกับ `latest.json` เพิ่ม `"channel": "beta"`) และแถวในตาราง README ของ branch `updates` ที่ติดป้าย "เบตา" โดย **ไม่แตะ `latest.json`** (server รุ่น 1.7.2 และเก่ากว่าอ่านแต่ `latest.json` จึงไม่เห็นเบตา)
- รุ่นปกติไม่รับ version `-beta` (ต้องใช้ `--beta`) และ `--beta` ไม่รับ version ปกติ เบตาต้องใหม่กว่า **ทุกเวอร์ชัน** ที่เผยแพร่แล้ว (ปกติและเบตา) ส่วนรุ่นปกติต้องใหม่กว่าทุก **รุ่นปกติ** (จึงออก `1.9.0` ต่อจาก `1.9.0-beta.2` ได้)
- ต้องเซ็นเสมอเหมือนรุ่นปกติ ไม่มีข้อยกเว้นสำหรับเบตา
- ฝั่งผู้ดูแลที่ติดตั้งเบตา ดู [คู่มือผู้ดูแล: เวอร์ชันทดลอง (เบตา)](admin-guide.md#เวอร์ชันทดลอง-เบตา)
