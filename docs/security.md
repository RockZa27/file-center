## หัว HTTP

- หน้าเว็บและไฟล์ JS/CSS ของหน้าเว็บส่ง `Content-Security-Policy` (โหลดสคริปต์ได้เฉพาะจากเว็บนี้เอง และจาก `OFFICE_URL` เมื่อเปิด ONLYOFFICE) และ `Permissions-Policy` (ปิดกล้อง ไมโครโฟน ตำแหน่ง)
- ไฟล์ที่ดาวน์โหลดและโลโก้ใช้ policy ของตัวเองที่เข้มกว่า (`sandbox`) ไม่ถูกแทนที่ ไฟล์ที่เปิดในแท็บ (`inline`) จำกัดเฉพาะชนิดที่ปลอดภัย
- เมื่อ `SECURE_COOKIE=true` ทุกคำตอบมี `Strict-Transport-Security: max-age=31536000` ด้วย และ cookie เป็นแบบ Secure
- คำตอบของ `/api/*` ทุกเส้นมี `Cache-Control: no-store`
- ทุกคำสั่งที่เปลี่ยนข้อมูลต้องส่งหัว `X-CSRF-Token` (ที่ได้จาก `GET /api/session`) ข้อยกเว้นคือเส้นทางที่ไม่มี session ของผู้ใช้ (ส่งไฟล์ผ่านลิงก์ขอไฟล์ ปลดล็อกลิงก์แชร์ webhook ของ LINE) ซึ่งใช้ cookie เฉพาะลิงก์หรือลายเซ็นแทน

## เลขเวอร์ชัน

`GET /api/health` ตอบแค่ `{ "status": "ok" }` เว้นแต่คำขอมาจากเครื่อง server เอง (ที่อยู่ของการเชื่อมต่อเป็น loopback และไม่มีหัว `X-Forwarded-For` / `CF-Connecting-IP` ที่ proxy ใส่มา) หรือจาก admin ที่เข้าสู่ระบบ ซึ่งได้ `version`, `release`, `boot`, `time` ตามเดิม (launcher และหน้าอัปเดต/กู้คืนใช้ค่าเหล่านี้) ส่วน `GET /api/session` ส่ง `config.version` ให้เฉพาะผู้ที่เข้าสู่ระบบ ผู้เยี่ยมชมจึงรู้เวอร์ชันของระบบไม่ได้

## รหัสผ่าน

- เก็บด้วย **argon2id** ผู้ใช้เดิมจาก FileGator ย้ายมาไม่ได้
- รหัสผ่านใหม่ (สร้างผู้ใช้ admin ตั้งให้ เปลี่ยนเอง) ต้อง
  - ยาวอย่างน้อย 10 ตัวอักษร (`GET /api/session` บอกความยาวขั้นต่ำใน `config.passwordMinLength`)
  - ไม่มีชื่อผู้ใช้อยู่ในรหัส (ไม่สนตัวพิมพ์เล็ก/ใหญ่)
  - ไม่เป็นรหัสที่ใช้กันบ่อย (100 อันดับแรก และรหัสยอดนิยมที่ยาว 10 ตัวขึ้นไป เช่น `password123`, `1q2w3e4r5t` รายการอยู่ใน `src/common-passwords.ts`)
  - ไม่เป็นตัวอักษรเดียวซ้ำกัน (`aaaaaaaaaa`) หรือเรียงตามแป้นพิมพ์/ตัวเลข/ตัวอักษร ทั้งไปและกลับ (`1234567890`, `0987654321`, `abcdefghij`, `qwertyuiop`, `asdfghjkl;`)
- รหัสผ่านเดิมที่ตั้งไว้ก่อนหน้ายังเข้าสู่ระบบได้ตามปกติ
- ผู้ใช้ที่ได้รหัสผ่านเริ่มต้นจากระบบต้องเปลี่ยนรหัสผ่านก่อน จึงจะเรียก API อื่นได้ (server บังคับ ไม่ใช่แค่หน้าเว็บ)
- **เปลี่ยนรหัสผ่าน** ใส่รหัสผ่านปัจจุบันผิดนับรวมในตัวนับเดียวกับการยืนยันรหัสผ่านก่อนทำงานอันตราย (ติดตั้งอัปเดต กู้คืน ลบกลุ่ม สร้างรหัสผ่านแอป ...) ผิดซ้ำถูกล็อก (429 `auth.confirm-locked` พร้อมแจ้งเตือน)
- รหัสผ่านของลิงก์แชร์ต้องยาวอย่างน้อย 6 ตัวอักษร เก็บแบบ hash เหมือนรหัสผ่านผู้ใช้

## การล็อกเมื่อรหัสผ่านผิดซ้ำ

| ตัวนับ | ค่าเริ่มต้น | ตัวแปร |
|---|---|---|
| IP + ชื่อผู้ใช้ เดียวกัน | ผิด 5 ครั้ง ล็อก 60 วินาที | `LOGIN_MAX_ATTEMPTS`, `LOGIN_LOCKOUT_SECONDS` |
| บัญชีเดียว จากทุก IP รวมกัน | 20 ครั้งใน 15 นาที | `LOGIN_ACCOUNT_MAX_ATTEMPTS`, `LOGIN_WIDE_WINDOW_MINUTES` |
| IP เดียว กับทุกชื่อผู้ใช้รวมกัน | 30 ครั้งใน 15 นาที | `LOGIN_ADDRESS_MAX_ATTEMPTS`, `LOGIN_WIDE_WINDOW_MINUTES` |

- สองตัวหลังกันการเดาแบบกระจาย IP (หนึ่งบัญชีหลาย IP) และการไล่เดาหลายชื่อจาก IP เดียว เกินแล้วบัญชีหรือ IP นั้นต้องรอ และส่งการแจ้งเตือนให้ผู้ดูแล **ใส่รหัสผ่านถูกก็ไม่ข้ามการรอ**
- ขั้นตอน 2FA (`/api/login/2fa`) ก็นับต่อบัญชีเช่นกัน รหัสผ่านแอป WebDAV ผิดซ้ำถูกล็อกเหมือนหน้าเข้าสู่ระบบ (ต่อ IP + ชื่อผู้ใช้ และต่อ IP) ตอบ 429 พร้อม `Retry-After`
- บันทึก `login-failed` เขียนไม่เกินนาทีละครั้งต่อ IP + ชื่อผู้ใช้ พร้อมจำนวนครั้ง กันบันทึกกิจกรรมถูกท่วม
- IP ที่ใช้นับมาจากการเชื่อมต่อ หรือจากหัวที่ proxy ใส่ ตามค่า `TRUST_PROXY` ถ้าตั้งผิด ผู้ใช้ทุกคนอาจเป็น IP เดียวกัน หรือ IP ปลอมได้

## ขีดจำกัดของคำขอ

- รายการในคำขอเดียว (`items` ของ batch, zip, ลบ, คัดลอก, ย้าย) ไม่เกิน 2,000 ชื่อ เกินแล้วตอบ 400 `files.bad-count` ชื่อซ้ำนับเป็นรายการเดียว และเช็กว่ามีอยู่จริงแบบ async
- คำขอ JSON ใหญ่เกิน 1 MB ตอบ 413 `request.too-big` ก่อนอ่านเนื้อหา (ยกเว้น `PUT /api/content` ที่ส่งข้อความได้ถึง 2 MB) ส่วนอัปโหลดชิ้นส่วนใช้ขีดจำกัดของตัวเอง
- ขนาดคำขอ: Bun รับเนื้อหาคำขอได้สูงสุดเท่า `UPLOAD_MAX_SIZE` เพื่อให้ `PUT` ของ WebDAV ไหลลงดิสก์ได้ทั้งไฟล์ ส่วนเส้นทางอื่นทั้งหมด (`/api/...`) รับได้ 2 ชิ้นอัปโหลด + 1 MB (`UPLOAD_CHUNK_SIZE`×2 + 1 MB) และ JSON ไม่เกิน 1 MB เกินแล้วตอบ 413 `request.too-big` ทันที ทั้งแบบมี `Content-Length` และแบบส่งเป็นท่อน (chunked) ที่ระบบนับไบต์ระหว่างรับ

## อัปโหลดของผู้เยี่ยมชม

ผู้ใช้หนึ่งคน (ผู้เยี่ยมชมที่ไม่ได้เข้าสู่ระบบนับแยกตาม IP ไม่ใช่รวมกัน จึงไม่มีใครเต็มโควตาแทนคนอื่นได้) ถืออัปโหลดที่ประกาศแล้วแต่ยังไม่เสร็จได้พร้อมกันไม่เกิน `UPLOAD_MAX_PENDING` งาน (ค่าเริ่มต้น 500, `0` = ไม่จำกัด) เกินแล้วตอบ 429 `upload.too-many-pending` จนกว่างานเดิมจะเสร็จ ถูกยกเลิก หรือหมดเวลา กันการประกาศไฟล์ค้างไปเรื่อย ๆ จนโฟลเดอร์ tmp บวม

ถ้าเปิดสิทธิ์ `upload` ให้ผู้เยี่ยมชม (ที่หน้า ระบบ → ตั้งค่า) ผู้เยี่ยมชมทุกคนใช้โควตารวมกันวันละ `GUEST_UPLOAD_DAILY_BYTES` (ค่าเริ่มต้น 1 GB, `0` = ห้ามอัปโหลด)

- ระบบนับขนาดไฟล์ตั้งแต่ตอนเริ่มอัปโหลด (อัปโหลดพร้อมกันหลายไฟล์จึงเกินโควตาไม่ได้) และคืนให้เมื่อยกเลิกหรือไม่อัปโหลดจนเสร็จ เกินโควตาจะได้ 429 งานของผู้เยี่ยมชมที่ไม่มีชิ้นใหม่เข้ามานาน 15 นาทีจะถูกลบและคืนโควตา (ไม่รอ `UPLOAD_STALE_HOURS`) การส่งชิ้นเดิมซ้ำไม่นับเป็นความคืบหน้า การถือโควตาไว้จึงต้องส่งข้อมูลใหม่จริง ซึ่งก็คือใช้โควตานั้นจริง
- ยอดที่ใช้เก็บใน `guest-uploads.json` ใน `DATA_DIR` จึงไม่หายเมื่อรีสตาร์ต และเริ่มนับใหม่ทุกวัน (ตามเวลาเครื่อง) ผู้ที่เข้าสู่ระบบไม่ถูกจำกัดด้วยโควตานี้
- ชื่อผู้ใช้ `guest` (ไม่สนตัวพิมพ์) สงวนไว้ เพราะไฟล์ที่ผู้เยี่ยมชมอัปโหลดและประวัติของผู้เยี่ยมชมใช้ชื่อนี้
- session ของผู้เยี่ยมชมอยู่ในหน่วยความจำและมีเพดาน ส่วน session ของผู้ที่เข้าสู่ระบบเก็บในดิสก์ จึงอยู่รอดหลังรีสตาร์ต

## การยืนยันสองขั้นตอน (2FA) และ secret.key

ผู้ใช้เปิด 2FA เองได้ (ดู [คู่มือผู้ใช้](user-guide.md#การยืนยันสองขั้นตอน-2fa)) ส่วนนี้อธิบายกลไก

- **เปิด 2FA (TOTP, RFC 6238):** ใช้กับแอป authenticator ทั่วไป รหัส 6 หลัก เปลี่ยนทุก 30 วินาที ยอมรับรหัสก่อนและหลังหนึ่งช่วง ขั้นตอนตั้งค่าต้องยืนยันรหัสผ่านก่อน เมื่อเปิดสำเร็จได้รหัสสำรอง 10 รหัส (`xxxx-xxxx`) **แสดงครั้งเดียว** และอุปกรณ์อื่นของผู้ใช้ถูกออกจากระบบ ปิด 2FA หรือขอรหัสสำรองชุดใหม่ต้องใส่รหัสผ่านและรหัสจากแอปหรือรหัสสำรอง ใส่ผิดซ้ำถูกล็อกเหมือนใส่รหัสผ่านผิด
- **เข้าสู่ระบบ:** ผู้ใช้ที่เปิด 2FA ใส่รหัสผ่านถูกแล้วจะ **ยังไม่ได้ session** ได้เพียง ticket (ใช้ได้ครั้งเดียว 5 นาที ผูกกับผู้ใช้และ IP) แล้วต้องส่งรหัสพร้อม ticket ภายหลัง รหัสผิดซ้ำถูกล็อกตาม `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_SECONDS` และแจ้งเตือนผู้ดูแล รหัส TOTP ใช้ได้ครั้งเดียว (ใช้ซ้ำไม่ได้แม้ยังอยู่ในช่วงเวลา) รหัสสำรองใช้ได้ครั้งเดียวแล้วถูกลบ
- **ความลับของ 2FA:** เก็บใน `users.json` แบบเข้ารหัส (AES-256-GCM) ด้วยกุญแจ `secret.key` ใน `DATA_DIR` (สร้างเองครั้งแรกที่ใช้ สิทธิ์ `0600`) ส่วนรหัสสำรองเก็บเฉพาะค่าแฮช `secret.key` ยังใช้เข้ารหัสโทเคนของลิงก์แชร์ที่เก็บไว้ให้คัดลอกซ้ำด้วย
- **ไฟล์สำรองข้อมูลไม่มี `secret.key`** เจตนา: ถ้าอยู่ไฟล์เดียวกับ `users.json` ใครได้ไฟล์สำรองไปก็ถอดความลับ 2FA ได้ ให้เก็บสำเนา `secret.key` แยกไว้ที่ปลอดภัยเอง
- **ติดตั้งเครื่องใหม่ต้องวาง `secret.key` เดิม** ไว้ใน `DATA_DIR` เองจึงจะใช้ 2FA เดิมได้ ถ้าไม่มีกุญแจนี้รหัส 2FA ของทุกคนใช้ไม่ได้ ให้ล้างด้วย `bun src/cli.ts reset-2fa <user>` แล้วให้แต่ละคนเปิด 2FA ใหม่ วิธีรับมือเมื่อกู้คืนข้อมูลสำรองบนเครื่องอื่น ดู [คู่มือผู้ดูแล: กู้คืนบนเครื่องอื่นและ 2FA](admin-guide.md#กู้คืนบนเครื่องอื่นและ-2fa) (ระบบเตือนผู้ใช้ที่ได้รับผลกระทบทันทีที่กู้คืน)
- **ลืมโทรศัพท์และรหัสสำรอง:** admin รีเซ็ตให้จากหน้าผู้ใช้ (ต้องใส่รหัสผ่านของ admin เอง) หรือที่เครื่อง server ด้วย CLI ดู [คู่มือผู้ดูแล: CLI](admin-guide.md#คำสั่งที่เครื่อง-server-cli)

## ตั้งค่าในหน้าเว็บและการยืนยันรหัสผ่าน

ค่าที่แก้ในหน้า **ระบบ → ตั้งค่า** เก็บใน `settings.json` ชนะ `.env` (ดู [ตั้งค่าระบบ](configuration.md#ลำดับความสำคัญของค่า)) และเปลี่ยนได้เฉพาะ admin

- **ต้องยืนยันรหัสผ่านของ admin** (step-up) เมื่อบันทึกหมวดความปลอดภัย (บังคับ 2FA อายุ session การล็อก) หรือหมวดอีเมลและแจ้งเตือน และเมื่อเพิ่มสิทธิ์ `write`, `upload`, `zip` ให้ผู้เยี่ยมชม เพราะ session ที่ถูกขโมยไปอย่างเดียวจึงเปลี่ยนกติกาการเข้าสู่ระบบ หรือเปลี่ยนปลายทางอีเมล หรือเปิดให้คนนอกแก้ไฟล์ไม่ได้ ใส่ผิดซ้ำถูกล็อกแบบเดียวกับการยืนยันรหัสผ่านอื่น การเปลี่ยนหมวดความปลอดภัยแจ้งผู้ดูแลทาง webhook และทุกการบันทึกลงประวัติการใช้งานเป็นชื่อค่าที่เปลี่ยน ไม่เก็บค่า หมวดอีเมลและแจ้งเตือน (ปลายทาง webhook, SMTP) ต้องใส่รหัสผ่านและส่งการแจ้งเตือนถึงผู้ดูแลเมื่อมีการเปลี่ยนเช่นเดียวกับหมวดความปลอดภัย ผู้ที่ได้ session ของ admin ไปอย่างเดียวจึงเปลี่ยนปลายทางแจ้งเตือนเงียบ ๆ ไม่ได้
- **ความลับในการตั้งค่า** (รหัสผ่าน SMTP, URL ของ webhook ที่มีโทเคน) เก็บใน `settings.json` แบบเข้ารหัส AES-256-GCM ด้วย `secret.key` เหมือนความลับ 2FA และ `GET /api/admin/settings` ไม่ส่งค่าเหล่านี้กลับ (ส่งแค่ว่าตั้งไว้ หรือโฮสต์ของ URL)
- **`settings.json` อยู่ในไฟล์สำรอง แต่ `secret.key` ไม่อยู่:** กู้คืนบนอีกเครื่องโดยไม่วาง `secret.key` เดิม ค่าลับสองอย่างนี้เปิดไม่ได้ ระบบปิดอีเมล/webhook ไว้ (ไม่ย้อนไปใช้ค่าอื่นเงียบ ๆ) และเตือน `admin.config-secret-unreadable` ให้เก็บสำเนา `secret.key` ไว้คู่กับไฟล์สำรอง หรือกรอกค่าใหม่ ดู [คู่มือผู้ดูแล](admin-guide.md#คำเตือนการตั้งค่าและวิธีแก้)
- **ขนาดอัปโหลด** ที่ตั้งในเว็บเกิน `UPLOAD_MAX_SIZE` ใน `.env` ไม่ได้ ผู้ดูแลที่เว็บจึงไม่ขยายเพดานของ server เองได้
- **บังคับ 2FA** บัญชีที่ถูกบังคับและยังไม่มี 2FA เรียกได้เฉพาะเส้นทางตั้งค่า 2FA กับออกจากระบบ ส่วนอื่นตอบ 403 `auth.2fa-required` ตรวจที่ server ทุกคำขอ ไม่ใช่แค่ซ่อนหน้าเว็บ
- **นโยบายลิงก์แชร์** (อายุสูงสุด ไม่หมดอายุ บังคับรหัสผ่าน) ตรวจที่ server ตอนสร้างลิงก์ ไม่ใช่แค่ในหน้าเว็บ

## อุปกรณ์ที่เข้าสู่ระบบ

- ผู้ใช้ดูอุปกรณ์ที่เข้าสู่ระบบอยู่ของตัวเอง (IP, ชนิดเบราว์เซอร์, เวลาสร้าง, ใช้ล่าสุด) และออกจากระบบทีละเครื่องหรือทุกเครื่องอื่นได้ session ที่สร้างก่อนมีรายการนี้แสดง IP/เบราว์เซอร์เป็น `unknown` และไม่มีใครถูกออกจากระบบเพราะการอัปเกรด
- admin (และ manager กับผู้ใช้ที่จัดการได้) ดูและเพิกถอนทุกอุปกรณ์ของผู้ใช้ได้ การเพิกถอนนี้ **ลบรหัสผ่านแอป WebDAV ของผู้ใช้ด้วย** และบันทึกในประวัติการใช้งาน
- session หมดอายุเมื่อไม่ได้ใช้งานเกิน `SESSION_TTL_HOURS` (ค่าเริ่มต้น 168 ชั่วโมง = 7 วัน) ผู้ดูแลเปลี่ยนได้ในหน้าตั้งค่า

## ลิงก์แชร์

- `shares.json` เก็บ **SHA-256 ของโทเคน** ไว้หาลิงก์ และเก็บตัวโทเคนแบบเข้ารหัส (AES-256-GCM ด้วย `secret.key` แบบเดียวกับความลับ 2FA) ไว้ให้คัดลอกซ้ำ ไฟล์ `shares.json` หลุดไปอย่างเดียวจึงใช้เปิดลิงก์ไม่ได้ (`secret.key` ไม่ลงไฟล์สำรอง) รหัสผ่านของลิงก์เก็บแบบ hash
- ลิงก์หยุดทำงานทันทีเมื่อหมดอายุ ถูกยกเลิก ดาวน์โหลดครบจำนวน รายการถูกลบ/ย้าย/เปลี่ยนชนิด เจ้าของถูกลบ หรือเจ้าของไม่มีสิทธิ์ `share`/`download` ในพื้นที่นั้นแล้ว (ตรวจใหม่ทุกครั้งที่ใช้) ทุกกรณีตอบ 404 `share.not-found` แบบเดียวกัน ผู้เดาลิงก์จึงไม่ได้ข้อมูลอะไร
- ปลดล็อกลิงก์ที่มีรหัสผ่านตั้ง cookie อายุ 1 ชั่วโมงที่ใช้ได้กับลิงก์นั้นลิงก์เดียว ใส่ผิด 5 ครั้งล็อกลิงก์นั้นสำหรับ IP นั้น 15 นาที (และแจ้งเตือนผู้ดูแล) และมีตัวนับของ **ลิงก์ทั้งลิงก์** รวมทุก IP: ผิด 50 ครั้งภายใน 15 นาที ลิงก์นั้นปลดล็อกไม่ได้เลย 15 นาที (ใส่รหัสถูกก็ไม่ข้าม) เพื่อให้ยังกันการเดารหัสได้ แม้ตั้ง `TRUST_PROXY` ไม่ตรงกับโครงสร้างจริงจน IP ที่เห็นเปลี่ยนไปมาได้
- ลิงก์โฟลเดอร์ไม่มีทางออกนอกโฟลเดอร์ที่แชร์ และไม่แสดง/ไม่ตาม symlink
- **ลิงก์ขอไฟล์:** งานอัปโหลดผูกกับลิงก์นั้นและกับผู้เยี่ยมชมคนนั้นด้วย cookie สุ่ม `fc_visitor` (HttpOnly, SameSite=Strict, ใช้ได้เฉพาะ path ของลิงก์) คนอื่นหรือลิงก์อื่นเพิ่มชิ้นส่วน จบ หรือยกเลิกไม่ได้ เพราะไม่มี session จึงไม่ต้องใช้ CSRF token สำหรับ 4 เส้นทางนี้ (ระบุใน `src/context.ts`) ลิงก์เก็บแค่แฮชของ cookie ผู้ส่ง ไม่เก็บตัว cookie ไม่เคยแสดงของที่อยู่ในโฟลเดอร์ ไม่เขียนทับไฟล์เดิม จำกัดอัปโหลดค้างพร้อมกัน 5 งานต่อลิงก์ และ 3 งานต่อ IP ไบต์ถูกจองตั้งแต่ประกาศไฟล์ (ตัวนับงานค้างอยู่ในหน่วยความจำ ประกาศไฟล์ไม่ต้องอ่านโฟลเดอร์ tmp ทุกครั้ง) กับโควตาของเจ้าของลิงก์ (หรือโควตารายวันของผู้เยี่ยมชม ถ้าลิงก์อยู่ในพื้นที่ public หรือของผู้ใช้ที่ไม่มีโควตา)
- ประวัติการใช้งานบันทึก `share-create`, `share-download`, `share-revoke`, `share-upload` พร้อมพาธ **ไม่บันทึกโทเคน**

## WebDAV

- ไม่รับรหัสผ่านบัญชีและไม่อ่าน cookie ของหน้าเว็บ รับเฉพาะ Basic auth `ชื่อผู้ใช้:รหัสผ่านแอป` ควรใช้ผ่าน HTTPS เสมอ
- รหัสผ่านแอป: รูปแบบ `fc-` + ตัวอักษรและตัวเลขสุ่ม 32 ตัว **แสดงครั้งเดียวตอนสร้าง** เก็บเฉพาะแฮช (argon2id) ใน `DATA_DIR/app-passwords.json` แม้แต่ผู้ดูแลก็ดูรหัสไม่ได้ ขอบเขต `read` / `readwrite` เป็นได้แค่ตัดสิทธิ์ ไม่เพิ่มเกินที่บัญชีมี
- สร้างได้คนละ 20 อัน ไม่ผ่าน 2FA (เป็นรหัสสุ่มแยกต่างหากที่ใช้ได้กับ WebDAV อย่างเดียว เข้า API หรือหน้าเว็บด้วยรหัสนี้ไม่ได้) การสร้างต้องยืนยันรหัสผ่านบัญชี
- ลบทั้งหมดเมื่อบัญชีถูกลบ เมื่อผู้ใช้เปลี่ยนรหัสผ่าน เมื่อผู้ดูแลตั้งรหัสผ่านใหม่ให้ และเมื่อเพิกถอนอุปกรณ์ของผู้ใช้ **ไม่อยู่ในไฟล์สำรอง** โดยเจตนา (เป็นข้อมูลรับรอง)
- ทุกพาธถูกแปลงเป็น (space, พาธใน space) แล้วผ่านการตรวจสิทธิ์และ `resolveIn` เหมือน API เสมอ พาธที่มี `..`, `\`, `%2f` หรือ NUL ถูกปฏิเสธ
- ตอบ 401 พร้อม `WWW-Authenticate: Basic realm="File Center", charset="UTF-8"` เมื่อรหัสผิด และ 429 พร้อม `Retry-After` เมื่อโดนล็อก
- คำตอบมี `X-Content-Type-Options: nosniff` และ `Cache-Control: no-store` ขนาดคำขอสูงสุดเท่า `UPLOAD_MAX_SIZE` ไฟล์เขียนลงโฟลเดอร์ชั่วคราวแล้วย้ายเข้าที่ในครั้งเดียว `PROPFIND` จำกัด `Depth` ไม่เกิน 1 ขอ property ไม่เกิน 50 ชื่อ (namespace ยาวไม่เกิน 256 ตัวอักษร เกินตอบ 400) คำตอบรวมไม่เกิน 32 MiB เกินตอบ 507 และโฟลเดอร์ใหญ่ตอบ 507 ตัวอ่าน XML จำกัดจำนวน element

## ภาพตัวอย่างและดูไฟล์ zip

**ภาพตัวอย่างฝั่งเซิร์ฟเวอร์**

- เครื่องมือ (`vipsthumbnail`, `pdftoppm`, `ffmpeg`) รันเป็นโพรเซสลูกด้วยอาร์กิวเมนต์แบบอาร์เรย์ (ไม่ผ่าน shell) สภาพแวดล้อมขั้นต่ำ (ไม่มีความลับของแอป) ตัดทิ้งเมื่อเกิน 10 วินาที (ฆ่าเฉพาะตัวนั้น) พร้อมกันได้ 2 งาน คิวรอ 16 งาน เกินนั้นตอบ 503 ทันที
- เครื่องมือไม่เคยได้พาธที่ผู้ใช้ตั้งชื่อ: ระบบสร้าง symlink ชื่อเรียบ ๆ ใน `DATA_DIR/thumbs/tmp` ชี้ไปไฟล์จริง (ชื่อเช่น `-x[page=2].png` จึงไม่ถูกอ่านเป็นตัวเลือก)
- `VIPS_BLOCK_UNTRUSTED=1` กัน libvips ส่งไฟล์ที่ไม่ใช่รูปจริงให้ ImageMagick/rsvg/poppler ffmpeg ถูกกำหนดตัวอ่านตามนามสกุลและเปิดเฉพาะโปรโตคอล `file` (playlist ที่ตั้งชื่อ `.mp4` จึงไม่ถูกตามไปยังไฟล์หรือ URL อื่น)
- ทุกเส้นทางผ่านการตรวจสิทธิ์ + `resolveIn` เหมือนการดาวน์โหลด ภาพขนาด 1024 ต้องมี `read` + `download` รูปที่ใหญ่เกิน 500 MB หรือ 100 ล้านพิกเซลถูกปฏิเสธก่อนสร้าง
- แคชอยู่ที่ `DATA_DIR/thumbs` ตัดให้ไม่เกิน `THUMB_CACHE_MAX_MB` ไม่อยู่ในไฟล์สำรอง

**ดูไฟล์ zip โดยไม่แตก**

- ต้องมี `read` + `download` อ่านเฉพาะสารบัญท้ายไฟล์ (central directory)
- **กัน zip ที่สารบัญใหญ่เกิน:** ระบบอ่าน EOCD (และ ZIP64 EOCD) ที่ท้ายไฟล์ก่อน ถ้าสารบัญใหญ่เกิน 64 MB หรือมีเกิน 100,000 รายการ → 413 โดยไม่เปิดไฟล์ เปิดดูพร้อมกันได้ 4 งาน (แตก zip 2 งาน) งานที่เกินตอบ 503 พร้อม `Retry-After: 3`
- **กัน zip bomb:** ขนาดที่ประกาศเกิน `UPLOAD_MAX_SIZE` หรือ (เกิน 100 MB และบีบอัดเกิน 100:1) → 413 ก่อนแตกแม้แต่ไบต์เดียว ระหว่างส่งนับไบต์จริงและตัดทิ้งถ้าเกินขนาดที่ประกาศ (และ zip.js ตรวจ CRC) การแตก zip (`POST /api/unzip`) จำกัดด้วย `UNZIP_MAX_BYTES` / `UNZIP_MAX_FILES` และกัน zip-slip
- รายการที่ส่งออกมา: `Content-Type` ตามนามสกุล, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (เว้น PDF ที่เปิดในแท็บ) และเปิดในแท็บ (`inline=1`) ได้เฉพาะรูป (ไม่รวม svg), PDF และ `.txt` ที่เหลือเป็น `attachment` เสมอ ชื่อรายการที่มี `..` ขึ้นต้นด้วย `/` มี `\` หรือ NUL ถูกปฏิเสธ
- ลิงก์แชร์โฟลเดอร์: การเอารายการออกจาก zip นับเป็นการดาวน์โหลดของลิงก์หนึ่งครั้ง (ลิงก์ที่จำกัดจำนวนครั้งจึงเลี่ยงด้วยการเปิดทีละรายการไม่ได้) ส่วนการดูรายการไม่นับ

**ดูตัวอย่างเอกสารในหน้าเว็บ:** ไม่มีสิ่งใดในไฟล์ถูกรัน (ไม่อ่าน macro, HTML ที่ได้จากไฟล์ผ่านการกรองด้วย DOMPurify ก่อนแสดง, ลิงก์ได้เฉพาะ http(s)/mailto/tel) และไฟล์ที่ใหญ่เกินกำหนดให้ดาวน์โหลดแทน

## ONLYOFFICE

เปิดเฉพาะเมื่อตั้ง `OFFICE_URL`, `OFFICE_INTERNAL_URL` และ `OFFICE_JWT_SECRET` (อย่างน้อย 32 ตัวอักษร) ครบ

- ลิงก์ที่ให้ document server มีโทเคนที่ File Center เซ็นด้วยกุญแจของตัวเอง (`office-links.key` ใน `DATA_DIR`) ระบุไฟล์ ผู้ใช้ โหมด และหมดอายุใน 24 ชั่วโมง
- ทุกครั้งที่ใช้ ตรวจสิทธิ์ของผู้ใช้ใหม่ (ถูกถอนสิทธิ์ `write` แล้วบันทึกไม่ได้ ลิงก์แบบดูบันทึกไม่ได้เลย) และ document server ต้องส่ง JWT ที่เซ็นด้วย `OFFICE_JWT_SECRET` ทุกคำขอ
- document server ติดต่อ File Center เอง ไม่ใช้ cookie ของผู้ใช้
- ไฟล์ที่บันทึกดาวน์โหลดจาก origin ของ document server (`OFFICE_SERVER_INTERNAL_URL` / `OFFICE_URL`) เท่านั้น ไม่ตาม redirect จำกัดขนาดตาม `OFFICE_MAX_SIZE` และจำกัดเวลา
- `Content-Security-Policy` ของหน้าเว็บเพิ่ม origin ของ `OFFICE_URL` ใน `script-src`, `frame-src`, `connect-src` เฉพาะเมื่อเปิดใช้งาน
- ฉบับเดิมถูกเก็บเป็นเวอร์ชันของไฟล์ก่อนเขียนทับ และไฟล์ใหม่ถูกวางแทนที่ในครั้งเดียว (ไม่มีช่วงที่ไฟล์เขียนไม่ครบ) ประวัติการใช้งานบันทึก `office-open` และ `office-save`
- document server ใน compose เปิดพอร์ตที่ `127.0.0.1` เท่านั้น

## การอัปเดตระบบ

- ระบบติดตั้งเฉพาะแพ็กเกจที่เซ็นแล้ว (Ed25519) แม้บัญชี admin ถูกยึดไปก็ติดตั้งโค้ดอื่นไม่ได้ ตรวจลายเซ็นตอนอัปโหลดและตรวจซ้ำตอนติดตั้ง
- ตอนติดตั้ง ระบบบันทึก SHA-256 ของ `server.js` ไว้ใน `state.json` และ launcher คำนวณซ้ำก่อนเริ่มทุกครั้ง (รวมถึงตอนย้อนกลับไปเวอร์ชันในประวัติ) ถ้าไฟล์ถูกแก้หลังติดตั้ง launcher ไม่เริ่มมัน บันทึกเหตุผลลง `launcher.log` และใช้เวอร์ชันที่มากับอิมเมจแทน อัปเดตที่ติดตั้งโดยรุ่นเก่าไม่มีค่านี้และทำงานต่อได้ตามเดิม ช่วยจำกัดความเสียหายถ้ามีช่องโหว่เขียนไฟล์ใน `DATA_DIR/app` ในอนาคต
- โค้ดของแพ็กเกจไม่ถูกรันจนกว่าจะใส่รหัสผ่านซ้ำ (ทุกครั้ง ผิดซ้ำถูกล็อกและแจ้งเตือน) ทุกไฟล์ต้องตรง `manifest.json` (ขนาดและ SHA-256) ไม่มีไฟล์เกิน ไม่มี symlink หรือพาธ `../`
- `UPDATE_SOURCE` รับเฉพาะ `https://` ไม่ตาม redirect และ SHA-256 ใน `latest.json` บอกได้แค่ว่าไฟล์ไม่เสียระหว่างทาง ความเชื่อถือมาจากลายเซ็น
- `TUNNEL_TOKEN` ไม่ถูกส่งให้ตัวแอปและโค้ดที่อัปเดตจากเว็บ
- `UPDATE_ALLOW_UNSIGNED=true` ลดการป้องกันนี้ลง ระบบเตือนเสมอ

รายละเอียดการใช้งาน: [คู่มือผู้ดูแล: อัปเดตระบบ](admin-guide.md#อัปเดตระบบ) และ [ติดตั้ง: กุญแจเซ็นแพ็กเกจ](install.md#กุญแจเซ็นแพ็กเกจ)

## ความปลอดภัยของคอนเทนเนอร์

สรุป (วิธีตั้งและตรวจอยู่ที่ [ติดตั้ง](install.md#ตั้งค่าความปลอดภัยของคอนเทนเนอร์))

- แอปรันเป็นผู้ใช้ `bun` (uid 1000) ไม่ใช่ root PID 1 (launcher) ก็เป็น 1000 และไม่มี capability เหลือ (`CapEff` = 0)
- ระบบไฟล์ของอิมเมจอ่านอย่างเดียว (`read_only: true`) เขียนได้เฉพาะ `/data` และ `/tmp` (tmpfs 256 MB)
- `cap_drop: [ALL]` เหลือเท่าที่ entrypoint ต้องใช้ตอนเริ่ม (`CHOWN`, `SETUID`, `SETGID`, `DAC_OVERRIDE`) และ `no-new-privileges`
- จำกัดหน่วยความจำ (2g) และจำนวนโปรเซส (512)
- พอร์ตเปิดที่ `127.0.0.1` เท่านั้นตามค่าเริ่มต้น ผู้ใช้ภายนอกเข้าผ่านโดเมน (Cloudflare Tunnel)
- `scripts/ci-docker.sh` ตรวจทุกข้อกับคอนเทนเนอร์จริงใน CI

ไฟล์ `.trivyignore` ยอมรับข้อยกเว้นเดียวคือ `DS-0002` (ไม่มี `USER` ใน Dockerfile เพราะ entrypoint ต้องเริ่มเป็น root เพื่อ `chown` ครั้งเดียวแล้วลดเป็น `bun`)

## ตรวจช่องโหว่ใน CI

งาน `security` ใน `.github/workflows/qa.yml` ตรวจสามอย่าง และ **ล้มเฉพาะช่องโหว่ระดับ HIGH หรือ CRITICAL ที่มีเวอร์ชันแก้แล้ว** (`ignore-unfixed`)

1. `bun audit --audit-level=high` ตรวจแพ็กเกจจาก `bun.lock` กับฐานข้อมูล advisory
2. Trivy `fs` บนโค้ด: ช่องโหว่ของแพ็กเกจ, ความลับที่หลุดในไฟล์, และการตั้งค่าผิดของ `Dockerfile` (Trivy ไม่ตรวจ `docker-compose.yml` ส่วนค่า hardening ของ compose ตรวจโดย `scripts/ci-docker.sh`)
3. Trivy `image` บนอิมเมจที่ build จาก `Dockerfile`: แพ็กเกจ Debian ของฐานและแพ็กเกจในอิมเมจ

**อ่านผล:** เปิด log ของ step `Trivy repository` / `Trivy image` จะเห็นตาราง (แพ็กเกจ, CVE, เวอร์ชันที่ติดตั้ง, เวอร์ชันที่แก้แล้ว) แก้โดยอัปเดตแพ็กเกจ (`bun update <ชื่อ>`) หรือเปลี่ยนแท็กฐานอิมเมจเป็นรุ่นใหม่ ไฟล์ SARIF ของทุกระดับ (รวม LOW/MEDIUM และที่ยังไม่มีเวอร์ชันแก้) อยู่ใน artifact `security-results` เปิดดูได้ด้วยโปรแกรมอ่าน SARIF

**ข้อยกเว้น:** ถ้าต้องยอมรับจริง ๆ ใส่ ID ใน `.trivyignore` โดย **ต้องมีบรรทัดคอมเมนต์บอกเหตุผลอยู่เหนือทุกรายการ** (เทสต์ตรวจข้อนี้) ตอนนี้มีรายการเดียวคือ `DS-0002` (และชื่อ `AVD-DS-0002` ของข้อเดียวกัน)

งานนี้ต้องดาวน์โหลดฐานข้อมูล Trivy จึงต้องมีอินเทอร์เน็ต และยืนยันผลจริงได้บน GitHub Actions เท่านั้น

**ผลสแกนครั้งแรก (รอบ 9):** โค้ดและแพ็กเกจ npm ไม่พบช่องโหว่ อิมเมจพบ 17 รายการ (HIGH 14, CRITICAL 3) ทั้งหมดอยู่ในแพ็กเกจ Debian ของฐาน (perl-base, pcre2, sqlite, openssl, gzip) และมีรุ่นแก้แล้ว `Dockerfile` จึงลงอัปเดตความปลอดภัยของ Debian (`apt-get upgrade`) ใน stage ที่ใช้รันทุกครั้งที่ build (ปิดได้ด้วย `--build-arg APT_UPGRADE=false` เฉพาะเครื่องที่เข้า mirror ของ Debian ไม่ได้ เช่น `FC_CI_NO_APT=1 bash scripts/ci-docker.sh`) ควร build อิมเมจใหม่เป็นระยะ (`docker compose build --pull`) เพื่อรับอัปเดตล่าสุด

ภาพรวมงานอื่นใน CI (`qa`, `seeded`, `docker`, `bench`) อยู่ที่ [คู่มือนักพัฒนา](development.md#ตรวจคุณภาพอัตโนมัติ-ci)

## ข้อจำกัดที่ควรรู้

- ทดสอบบน Linux และด้วย Docker Desktop บน Windows แล้ว แต่การรันด้วย Bun บน Windows โดยตรง (ไม่ผ่าน Docker) ยังไม่ได้ทดสอบ (พาธ, `statfs`, ชื่อไฟล์ต้องห้ามของ Windows)
- ชื่อไฟล์ที่ไม่ใช่ ASCII ส่งไปในหัว `Content-Disposition` ตามมาตรฐาน RFC 6266 (`filename*=UTF-8''...`) ควรลองดาวน์โหลดไฟล์ชื่อไทยในเบราว์เซอร์ที่ใช้จริงอีกครั้ง
- ชื่อไฟล์/โฟลเดอร์ห้ามมีอักขระ `\ / : * ? " < > |` (เพื่อให้ย้ายข้ามระบบปฏิบัติการได้) และยาวได้ไม่เกิน 255 ไบต์ ซึ่งเท่ากับภาษาไทยประมาณ 85 ตัวอักษร (ชื่อที่ยาวเกินในไฟล์ zip จะถูกตัดให้สั้นลงโดยคงนามสกุลไว้)
- ผู้ใช้ที่ได้รหัสผ่านเริ่มต้นจากระบบต้องเปลี่ยนรหัสผ่านก่อน จึงจะเรียก API อื่นได้ (server บังคับ ไม่ใช่แค่หน้าเว็บ)
- โฟลเดอร์ระบบ `/public` และ `/users` คัดลอกได้ แต่ลบ ย้าย หรือเปลี่ยนชื่อไม่ได้
- **จำนวนและขนาดไฟล์ในหน้าภาพรวมอาจช้ากว่าความจริงได้ราวหนึ่งนาที** ระบบนับไฟล์อยู่เบื้องหลัง (ไม่ให้ผู้ใช้คนอื่นต้องรอ) และแสดงผลที่นับไว้ล่าสุดทันที `GET /api/admin/status` ตอบ `stale: true` เมื่อตัวเลขเก่ากว่าหนึ่งนาทีและกำลังนับใหม่ ครั้งแรกหลังติดตั้งที่ยังไม่เคยนับเลยจะได้ `storage: null` (เปิดหน้าใหม่อีกครั้งเมื่อนับเสร็จ) ผลที่นับเก็บไว้ใน `stats-cache.json` ใน `DATA_DIR` หลังรีสตาร์ตจึงเห็นตัวเลขล่าสุดทันที
- **ค้นหาไฟล์:** ปกติใช้ดัชนีค้นหาใน `DATA_DIR/search.db` (สร้างเบื้องหลังตอนเริ่ม สร้างใหม่เองถ้าเสีย) ระหว่างที่ดัชนียังสร้างไม่เสร็จ (หรือเมื่อตั้ง `SEARCH_INDEX=false`) ระบบเดินดูโฟลเดอร์ตอนค้นหา ซึ่งช้ากว่าและหยุดที่ 50,000 รายการต่อการค้นหา การค้นหาและการคัดลอกทำทีละชุดสลับกับคำขออื่น ผู้ใช้คนอื่นจึงไม่ต้องรอ
- การคัดลอกข้ามลิงก์ (symlink) ไปเสมอ ไม่ตามลิงก์และไม่คัดลอกตัวลิงก์ ถ้าคัดลอกไม่สำเร็จกลางทาง (เช่น ดิสก์เต็ม) ส่วนที่คัดลอกไปแล้วจะถูกลบออก
- ลิงก์แชร์ออกจากโฟลเดอร์กลุ่มยังไม่รองรับ (สร้างลิงก์ในโฟลเดอร์กลุ่มได้ 403)
- WebDAV: lock ไม่บังคับและอยู่ในหน่วยความจำ (หายเมื่อรีสตาร์ต) ไม่มี dead properties อัปโหลดไฟล์เกิน 100 MB ผ่าน Cloudflare Free/Pro ไม่ได้ และ Windows จำกัดไฟล์ 50 MB ตามค่าเริ่มต้น ดู [ข้อจำกัดของ WebDAV](user-guide.md#ข้อจำกัดของ-webdav)
- ดูไฟล์ในไฟล์ archive ได้เฉพาะ `.zip` (ไม่รองรับ `.rar` และ `.7z`)
- การกู้คืนข้อมูลจากหน้าเว็บคืนเฉพาะ `users.json`, `settings.json`, `branding/` และไม่คืนไฟล์ใน `storage` ดู [คู่มือผู้ดูแล](admin-guide.md#สำรองและกู้คืนข้อมูล)
- การกู้คืนเทียบบัญชีด้วยคู่ (ชื่อผู้ใช้, `createdAt`) ไม่ใช่ชื่ออย่างเดียว: เซสชัน รหัสผ่านแอป ลิงก์แชร์ สิทธิ์ที่ให้/ได้รับ และการเป็นสมาชิกกลุ่มของบัญชีที่ `createdAt` ตรงกับไฟล์สำรองยังอยู่ (เซสชันเฉพาะที่สร้างหลังบัญชีนั้น) ส่วนของชื่อที่ `createdAt` ต่างกัน ไม่มีบัญชีใช้อยู่ หรือไม่มี `createdAt` ถูกลบทั้งหมดเหมือนตอนลบบัญชี ดังนั้นบัญชีที่มาทีหลังด้วยชื่อเดิมไม่สืบทอดอะไรไปเป็นบัญชีที่กู้คืน
- การแจ้งเตือนทางอีเมลและ LINE ใช้คิวในหน่วยความจำ รีสตาร์ตแล้วข้อความที่ยังไม่ได้ส่งหายไป (กระดิ่งยังอยู่)
- ONLYOFFICE Community รองรับ 20 การเชื่อมต่อพร้อมกัน
