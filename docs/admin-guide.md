## บทบาทและสิทธิ์

มี 4 แบบ (ชื่อที่เก็บในระบบ → ชื่อที่แสดงในหน้าเว็บ)

| บทบาท | เห็นอะไร |
|---|---|
| ผู้เยี่ยมชม (guest) | เห็นเฉพาะโฟลเดอร์สาธารณะ (`storage/public`) ไม่ต้องเข้าสู่ระบบ ปิดได้ที่ตั้งค่า |
| `user` → "ผู้ใช้" | เห็นเฉพาะโฟลเดอร์ส่วนตัว (admin เลือกได้ ค่าเริ่มต้น `/users/<ชื่อผู้ใช้>`) กับโฟลเดอร์สาธารณะตามสิทธิ์ที่ได้รับ |
| `manager` → "ผู้ดูแล" | ใช้ไฟล์เหมือนผู้ใช้ และจัดการผู้ใช้ทั่วไปที่ตัวเองดูแลได้ กับดูไฟล์ของพวกเขาแบบอ่านอย่างเดียว |
| `admin` → "ผู้ดูแลระบบสูงสุด" | เห็นทุกโฟลเดอร์ (ทั้ง storage) จัดการผู้ใช้ สิทธิ์ ตั้งค่า อัปเดต สำรองข้อมูล ถังขยะ ทุกอย่าง |

### ตารางสิทธิ์

| ทำอะไรได้ | ผู้เยี่ยมชม | user | manager | admin |
|---|---|---|---|---|
| ไฟล์ของตัวเอง + โฟลเดอร์สาธารณะ ตามสิทธิ์ที่ได้รับ | สาธารณะเท่านั้น | ใช่ | ใช่ (เหมือน user ไม่เห็นทั้ง storage) | ทั้ง storage ทุกสิทธิ์ |
| รายการผู้ใช้ทุกคน (มีป้ายว่าจัดการได้หรือไม่) | - | - | ใช่ | ใช่ |
| สร้าง/แก้/ลบ ผู้ใช้ · รีเซ็ตรหัสผ่าน · 2FA · ดู/เพิกถอนอุปกรณ์ | - | - | เฉพาะผู้ใช้ที่จัดการได้ | ทุกคน |
| กำหนดบทบาท "ผู้ดูแล"/"ผู้ดูแลระบบสูงสุด" | - | - | ไม่ได้ | ได้ |
| ดูไฟล์ของผู้ใช้ (อ่านอย่างเดียว) | - | - | เฉพาะที่จัดการได้ | ทุกคน |
| ภาพรวมระบบ | - | - | ฉบับย่อ | ฉบับเต็ม |
| ประวัติการใช้งาน | - | - | เฉพาะของตัวเองและผู้ใช้ที่จัดการได้ | ทั้งหมด |
| ลิงก์ที่แชร์ของผู้ใช้ + ยกเลิกลิงก์ | - | - | เฉพาะลิงก์ของผู้ใช้ที่จัดการได้ (ดูลิงก์ซ้ำไม่ได้) | ทั้งหมด |
| กลุ่ม | - | - | เพิ่ม/ถอด/เปลี่ยนสิทธิ์สมาชิกที่ตัวเองดูแล ในกลุ่มที่ตัวเองเป็นสมาชิก | สร้าง/แก้/ลบกลุ่ม จัดการสมาชิกทุกกลุ่ม |
| ตั้งค่า โลโก้ อัปเดต สำรอง/กู้คืน บันทึกระบบ การแจ้งเตือน ถังขยะทั้งระบบ | - | - | ไม่ได้ | ใช่ |

เมนูของ **ผู้ดูแล** มี: ภาพรวมระบบ (ฉบับย่อ) ผู้ใช้ กลุ่ม ประวัติการใช้งาน ลิงก์ที่แชร์ ไม่มีหน้า "ระบบ" (ตั้งค่า สำรองข้อมูล อัปเดต บันทึก ถังขยะ) ปุ่มส่งออก CSV ของประวัติการใช้งาน และการคัดลอก/เปิดลิงก์ของคนอื่นเป็นของ admin เท่านั้น

### สิทธิ์ที่กำหนดได้ในแต่ละโฟลเดอร์

| สิทธิ์ | ชื่อในหน้าเว็บ | ทำอะไรได้ |
|---|---|---|
| `read` | ดูรายการ | เห็นรายชื่อไฟล์และโฟลเดอร์ |
| `download` | ดาวน์โหลด | ดาวน์โหลด/ดูตัวอย่างไฟล์ |
| `batchdownload` | ดาวน์โหลดหลายไฟล์ | ดาวน์โหลดหลายไฟล์หรือทั้งโฟลเดอร์เป็น zip |
| `upload` | อัปโหลด | อัปโหลดไฟล์เข้าโฟลเดอร์ |
| `write` | สร้าง/แก้ไข/ลบ | สร้าง แก้ไข เปลี่ยนชื่อ คัดลอก ย้าย ลบ |
| `zip` | บีบอัด/แตกไฟล์ | บีบอัดเป็น zip และแตกไฟล์ zip |
| `share` | แชร์ลิงก์ | สร้างลิงก์แชร์ และแชร์กับผู้ใช้/กลุ่ม (ต้องมี `download` ในพื้นที่เดียวกันด้วย) |

- ผู้ใช้แต่ละคนมีชุดสิทธิ์ **2 ชุดแยกกัน** คือในโฟลเดอร์ของตัวเอง และในโฟลเดอร์สาธารณะ ถ้าไม่ติ๊กสิทธิ์โฟลเดอร์สาธารณะเลย ผู้ใช้จะไม่เห็นเมนูโฟลเดอร์สาธารณะ
- สิทธิ์ของผู้เยี่ยมชมตั้งที่หน้า **ระบบ → ตั้งค่า** ("สิ่งที่ผู้เยี่ยมชมทำได้") ผู้เยี่ยมชมแชร์ลิงก์ไม่ได้ไม่ว่าตั้งอะไร
- `share` เป็นสิทธิ์ใหม่ บัญชีเดิมยังไม่มี ต้องให้เองที่หน้าผู้ใช้ (admin แชร์ได้เสมอ)
- สิทธิ์ถูกตรวจที่ server ทุกคำสั่ง ไม่ใช่แค่ซ่อนปุ่มในหน้าเว็บ

### กฎของผู้ดูแล (manager)

ตรวจที่ server ทุกคำสั่ง

- **"จัดการได้"** = บทบาท `user` และโฟลเดอร์คือ `/users/<ชื่อผู้ใช้>` พอดี ผู้ใช้ที่ admin ชี้ไปโฟลเดอร์อื่นหรือโฟลเดอร์ร่วม จัดการได้เฉพาะ admin (สำหรับ admin ทุกคนเป็น "จัดการได้")
- สร้าง/เลื่อนเป็น "ผู้ดูแล" หรือ "ผู้ดูแลระบบสูงสุด" ไม่ได้ แตะผู้ดูแล/admin หรือตัวเอง (รวมการเปลี่ยนบทบาทของตัวเองและการลบตัวเอง) ไม่ได้
- โฟลเดอร์ของผู้ใช้ที่ manager สร้างถูกบังคับเป็น `/users/<ชื่อ>` (ฟอร์มไม่มีช่องโฟลเดอร์) ให้สิทธิ์ในโฟลเดอร์ตัวเองได้ทุกอย่าง และตั้งโควตาได้
- สิทธิ์ในโฟลเดอร์สาธารณะที่ให้ผู้ใช้ ให้ได้ไม่เกินของ manager เอง (ติ๊กได้เฉพาะสิทธิ์ที่ตัวเองมี)
- รีเซ็ต 2FA และตั้งรหัสผ่านใหม่ให้ผู้ใช้ ต้องใส่รหัสผ่านของ manager เองยืนยัน ผู้ใช้ต้องเปลี่ยนรหัสผ่านเมื่อเข้าสู่ระบบครั้งหน้า
- สร้างผู้ใช้ได้เฉพาะเมื่อโฟลเดอร์ `/users/<ชื่อ>` ยังไม่มีอยู่ในดิสก์ (ไม่สนตัวพิมพ์เล็กใหญ่ ว่างหรือไม่ก็ตาม) และไม่ซ้อน/ซ้ำกับโฟลเดอร์ของบัญชีอื่น (กันการยึดโฟลเดอร์ที่ admin แชร์ไว้หรือที่เหลือจากผู้ใช้ที่ถูกลบ)
- แถวผู้ใช้ที่จัดการไม่ได้แสดงเป็นอ่านอย่างเดียวพร้อมป้าย "จัดการไม่ได้"
- admin คนสุดท้ายลบหรือลดบทบาทไม่ได้
- ชื่อผู้ใช้ `guest` (ไม่สนตัวพิมพ์) สงวนไว้ สร้างบัญชีชื่อนี้ไม่ได้

## จัดการผู้ใช้

เมนู **จัดการ → ผู้ใช้** (ผู้ดูแลและผู้ดูแลระบบสูงสุด)

**เพิ่มผู้ใช้**

1. กด **เพิ่มผู้ใช้**
2. ใส่ชื่อผู้ใช้ ชื่อที่แสดง รหัสผ่านเริ่มต้น และเลือก **บทบาท** (ผู้ดูแลเลือกได้แค่ "ผู้ใช้")
3. เลือก **โฟลเดอร์ส่วนตัว** (ผู้ดูแลระบบสูงสุดเลือกได้ ผู้ดูแลได้ `/users/<ชื่อ>` อัตโนมัติ)
4. ติ๊ก **สิทธิ์ในโฟลเดอร์ของตัวเอง** และ **สิทธิ์ในโฟลเดอร์สาธารณะ**
5. ตั้ง **พื้นที่เก็บไฟล์** (โควตา) ถ้าต้องการจำกัด (ดู [โควตาพื้นที่](#โควตาพื้นที่))
6. กดบันทึก แล้วแจ้งชื่อผู้ใช้และรหัสผ่านเริ่มต้นให้เจ้าของบัญชี

**รหัสผ่าน**

- รหัสผ่านใหม่ (สร้างผู้ใช้ ตั้งให้ผู้อื่น เปลี่ยนเอง) ต้องยาวอย่างน้อย 10 ตัวอักษร ไม่มีชื่อผู้ใช้อยู่ในรหัส ไม่ใช่รหัสที่ใช้กันบ่อย และไม่ใช่ตัวอักษรเดียวซ้ำหรือเรียงตามแป้นพิมพ์/ตัวเลข/ตัวอักษร (รายละเอียดที่ [ความปลอดภัย](security.md#รหัสผ่าน)) รหัสผ่านเดิมที่ตั้งไว้ก่อนหน้ายังเข้าสู่ระบบได้ตามปกติ
- ผู้ใช้ที่ได้รหัสผ่านเริ่มต้นจากระบบ **ต้องเปลี่ยนรหัสผ่านก่อน** จึงจะใช้ส่วนอื่นได้ (server บังคับ) หน้าภาพรวมมีคำเตือน "ยังใช้รหัสผ่านเริ่มต้น" จนกว่าทุกคนจะเปลี่ยน
- ตั้งรหัสผ่านใหม่ให้ผู้อื่น (แก้ผู้ใช้ → รหัสผ่านใหม่) ต้องใส่ **รหัสผ่านของคุณเอง** ยืนยัน และผู้ใช้ต้องเปลี่ยนเมื่อเข้าครั้งหน้า บันทึกเป็น `user-password-reset`
- การตั้งรหัสผ่านใหม่ให้ผู้ใช้ **ลบรหัสผ่านแอป WebDAV ทั้งหมดของเขา** ด้วย

**เมนูอื่นของแถวผู้ใช้**

- **อุปกรณ์ที่เข้าสู่ระบบ / ออกจากระบบทุกเครื่อง:** ดูอุปกรณ์ของผู้ใช้และบังคับออกจากระบบ (ลบรหัสผ่านแอป WebDAV ของเขาด้วย) ใช้เมื่อเครื่องหายหรือบัญชีถูกขโมย
- **รีเซ็ตการยืนยันสองขั้นตอน:** ใช้เมื่อผู้ใช้ลืมโทรศัพท์และรหัสสำรอง ปิด 2FA ของเขา ล้างรหัสสำรอง ออกจากระบบทุกอุปกรณ์ และลบรหัสผ่านแอป WebDAV ของเขา ผู้ใช้เปิดใหม่เองได้หลังเข้าสู่ระบบ ต้องใส่รหัสผ่านของคุณยืนยัน
- **ดูไฟล์:** เปิดไฟล์ของผู้ใช้แบบอ่านอย่างเดียว ดู [ดูไฟล์ของผู้ใช้แบบอ่านอย่างเดียว](#ดูไฟล์ของผู้ใช้แบบอ่านอย่างเดียว)
- **ลบผู้ใช้:** ลบบัญชี **ไม่ลบไฟล์** ในโฟลเดอร์ของเขา ลิงก์แชร์ของเขาถูกยกเลิกและสร้างบัญชีชื่อเดิมใหม่ก็ไม่กลับมา สิทธิ์ที่เขาให้และได้รับถูกลบ เขาถูกถอดจากทุกกลุ่ม ของในถังขยะที่เป็นของเขาถูกเปลี่ยนเป็นชื่อที่ไม่มีบัญชีไหนใช้ได้ (เห็นเฉพาะ admin ในถังขยะทั้งระบบ)

## โควตาพื้นที่

กำหนดโควตาให้ผู้ใช้แต่ละคนที่ช่อง **พื้นที่เก็บไฟล์** ในฟอร์มผู้ใช้ (ไม่จำกัด หรือจำกัดเป็นจำนวนไบต์/GB) กลุ่มมีโควตาของตัวเอง (ดู [กลุ่ม](#กลุ่ม))

- **นับอะไร:** เฉพาะโฟลเดอร์ของผู้ใช้เอง **ถังขยะอยู่นอกโฟลเดอร์นั้น จึงไม่นับ** ลบไฟล์แล้วพื้นที่ว่างคืนทันที แต่กู้คืนจากถังขยะก็นับกลับเข้าไปใหม่ และอาจถูกปฏิเสธถ้าเต็ม เวอร์ชันเก่าของไฟล์นับรวมด้วย
- โฟลเดอร์สาธารณะไม่มีโควตา และ admin (ที่โฟลเดอร์คือทั้ง storage) ไม่ถูกจำกัดแม้ตั้งโควตา
- **ตรวจที่ไหน:** ตอนเริ่มอัปโหลด บันทึกไฟล์ข้อความ บีบอัด แตก zip คัดลอก บันทึกจาก ONLYOFFICE กู้คืนจากถังขยะ และอัปโหลดผ่านลิงก์รับไฟล์ (นับกับเจ้าของลิงก์) การย้ายภายในโฟลเดอร์เดียวกันไม่เปลี่ยนยอด ถ้าเต็มได้ error 507 พร้อมยอดที่ใช้และโควตา
- ผู้ใช้เห็นยอดของตัวเองที่แถบพื้นที่ในหน้า "ไฟล์ของฉัน" และใน "บัญชีและความปลอดภัย → ความปลอดภัย" (แสดงเมื่อมีโควตา)
- **นับอย่างไร:** นับด้วยการเดินโฟลเดอร์ (ไม่เกิน 1,000,000 รายการ ถ้าเกินถือว่าเต็ม) เก็บผลไว้ 60 วินาทีต่อผู้ใช้ และนับใหม่ทันทีหลังลบ งานที่กำลังเขียนอยู่จองพื้นที่ไว้ก่อนในจังหวะเดียวกับที่ตรวจ ส่งหลายคำขอพร้อมกันจึงแย่งไบต์สุดท้ายไม่ได้ และคืนที่จองเมื่อยกเลิก ล้มเหลว หรือถูกลบเพราะค้างนาน

## ดูไฟล์ของผู้ใช้แบบอ่านอย่างเดียว

ผู้ดูแลและ admin เปิดไฟล์ของผู้ใช้ได้ที่ **จัดการ → ผู้ใช้ → ดูไฟล์** (ที่อยู่ `/admin/users/<ชื่อ>/files`) หน้าตาเหมือนหน้าไฟล์ แต่ซ่อนทุกปุ่มที่เขียนได้ และมีแถบบอกว่ากำลังดูไฟล์ของใคร ("ทุกการดาวน์โหลดถูกบันทึก")

- สิทธิ์ในพื้นที่นี้มีเพียง ดูรายการ ดาวน์โหลด ดาวน์โหลดหลายไฟล์ และ zip คำสั่งเขียนทุกตัว (สร้างโฟลเดอร์ สร้างไฟล์ แก้ เปลี่ยนชื่อ คัดลอก ย้าย ลบ อัปโหลด แชร์ รายการโปรด ฯลฯ) ถูกปฏิเสธ รวมถึงการคัดลอกออกจากพื้นที่นี้ไปโฟลเดอร์ตัวเอง
- manager ดูได้เฉพาะผู้ใช้ที่จัดการได้ ถ้าเป็นผู้ใช้อื่นหรือผู้ดูแล/admin ได้ 403
- **ทุกการอ่านที่มีผลกับไฟล์ถูกบันทึกในประวัติการใช้งาน:** `download` (รวมพรีวิว) `download-zip` และ `view` (อ่านไฟล์ข้อความ) โดย `detail` บอก `user:<ชื่อ>` การเปิดดูโฟลเดอร์บันทึกเป็น `browse` (โฟลเดอร์เดิมซ้ำภายใน 1 นาทีบันทึกครั้งเดียว) ไฟล์ที่เปิดไม่ถูกจำใน "ล่าสุด"/"รายการโปรด" ของคุณ
- ในทางเทคนิค คือเรียก route ไฟล์เดิมด้วย `space=user:<ชื่อผู้ใช้>` (ชื่อไม่สนตัวพิมพ์) ดู [คู่มือนักพัฒนา](development.md#ดูไฟล์ของผู้ใช้-spaceuser)

## กลุ่ม

กลุ่มคือโฟลเดอร์ร่วมของสมาชิก เมนู **จัดการ → กลุ่ม** (ผู้ใช้เห็นเป็น "โฟลเดอร์กลุ่ม" ดู [คู่มือผู้ใช้](user-guide.md#โฟลเดอร์กลุ่ม))

**สร้างกลุ่ม (admin)**

1. กด **สร้างกลุ่ม** ใส่ชื่อกลุ่ม (1–64 ตัวอักษร ไม่ซ้ำ ไม่มี `/` `\` หรืออักขระควบคุม ไม่ใช่จุดล้วน) และพื้นที่ของกลุ่ม (โควตา 0 = ไม่จำกัด)
2. กด **จัดการสมาชิก** เพิ่มผู้ใช้ และเลือกสิทธิ์ของแต่ละคน: **ดูอย่างเดียว** (`view`: ดู ดาวน์โหลด ดาวน์โหลดหลายไฟล์ zip) หรือ **แก้ไขได้** (`edit`: เพิ่มอัปโหลด แก้ไข ลบ ด้วย)

ระบบสร้างโฟลเดอร์ `<storage>/groups/<id>` ให้ (`id` สุ่มเป็นตัวพิมพ์เล็กและตัวเลข) ข้อมูลกลุ่มเก็บใน `DATA_DIR/groups.json`

**กฎ**

- ชื่อกลุ่มเปลี่ยนได้ id และโฟลเดอร์ไม่เปลี่ยน
- admin เข้าได้ทุกกลุ่มด้วยสิทธิ์เต็ม (เห็นเป็น `/groups/<id>` ใต้ `/` ของตัวเอง) สมาชิกถูกตรวจใหม่ทุกคำขอ ถอดสมาชิกหรือลบกลุ่ม = เข้าไม่ได้ทันที
- **โควตาของกลุ่ม** นับจากทั้งโฟลเดอร์กลุ่มรวมเวอร์ชันเก่าของไฟล์ อัปโหลด บันทึก คัดลอก แตก zip และกู้คืนจากถังขยะนับกับ **กลุ่ม** ไม่ใช่โควตาส่วนตัวของสมาชิก ข้อยกเว้น: admin ที่เขียนผ่าน `/` ของตัวเองไม่ถูกจำกัด และการบันทึกจาก ONLYOFFICE ในโฟลเดอร์กลุ่มยังไม่นับกับกลุ่ม
- **ถังขยะ:** ของที่ลบจากโฟลเดอร์กลุ่มเป็นของกลุ่ม สมาชิกที่มีสิทธิ์ `edit` ทุกคนเห็นและกู้คืนได้ แต่ลบถาวรได้เฉพาะคนที่ลบรายการนั้นหรือ admin
- **ลบกลุ่ม** (ต้องใส่รหัสผ่านของคุณยืนยัน): สมาชิกเข้าไม่ได้ทันที การแชร์ที่ให้กลุ่มนี้ถูกยกเลิก และย้ายโฟลเดอร์ทั้งโฟลเดอร์ไปถังขยะของ admin (ไม่ลบถาวร กู้คืนเป็นโฟลเดอร์ `/groups/<id>` ได้ แต่กลุ่มไม่กลับมา)
- ห้ามตั้งโฟลเดอร์ส่วนตัวของผู้ใช้เป็น `/groups` หรือข้างใน
- ผู้ใช้ที่ถูกลบจะถูกถอดจากทุกกลุ่ม (บัญชีใหม่ชื่อเดิมไม่ได้ที่เดิมคืน)
- **ผู้ดูแล (manager)** สร้าง/แก้/ลบกลุ่มไม่ได้ และไม่เห็นกลุ่มที่ตัวเองไม่ได้อยู่ แต่เพิ่ม/ถอด/เปลี่ยนสิทธิ์สมาชิกที่เป็น "ผู้ใช้ทั่วไปที่ตัวเองดูแล" ในกลุ่มที่ตัวเองเป็นสมาชิกได้ และให้สิทธิ์ได้ไม่เกินของตัวเอง (สมาชิก `view` ให้ได้แค่ `view`)
- **แชร์โฟลเดอร์ให้กลุ่ม:** ผู้ใช้ที่มีสิทธิ์ `share` แชร์โฟลเดอร์ของตัวเองให้ **กลุ่มที่ตัวเองเป็นสมาชิก** ได้ (admin ให้กลุ่มไหนก็ได้) สมาชิกที่เป็น `view` ได้ไม่เกิน `view` แม้แชร์แบบ `edit` สมาชิกออกจากการแชร์ของกลุ่มเองไม่ได้ เฉพาะเจ้าของยกเลิกได้
- **ลิงก์แชร์ออกจากโฟลเดอร์กลุ่มยังทำไม่ได้** (แชร์ลิงก์ในโฟลเดอร์กลุ่มถูกปฏิเสธ)
- ไฟล์สำรองมี `groups.json` แต่การกู้คืนจากหน้าเว็บคืนเฉพาะ `users.json`, `settings.json`, `branding/` (กลุ่มคือโฟลเดอร์ใน `storage/` กับรายชื่อสมาชิก ต้องกู้คืนคู่กันด้วยมือ)

## ภาพรวมระบบและประวัติการใช้งาน

### ภาพรวมระบบ

เมนู **จัดการ → ภาพรวมระบบ** แสดงสถานะของเซิร์ฟเวอร์และพื้นที่เก็บไฟล์

- พื้นที่ดิสก์ (ว่าง/ใช้ไป) จำนวนและขนาดไฟล์ทั้งหมด ไฟล์สาธารณะ ของในถังขยะ จำนวนผู้ใช้ งานอัปโหลดที่กำลังทำ สถานะการสำรองข้อมูลล่าสุด เวอร์ชันและเวลาที่เปิดมา
- ผู้ใช้หนึ่งคนถืออัปโหลดที่ประกาศแล้วแต่ยังไม่เสร็จได้ไม่เกิน `UPLOAD_MAX_PENDING` งาน (ค่าเริ่มต้น 500) เกินแล้วได้ข้อความให้รอหรือยกเลิกบางรายการก่อน งานที่ไม่มีชิ้นใหม่เข้ามานานเกินกำหนดถูกลบเอง ดู [ขั้นสูง](configuration.md)
- **คำเตือน** ที่ระบบตรวจให้ เช่น ดิสก์ว่างต่ำกว่า 10% (เตือน) หรือ 5% (วิกฤต) ยังไม่เคยสำรองข้อมูล / สำรองล่าสุดล้มเหลว / เก่าเกินกำหนด (2 วัน หรือ 2 เท่าของช่วงตารางเวลา ถ้าช่วงยาวกว่านั้น) มีผู้ใช้ยังใช้รหัสผ่านเริ่มต้น มี error ใน 24 ชั่วโมงที่ผ่านมา (มีลิงก์ไปบันทึกระบบ) มีเวอร์ชันใหม่ ใช้เวอร์ชันทดลองอยู่ และเปิดรับแพ็กเกจที่ไม่เซ็น ตัวเลขสีบนเมนู "ภาพรวมระบบ" บอกว่ามีเรื่องที่ต้องดู
- **จำนวนและขนาดไฟล์อาจช้ากว่าความจริงได้ราวหนึ่งนาที** ระบบนับไฟล์อยู่เบื้องหลัง (ไม่ให้ผู้ใช้คนอื่นต้องรอ) และแสดงผลที่นับไว้ล่าสุดทันที ขณะนับแสดง "กำลังนับ…" ครั้งแรกหลังติดตั้งที่ยังไม่เคยนับเลย ยังไม่มีตัวเลข (เปิดหน้าใหม่อีกครั้งเมื่อนับเสร็จ) ผลที่นับเก็บไว้ใน `stats-cache.json` หลังรีสตาร์ตจึงเห็นตัวเลขล่าสุดทันที
- **ผู้ดูแล (manager)** เห็นฉบับย่อ: จำนวนผู้ใช้ที่จัดการได้ พื้นที่ที่โฮมของพวกเขาใช้ และคำเตือนเรื่องรหัสผ่านเริ่มต้นของผู้ใช้เหล่านั้น ไม่เห็นเวอร์ชัน เวลาทำงาน ดิสก์ สำรองข้อมูล ถังขยะ หรือข้อมูลอัปเดต

### ประวัติการใช้งาน

เมนู **จัดการ → ประวัติการใช้งาน** บอกว่าใครเข้าสู่ระบบ อัปโหลด ดาวน์โหลด ลบ หรือแก้ไขอะไรบ้าง

- กรองตามผู้ใช้ การกระทำ หรือค้นหาจากชื่อไฟล์/รายละเอียด
- **ส่งออก CSV** (เฉพาะ admin) ตามตัวกรองที่ตั้งไว้ เปิดด้วย Excel ได้ (UTF-8 มี BOM ช่องที่ขึ้นต้นด้วย `=` `+` `-` `@` มี `'` นำหน้ากันสูตร Excel)
- manager เห็นเฉพาะของตัวเองและผู้ใช้ที่จัดการได้
- `login-failed` เขียนไม่เกินนาทีละครั้งต่อ IP + ชื่อผู้ใช้ พร้อมจำนวนครั้ง กันประวัติถูกท่วม
- ไฟล์ `audit.log` หมุนที่ 10 MB × 10 ไฟล์ ปัจจุบันรวมอยู่ในไฟล์สำรองข้อมูล

## หน้า "ระบบ"

เมนู **ระบบ** (เฉพาะ admin) รวมงานดูแลทั้งหมดไว้เป็นแท็บเดียวกัน: **ตั้งค่า · สำรองข้อมูล · อัปเดตระบบ · บันทึกระบบ · ถังขยะทั้งระบบ** ลิงก์เดิมอย่าง `/admin/backup` ยังเปิดได้ และเปิดแท็บที่ตรงกัน จุดสีฟ้าที่แท็บ "อัปเดตระบบ" บอกว่ามีเวอร์ชันใหม่

### ตั้งค่า ชื่อเว็บ โลโก้ และหน้าสาธารณะ

แท็บ **ตั้งค่า**

- **แบรนด์:** ชื่อเว็บ สีหลัก และโลโก้ (PNG, JPG, WebP หรือ SVG ไม่เกิน 1 MB) ชื่อเว็บใช้เป็นชื่อของ QR 2FA ด้วย
- **หน้าสาธารณะ:** สวิตช์ "เปิดให้ผู้เยี่ยมชมดาวน์โหลดโดยไม่ต้องเข้าสู่ระบบ" · หัวข้อต้อนรับ · ข้อความต้อนรับ · ข้อความเมื่อไม่มีไฟล์ (เว้นว่างไว้ = ใช้ข้อความมาตรฐานในภาษาที่ผู้เยี่ยมชมเลือก) · **สิ่งที่ผู้เยี่ยมชมทำได้** (สิทธิ์ของผู้เยี่ยมชม)
  - ระวังการติ๊กอัปโหลด/สร้างแก้ไขลบ/บีบอัด ให้ผู้เยี่ยมชม ใครก็อัปโหลดหรือแก้ไฟล์ได้โดยไม่ต้องเข้าสู่ระบบ ควรเปิดเฉพาะเมื่อจำเป็นจริง ๆ
  - ถ้าเปิดสิทธิ์ `upload` ผู้เยี่ยมชมทุกคนใช้โควตารวมกันวันละ `GUEST_UPLOAD_DAILY_BYTES` (ค่าเริ่มต้น 1 GB, `0` = ห้ามอัปโหลด) ระบบนับขนาดไฟล์ตั้งแต่ตอนเริ่มอัปโหลด และคืนให้เมื่อยกเลิกหรืออัปโหลดไม่จบ เกินโควตาได้ 429 ยอดที่ใช้เก็บใน `guest-uploads.json` จึงไม่หายเมื่อรีสตาร์ต และเริ่มนับใหม่ทุกวัน (ตามเวลาเครื่อง) ผู้ที่เข้าสู่ระบบไม่ถูกจำกัดด้วยโควตานี้
- **การแจ้งเตือน** (การ์ดสถานะ webhook ของผู้ดูแล พร้อมปุ่ม "ส่งข้อความทดสอบ") ดู [การแจ้งเตือนระบบ (webhook)](#การแจ้งเตือนระบบ-webhook)
- **ข้อมูลระบบ:** ขนาดชิ้นอัปโหลด × จำนวนพร้อมกัน (อ่านอย่างเดียว ค่ามาจาก `.env` ดู [ตั้งค่าระบบ](configuration.md#ขั้นสูง-ปกติไม่ต้องแตะ)) ส่วนขนาดไฟล์สูงสุดและระยะเก็บถังขยะแก้ได้ใน [ตั้งค่าระบบในหน้าเว็บ](#ตั้งค่าระบบในหน้าเว็บ)

### ตั้งค่าระบบในหน้าเว็บ

ตั้งแต่ 1.13 ค่าที่ผู้ดูแลต้องแก้บ่อยตั้งได้ที่แท็บ **ตั้งค่า** โดยไม่ต้องแก้ `.env` และ **มีผลทันทีโดยไม่ต้องรีสตาร์ต** ลำดับคือ **ค่าในเว็บ → `.env` → ค่าเริ่มต้น** (ดู [ตั้งค่าระบบ: ลำดับความสำคัญ](configuration.md#ลำดับความสำคัญของค่า)) แต่ละช่องบอกที่มาของค่า (เว็บ / `.env` / ค่าเริ่มต้น) และล้างค่าในเว็บเพื่อกลับไปใช้ค่าจาก `.env` ได้

| หมวด | ตั้งอะไรได้ |
|---|---|
| **แชร์** | อายุลิงก์เริ่มต้น (`defaultDays`) · อายุสูงสุด (`maxDays` ตัวเลือก 1, 3, 7, 14, 30, 90 วัน) · อนุญาตลิงก์ไม่หมดอายุ (`allowNever`) · บังคับให้ลิงก์ต้องมีรหัสผ่าน (`requirePassword`) |
| **ความปลอดภัย** | บังคับ 2FA (`none` / `admin` / `staff` = admin + manager / `all`) · อายุ session เป็นชั่วโมง · จำนวนครั้งที่ใส่รหัสผิดได้ · เวลาล็อกเป็นวินาที |
| **ไฟล์** | โควตาเริ่มต้นของผู้ใช้ใหม่ · ระยะเก็บถังขยะ · จำนวนและอายุของเวอร์ชันเก่า · ขนาดอัปโหลดสูงสุดต่อไฟล์ (ไม่เกินค่า `UPLOAD_MAX_SIZE` ใน `.env` ซึ่งเป็นเพดานตอนเริ่มระบบ) · เปิด/ปิด WebDAV · เปิด/ปิดภาพตัวอย่าง |
| **อีเมล** | SMTP: เซิร์ฟเวอร์ พอร์ต การเข้ารหัส บัญชี รหัสผ่าน ผู้ส่ง |
| **การแจ้งเตือน** | webhook ของผู้ดูแล: URL ชนิด (Discord/Slack/Telegram/JSON) chat id ของ Telegram ภาษา |

ตัวแปรที่ไม่อยู่ในตาราง (พอร์ต ที่เก็บข้อมูล HTTPS และค่าปรับจูนอื่น) ยังตั้งใน `.env` เท่านั้น

**ต้องยืนยันรหัสผ่านของคุณ** เมื่อบันทึกหมวด **ความปลอดภัย** หรือ **อีเมลและแจ้งเตือน** (รวมปลายทาง webhook แจ้งเตือน) หรือเมื่อ **เพิ่มสิทธิ์ให้ผู้เยี่ยมชม** ในรายการ `write` (สร้างแก้ไขลบ) `upload` หรือ `zip` (ลดสิทธิ์ไม่ต้อง) ใส่ผิดซ้ำถูกล็อกเหมือนการยืนยันรหัสผ่านอื่น การเปลี่ยนหมวดความปลอดภัย อีเมล หรือแจ้งเตือนส่งการแจ้งเตือน webhook ถึงผู้ดูแลด้วย (บอกชื่อผู้เปลี่ยนและชื่อค่า ไม่บอกค่า) และบันทึกใน [ประวัติการใช้งาน](#ประวัติการใช้งาน) (`settings-update` ระบุแต่ชื่อค่า)

#### นโยบายลิงก์แชร์

- **อายุสูงสุด** ตัดตัวเลือกอายุที่ยาวกว่าออกจากหน้าสร้างลิงก์ และ server ปฏิเสธอายุที่เกินแม้ส่งตรงผ่าน API ลิงก์ที่สร้างไว้แล้วไม่ถูกแก้
- **อนุญาตลิงก์ไม่หมดอายุ** เปิดตัวเลือก "ไม่หมดอายุ" ในหน้าสร้างลิงก์ (ปิดไว้เป็นค่าเริ่มต้น) ลิงก์ยังยกเลิกได้เสมอ
- **บังคับรหัสผ่าน** ลิงก์ที่สร้างใหม่ต้องตั้งรหัสผ่าน (อย่างน้อย 6 ตัวอักษร) ไม่ตั้งได้ 400 ที่ server ลิงก์เก่าที่ไม่มีรหัสผ่านยังใช้ได้จนกว่าจะหมดอายุหรือถูกยกเลิก

#### บังคับ 2FA

ตั้งที่หมวด **ความปลอดภัย** → **บังคับ 2FA**: ไม่บังคับ · เฉพาะ admin · admin และ manager · ทุกคน ผู้ใช้ในกลุ่มที่ถูกบังคับและยังไม่เปิด 2FA จะเห็นหน้า **ตั้งค่า 2FA** ทันทีที่ส่งคำขอครั้งถัดไป และใช้ฟีเจอร์อื่นไม่ได้ (API ตอบ 403 `auth.2fa-required`) จนกว่าจะเปิดสำเร็จ ผู้ที่มี 2FA อยู่แล้วไม่ถูกกระทบ

> **ระวังล็อกตัวเองออก:** ถ้าเลือก admin ขึ้นไป ตัวคุณเองก็ถูกบังคับด้วย
> 1. เปิด 2FA ให้บัญชีของคุณเองก่อน (บัญชีและความปลอดภัย → ความปลอดภัย) และเก็บรหัสสำรองไว้
> 2. ตรวจว่าผู้ดูแลทุกคนมีแอป authenticator พร้อม ผู้ที่ไม่มีจะทำได้แค่ตั้งค่า 2FA หรือออกจากระบบ
> 3. ถ้ายังมีผู้ดูแลที่เข้าไม่ได้ ใช้ CLI ที่เครื่อง server: `bun src/cli.ts reset-2fa <user>` (ล้าง 2FA ของผู้ใช้นั้น เขาจะถูกบังคับตั้งใหม่ตอนเข้าสู่ระบบ) หรือกลับไปตั้ง **ไม่บังคับ** ผ่านคนที่ยังเข้าได้ ดู [CLI](#คำสั่งที่เครื่อง-server-cli)
> 4. กู้คืนข้อมูลบนเครื่องที่ `secret.key` ต่างไป ทำให้ 2FA ของทุกคนใช้ไม่ได้ ดู [กู้คืนบนเครื่องอื่นและ 2FA](#กู้คืนบนเครื่องอื่นและ-2fa)

#### อีเมล (SMTP) และ webhook ในหน้าเว็บ

หมวด **อีเมล** กับ **การแจ้งเตือน** แทนการแก้ `.env` ได้ทั้งหมด (ขั้นตอนของแต่ละระบบอยู่ที่ [อีเมล](#อีเมล) และ [การแจ้งเตือนระบบ](#การแจ้งเตือนระบบ-webhook))

- **รหัสผ่าน SMTP และ URL ของ webhook เป็นความลับ** ระบบเก็บใน `settings.json` แบบเข้ารหัสด้วย `secret.key` และไม่ส่งกลับมาที่หน้าเว็บอีก (หน้าเว็บเห็นแค่ว่า "ตั้งไว้แล้ว" และ URL แบบตัดเหลือโฮสต์) ลบค่าที่เก็บในเว็บได้เพื่อกลับไปใช้ค่าจาก `.env`
- ปุ่ม **ส่งอีเมลทดสอบ** (`POST /api/admin/mail/test`) ส่งด้วยค่าที่ใช้อยู่จริงขณะนี้ไปที่อีเมลที่คุณยืนยันไว้ หรืออีเมลที่ระบุ ส่งได้ 1 ครั้งต่อผู้ดูแลต่อช่วงสั้น ๆ ถ้าส่งไม่สำเร็จจะบอกสาเหตุ (เช่น เชื่อมต่อไม่ได้ รหัสผ่านผิด) และบันทึก `mail-test` ในประวัติการใช้งาน
- ปุ่ม **ส่งข้อความทดสอบ** ของ webhook ส่งข้อความตัวอย่างถึงปลายทางที่ตั้งไว้ (บันทึก `alert-test`)
- ย้ายเครื่องแล้วต้องมี `secret.key` เดิม มิฉะนั้นค่าลับเปิดไม่ได้ ดู [คำเตือน](#คำเตือนการตั้งค่าและวิธีแก้) `admin.config-secret-unreadable`

#### คำเตือนการตั้งค่าและวิธีแก้

หน้าตั้งค่าแสดงแถบคำเตือนเมื่อ `.env` เสี่ยงหรือไม่ตรงกับวิธีที่คนเข้าใช้ (`GET /api/admin/config-warnings`) ระบบตรวจค่าที่ไม่ต้องมีคำขอตอนเริ่มด้วย และถ้ามีจะส่งแจ้งเตือน webhook หนึ่งครั้ง แก้ที่ `.env` แล้ว `docker compose up -d`

| รหัส | ระดับ | ความหมายและวิธีแก้ |
|---|---|---|
| `update.allow-unsigned` | critical | `UPDATE_ALLOW_UNSIGNED=true` รับแพ็กเกจที่ไม่เซ็น ลบบรรทัดนี้ออกจาก `.env` (หรือตั้ง `false`) และใช้ `UPDATE_PUBLIC_KEY` ถ้าสร้างแพ็กเกจเอง |
| `admin.config-admin-initial-password` | critical | ผู้ดูแลคนใดคนหนึ่งยังใช้รหัสผ่านที่ระบบสุ่มหรือที่ตั้งให้ (ยังไม่ได้เปลี่ยน) เข้าสู่ระบบด้วยบัญชีนั้นแล้วเปลี่ยนรหัสผ่าน |
| `admin.config-insecure-cookie` | warning | เข้าใช้ผ่าน HTTPS (หรือ `PUBLIC_URL` เป็น `https://`) แต่ `SECURE_COOKIE` ไม่เป็น `true` ตั้ง `SECURE_COOKIE=true` |
| `admin.config-proxy-no-headers` | warning | ตั้ง `TRUST_PROXY` ไว้ แต่คำขอที่ตรวจไม่มีหัวจาก proxy (`CF-Connecting-IP` สำหรับ `cloudflare`, `X-Forwarded-For` สำหรับ `true`) IP ในการล็อกและประวัติจึงผิด หรือ proxy ไม่ได้อยู่หน้าระบบ ตรวจว่า proxy ส่งหัวนี้ หรือตั้ง `TRUST_PROXY=false` ถ้าไม่มี proxy ระวัง: เปิด `TRUST_PROXY` โดยไม่มี proxy ทำให้ผู้ใช้ปลอม IP ได้ |
| `admin.config-admin-password-env` | warning | `ADMIN_PASSWORD` ยังอยู่ใน `.env` ทั้งที่มีบัญชี admin แล้ว (ไม่มีผลแล้ว แต่รหัสผ่านค้างในไฟล์) ลบบรรทัดนี้ |
| `admin.config-secret-unreadable` | warning | รหัสผ่าน SMTP หรือ URL webhook ที่บันทึกในเว็บเปิดไม่ได้ เพราะ `secret.key` ต่างจากที่ใช้เข้ารหัส (เช่นกู้คืนบนเครื่องใหม่) วาง `secret.key` เดิมคืนใน `DATA_DIR` หรือกรอกค่าสองอย่างนี้ใหม่ในหน้าตั้งค่า ระหว่างนั้นอีเมลหรือ webhook ถูกปิด |

### สำรองและกู้คืนข้อมูล

แท็บ **สำรองข้อมูล** ถ้าดิสก์เสีย บัญชีผู้ใช้ รหัสผ่าน และการตั้งค่าจะหายทั้งหมด ระบบจึงสำรองข้อมูลระบบให้เองทุกวัน

**สำรองอะไรบ้าง**

หนึ่งครั้ง = ไฟล์เดียว `file-center-backup-YYYYMMDD-HHMMSS.zip` (เวลาในชื่อเป็น **UTC** ตั้งแต่ 1.12.1 เพื่อไม่ให้สับสนช่วงเปลี่ยนเวลาออมแสง ถ้าชื่อซ้ำในวินาทีเดียวกันจะเลื่อนไปวินาทีถัดไปที่ว่าง ไฟล์เก่าที่ชื่อเป็นเวลาท้องถิ่นยังอ่านและกู้คืนได้ รายการเรียงและลบตามเวลาใน `backup.json` ไม่ใช่ตามชื่อ)

| อยู่ในไฟล์สำรอง | ไม่อยู่ |
|---|---|
| `users.json` (ผู้ใช้และรหัสผ่านที่เข้ารหัสแล้ว) `settings.json` `groups.json` `grants.json` `shares.json` และไฟล์ข้อมูลเล็ก ๆ อื่นใน `DATA_DIR` (รายการโปรด สถานะทัวร์ การแจ้งเตือน ยอดอัปโหลดของผู้เยี่ยมชม) | `secret.key` (กุญแจ 2FA) · `app-passwords.json` (รหัสผ่านแอป WebDAV) · `office-links.key` |
| `branding/` (โลโก้) | session ถังขยะ เวอร์ชันเก่าของไฟล์ ไฟล์อัปโหลดที่ยังไม่เสร็จ แคชภาพตัวอย่าง (`thumbs/`) ดัชนีค้นหา เวอร์ชันที่อัปเดตผ่านเว็บ |
| `logs/audit.log` และ `logs/system.log` ปัจจุบัน | log เก่าที่หมุนไฟล์แล้ว `access.log` และ `launcher.log` |
| `backup.json` (`version`, `createdAt`, `includesFiles`, ขนาดของแต่ละส่วนใน `parts`) | |
| `storage/` (ไฟล์ที่ผู้ใช้อัปโหลด) **เฉพาะเมื่อเปิด "รวมไฟล์"** | |

- `secret.key` ไม่อยู่ในไฟล์สำรองโดยเจตนา (ถ้าอยู่ไฟล์เดียวกับ `users.json` ใครได้ไฟล์สำรองไปก็ถอดความลับ 2FA ได้) **ให้เก็บสำเนา `secret.key` แยกไว้ที่ปลอดภัยเอง** (ใน Docker คือ `data/system/secret.key`)
- `app-passwords.json` ไม่อยู่ในไฟล์สำรองโดยเจตนา เพราะเป็นข้อมูลรับรอง หลังกู้คืนผู้ใช้ต้องสร้างรหัสผ่านแอปใหม่เอง
- `backup.json` ของเวอร์ชันก่อน 1.10 ไม่มีขนาดของแต่ละส่วน ยังกู้คืนได้ตามเดิม

**ตั้งค่าการสำรอง** (การ์ด "ตั้งค่าการสำรอง" บันทึกใน `settings.json`)

| ตั้งค่า | ตัวเลือก |
|---|---|
| **การบีบอัด** | เร็ว (ระดับ 1) · สมดุล (ระดับ 6) · เล็กที่สุด (ระดับ 9 ค่าเริ่มต้น) ไฟล์ที่บีบอยู่แล้ว (zip, rar, jpg, mp4, pdf, docx ...) เก็บตามเดิมไม่บีบซ้ำ ตัวอย่างวัดจริง: log และ json รวม 10 MB บีบได้ 1.30 MB (ระดับ 1, 0.12 วินาที) / 0.96 MB (ระดับ 6, 0.09 วินาที) / 0.91 MB (ระดับ 9, 0.39 วินาที) |
| **สำรองอัตโนมัติ** (ตารางเวลา) | ปิด · ทุกวัน (เวลา) · ทุกสัปดาห์ (เลือกวัน + เวลา) · ทุก ๆ N ชั่วโมง (1–168) เวลาเป็น **เวลาของเครื่อง server** ไม่ใช่ของเบราว์เซอร์ (หน้าเว็บแสดงเขตเวลาของ server และการสำรองครั้งต่อไป) |
| **จำนวนไฟล์สำรองที่เก็บไว้** | 1–30 ไฟล์ล่าสุด เก่ากว่านั้นถูกลบเอง |
| **รวมไฟล์ที่ผู้ใช้อัปโหลด** | เปิดต้องใส่รหัสผ่านซ้ำ ปิดไม่ต้อง |

- `BACKUP_HOUR`, `BACKUP_KEEP`, `BACKUP_INCLUDE_FILES` เป็นเพียงค่าเริ่มต้นเมื่อยังไม่เคยตั้งในหน้านี้ ตั้งแล้วจะใช้ค่าในหน้าเว็บแทน
- ค่าเริ่มต้นสำรองทุกวันตี 3 และทันทีที่ครั้งล่าสุดที่สำเร็จเก่ากว่า 2 วัน (เช่น เปิดระบบครั้งแรก หรือเครื่องปิดอยู่ตอนถึงเวลา) ไม่เกินชั่วโมงละครั้ง
- ระบบตรวจตารางทุกนาที: ทุกวัน/ทุกสัปดาห์ เริ่มภายใน 1 ชั่วโมงหลังเวลาที่ตั้ง และข้ามถ้ามีชุดล่าสุดอายุไม่ถึง 20 ชั่วโมง ตารางที่เพิ่งบันทึกไม่ย้อนไปรันเวลาที่ผ่านไปแล้ว ชุดที่ล้มเหลวนับเป็นความพยายามครั้งล่าสุด จึงไม่ลองซ้ำทุกนาที
- ใน Docker เวลาของเครื่องปกติเป็น UTC ถ้าต้องการเวลาไทย ใส่ `TZ=Asia/Bangkok` ใน `.env` (ดู [ตั้งค่าระบบ](configuration.md#docker-และ-compose))

**สำรองด้วยมือ:** กด **สำรองตอนนี้** ได้ทุกเมื่อ ในรายการ "ไฟล์สำรองข้อมูล" ดาวน์โหลด ลบ หรือกู้คืนแต่ละชุดได้ ถ้า `BACKUP_HOUR=off` ก็ยังกดสำรองเองได้ ผลของการสำรองทุกครั้งเขียนใน `DATA_DIR/backup-status.json` หน้าภาพรวมแสดงผลและเตือนเมื่อล้มเหลวหรือเก่าเกิน 2 วัน

**ถ้ารวมไฟล์ที่อัปโหลด** ไฟล์สำรองแต่ละชุดจะใหญ่เท่ากับพื้นที่เก็บไฟล์ทั้งหมด (rar, zip, วิดีโอบีบอัดไม่ลงอีก) แนะนำให้เก็บแค่ 1–2 ชุด (ถ้าไม่ได้ตั้งจำนวนเอง ระบบเก็บ 2 ชุดให้) และชี้ `BACKUP_DIR` ไปดิสก์อีกลูก หน้าเว็บแสดงขนาดโดยประมาณ พื้นที่ว่าง และเตือนถ้าไม่พอ

**เก็บที่ไหน**

`BACKUP_DIR` ค่าเริ่มต้นคือโฟลเดอร์ `backups` ข้าง `DATA_DIR` (Docker: `./data/backups`) ซึ่งอยู่บนดิสก์เดียวกับข้อมูล **ถ้าดิสก์นั้นเสีย ไฟล์สำรองก็หายไปด้วย** หน้าเว็บจะเตือนเมื่อยังอยู่ดิสก์เดียวกัน ควรทำอย่างใดอย่างหนึ่ง

1. ชี้ไปดิสก์อื่น: ใน Docker เพิ่ม volume ใน `docker-compose.yml` ที่บริการ `file-center`
   ```yaml
       volumes:
         - ./data:/data
         - /mnt/backup-disk/file-center:/backups
   ```
   แล้วใส่ `BACKUP_DIR=/backups` ใน `.env` และ `docker compose up -d`
2. หรือดาวน์โหลดไฟล์สำรองเก็บไว้นอกเครื่องเป็นระยะ

**ตรวจพื้นที่ดิสก์ก่อนสำรอง** (ทั้งสำรองเองและอัตโนมัติ)

- ประมาณขนาด = ข้อมูลระบบ + (ถ้ารวมไฟล์) ขนาด `storage` โดยถือว่าบีบไม่ได้เลย ต้องมีที่ว่างใน `BACKUP_DIR` อย่างน้อย ประมาณการ × 1.05 + 1 GB
- ถ้าไม่พอ ระบบลบไฟล์สำรองเก่าที่สุดทีละไฟล์แล้วตรวจใหม่ (ลบเท่าที่จำเป็นเท่านั้น) **โดยไม่ลบชุดล่าสุด** (ต้องเหลืออย่างน้อย 1 ชุดจนกว่าชุดใหม่จะเสร็จ) ถ้าลบไปแล้วแต่ชุดใหม่ล้มเหลว ผู้ดูแลได้รับการแจ้งเตือน (กระดิ่ง/LINE กลุ่ม `backup.pruned-then-failed`) ว่าลบไปกี่ชุด
- ถ้ายังไม่พอ จะไม่เริ่มสำรอง บันทึกสถานะ `backup.no-space` (507) และส่งการแจ้งเตือน หน้าเว็บบอกวิธีแก้: ลดจำนวนไฟล์สำรองที่เก็บไว้ · ปิดการรวมไฟล์ที่ผู้ใช้อัปโหลด · ย้าย `BACKUP_DIR` ไปดิสก์ที่ใหญ่กว่า
- ระหว่างเขียน ตรวจที่ว่างทุก ๆ 256 MB ที่อ่าน ถ้าเหลือต่ำกว่า 1 GB จะหยุด ลบไฟล์ `.partial` และบันทึกสถานะ `backup.aborted-no-space`
- ระหว่างเขียนไฟล์ชื่อจะลงท้าย `.partial` จึงไม่มีไฟล์ที่เขียนไม่ครบปนอยู่ในรายการ และลบไฟล์เก่าตามจำนวนที่เก็บเฉพาะหลังสำรองสำเร็จ

**กู้คืน (admin)**

1. ในรายการไฟล์สำรอง กด **กู้คืน** ที่ชุดที่ต้องการ อ่านสิ่งที่จะถูกแทนที่
2. ใส่รหัสผ่านของคุณยืนยัน (ใส่ผิดซ้ำจะถูกล็อกเหมือนการเข้าสู่ระบบ)
3. กด **กู้คืนและรีสตาร์ต** รอจนหน้าโหลดใหม่ (ประมาณ 2–5 วินาที)
4. เข้าสู่ระบบด้วยรหัสผ่านตามไฟล์สำรอง

สิ่งที่เกิดขึ้น

1. ระบบสำรองสถานะปัจจุบันไว้ก่อนหนึ่งไฟล์ (ถ้ากู้ผิดไฟล์ก็กู้กลับจากไฟล์นี้ได้)
2. ตรวจว่า `users.json` ในไฟล์สำรองอ่านได้และมีผู้ดูแลระบบสูงสุดอย่างน้อยหนึ่งคน
3. แทนที่ `users.json`, `settings.json` และ `branding/` (ผู้ใช้ที่เพิ่มหลังวันนั้นหายไป รหัสผ่านที่เปลี่ยนหลังวันนั้นกลับเป็นรหัสเดิม)
4. รีสตาร์ตแอปผ่าน launcher (ต้องเริ่มด้วย `bun start` หรือ Docker) ผู้ที่ login อยู่ยัง login ต่อได้ถ้าบัญชีมีอยู่ในไฟล์สำรอง

ข้อควรรู้

- **ไฟล์ใน `storage` ไม่ถูกกู้คืนจากหน้าเว็บ** แม้ไฟล์สำรองจะรวมไว้ ให้แตก `storage/` จาก zip ด้วยมือเมื่อต้องการ
- หน้าเว็บคืนเฉพาะ `users.json`, `settings.json`, `branding/` ไฟล์อื่นในไฟล์สำรอง (`groups.json`, `grants.json`, `shares.json` ฯลฯ) ต้องแตกจาก zip ใส่ `DATA_DIR` เองถ้าต้องการ
- รหัสผ่านแอป WebDAV ไม่อยู่ในไฟล์สำรอง ผู้ใช้สร้างใหม่เอง

**ดิสก์เสียทั้งลูก:** ติดตั้งระบบใหม่ เริ่มระบบหนึ่งครั้งแล้วหยุด จากนั้นแตก `users.json`, `settings.json` และ `branding/` จากไฟล์สำรองลงใน `DATA_DIR` (Docker: `data/system/`) วาง `secret.key` เดิมไว้ใน `DATA_DIR` (ถ้ามีสำเนา) แล้วเริ่มระบบอีกครั้ง

#### กู้คืนบนเครื่องอื่นและ 2FA

ไฟล์สำรองไม่มี `secret.key` ถ้ากู้คืนบนเครื่องที่ `secret.key` ต่างไป (เครื่องใหม่ที่ติดตั้งสด หรือ `secret.key` หาย) `users.json` จะกลับมาพร้อมความลับ 2FA ที่เข้ารหัสด้วยกุญแจของเครื่องเดิม ซึ่งเครื่องนี้เปิดไม่ได้

- หน้ากู้คืนแจ้งคำเตือนพร้อมรายชื่อผู้ใช้ที่ได้รับผลกระทบ (`twoFactorLost`, `backup.restore-2fa-lost`) บันทึกในประวัติการใช้งานและ log ด้วย
- ผู้ใช้เหล่านั้น (รวมถึง admin ถ้าเปิด 2FA) จะผ่านรหัสผ่านแล้วใส่รหัส 2FA ไม่ผ่าน

ทางแก้ (เลือกอย่างใดอย่างหนึ่ง)

1. **วาง `secret.key` เดิม** ไว้ใน `DATA_DIR` (Docker: `data/system/secret.key`) ถ้ายังมีสำเนา แล้วรีสตาร์ต 2FA เดิมของทุกคนใช้ได้ต่อ
2. **รีเซ็ต 2FA ที่เครื่อง server** ก่อนออกจากระบบ/หลังรีสตาร์ต ไม่ต้องใช้ session ของ admin
   ```bash
   bun src/cli.ts reset-2fa <ชื่อผู้ใช้>
   docker compose exec file-center bun src/cli.ts reset-2fa admin     # แบบ Docker
   ```
   แล้วให้แต่ละคนเปิด 2FA ใหม่เองหลังเข้าสู่ระบบ ถ้าไม่มีกุญแจนี้ รหัส 2FA ของทุกคนใช้ไม่ได้ ต้องรีเซ็ตทีละคน

### อัปเดตระบบ

แท็บ **อัปเดตระบบ** ผู้ดูแลระบบสูงสุดอัปเดตโค้ดได้เองจากหน้าเว็บ ไม่ต้อง FTP ไม่ต้องเข้าเครื่อง server ไม่ต้องรัน `docker compose` และไม่ต้องปิดระบบ

หน้านี้แสดง **เวอร์ชันที่ใช้อยู่** ที่มา (เวอร์ชันที่มากับระบบ หรืออัปเดตผ่านเว็บ) และ **ลายเซ็นแพ็กเกจ** (บังคับ / ไม่บังคับ) ถ้าระบบไม่ได้เริ่มผ่านตัวควบคุม (launcher) หน้านี้จะแจ้งว่ารีสตาร์ตตัวเองไม่ได้ ให้เริ่มด้วย `bun start` หรือ Docker

#### อัปเดตจากหน้าเว็บในปุ่มเดียว

เมื่อมี `UPDATE_SOURCE` (รุ่นทางการตั้งไว้ใน `.env.example`)

1. เปิด **ระบบ → อัปเดตระบบ** กด **ตรวจและอัปเดต** (หน้านี้บอกล่วงหน้าว่าเวอร์ชันล่าสุดเซ็นหรือไม่ ถ้าไม่เซ็นจะแจ้งว่า "จะถูกปฏิเสธ")
2. ถ้ามีเวอร์ชันใหม่กว่า จะแสดง "มีเวอร์ชันใหม่ v…" พร้อมหมายเหตุ กด **อัปเดตเลย**
3. ใส่รหัสผ่านของคุณยืนยัน กด **ติดตั้งและรีสตาร์ต**
4. รอ 2–5 วินาที หน้าโหลดใหม่เองเมื่อกลับมา

ระบบดึงไฟล์มาเอง ตรวจ SHA-256 และขนาดกับ `latest.json` ตรวจไฟล์ในแพ็กเกจแบบเดียวกับที่ลากมาวาง ตรวจลายเซ็น แล้วลองเปิดเวอร์ชันใหม่แยกต่างหากก่อน ถ้าขั้นใดล้มเหลวหน้านี้บอกขั้นนั้น (ตรวจหาเวอร์ชันใหม่ / ดาวน์โหลดแพ็กเกจ / ตรวจไฟล์และลายเซ็น / ติดตั้งและทดลองเปิด / รีสตาร์ต) และไม่มีแพ็กเกจค้างอยู่

**ตรวจเองเบื้องหลัง:** server อ่านเฉพาะ `latest.json` ราว 1 นาทีหลังเริ่มระบบและวันละครั้ง (ไม่ดาวน์โหลดหรือติดตั้งอะไรเอง) ถ้ามีเวอร์ชันใหม่กว่า หน้าภาพรวมเตือน และส่งการแจ้งเตือนหนึ่งครั้งต่อเวอร์ชันใหม่ (กระดิ่ง และ webhook ถ้าตั้งไว้) ผลเก็บในหน่วยความจำ เริ่มระบบใหม่ก็ตรวจใหม่

#### อัปโหลดแพ็กเกจเอง

ใช้เมื่อ repo เป็นส่วนตัว ปิด `UPDATE_SOURCE` หรือสร้างแพ็กเกจเอง ([วิธีสร้าง](install.md#สร้างแพ็กเกจ))

1. เปิด **ระบบ → อัปเดตระบบ** ลากไฟล์ `.zip` มาวาง (หรือคลิกเลือกไฟล์ ขนาดไม่เกิน `UPDATE_MAX_SIZE` 200 MB)
2. ระบบตรวจไฟล์ในแพ็กเกจ **โดยยังไม่รันโค้ดใด ๆ ของแพ็กเกจ** แสดงเวอร์ชันใหม่ เวลาสร้าง จำนวนไฟล์ หมายเหตุ และสถานะลายเซ็น
3. ใส่รหัสผ่านของคุณยืนยัน กด **ติดตั้งและรีสตาร์ต** ระบบจะลองเปิดเวอร์ชันใหม่แยกต่างหากก่อน (ไม่เกินครึ่งนาที) ถ้าเปิดไม่ขึ้นจะไม่ติดตั้ง

ข้อควรรู้

- ระบบรีสตาร์ตเฉพาะโปรเซสของแอปประมาณ 2–5 วินาที คอนเทนเนอร์และ Cloudflare Tunnel ไม่ดับ ผู้ใช้ที่ login อยู่ยัง login ต่อได้ ข้อมูลและไฟล์ไม่ถูกแตะต้อง การอัปโหลดที่กำลังส่งอยู่จะลองส่งชิ้นส่วนใหม่เอง (หน้านี้เตือนถ้ามีอัปโหลดค้างอยู่)
- ระบบรับเฉพาะเวอร์ชันที่ **ใหม่กว่า** ที่ใช้อยู่ จึงติดตั้งรุ่นเก่ากว่าด้วยการอัปโหลดไม่ได้ (ย้อนกลับใช้ปุ่ม "ย้อนกลับ" ด้านล่าง)
- **ครั้งแรกที่เปิดใช้ฟีเจอร์นี้** ต้องสร้างอิมเมจใหม่หนึ่งครั้ง และบางรุ่นต้อง build ใหม่หลังอัปเดต ดู [เมื่อไรต้อง build อิมเมจใหม่](install.md#เมื่อไรต้อง-build-อิมเมจใหม่)
- ปิดฟีเจอร์ทั้งหมดด้วย `WEB_UPDATE=false`

**ความปลอดภัยของการติดตั้ง:** เฉพาะ admin · โค้ดของแพ็กเกจไม่ถูกรันจนกว่าจะใส่รหัสผ่านซ้ำ (ทุกครั้งที่ติดตั้ง/ย้อนกลับ ใส่ผิดซ้ำจะถูกล็อกเหมือนการเข้าสู่ระบบ) · ทุกไฟล์ในแพ็กเกจต้องตรง `manifest.json` (ขนาดและ SHA-256) ไม่มีไฟล์เกิน ไม่มี symlink หรือพาธ `../` · บันทึกลงประวัติการใช้งานทุกครั้ง แพ็กเกจคือโค้ดที่จะรันบนเซิร์ฟเวอร์ ให้อัปโหลดเฉพาะแพ็กเกจที่คุณสร้างเองหรือเชื่อถือได้

#### ลายเซ็นแพ็กเกจ

**ระบบติดตั้งเฉพาะแพ็กเกจที่เซ็นแล้ว** (ทั้งไฟล์ที่อัปโหลดและที่ดึงจาก `UPDATE_SOURCE`) แม้บัญชี admin ถูกยึดไปก็ติดตั้งโค้ดอื่นไม่ได้ ระบบฝังกุญแจสาธารณะของ File Center ไว้ จึงติดตั้งรุ่นทางการที่เซ็นแล้วได้ทันทีโดยไม่ต้องตั้งอะไร

| สถานการณ์ | ทำอย่างไร |
|---|---|
| ใช้รุ่นทางการ | ไม่ต้องทำอะไร |
| สร้างแพ็กเกจเอง | สร้างกุญแจของคุณเอง ตั้ง `UPDATE_PUBLIC_KEY` (ใช้แทนกุญแจที่ฝังมา) ดู [กุญแจเซ็นแพ็กเกจ](install.md#กุญแจเซ็นแพ็กเกจ) |
| ปิดการบังคับ | `UPDATE_ALLOW_UNSIGNED=true` (เสี่ยง ระบบเตือนตอนเริ่ม ในหน้าภาพรวมและหน้าอัปเดต และบันทึกการติดตั้งเป็น `update-apply-unsigned`) |
| อัปเกรดจากรุ่นเก่า | เซิร์ฟเวอร์รุ่น 1.6.0 และเก่ากว่ารับ 1.7.0 ที่เซ็นแล้วได้ตามปกติ ตั้งแต่ 1.7.0 เป็นต้นไปติดตั้งได้เฉพาะแพ็กเกจที่เซ็น |

หน้าอัปเดตแสดงสถานะลายเซ็นของแพ็กเกจแต่ละอัน: ลงนามแล้ว ตรวจลายเซ็นผ่าน / ลงนามแล้ว (ระบบยังไม่ได้ตั้งกุญแจตรวจ) / แพ็กเกจไม่ได้ลงนาม แพ็กเกจที่ไม่มีลายเซ็น เซ็นด้วยกุญแจอื่น หรือถูกแก้หลังเซ็น จะถูกปฏิเสธ

#### ย้อนกลับและประวัติเวอร์ชัน

- **ย้อนกลับอัตโนมัติ:** ถ้าเวอร์ชันใหม่เปิดไม่ขึ้นหรือล้มภายในไม่กี่วินาทีหลังติดตั้ง launcher กลับไปใช้เวอร์ชันก่อนหน้าเอง และหน้าอัปเดตบอกสาเหตุ ("เวอร์ชันใหม่เปิดไม่ขึ้น ระบบย้อนกลับเป็นเวอร์ชัน … แล้ว")
- **ตรวจ `server.js` ก่อนเริ่ม:** ตอนติดตั้ง ระบบจำ SHA-256 ของ `server.js` ไว้ และ launcher ตรวจซ้ำก่อนเริ่มทุกครั้งและก่อนย้อนกลับไปเวอร์ชันในประวัติ ถ้าไฟล์ไม่ตรง (ถูกแก้หลังติดตั้ง) ระบบใช้เวอร์ชันที่มากับอิมเมจแทน หน้าอัปเดตบอกเหตุผล ("ไฟล์ server.js … ไม่ตรงกับที่ติดตั้งไว้") และ `launcher.log` มีบรรทัด `server-changed` อัปเดตที่ติดตั้งก่อน 1.13.2 ไม่ถูกตรวจ จนกว่าจะติดตั้งใหม่
- **ย้อนกลับด้วยมือ:** ส่วน **เวอร์ชันที่ย้อนกลับได้** ในหน้าอัปเดตแสดงประวัติ (ระบบเก็บ **2 เวอร์ชันล่าสุด** และเวอร์ชันที่มากับอิมเมจ) กด **ย้อนกลับ** ที่เวอร์ชันที่ต้องการ ใส่รหัสผ่านยืนยัน ระบบรีสตาร์ตเป็นเวอร์ชันนั้น การย้อนกลับเปลี่ยนเฉพาะโค้ด **ไม่ย้อนข้อมูล** (ผู้ใช้ ไฟล์ การตั้งค่า)
- **เวลารอให้เวอร์ชันใหม่ตอบ:** `FC_HEALTH_TIMEOUT_MS` (ค่าเริ่มต้น `40000` = 40 วินาที) เป็นเวลาที่ launcher รอให้โปรเซสใหม่ตอบ `/api/health` ถ้าเครื่องช้าหรือข้อมูลมาก (เริ่มระบบนาน) ให้ตั้งเพิ่มใน `.env` และ `FC_STABLE_MS` (ค่าเริ่มต้น `8000`) คือเวลาที่ต้องอยู่รอดหลังตอบครั้งแรกจึงนับว่าติดตั้งสำเร็จ
- **ย้อนกลับเพราะช้าเกินเวลา ไม่ลบไฟล์เวอร์ชันนั้น:** ถ้าสาเหตุคือ "ไม่ตอบภายในเวลา" (`update.health-timeout`) launcher ย้อนกลับแต่ **เก็บโฟลเดอร์ของเวอร์ชันนั้นไว้** และใส่เป็นรายการแรกในประวัติ สลับกลับไปลองใหม่จากหน้าอัปเดต (ย้อนกลับ/สลับเวอร์ชัน) ได้โดยไม่ต้องอัปโหลดแพ็กเกจซ้ำ (เพิ่ม `FC_HEALTH_TIMEOUT_MS` ก่อน) ส่วนที่ครบ 2 รายการในประวัติแล้วจะถูกลบเอง ถ้าโปรเซสล้มหรือหยุดเอง (`update.exited-unconfirmed`) โฟลเดอร์ถูกลบ
- ถ้าภายหลังสร้างอิมเมจใหม่แล้วเวอร์ชันในอิมเมจใหม่กว่าเวอร์ชันที่อัปเดตไว้ ระบบใช้เวอร์ชันในอิมเมจ
- ถ้าเวอร์ชันที่รันอยู่ล้มทีหลัง launcher เริ่มใหม่ให้ตามเดิม ไม่ย้อนกลับ (กันการบังและซ่อนความผิดพลาดใน `.env` หรือดิสก์)

#### เวอร์ชันทดลอง (เบตา)

เบตาคือเวอร์ชันทดลอง (`x.y.z-beta.N` เช่น `1.9.0-beta.1`) ที่ออกก่อนรุ่นปกติ **ยังไม่เสถียรและอาจมีข้อบกพร่อง หรือทำให้ระบบใช้งานไม่ได้** ใช้เมื่อต้องการลองของใหม่เท่านั้น ไม่ควรใช้กับเซิร์ฟเวอร์ที่คนอื่นพึ่งพาอยู่ **สำรองข้อมูลก่อนลองเบตา**

- ระบบไม่เสนอเบตาให้เอง การตรวจรายวัน คำเตือน "มีเวอร์ชันใหม่" และการแจ้งเตือนดูเฉพาะรุ่นปกติ
- ถ้ามีเบตา (ใหม่กว่าทั้งที่ใช้อยู่และรุ่นปกติล่าสุด) หน้าอัปเดตแสดงการ์ด **เวอร์ชันทดลอง (beta)** พร้อมคำเตือน ให้ติ๊ก "ฉันเข้าใจความเสี่ยงและต้องการติดตั้งเวอร์ชันทดลอง" แล้วกด **ติดตั้งเวอร์ชันทดลอง** ใส่รหัสผ่านยืนยัน ขั้นตอนตรวจ (รหัสผ่าน SHA-256 ขนาด ลายเซ็น) เหมือนรุ่นปกติทุกอย่าง **ไม่มีข้อยกเว้นเรื่องลายเซ็น** ประวัติการใช้งานบันทึก `update-apply-beta` เพิ่ม
- ขณะใช้เบตา หน้าภาพรวมเตือนว่ากำลังใช้เวอร์ชันทดลอง และเสนอรุ่นปกติที่ใหม่กว่าตามปกติ (รวมรุ่นปกติของ x.y.z เดียวกัน เช่น `1.9.0` หลัง `1.9.0-beta.2`)
- **กลับไปรุ่นปกติ:** (1) ติดตั้งรุ่นปกติถัดไปเมื่อออกแล้ว (จากหน้าอัปเดตหรืออัปโหลดแพ็กเกจรุ่นปกติ ต้องใหม่กว่าที่ใช้อยู่) หรือ (2) ย้อนกลับไปเวอร์ชันที่ใช้ก่อนหน้าในรายการ "เวอร์ชันที่ย้อนกลับได้" (หรือเวอร์ชันที่มากับอิมเมจ) การย้อนกลับเปลี่ยนเฉพาะโค้ด **ไม่ย้อนข้อมูล** ที่เบตาเขียนไว้แล้ว จึงควรสำรองข้อมูลก่อนลองเบตา

### บันทึกระบบ

แท็บ **บันทึกระบบ** error และเหตุการณ์สำคัญของระบบเขียนลงไฟล์ ไม่หายไปพร้อมคอนเทนเนอร์ ผู้ดูแลดูได้จากหน้าเว็บโดยไม่ต้องเข้าเครื่อง server

- กรองตามระดับ (ข้อมูล / คำเตือน / ข้อผิดพลาด) และค้นหาเหตุการณ์หรือรายละเอียด ใหม่สุดก่อน อ่านต่อไปยังไฟล์ที่หมุนแล้ว
- ปุ่ม **ดาวน์โหลด log ทั้งหมด (.zip)** ได้ `system.log`, `launcher.log`, `audit.log` (รวมไฟล์ที่หมุนแล้ว)

ไฟล์ log (ใน `DATA_DIR/logs`)

| ไฟล์ | เขียนโดย | เนื้อหา |
|---|---|---|
| `system.log` | แอป | บรรทัดละหนึ่งรายการแบบ JSON `{ ts, level, event, detail }` (`level` = `info` / `warn` / `error`) และพิมพ์ออก stdout (`docker compose logs`) ด้วย มี error ที่ไม่มีใครดักไว้ (`unhandledRejection` บันทึกแล้วทำงานต่อ, `uncaughtException` บันทึกแล้วปิดโปรเซสให้ launcher เริ่มใหม่) error ระหว่างตอบคำขอ (500) สำรอง/กู้คืนข้อมูลล้มเหลว เขียนไฟล์ข้อมูลไม่ได้ ฯลฯ |
| `launcher.log` | launcher | เริ่มระบบ รีสตาร์ต ย้อนกลับเวอร์ชัน ระบบหยุดทำงาน (crash) |
| `access.log` | แอป เฉพาะเมื่อ `ACCESS_LOG=true` | บรรทัดละคำขอ (method, path ที่ตัด query และโทเคนออกแล้ว, status, เวลาที่ใช้ ms, IP, ผู้ใช้) |
| `audit.log` | แอป | ประวัติการใช้งาน (ดูหน้า "ประวัติการใช้งาน") |

- ทุกไฟล์หมุนเมื่อใหญ่ถึง `LOG_MAX_BYTES` (`system.log` → `system.log.1` → ...) เก็บไว้ `LOG_MAX_FILES` ไฟล์ ส่วน `audit.log` หมุนที่ 10 MB × 10 ไฟล์
- **ไม่มีความลับใน log:** ไม่บันทึกรหัสผ่าน, cookie, CSRF token, โทเคนใน `/api/batch/:token`, ในลิงก์แชร์ (`/api/s/:token`, `/s/:token`) และในลิงก์ของ ONLYOFFICE, รหัสการอัปโหลด และ query string ของ URL (ตัดออกก่อนเขียน ทั้งในไฟล์และ stdout) ข้อยกเว้นเดียวคือรหัสผ่าน admin ที่สุ่มให้ตอนเริ่มครั้งแรก ซึ่งแสดงบน stdout เท่านั้น ไม่ลงไฟล์
- หน้าภาพรวมเตือน "มี error N รายการใน 24 ชั่วโมงที่ผ่านมา" และส่งการแจ้งเตือนเมื่อเกิน `ALERT_ERRORS_PER_HOUR` ต่อชั่วโมง
- `system.log` ปัจจุบันรวมอยู่ในไฟล์สำรองข้อมูลด้วย

### ถังขยะทั้งระบบ

แท็บ **ถังขยะทั้งระบบ** เห็นของที่ผู้ใช้ทุกคนลบ (ผู้ใช้เห็นเฉพาะถังขยะของตัวเองในเมนู "ถังขยะ" ดู [คู่มือผู้ใช้](user-guide.md#ถังขยะของฉันและเลิกทำ))

- ของที่ลบอยู่ที่นี่ `TRASH_RETENTION_DAYS` วัน (ค่าเริ่มต้น 30) ก่อนถูกลบถาวร
- แต่ละรายการบอกว่าใครลบ ลบเมื่อไร และเหลือเวลาอีกกี่วัน **กู้คืน** กลับตำแหน่งเดิม หรือ **ลบถาวร** ได้ และ **ล้างถังขยะ** ลบทั้งหมด
- ของที่เคยเป็นของกลุ่ม ของผู้ใช้ที่ถูกลบบัญชี และโฟลเดอร์กลุ่มที่ถูกลบ เห็นเฉพาะที่นี่
- การลบเขียนบันทึก `meta.json` ของรายการ **ก่อน** ย้ายไฟล์เข้าถังขยะ (ตั้งแต่ 1.12.1) ถ้าระบบล้มกลางทาง ไม่มีไฟล์ที่ไม่มีใครเห็น: ตอนเริ่มและทุกชั่วโมง ระบบรับรายการที่มีไฟล์แต่ไม่มี `meta.json` (จากเวอร์ชันเก่า) เป็นรายการของ admin (กู้คืนไปที่ `/recovered-from-trash/<id>` ชื่อเดิมและที่เดิมสูญไปพร้อมโปรเซส) และลบรายการที่มี `meta.json` แต่ไม่มีไฟล์

## การแจ้งเตือนระบบ (webhook)

การตั้งหรือเปลี่ยนปลายทาง webhook ที่หน้าเว็บต้องยืนยันรหัสผ่านของ admin และส่งการแจ้งเตือน "เปลี่ยนการตั้งค่า" ถึงผู้ดูแล (บอกชื่อค่า ไม่บอกค่า)

ระบบส่งข้อความสั้น ๆ ถึงผู้ดูแลทาง Discord, Slack, Telegram หรือ webhook ใด ๆ ที่รับ JSON เมื่อมีเรื่องที่ต้องดู จึงไม่ต้องเปิดหน้าเว็บคอยดู

**เรื่องที่แจ้ง**

- สำรองข้อมูลไม่สำเร็จ (ทั้งอัตโนมัติและที่กดเอง) พร้อมสาเหตุ
- error มากกว่า `ALERT_ERRORS_PER_HOUR` (ค่าเริ่มต้น 20) ในหนึ่งชั่วโมงที่ผ่านมา (ตรวจทุก 5 นาที)
- บัญชีหรือลิงก์แชร์ถูกล็อกเพราะใส่รหัสผ่านผิดซ้ำ (ลิงก์ล็อกได้ทั้งต่อ IP ผิด 5 ครั้ง และทั้งลิงก์ ผิด 50 ครั้งจากทุก IP รวมกันใน 15 นาที): เข้าสู่ระบบ, ยืนยันรหัสผ่านก่อนติดตั้งอัปเดต/กู้คืน, ปลดล็อกลิงก์แชร์ (บอกชื่อผู้ใช้หรือรหัสลิงก์ และ IP แบบเดียวกับประวัติการใช้งาน)
- ดิสก์เหลือน้อยขั้นวิกฤต (ต่ำกว่า 5% เกณฑ์เดียวกับคำเตือนในหน้าภาพรวม ตรวจทุก 5 นาที)
- มีเวอร์ชันใหม่ที่ `UPDATE_SOURCE` (หนึ่งครั้งต่อเวอร์ชัน)
- เขียนไฟล์ข้อมูล (`users.json`, `settings.json` ฯลฯ) ไม่ได้หลังลองซ้ำหลายครั้ง (เช่น ดิสก์เต็ม) `store-write-failed`: การเปลี่ยนแปลงล่าสุดอยู่ในหน่วยความจำอย่างเดียวและจะหายถ้ารีสตาร์ต ระบบลองเขียนใหม่เองทุก 30 วินาที

**ตั้งค่า** ได้สองทาง: ในหน้าเว็บ **ระบบ → ตั้งค่า → หมวดอีเมลและแจ้งเตือน** (ใส่ URL ชนิด chat id ภาษา มีผลทันที ไม่ต้องรีสตาร์ต ค่าในเว็บชนะ `.env` และ URL เก็บแบบเข้ารหัส ดู [ตั้งค่าระบบในหน้าเว็บ](#ตั้งค่าระบบในหน้าเว็บ)) หรือใน `.env` แล้วรีสตาร์ต (`docker compose up -d`) ขั้นตอนด้านล่างใช้ `.env` เป็นตัวอย่าง ถ้าตั้งในเว็บให้ข้ามข้อ 2-3

1. สร้าง webhook ที่ปลายทาง
   - Discord: การตั้งค่าช่อง → Integrations → Webhooks → สร้างและคัดลอก URL
   - Slack: สร้าง Incoming Webhook แล้วคัดลอก URL
   - Telegram: สร้างบอทกับ @BotFather ได้โทเคน แล้วหา chat id ที่บอทจะส่งถึง
   - ระบบอื่น: URL ที่รับ `POST` JSON
2. ใส่ใน `.env`
   ```env
   ALERT_WEBHOOK_URL=https://discord.com/api/webhooks/<id>/<token>
   ALERT_WEBHOOK_KIND=discord        # slack: URL ของ Incoming Webhook, json: ส่ง { event, code, message, params, lang, version, time }
   # Telegram: ALERT_WEBHOOK_KIND=telegram, ALERT_WEBHOOK_URL=https://api.telegram.org/bot<token>/sendMessage, ALERT_TELEGRAM_CHAT_ID=<chat id>
   ALERT_LANG=th
   ```
3. เริ่มระบบใหม่ (`docker compose up -d`)
4. เปิด **ระบบ → ตั้งค่า** ที่การ์ด **การแจ้งเตือน** ตรวจว่าขึ้น "เปิดอยู่" ช่องทางและโฮสต์ถูกต้อง แล้วกด **ส่งข้อความทดสอบ** ควรเห็นข้อความที่ปลายทาง (ประวัติการใช้งานบันทึก `alert-test`)

**ข้อควรรู้**

- แต่ละเรื่องส่งไม่เกินชั่วโมงละครั้ง ส่งเบื้องหลัง รอไม่เกิน 10 วินาที ไม่ตาม redirect ส่งไม่สำเร็จแค่บันทึก `alert-failed` (warn) ใน log ไม่ทำให้คำขอใดช้าหรือล้มเหลว
- ข้อความมาจากรายการข้อความ (`src/messages.ts`) ตาม `ALERT_LANG` และผ่านการตัดความลับแบบเดียวกับ log: ไม่มีรหัสผ่าน โทเคน หรือ cookie ชื่อที่ผู้เยี่ยมชมพิมพ์มา (เช่น ชื่อผู้ใช้ที่ login ผิด) เรียก `@everyone` ใน Discord หรือ `<!channel>` ใน Slack ไม่ได้
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) URL ของ webhook และ Telegram มีโทเคนอยู่ในตัว หน้าเว็บและ log จึงแสดงแค่ชื่อโฮสต์ ค่าที่ใช้ไม่ได้ ระบบยังเปิดได้ แต่ปิดการแจ้งเตือนและเตือนใน log ตอนเริ่ม (การ์ดแจ้งว่าตั้ง `ALERT_WEBHOOK_URL` ไว้แต่ใช้ไม่ได้)
- **ผู้ดูแลระบบสูงสุดได้รับเรื่องเดียวกันที่กระดิ่งในเว็บด้วย** (ชนิด `system-alert`) ชั่วโมงละครั้งต่อเรื่อง แม้ไม่ได้ตั้ง `ALERT_WEBHOOK_URL` และส่งเข้ากลุ่ม LINE ได้ถ้าตั้ง `LINE_GROUP_ID`
- API: `GET /api/admin/alerts` · `POST /api/admin/alerts/test` ดู [คู่มือนักพัฒนา](development.md#การแจ้งเตือนผู้ดูแล)

## ตั้งค่าการแจ้งเตือนส่วนตัว (อีเมลและ LINE)

ต่างจากการแจ้งเตือนระบบด้านบน อันนี้ส่งถึงผู้ใช้แต่ละคน (ตั้งแต่ 1.10) เห็นเฉพาะของตัวเอง **กระดิ่งในเว็บเปิดอยู่เสมอ ไม่ต้องตั้งค่า** ผู้ใช้เลือกเองต่อชนิดและต่อช่องทางว่าจะรับเรื่องไหนทางไหน ดูฝั่งผู้ใช้ที่ [คู่มือผู้ใช้: การแจ้งเตือน](user-guide.md#การแจ้งเตือน-กระดิ่ง-อีเมล-line) ส่วนที่ผู้ดูแลต้องทำคือเปิดช่องทางอีเมลและ LINE (ไม่บังคับ)

ระบบเก็บแค่ชนิดกับค่าที่เกี่ยวข้อง ข้อความเขียนตอนอ่านตามภาษาของผู้อ่าน และไม่มีโทเคนของลิงก์แชร์ รหัสผ่าน หรือลิงก์ลับอยู่ในข้อความใด ๆ ส่งทางอีเมลและ LINE เป็นงานเบื้องหลัง ลองใหม่ได้ 3 ครั้งแล้วเลิก คิวอยู่ในหน่วยความจำ รีสตาร์ตแล้วข้อความที่ยังไม่ได้ส่งหายไป (กระดิ่งยังอยู่)

### อีเมล

ตั้งได้ในหน้าเว็บ **ระบบ → ตั้งค่า → หมวดอีเมลและแจ้งเตือน** (ต้องยืนยันรหัสผ่าน มีปุ่มส่งอีเมลทดสอบ รหัสผ่านเก็บแบบเข้ารหัส ค่าในเว็บชนะ `.env` ดู [ตั้งค่าระบบในหน้าเว็บ](#ตั้งค่าระบบในหน้าเว็บ)) หรือใน `.env` ตามนี้ (`PUBLIC_URL` ตั้งใน `.env` เท่านั้น)

1. ใส่ใน `.env`
   ```env
   PUBLIC_URL=https://files.example.com   # ใช้สร้างลิงก์ยืนยันในอีเมล
   SMTP_HOST=smtp.example.com
   SMTP_PORT=587
   SMTP_SECURE=starttls                   # หรือ tls (พอร์ต 465) / none (เฉพาะเซิร์ฟเวอร์ในเครื่องนี้)
   SMTP_USER=files@example.com
   SMTP_PASS=รหัสผ่านหรือ app password
   SMTP_FROM=File Center <files@example.com>
   ```
2. `docker compose up -d`
3. ให้ผู้ใช้ตั้งอีเมลที่ **บัญชีและความปลอดภัย → แจ้งเตือน** ระบบส่งลิงก์ยืนยันไปให้

- ไม่ตั้ง `SMTP_HOST` = ไม่ส่งอีเมล ค่าที่ใช้ไม่ได้ ระบบยังเปิดได้แต่ปิดอีเมลและเตือนใน log ตอนเริ่ม
- ใช้ SMTP client ในตัว (`src/mail.ts`, ไม่มีไลบรารีเพิ่ม): EHLO, STARTTLS หรือ TLS ทันที, AUTH PLAIN/LOGIN, ตรวจใบรับรองของเซิร์ฟเวอร์ รหัสผ่านส่งผ่านการเข้ารหัสเท่านั้น (หรือไปยังเครื่องนี้) หัวจดหมายกัน CR/LF (ที่อยู่หรือหัวเรื่องที่มีขึ้นบรรทัดใหม่ถูกปฏิเสธ) หัวเรื่องภาษาไทยเข้ารหัส RFC 2047 เนื้อความ UTF-8 แบบ base64
- ลิงก์ยืนยันเป็นโทเคนสุ่ม เก็บแบบแฮช ใช้ได้ 24 ชั่วโมง ใช้ได้ครั้งเดียว **ก่อนยืนยัน ไม่มีจดหมายอื่นถูกส่งไปที่อยู่นั้น**
- จำกัดต่อผู้ใช้: แจ้งเตือนไม่เกิน 20 ฉบับต่อชั่วโมง และลิงก์ยืนยันไม่เกิน 1 ฉบับต่อ 2 นาที (โควตาของอีเมลยืนยันแยกจากอีเมลแจ้งเตือน)
- การอัปโหลดผ่านลิงก์รับไฟล์เดียวกันภายใน 10 นาทีรวมเป็นรายการเดียวในกระดิ่ง และส่งอีเมล/LINE ไม่เกิน 1 ครั้งต่อลิงก์ต่อ 10 นาที ชื่อไฟล์จากผู้เยี่ยมชมถูกตัดเหลือ 80 ตัวอักษรในข้อความ

### LINE

LINE Notify เลิกให้บริการแล้ว ระบบจึงใช้ LINE Messaging API (บอท) ส่งข้อความ

1. ไปที่ [LINE Developers Console](https://developers.line.biz/console/) สร้าง Provider แล้วสร้างช่องทาง **Messaging API** (ต้องมี LINE Official Account)
2. แท็บ **Messaging API** กด Issue ที่ *Channel access token (long-lived)* ใส่ใน `LINE_CHANNEL_TOKEN` และแท็บ **Basic settings** คัดลอก *Channel secret* ใส่ใน `LINE_CHANNEL_SECRET`
3. ที่ **Webhook URL** ใส่ `https://<โดเมนของคุณ>/api/line/webhook` (ต้องเป็น https ที่ LINE เรียกถึงได้ เช่นผ่าน Cloudflare Tunnel) กด Verify แล้วเปิด **Use webhook** ปิด *Auto-reply messages* และ *Greeting messages* ที่ LINE Official Account Manager เพื่อไม่ให้ตอบซ้ำ
4. เพิ่มบอทเป็นเพื่อนด้วย QR code ในแท็บ Messaging API
5. (ไม่บังคับ) ส่งการแจ้งเตือนระบบของ admin เข้ากลุ่ม: เชิญบอทเข้ากลุ่ม แล้วใส่ group id ใน `LINE_GROUP_ID` (ได้จาก `source.groupId` ของ event ที่ webhook รับ)
6. ใส่ค่าใน `.env` แล้ว `docker compose up -d`

ผู้ใช้เชื่อมบัญชีเอง: **บัญชีและความปลอดภัย → แจ้งเตือน → เชื่อม LINE** ได้รหัส 6 หลัก ใช้ได้ 10 นาที ส่งรหัสนั้นให้บอทในแชต บอทจับคู่ LINE ของผู้ส่งกับบัญชีและตอบกลับ ยกเลิกการเชื่อมได้ที่เดิม (บล็อกหรือลบบอทก็ยกเลิกให้)

- webhook รับเฉพาะคำขอที่ลายเซ็น `X-Line-Signature` (HMAC-SHA256 ด้วย Channel secret) ถูกต้อง นอกนั้น 401 ไม่ต้องมี CSRF token เพราะไม่มี session เดารหัสผิด 5 ครั้งจาก LINE เดียวจะถูกเมิน
- ที่อยู่ปลายทางคงที่ที่ `https://api.line.me` ไม่มีทางให้ผู้ใช้กำหนด host
- ข้อความ LINE ถึงผู้ใช้แต่ละคนไม่เกิน 30 ข้อความต่อชั่วโมง (ที่เหลือยังอยู่ในกระดิ่ง)

## WebDAV สำหรับผู้ดูแล

WebDAV เปิดอยู่ตามค่าเริ่มต้น (`WEBDAV=on`) ผู้ใช้สร้างรหัสผ่านแอปเองและเชื่อมต่อเอง ดูวิธีที่ [คู่มือผู้ใช้: WebDAV](user-guide.md#webdav-เปิดไฟล์เป็นไดรฟ์ในเครื่อง)

- ปิดทั้งหมดด้วย `WEBDAV=off` ใน `.env` (ทุกพาธใต้ `/dav` ตอบ 404 หน้าเว็บและ API ไม่เปลี่ยน)
- WebDAV ผ่านกติกาเดียวกับหน้าเว็บ: สิทธิ์ โควตา ถังขยะ (ลบผ่าน WebDAV ไปอยู่ในถังขยะของเจ้าของ) เวอร์ชันของไฟล์ การสร้าง ลบ อัปโหลด แก้ไข ย้าย คัดลอก ลงประวัติการใช้งาน (`detail` ขึ้นต้นด้วย `WebDAV`)
- เพิกถอนทุกอุปกรณ์ของผู้ใช้ (**ผู้ใช้ → อุปกรณ์ → ออกจากระบบทุกเครื่อง** หรือ `bun src/cli.ts sessions-revoke <ชื่อ>`) ลบรหัสผ่านแอปของเขาด้วย รหัสผ่านแอปทั้งหมดถูกลบเมื่อบัญชีถูกลบ เมื่อผู้ใช้เปลี่ยนรหัสผ่าน และเมื่อผู้ดูแลตั้งรหัสผ่านใหม่ให้
- รหัสผิดซ้ำถูกล็อกเหมือนหน้าเข้าสู่ระบบ (ตอบ 429 พร้อม `Retry-After`)
- ขีดจำกัด: Cloudflare Free/Pro รับคำขอไม่เกิน 100 MB จึงอัปโหลดไฟล์ใหญ่ผ่าน WebDAV ทางโดเมนไม่ได้ (ดู [ข้อจำกัดของ WebDAV](user-guide.md#ข้อจำกัดของ-webdav))

## คำสั่งที่เครื่อง server (CLI)

คำสั่งสำหรับผู้ดูแลที่เครื่อง server ทำงานกับ `DATA_DIR` เดียวกับแอป (`src/cli.ts`) ใช้เมื่อเข้าหน้าเว็บไม่ได้ เช่น ลืมโทรศัพท์ 2FA ของ admin

| คำสั่ง | ทำอะไร |
|---|---|
| `bun src/cli.ts reset-2fa <ชื่อผู้ใช้>` | ปิด 2FA ของผู้ใช้ ออกจากระบบทุกอุปกรณ์ และลบรหัสผ่านแอป WebDAV |
| `bun src/cli.ts sessions-revoke <ชื่อผู้ใช้>` | ออกจากระบบทุกอุปกรณ์ และลบรหัสผ่านแอป WebDAV ของผู้ใช้ (บอกจำนวนในผลลัพธ์) |

แบบ Docker (รันในคอนเทนเนอร์ที่ทำงานอยู่)

```bash
docker compose exec file-center bun src/cli.ts reset-2fa admin
docker compose exec file-center bun src/cli.ts sessions-revoke alice
```

- ไม่ใส่ชื่อผู้ใช้ หรือใส่คำสั่งอื่น จะแสดงวิธีใช้ (`Usage: bun src/cli.ts reset-2fa <user> | sessions-revoke <user>`) และจบด้วยรหัส 1 เช่นเดียวกับกรณีไม่พบผู้ใช้ (`No such user: <ชื่อ>`)
- เขียนประวัติการใช้งาน (ผู้ใช้ `cli`: `2fa-reset`, `sessions-revoke`)
- **ไม่ต้องรีสตาร์ตแอป:** คำสั่งแตะไฟล์ `cli-changed` ใน `DATA_DIR` เมื่อเสร็จ แอปที่เปิดอยู่เห็นแล้วอ่าน `users.json` และ `sessions.json` ใหม่ในคำขอถัดไป (ไฟล์นี้ไม่ถูกสำรอง)
- นอกจาก CLI แล้ว admin รีเซ็ต 2FA จากหน้าเว็บได้ที่ **ผู้ใช้ → รีเซ็ตการยืนยันสองขั้นตอน**

คำสั่งอื่นสำหรับ build แพ็กเกจและออกรุ่น (`bun run package`, `bun run release`) อยู่ที่ [ติดตั้ง](install.md#สร้างและเผยแพร่อัปเดตของคุณเอง) คำสั่งสำหรับนักพัฒนา (`bun run qa`, `bun run bench`) อยู่ที่ [คู่มือนักพัฒนา](development.md)
