Hardening in four parts. Keep each part small and tested.

1. Security headers (`src/index.ts`). Every HTML/JS/CSS response of the web app gets a Content-Security-Policy:
   `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self' blob:; font-src 'self' data:; connect-src 'self'; frame-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'`
   plus `Permissions-Policy: camera=(), microphone=(), geolocation=()`. When `SECURE_COOKIE=true` (the site is on HTTPS) every response also gets `Strict-Transport-Security: max-age=31536000`. The stricter CSP that file downloads (`src/routes/files.ts`) and the logo (`src/routes/admin.ts`) already send must stay exactly as it is on those responses: check that your header does not replace or merge into theirs.
2. Version only for those who need it. `GET /api/health` answers `{ status: 'ok' }` only, unless the request comes from the machine itself (the socket address is a loopback address: 127.0.0.1, ::1 or ::ffff:127.0.0.1; use the socket address, NEVER X-Forwarded-For or CF-Connecting-IP, which a client can fake) or from a signed-in admin, who get the full answer as now (`version`, `release`, `boot`, `time`). The launcher, the update and backup pages and the Docker healthcheck depend on this, so check each still works (`tests/update.test.ts` and `tests/backup.test.ts` run the launcher). `GET /api/session` stops sending `config.version` to visitors who are not signed in.
3. Password policy (`checkPasswordStrength` in `src/auth.ts`): at least 10 characters; not the username and not containing it (ignoring case); not one of the 100 most common passwords (keep the list in a small new file, e.g. `src/common-passwords.ts`). Applies to new users, admin-set passwords and password changes; existing passwords keep working. `GET /api/session` exposes `config.passwordMinLength` so the page can show the rule. Update test data that now breaks (weak passwords in tests), without removing or weakening any test.
4. Upload limit for visitors (`src/uploads.ts`, `src/routes/upload.ts`): when visitors (not signed in) may upload, they share a daily total, `GUEST_UPLOAD_DAILY_BYTES` (default 1 GB, `0` = no visitor uploads at all), counted when an upload is announced (so parallel uploads cannot overshoot) and given back if it is cancelled or never completes. Over the limit: 429 with a Thai message. The count lives in DATA_DIR so a restart does not reset it, and starts again each day. Signed-in users are not affected.
