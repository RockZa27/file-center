Updates published in git, and the server checking for them. Another backend-dev edits src/fsx.ts, src/backup.ts, src/settings.ts, src/context.ts and Dockerfile at the same time: stay out of those.

1. `bun run release [--notes "..."] [--sign <key file>] [--push]` (`scripts/release.ts`, script entry in package.json): refuse unless the git working tree is clean and package.json's version is newer than every version already in branch `updates` (read its `latest.json`; create the branch as an orphan if it does not exist). Build with the existing `scripts/package.ts` (call it, do not copy it; `--out` to a temp dir, `--sign` passed through). Check out `updates` in a temporary `git worktree`, add the zip, rewrite `SHA256SUMS` (all zips), add a row to the table in its README.md (version, file link, source commit short hash, notes, signed yes/no; create the README in Thai like the one already there if missing), write `latest.json` `{ "version", "file", "sha256", "size", "builtAt", "commit", "notes", "signed" }`, commit, `git push origin updates` only with `--push`, and remove the worktree whatever happens. The branch `updates` on origin already holds 1.2.0 with README.md and SHA256SUMS but no latest.json: the first run must keep that row and add latest.json. Test it against a throw-away git repo (bare remote in a temp dir), never against this repo's real branches.
2. Server: env `UPDATE_SOURCE` (empty = off), a base URL such as `https://raw.githubusercontent.com/RockZa27/file-center/updates`. Only https, except http to 127.0.0.1/localhost (for tests); reject anything else at startup with a log warning and keep it off. No background polling.
   - `GET /api/admin/update/check` (admin) → fetch `<source>/latest.json` (timeout 10 s, max 64 KB, JSON validated) → `{ enabled, current, latest: { version, notes, size, signed, builtAt }, newer: boolean }`; `enabled:false` when no source.
   - `POST /api/admin/update/fetch` (admin, CSRF) → download `<source>/<file>` from latest.json (file name must be a plain `file-center-<semver>.zip`, no slashes), refuse when not newer than running, stream to the incoming folder with the size cap `config.updateMaxSize` and a timeout, check the SHA-256 against latest.json, then run the SAME staging path an uploaded package goes through (`src/updater.ts`), answering exactly what `/stage` answers. Installing still goes through `/apply` with the password step-up, and with `UPDATE_PUBLIC_KEY` set the signature is still required. Audit `update-fetch`. Errors as catalog codes (th/en) in `src/messages.ts`.
   - `GET /api/admin/update` also reports `source: { enabled, url }` (url without credentials) so the page knows to show the button.

Update results in the page's language: `last` (written by `src/launcher.ts` and `src/updater.ts`, type in `src/release.ts`) also stores `code` + `params`; `GET /api/admin/update` answers `last.message` via `text(langOf(request), ...)`; a state written by an older launcher (message only) keeps its message. Keep the state.json schema backward compatible (the launcher of 1.2.0 must still read what 1.3.0 writes and the other way round).

New routes go in the route lists of tests/api.test.ts.
