The server now answers every error as `{ error, code, params }` with `error` already in the visitor's language, picked from the `x-lang` request header (`th`/`en`), else Accept-Language, else Thai (see `src/messages.ts`, `langOf`). Dashboard warnings in `GET /api/admin/status` are `{ level, code, message, params }`, `message` in the request language. The page does not send `x-lang` yet, so a Thai page in an English browser shows English errors and an English page in a Thai browser shows Thai ones.

1. `web/src/api.js`: send `x-lang: <current vue-i18n locale>` on every fetch and on the upload XHR. Its own fallback texts (`เกิดข้อผิดพลาด (status)`, `การเชื่อมต่อขัดข้อง`, and any other hard-coded Thai there) go through i18n. Keep `ApiError` carrying `code` and `params` from the answer so pages can tell cases apart.
2. Language switch: data whose text came from the server (dashboard warnings, at least) is fetched again when the locale changes, so it never shows the old language next to new labels.
3. Downloads after the session expired: the log download (LogsView), the CSV export (ActivityView) and backup downloads (BackupView) are plain links today, so with an expired session the browser saves a JSON error as the file. Before following the link, check the session (`GET /api/session`, see `src/routes/session.ts`); when signed out, show the error on the page (and send the user to sign in the way the rest of the app does) instead of downloading. Normal downloads must still be real browser downloads (no buffering a big backup in memory).
4. Trash at 1200 px: the name column is too narrow (long names are cut after a few letters). Give it the room; dates/size/actions keep fitting. The 375 px card layout stays as it is.
5. Check in the browser at 1200 px and 375 px, in Thai and English: a wrong password on sign-in, a bad file name (e.g. `a:b`), a dashboard warning, all in the page's language whatever the browser language is (set the browser context `locale` to the other language to prove it).
