## Security posture

No critical or high finding. The request gates were exercised at runtime under Elysia 2.0.0-rc.3 and held: all 153 routes of 22 plugins refuse a state change without the CSRF token, accounts that must change their password or set up 2FA reach no route outside the allowlists, and no path variant (trailing or double slash, dot segments, %2e, %2f, case, fragment, backslash, raw request lines) separates the routed path from the path the gates test. Update packages are refused unless signed, complete and newer. Share links, uploads, WebDAV, signed inbound calls (ONLYOFFICE, LINE) and the outbound integrations held under review, most of it with local checks. The fixes of the 1.13.x audits still hold where re-tested (PROPFIND/PROPPATCH bounds, upload cancel during completion, restore and same-name accounts for the stores then covered).

Ten findings were confirmed: three medium, six low and one informational. The medium ones are: the admin password step-up can be re-derived by making a new admin from a session alone; a crafted zip passes the central-directory size check that protects the server's memory; and anonymous visitors can make the server keep an unbounded number of batch-download tokens. The low ones are lifecycle gaps of the account-instance rule (name, createdAt) in places added since 1.13.3 or not reached by the earlier fixes, and two availability or integrity limits. The informational one is the fast unkeyed hash of the 2FA backup codes.

### POST /api/batch retains one token entry per call with no cap, reachable by an anonymous visitor in the default configuration

- Fingerprint: `files:batch-token-map-unbounded` — severity **medium** (likelihood medium, impact medium); confidence medium; Phase 5: verified
- Source: `src/routes/files.ts:440`, `src/routes/files.ts:445`, `src/routes/files.ts:449`, `src/routes/files.ts:448`, `src/routes/files.ts:111`, `src/settings.ts:90`
- Lower-trust principal: Anonymous visitor with a session cookie and CSRF token, calling the batch endpoint repeatedly
- Conditions: Anonymous session plus its CSRF token (GET /api/session); no login; Public page on (default) and guestPermissions include download and batchdownload (default); The public folder holds at least one file; entry size scales with the number of names (up to 2000 per call); A rate limit in a reverse proxy or tunnel and the container memory limit were not observed and decide how fast it grows
- Reproduction (local, dummy data): GET /api/session, keep the fc_sid cookie and csrf → POST /api/batch with the public space and all file names, 2000 times → GET /api/batch/<first token> and <last token> to see that both are still live
- Result: 2000 of 2000 calls returned 200; first and last token redeemable with 200; heap grew about 82.8 MB (about 42 KB per entry) in two runs (82816 and 82820 KB); about 1 ms per call.
- What it is: Each POST /api/batch stores {owner, space, root, dir, names[], expires} in the module-level Map batches for 5 minutes. The only removal is the expiry sweep on the next POST; there is no per-session, per-address or global cap. In an in-process run in the sandbox, an anonymous session with its CSRF token called POST /api/batch 2000 times on a public folder of 300 files (name length about 55 chars), naming all files. All 2000 calls returned 200 with a token, and the first and the last token were still redeemable (GET /api/batch/:token gave 200). Heap grew by about 82.8 MB (about 42 KB per entry, about 140 bytes per name) in about 1.3 to 1.6 s of handler time (about 1 ms per call, so the O(n) sweep was not a limiter at this size). No app-level rate limit was found on this route. Arithmetic, not measured: at the same per-call cost, 100000 calls would hold about 4 GB for 5 minutes, and a folder near the 2000-name per-request limit would hold about 280 KB per entry. Real HTTP overhead and any proxy rate limit or container memory limit would change the rate; those are deployment facts that were not observed. No saturation was run.
- Priority: likelihood medium (Reachable without login in the default configuration with one session and CSRF token; cost to the caller is one small request per entry. A proxy rate limit may slow it.); impact medium (Memory is retained for 5 minutes per entry and grows linearly: about 4 GB at 100000 calls (arithmetic). The shared single Bun process is affected, but no exhaustion was demonstrated and the effect clears after expiry or restart.).
- Root cause: The batches Map has time-based expiry only; there is no cardinality or per-principal bound, and each entry stores the full name list.
- Smallest fix: Cap the Map (global and per owner, evicting the oldest or refusing with 429 when full), and sweep on a timer; or make the token self-contained and signed so that no server memory is held.

### An admin session alone can mint a new admin with a chosen password and then pass every password step-up

- Fingerprint: `stepup:admin-account-create-and-password-set-without-step-up` — severity **medium** (likelihood low, impact medium); confidence high; Phase 5: replaced, non-material (applied)
- Phase 5 correction applied: Evidence line for the settings step-up call was src/routes/admin.ts:559 (that line is savePolicy); the confirmPassword call is at :558, corrected. Also the REQUIRE_2FA condition was untested; now tested (REQUIRE_2FA=admin, admin with 2FA already enabled, new admin enrolls its own 2FA then passes the step-up: still exploitable) and its condition text updated. Verdict, severity and the rest verified.
- Source: `src/routes/admin.ts:153`, `src/routes/admin.ts:232`, `src/auth.ts:524`, `src/routes/admin.ts:162`, `src/routes/admin.ts:558`, `tests/roles-fixes.test.ts:129`
- Lower-trust principal: Holder of a stolen admin session only (cookie + csrf), password unknown
- Conditions: attacker holds a valid admin session cookie and CSRF token (stolen session); no admin password known; with REQUIRE_2FA=admin the stolen session must belong to an admin that already has 2FA (an unenrolled admin is blocked with 403 auth.2fa-required); the new admin then enrolls its own 2FA with its known password and a self-computed TOTP, after which the step-up passes (tested), so 2FA is not a barrier
- Reproduction (local, dummy data): Login as admin A, keep only its cookie/csrf → Create admin evil2 with a chosen password: 200 → Login as evil2 in a second client: 200 → PUT /api/admin/settings with security group and evil2's password: 200 (a wrong password gives 403) → PUT /api/admin/users/evil2 {password} from the session-only client: 200 without confirmation
- Result: All steps returned 200 in an in-process sandbox run (re-run by the final verifier, exit 42); the wrong-password control gave 403. With REQUIRE_2FA=admin and an admin already enrolled in 2FA, the new admin enrolled its own 2FA and the step-up still gave 200 (wrong password 403).
- What it is: POST /api/admin/users with role admin, and PUT /api/admin/users/:username with a password, ask an admin caller for no password. A holder of only an admin session cookie creates a second admin with a password of their choosing, signs in as it, and passes confirmPassword on step-up routes (observed: PUT /api/admin/settings with a security group returned 200 using the new admin's password and 403 with a wrong one). docs/security.md says a stolen session alone cannot change sign-in rules because the admin password is asked. The settings step-up field is body.password, not confirmPassword.
- Priority: likelihood low (needs a stolen or hijacked admin session first); impact medium (defeats the documented step-up for all admin actions (settings, restore, update) but the session already holds admin authority and the new account is visible and audited; only a security-group settings change was demonstrated).
- Root cause: confirmPassword is checked against the signed-in account's own hash, and the routes that mint or re-key an admin account (create with role admin, set password / promote role as admin) have no step-up, so the control can be re-derived through a new principal. src/routes/admin.ts:232 requires step-up only when the actor is not an admin.
- Smallest fix: Require confirmPassword of the acting admin on create with role admin, on role promotion to admin, and on an admin setting another account's password (at least for admin targets); keep the audit trail and consider alerting on new admin creation.

### Central-directory entry/size pre-check bypassed by a fake EOCD hidden in the real EOCD comment

- Fingerprint: `zip-checkdirectory-eocd-mismatch-bypass` — severity **medium** (likelihood medium, impact medium); confidence medium; Phase 5: verified
- Source: `src/routes/archive.ts:32`, `src/zip.ts:27`, `src/zip.ts:181`, `src/zip.ts:50`, `src/zip.ts:49`, `src/archive.ts:63`, `src/zip.ts:183`, `src/config.ts:160`
- Lower-trust principal: low-privilege user who stores a crafted zip and requests its listing or extraction
- Conditions: an account (or public-space guest, or upload-request visitor) able to place a zip that someone can list or unzip, or a share-link holder of a folder containing it
- Reproduction (local, dummy data): Build 120000-entry ZIP64 zip plain and with the fake EOCD in the comment → Call checkDirectory and listArchive on both, then zip.js getEntries, measuring RSS growth, in the sandbox
- Result: plain: refused 413; crafted: check passed, listArchive returned 10000 entries (truncated), zip.js read 120000 entries, RSS growth about 314-343 MB versus 367-372 MB for the plain file. Runs repeated twice. Not scaled further.
- What it is: checkDirectory reads the last PK\5\6 signature in the file tail, while zip.js uses the EOCD that actually locates the directory. A zip whose real (ZIP64) EOCD has a 22-byte comment holding a zero-count EOCD passes the check, yet zip.js still loads the whole directory. Locally a 120000-entry zip (cap 100000) was refused 413 when plain but passed when crafted; zip.js getEntries then read 120000 entries and grew RSS by about 300 MB for a roughly 6 MB file (about 50x). The pre-check exists solely to stop zip.js holding an oversized directory in memory. After the bypass only the file size (UPLOAD_MAX_SIZE default 10 GB), the post-hoc files.length check in unzipTo (read after getEntries) and the 10000-entry display cut in listArchive (applied after the directory is loaded) remain, and none bound zip.js memory. Reached through archive list/file, unzip, and the share archive routes.
- Priority: likelihood medium (needs a crafted zip uploaded by an account or guest with write rights; trivial once placed); impact medium (the defeated control exists to bound zip.js memory; about 50x memory per file byte measured, and only the 10 GB upload cap remains, so a modest zip can exhaust the single shared process (availability only, no data exposure; not run at scale)).
- Root cause: The pre-check and the parser pick different EOCD records: the check takes the last signature in the tail, zip.js takes the one that locates a valid directory.
- Smallest fix: Mirror zip.js EOCD selection, or reject any archive with more than one EOCD signature in the tail or whose EOCD comment length does not end the file; additionally stream/limit entries while reading so the cap does not depend on the pre-check.

### Anonymous guest or share-link holder can rotate earlier audit entries away with repeated downloads

- Fingerprint: `audit-trail-flood-by-unmetered-download-audit` — severity **low** (likelihood low, impact medium); confidence medium; Phase 5: verified
- Source: `src/routes/files.ts:434`, `src/audit.ts:16`, `src/logger.ts:23`, `src/routes/shares.ts:328`, `src/config.ts:212`, `src/routes/session.ts:70`, `src/audit-forward.ts:80`
- Lower-trust principal: Anonymous visitor with only the public page, or a holder of one unlimited share link
- Conditions: Public page on with default guestPermissions including download (or an existing share link without a download limit); No reverse proxy or tunnel rate limit; at default caps roughly 0.6 to 0.9 million requests are needed (arithmetic from measured line sizes)
- Reproduction (local, dummy data): Boot the app in-process with fresh dirs, record an admin action (create user) in the audit log → Lower config.auditMaxBytes to 4096 and auditMaxFiles to 2 in-process → As an anonymous session repeat the public download 600 times, then do the same through an unlimited share link → Search audit.log and audit.log.1 for the admin entry
- Result: 600/600 downloads 200, no dedupe or rate limit intervened, admin entry gone from audit.log and audit.log.1 (after request 71 for guest download; also gone after the share-link flood); run twice, identical.
- What it is: Every successful non-inline GET /api/download (guest allowed by default guestPermissions on the public space) and every GET /api/s/:token/download writes one audit line with no dedupe, rate limit or per-caller cap, whereas failed sign-ins (session.ts:70) and browse use deduplication so they cannot fill and rotate away the trail. In a bounded in-process run with the audit cap lowered to 4096 bytes x 2 files (the real cap is a code literal, not configurable), an anonymous session repeated GET /api/download of one 5-byte public file: all 600 requests returned 200 and an earlier admin entry (user creation) was gone from audit.log and audit.log.1 after request 71. The same happened through an unlimited share link (600/600 200, admin entry gone). Measured line sizes: 113 bytes (guest download, in-process ip 'unknown') and 163 bytes (share download). Arithmetic, not measured at scale: the default 10 x 10 MiB = 104,857,600 bytes would take about 928,000 guest downloads (104857600/113) or about 643,000 share downloads (104857600/163); real client IPs make lines slightly longer, so somewhat fewer. The forwarding queue was not exercised (no forwarding configured; source: audit-forward.ts:80 drops the newest entries at 1000 queued), so the SIEM copy claim is source-only. The cost is large, the flood is itself visible until it overwrites, and a configured SIEM keeps its already-forwarded copy, so impact is bounded.
- Priority: likelihood low (Needs roughly 0.6 to 0.9 million requests at default caps (arithmetic), reachable anonymously but noisy and subject to any proxy rate limit.); impact medium (Audit trail integrity is a protected asset and an account-less principal erases earlier admin entries, but only a bounded history window and not other data or access.).
- Root cause: audit() is called on every public download path without the auditOnce/auditFailure dedupe or any per-caller cap, and rotateFile unlinks the oldest file once maxFiles is reached, so the capacity of the trail is controlled by unauthenticated request volume.
- Smallest fix: Deduplicate anonymous and share downloads with auditOnce keyed per (ip or share id, target) per minute with a repeat count, or add a per-caller cap; optionally keep a separate non-rotating store for administrative actions.

### A restored older account reads the activity of a later same-name account through /api/me/activity and /api/me/export

- Fingerprint: `lifecycle.audit-own-entries-not-bound-to-account-instance` — severity **low** (likelihood low, impact low); confidence high; Phase 5: verified
- Source: `src/routes/me.ts:35`, `src/routes/me.ts:42`, `src/my-data.ts:53`, `src/my-data.ts:58`, `src/my-data.ts:48`, `src/backup.ts:760`, `src/backup.ts:77`
- Lower-trust principal: holder of the earlier account that comes back with a restore
- Conditions: an admin deletes and re-creates a name, then restores an older backup that holds the first instance; the reader signs in as the restored account with its old password; the backup was taken while the first instance existed, before the delete
- Reproduction (local, dummy data): admin creates alice, alice acts, backup, delete alice, create alice again, alice#2 acts (app password named SECOND-ALICE-SECRET-DEVICE) → restoreBackup(backup) then restart (fresh process) → sign in as alice with the first password and GET /api/me/activity
- Result: two runs: exit 42; the activity list holds alice#2's login and app-password-create entry with target SECOND-ALICE-SECRET-DEVICE next to alice#1's own entries.
- What it is: ownEntries keeps audit entries with r.user === username and ts >= createdAt of the account, a lower time bound only. After alice#1 is deleted and alice#2 is created, a restore of a backup taken while alice#1 existed brings alice#1 back with its older createdAt (users.json is swapped, planRestore drops the live instance's records). restoreBackup rewrites only users, settings and branding; logs/audit.log is not touched (not extracted, kept). End to end run in the sandbox: after the restore and restart, alice#1 signs in with the old password and GET /api/me/activity returns alice#2's login and app-password-create entries (target SECOND-ALICE-SECRET-DEVICE). POST /api/me/export uses the same filter (my-data.ts:58). The delete and the re-create do not bound or rewrite the log either. Restore was driven by calling restoreBackup (the function the route calls) in a child process, then a fresh process for the check, as tests/security-1132-restore.test.ts does; the HTTP restore route itself was not run. The export path was read in source, not run.
- Priority: likelihood low (needs an admin restore of an older snapshot across a delete and re-create of the same name); impact low (action names, IPs, targets and details of one other account's audit entries, no file contents).
- Root cause: src/my-data.ts ownEntries (line 48) approximates the account instance by a lower time bound on createdAt; audit entries carry no instance id and nothing bounds the end of an earlier instance's life, and the restore leaves the audit log as it is.
- Smallest fix: Record the account createdAt (or an instance id) in audit entries for sign-in and file actions and match it in ownEntries, or write an audit marker at delete, re-create and restore and bound ownEntries to entries between the instance's start and its end.

### A LINE link code issued by a deleted account still links a LINE user to a new account of the same name

- Fingerprint: `lifecycle.line-link-code-survives-account-delete` — severity **low** (likelihood low, impact low); confidence high; Phase 5: verified
- Source: `src/routes/admin.ts:358`, `src/account-records.ts:23`, `src/line.ts:96`, `src/line.ts:108`, `src/routes/notify.ts:35`, `src/line.ts:91`, `src/account-records.ts:34`, `src/routes/notify.ts:101`
- Lower-trust principal: former account holder with a LINE account
- Conditions: attacker is a former holder of the deleted account who requested a LINE link code before deletion and has a LINE account; admin deletes and re-creates the same username within the 10 minute code lifetime, with no server restart; LINE channel token and secret configured; the new owner enables the line channel for a notification kind (default off) for anything to be pushed
- Reproduction (local, dummy data): Boot the app in-process with dummy dirs, LINE_CHANNEL_SECRET and LINE_CHANNEL_TOKEN set to dummy values → Admin creates alice; alice logs in and requests a link code → Admin deletes alice and creates alice again with a new password → Send the code in a webhook body signed with the dummy secret → New alice's GET /api/me/notify-prefs shows line.linked
- Result: Run twice in the sandbox, both exit 42: webhook 200, new alice line linked before=false after=true (scratch/full.ts, evidence/run1.txt, evidence/run2.txt).
- What it is: issueLinkCode (POST /api/me/line/link) keeps { username, expires } in a memory map for ten minutes. forgetAccount, called by DELETE /api/admin/users/:username and by POST /api/admin/users, does not clear that map. A former holder who generated a code while the account existed can, if an admin deletes and re-creates that username within ten minutes, send the code to the LINE bot from their own LINE account. The signed webhook handler redeems it to the bare username, resolves it with findUser to the NEW account and linkLine ties the sender's LINE id to it. Observed end to end in-process: the new account's notify-prefs showed line.linked false before and true after a self-signed webhook. The sender then gets that account's LINE pushes once the new owner enables the line channel for a kind (off by default per kind); the bot also replies with the new account's display name.
- Priority: likelihood low (needs an admin delete and re-create of the same name within 10 minutes, a LINE-enabled server and a former holder with a LINE account); impact low (notification text of one account to a stranger's LINE, only after the new owner turns the line channel on; no file access).
- Root cause: src/line.ts codes map stores only the username and is never invalidated on account deletion or re-creation; src/account-records.ts forgetAccount clears every other per-account store but not this one, and redeem does not bind the code to the account instance (name, createdAt).
- Smallest fix: Drop link codes of a name in forgetAccount (forgetLinkCodes(username) exported from line.ts) and/or store the account createdAt in the code and refuse redeem when it differs; regression test: issue, delete, re-create, redeem returns null.

### Two concurrent admin account creations with the same username both succeed

- Fingerprint: `lifecycle.user-create-concurrent-duplicate-username` — severity **low** (likelihood low, impact low); confidence high; Phase 5: replacement proposed, NOT applied (see below)
- **Unreconciled Phase 5 proposal (not applied):** Severity changed from low to informational. The race is real (re-run in sandbox: 200/200, two bobby entries, second password 401 until first deleted, then 200; manager case 409), and all cited lines are correct. But only an admin can trigger it, an admin already controls every account, and no boundary is crossed and no other principal's data is read or changed. That is a robustness/uniqueness-invariant defect with minimal impact, which fits 'informational' rather than 'low'. Also added the checkAdoptHome step (line 177) the second admin request passes.
- Source: `src/routes/admin.ts:153`, `src/routes/admin.ts:166`, `src/routes/admin.ts:190`, `src/routes/admin.ts:175`
- Lower-trust principal: admin session with CSRF token
- Conditions: admin session (manager attempt refused with 409 admin.home-exists); two requests in flight during the argon2 hash
- Reproduction (local, dummy data): Login as admin in-process → Promise.all both POSTs → GET /api/admin/users and count bobby; login with each password; DELETE bobby and login again

### Unzip creates unbounded implied directories with synchronous mkdir, stalling the single server thread

- Fingerprint: `zip-unzip-directory-entries-uncounted-sync-mkdir` — severity **low** (likelihood medium, impact low); confidence high; Phase 5: replaced, non-material (applied)

- Source: `src/routes/files.ts:346`, `src/zip.ts:198`, `src/zip.ts:199`, `src/zip.ts:178`, `src/zip.ts:182`, `src/zip.ts:183`

- Conditions: Signed-in user (or visitor under public permissions) holding zip and write on a space, and a way to place a .zip there (upload). Default guest permissions do not include zip or write.

### 2FA backup codes are kept as unsalted, unkeyed SHA-256 of a ~39.6-bit code (hardening: recoverable offline from a plain users.json copy)

- Fingerprint: `2fa:backup-codes-stored-as-unsalted-sha256` — severity **informational** (likelihood informational, impact informational); confidence high; Phase 5: replaced, non-material (applied)
- Phase 5 correction applied: Severity lowered from low to informational by the Phase 5 verifier and accepted by a further independent verifier (x01): Severity lowered from low to informational (likelihood low->informational, impact low->informational) and intended_behavior/description corrected. docs/security.md line 97 says 2FA secrets are sealed with secret.key and 'ส่วนรหัสสำรองเก็บเฉพาะค่าแฮช' (backup codes are kept only as hashes); line 98 says secret.key is kept out of backups so a backup holder cannot unseal the 2FA secrets. The demonstrated result (hashes only, TOTP secret sealed, secret.key absent) matches that, it does not contradict it. No boundary is crossed: the precondition (plain backup/users.json copy) is outside the request surface, the password is also needed, and the search time is arithmetic only. All trace/evidence lines were re-read and are correct; the fingerprint is unchanged.
- Source: `src/routes/backup.ts:53`, `src/auth.ts:355`, `src/auth.ts:396`, `src/auth.ts:348`, `src/auth.ts:346`, `src/backup.ts:67`
- Lower-trust principal: Holder of an unencrypted backup zip or users.json copy, offline.
- Conditions: Attacker holds a copy of users.json or a backup made without BACKUP_ENCRYPTION_KEY (stolen volume, off-site copy, leaked backup file); no app request provides this to a low-trust caller; Target account has 2FA enabled and has unused backup codes; attacker also needs the account password (argon2id hash in the same file) to reach the second step
- Reproduction (local, dummy data): Create a 2FA user in an in-process app with a sandboxed STORAGE_DIR and DATA_DIR and no BACKUP_ENCRYPTION_KEY → Call runBackup and list the zip: users.json present, secret.key absent → Read users.json from the zip: twoFactor.backup hashes equal sha256 of the plain codes; twoFactor.secret is sealed → Time 2M SHA-256 hashes locally for the rate; compute 31^8 / rate as arithmetic
- Result: Repeated runs: hash == sha256(code) true; zip contains users.json and no secret.key; all 10 hashes in the zip equal sha256 of the codes; TOTP secret sealed; 1.1-1.8M hashes/s. Full-space search time is arithmetic, not run; no code was actually recovered.
- What it is: newBackupCodes builds each code from two groups of 4 symbols of a 31-symbol alphabet (31^8 = 8.5e11, 39.6 bits) and stores sha256(code) with no salt or key in users.json. In a local in-process run (repeated), a stored hash equalled plain sha256(code), a backup made without BACKUP_ENCRYPTION_KEY was a plain zip containing users.json (all 10 hashes) and no secret.key, and the TOTP secret in the same file was sealed. docs/security.md says the 2FA secret is sealed with secret.key and 'ส่วนรหัสสำรองเก็บเฉพาะค่าแฮช' (backup codes are kept only as hashes), and that secret.key stays out of backups; the observed result matches those statements and does not contradict them. The weakness is that the hash is fast and unsalted, so a holder of a users.json copy could in principle search the code space offline (arithmetic only, not run: 8.5e11 at about 1.1-1.8M hashes/s measured is about 5-9 days on one core, less with 10 targets). The attacker would also need the account password (argon2id), and online guessing is locked out. No request hands such a copy to a low-trust caller (download route is admin-only). This is a defence-in-depth hardening note with no crossed boundary demonstrated.
- Priority: likelihood informational (needs a plain backup or users.json copy first (outside the request surface), plus the account password); impact informational (demonstrated result matches the documented design (hashes only, TOTP secret sealed); the recovery of a code is arithmetic, not demonstrated, and costs days of compute).
- Root cause: Backup codes are a low-entropy secret protected by a fast unkeyed hash (createHash sha256, no salt, no pepper, no secret.key HMAC) while the TOTP secret beside it is sealed with secret.key.
- Smallest fix: Store the backup codes as an HMAC keyed with a secret derived from secret.key (which is kept out of backups), or as slow salted hashes (argon2id) per code, or lengthen the code so offline search is impractical; compare in constant time.
