Build automatic backups of the system data, with restore. Users of this system lose everything (accounts, passwords, settings) if the disk dies, and today the dashboard only shows a backup status that some outside script has to write.

Scope
- New `src/backup.ts` and `src/routes/backup.ts` (admin only, mounted in `src/index.ts`), config in `src/config.ts`, docs in `README.md` and `.env.example`.
- A backup is one zip file `file-center-backup-YYYYMMDD-HHMMSS.zip` containing what is in DATA_DIR except: `tmp/`, `trash/`, `app/`, `sessions.json`, rotated logs (`logs/audit.log.N`), and the backup folder itself. So: `users.json`, `settings.json`, `branding/`, `logs/audit.log`, plus a `backup.json` with `{ version, createdAt, includesFiles }`. Reuse `collectZipItems` / `zipStream` from `src/zip.ts`. Write to `<name>.partial` then rename, so a half-written backup never looks complete.
- Optional `BACKUP_INCLUDE_FILES=true` also puts the storage folder in the zip under `storage/` (off by default: it can be huge). Check free space first with `ensureSpace` from `src/fsx.ts`.
- Settings (env, documented): `BACKUP_DIR` (default: a folder `backups` next to DATA_DIR, i.e. `join(dirname(config.dataDir), 'backups')`), `BACKUP_KEEP` (default 7: delete the oldest beyond that after a successful backup), `BACKUP_HOUR` (0-23, default 3; `off` disables the schedule).
- Schedule: the hourly `housekeeping()` in `src/index.ts` runs a backup when the last success is older than 20 hours and the current local hour equals BACKUP_HOUR, or when the last success is older than 48 hours.
- After each attempt write `paths.backupStatus` (`backup-status.json`, already read by the dashboard in `src/routes/admin.ts`): `{ "status": "ok"|"failed", "lastSuccess": iso|null, "lastAttempt": iso, "message": string, "file": name|null, "size": number|null }`. Keep `lastSuccess` from the previous file when an attempt fails.
- API (all `requireAdmin`, audit every action):
  - `GET /api/admin/backups` → `{ items: [{ name, size, createdAt }], status, settings: { dir, keep, hour, includesFiles, sameDisk } }` newest first. `sameDisk` is true when BACKUP_DIR is on the same device as DATA_DIR (compare `statSync().dev`): the page will warn that a dead disk takes the backups with it.
  - `POST /api/admin/backups` → runs one now, returns the new item. One backup at a time (409 if one is running).
  - `GET /api/admin/backups/:name/download` → the zip as an attachment.
  - `DELETE /api/admin/backups/:name`.
  - `POST /api/admin/backups/restore` `{ name, password }` → password step-up exactly like updates (move `confirmPassword` out of `src/routes/update.ts` into a shared module and use it in both; keep its lockout behaviour). Then: take a safety backup of the current state first; extract the chosen zip to a temporary folder; refuse it unless `users.json` parses and has at least one admin; replace `users.json`, `settings.json` and `branding/` in DATA_DIR; then restart with `restartSoon()` from `src/lifecycle.ts` (the in-memory stores must reload). Refuse with 409 when not supervised (`supervised()`), like updates. Never restore `storage/` from the zip in this task.
  - `:name` must match `^file-center-backup-\d{8}-\d{6}\.zip$` (no paths).
- Tests: a new `tests/backup.test.ts`. In-process tests (like `tests/api.test.ts`) for create / list / download (the zip has users.json and backup.json, no sessions.json) / retention / bad names / non-admin 403 / wrong password 403. An end-to-end restore test that starts the real launcher like `tests/update.test.ts` does: back up, delete a user, restore, wait for the restart, the user is back and the admin is still logged in. Add every new route to BOTH route lists in `tests/api.test.ts`.
