1. Devices (src/auth.ts sessions, src/routes/session.ts):
   - `Session` gets `id` (random, 16 bytes base64url — never the sid or its hash), `ip`, `ua` (user agent cut to 200 chars). `createSession(username, { ip, ua })`; the login route passes them. Sessions already on disk without these fields keep working (give them an id when read; missing ip/ua shown as unknown) — nobody is logged out by the upgrade.
   - `GET /api/sessions` (signed in): own sessions `{ id, ip, ua, created, seen, current }`, newest first. `DELETE /api/sessions/:id` (own only; 404 for another user's id; deleting the current one logs out). `POST /api/sessions/revoke-others` keeps only the current one (reuse `destroyUserSessions(user, sid)`).
   - Admin: `GET /api/admin/users/:username/sessions` and `POST /api/admin/users/:username/sessions/revoke` (all of that user's sessions; audit `sessions-revoke`).
2. Secret storage (`src/secret-box.ts`): AES-256-GCM `seal(text) / open(sealed)` with a 32-byte key in `DATA_DIR/secret.key`, created on first use with mode 0o600 (same pattern as `tokenKey()` in src/office.ts; add the path to `paths` in src/config.ts). A tampered or wrong-key value fails closed. Check src/backup.ts: say in README whether backups contain secret.key, and that restoring 2FA needs it.
3. TOTP (`src/totp.ts`): RFC 6238, HMAC-SHA1, 6 digits, 30 s step, accept the step before/after; base32 encode/decode; `otpauth://totp/<issuer>:<user>?secret=..&issuer=..` with issuer = the app name from settings. Tests use the RFC 6238 test vectors (SHA1, adapted to 6 digits) and the window edges.
   - `User.twoFactor?: { secret: <sealed>, enabledAt, lastStep, backup: string[] }` — backup = sha256 hex of 10 random codes (format `xxxx-xxxx`, shown once). A code whose step is ≤ `lastStep` is refused (no replay); a used backup code is removed. `publicUser` adds only `twoFactor: boolean`. The secret never goes to logs, audit or any answer after setup.
   - `POST /api/2fa/setup { password }` → `confirmPassword` first; a pending secret kept in memory for 10 min per user; answers `{ secret, uri }`. `POST /api/2fa/enable { code }` → checks against the pending secret, saves, answers `{ backupCodes }`, drops the user's other sessions. `POST /api/2fa/disable { password, code }` (TOTP or backup code). `POST /api/2fa/backup-codes { password, code }` → a new set. Wrong codes on these count in the step-up lockout.
   - Two-step login: `POST /api/login` with the right password for a 2FA user creates NO signed-in session; it answers `{ twoFactor: true, ticket }` (ticket random, kept hashed in memory, bound to user + IP, 5 min, one use, at most a few per user). `POST /api/login/2fa { ticket, code }` (TOTP or backup code): wrong code → `recordFailure` key `2fa|<ip>|<user>` with the login limits, lock → `alert('lockout', 'admin.alert-2fa-locked', …)`, audit `login-2fa-failed`; right code → exactly what /login does today on success (destroy the old sid, new session with ip/ua, cookie, lastLogin, audit `login`). No other route may give a signed-in session for a 2FA user without the code. `mustChangePassword` still applies after the second step.
   - Admin: `POST /api/admin/users/:username/2fa/reset { password }` (admin's own password via `confirmPassword`; audit `2fa-reset`; drops that user's sessions).
