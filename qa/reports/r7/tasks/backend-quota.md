1. Quota (new `src/quota.ts`):
   - `User.quotaBytes?: number` (absent or 0 = no limit). Settable in `POST /api/admin/users` and `PUT /api/admin/users/:username` (whole bytes, ≥ 0, ≤ 2^50), shown by `publicUser`. Counts only the user's home space (`accessFor(user,'home').root`); admins (root `/`) and the public space have no quota.
   - Usage counted with `treeStats` (src/fsx.ts), cached per user like src/stats.ts (fresh for 60 s; a count that hits the limit/truncates counts as full). Reservations for writes in progress, like `reserveGuest` in src/uploads.ts (check and reserve in the same tick, released on cancel, failure and stale-upload cleanup). After a write completes the cache is adjusted or marked stale; after delete/move-to-trash marked stale.
   - Over quota → 507 `quota.exceeded` with params `{ used, quota }` (Thai/English in src/messages.ts). Checked everywhere bytes land in a home space: upload announce (`initUpload`), `PUT /api/content` (size difference), `/zip`, `/unzip` (lower its byte budget to what is left), copy and cross-space move in `transfer()` (public → home counts), the ONLYOFFICE save callback (src/office.ts), restore from trash. Moves inside one home do not change usage. Trash is outside the home and does not count — say so in README.
   - `GET /api/me/usage` (signed in) → `{ used, quota, counting }` (`counting` true while a count runs and the cache is cold).
2. Upload-request links (src/shares.ts, src/routes/shares.ts, src/uploads.ts):
   - Share gets `kind: 'download' | 'upload'` (absent = download, so every existing link keeps working unchanged). `POST /api/shares` takes `kind`; `upload` only for folders and needs the creator's `share` + `upload` permissions in that space (`sharedItem` re-checks these per kind every time, like it does for download). Options: `maxFileBytes`, `maxFiles`, `maxTotalBytes` (each optional, capped by config/upload limits), `note` (≤ 500 chars, shown to the visitor as plain text), expiry (`allowedShareDays`), optional password (same unlock cookie and lockout as today).
   - `GET /api/s/:token` for an upload link answers the folder name, limits, note, counts used — NEVER the folder's contents. Download routes refuse an upload link (same 404 as every other failure); upload routes refuse a download link.
   - Public upload: `POST /api/s/:token/upload { name, size }` → `{ id, chunkSize, total }`; `PUT /api/s/:token/upload/:id/:n`; `POST /api/s/:token/upload/:id/complete`; `DELETE /api/s/:token/upload/:id`. The upload's owner must tie it to this link AND to this visitor (e.g. `share:<shareId>:<random visitor key>` with the key in an HttpOnly SameSite=Strict cookie scoped to the link path), so another visitor or another link cannot add chunks to, complete or cancel it. Files go straight into the shared folder (no sub-folders from the visitor), names through the existing name checks, an existing name gets a new one (`uniquePath`) — never overwrite. Bytes count against the link owner's quota and the link's limits (reserved at announce). Audit `share-upload` (owner, link id, file name, size).
