# File Center (ElysiaJS)

[![qa](https://github.com/RockZa27/file-center/actions/workflows/qa.yml/badge.svg)](https://github.com/RockZa27/file-center/actions/workflows/qa.yml)

ระบบฝากและแจกจ่ายไฟล์บนเว็บ เขียนใหม่ทั้งหมดด้วย **ElysiaJS + Bun** (backend) และ **Vue 3 + Naive UI** (frontend)
ออกแบบให้ใช้งานและหน้าตาใกล้เคียง File Center ที่สร้างต่อจาก FileGator แต่ไม่ได้ใช้โค้ดหรือข้อมูลเดิมเลย

- **ผู้เยี่ยมชม** เปิดเว็บแล้วดาวน์โหลดไฟล์ในโฟลเดอร์สาธารณะได้ทันที (ปิดได้จากหน้าตั้งค่า)
- **ผู้ใช้** เข้าสู่ระบบแล้วจัดการไฟล์ในโฟลเดอร์ของตัวเอง และใช้โฟลเดอร์สาธารณะตามสิทธิ์ที่ได้รับ
- **ผู้ดูแล** (manager) จัดการผู้ใช้ทั่วไปและดูไฟล์ของพวกเขาแบบอ่านอย่างเดียว (ดู "สิทธิ์")
- **ผู้ดูแลระบบสูงสุด** (admin) จัดการไฟล์ทั้งหมด ผู้ใช้ สิทธิ์ ดูสุขภาพระบบ ประวัติการใช้งาน ถังขยะ และตั้งค่าเว็บ

## เริ่มใช้งาน

ต้องมี [Bun](https://bun.sh) 1.1 ขึ้นไป

```bash
bun install
bun run build      # คอมไพล์หน้าเว็บ (ถ้าไม่มี Node ในเครื่องให้ใช้: bun --bun run build)
bun start          # เปิดที่ http://localhost:3000 (เริ่มผ่าน launcher เพื่อให้อัปเดตจากหน้าเว็บได้)
```

ครั้งแรกระบบสร้างบัญชี `admin` ให้และ **แสดงรหัสผ่านที่สุ่มไว้ในหน้าจอ** (จะบังคับให้เปลี่ยนทันทีที่เข้าสู่ระบบ)
หรือกำหนดเองด้วย `ADMIN_PASSWORD=...` ก่อนเริ่มครั้งแรก

ระหว่างพัฒนา:

```bash
bun run dev        # API ที่ :3000 + หน้าเว็บ (Vite, hot reload) ที่ :5173
bun test           # ทดสอบ API และระบบอัปเดต (SLOW_TESTS=1 bun test เพิ่มเทสต์ zip ขนาด 4.4 GB)
bun run typecheck
```

## วัดความเร็ว (benchmark)

```bash
bun --bun run build                                  # ต้องมี web/dist ก่อน (แถว static)
bun run bench [--quick] [--json out.json]            # เริ่มแอปเป็น child บนโฟลเดอร์ชั่วคราว สร้างไฟล์ 20,000 ไฟล์ (--quick: 2,000) แล้ววัด
bun run bench --compare qa/bench/baseline.json       # วัดแล้วพิมพ์ผลต่างจาก baseline (ไม่ทำให้ล้มเหลว; "!" = แย่ลง 10% ขึ้นไป)
```

ตารางมีต่อแถว: req/s, p50/p95/p99 (ms), errors และ MB/s (ดาวน์โหลด/อัปโหลด) ส่วน `login` ช้าโดยตั้งใจ (argon2) วัดไว้เฉยๆ
ตัวสร้างโหลดรันบนเครื่องเดียวกับแอป ตัวเลขจึงเทียบได้เฉพาะระหว่างการรันบนเครื่องเดียวกัน (CI รัน `--quick` แล้วเก็บ `bench.json` เป็น artifact ไม่ตัดสินผ่าน/ไม่ผ่านจากตัวเลข)
`qa/bench/baseline.json` คือผล **ก่อน** ปรับปรุงรอบนี้ (Intel Xeon 2.8 GHz 4 คอร์, Bun 1.4.2, โหมดเต็ม, concurrency 8, 5 วินาที/แถว)

ผลบนเครื่องนี้ ก่อน → หลัง:

| แถว | ก่อน | หลัง | สิ่งที่แก้ |
|---|---|---|---|
| list-2000 | 12.7 req/s, p50 587 ms | 46.9 req/s, p50 160 ms | เรียงชื่อด้วย `Intl.Collator` ตัวเดียว (`localeCompare` สร้าง collator ใหม่ทุกครั้งที่เทียบ ใช้เวลาเรียง ~60 ms ต่อ 2,000 ชื่อ) |
| static-asset (bundle 1,121 KB) | ส่ง 1,121 KB | ส่ง 316 KB (br), 2,094 req/s | บีบ br/gzip ครั้งเดียวแล้วเก็บไว้ + `Vary: Accept-Encoding` + ETag/304 (index.html และไฟล์อื่นด้วย) |
| RSS หลังอุ่นเครื่อง | 174 MB | 107 MB | (ความแตกต่างระหว่างรอบ ไม่ได้ตั้งใจแก้) |
| recent files | เขียน user-state.json ทุกการดาวน์โหลด | รวมเป็น 1 ครั้งต่อวินาที | `JsonStore.updateSoon`; ปิดระบบและสำรองข้อมูลเขียนที่ค้างอยู่ก่อนเสมอ |

แถวอื่น (session, download, upload) ต่างกันอยู่ในช่วงความผันผวนของเครื่อง ไม่ได้แก้อะไร (search และ zip แก้ในรอบ 1.8 ด้านล่าง)
การดาวน์โหลดใช้ `Bun.file` และรองรับ Range (206/416) อยู่แล้ว

รอบ 1.8 (รายการโฟลเดอร์ 2,000 รายการ, `bun run bench --quick`, concurrency 8, เครื่องเดียวกัน): list-2000 69.7 → 104.8 req/s, p50 106 → 74 ms
- โปรไฟล์ (`bun --cpu-prof`) ก่อนแก้: `lstatSync` 39%, เรียงชื่อด้วย collator 28%, JSON 8%, `readdirSync` 7% จึงเก็บ **ลำดับชื่อ** ต่อโฟลเดอร์ไว้ (LRU 200 โฟลเดอร์) และใช้ก็ต่อเมื่อตรงกับรายการที่อ่านสดทุกครั้ง (จำนวนเท่ากัน ทุกชื่อรู้จัก ชนิดตรงกัน) ขนาดและเวลาจึงสดเสมอ และไฟล์ที่เพิ่ม/ลบ/เปลี่ยนชื่อโผล่ทันที; `lstat` ทำเป็นก้อนละ 64 แล้วคืนคิวให้คำขออื่น (ลอง `lstat` แบบ async ขนาน 64 แล้ว: 49 req/s ช้ากว่าเดิม 55 เพราะค่า promise/thread pool จึงไม่ใช้)
- คำตอบ JSON ของ `/api/list`, `/folders`, `/search`, `/versions`, `/me/favorites`, `/me/recent` และรายการ admin (users, activity, logs, folders) บีบ br (quality 4, ~1.5 ms) หรือ gzip (level 3, ~1 ms) เมื่อใหญ่ตั้งแต่ 1 KB: 222 KB → 10 KB (br) / 18 KB (gzip) บนสาย แลกกับ CPU ราว 10% บน loopback (~90 req/s); เส้นทางที่มี token/โค้ด (session, login, 2FA, แชร์, อัปโหลด) และไฟล์ดาวน์โหลดไม่บีบ (BREACH) รายการอยู่ใน `src/compress.ts`

รอบ 1.8 (ค้นหา zip อัปโหลด; เครื่องเดิม โหมดเต็ม 20,000 ไฟล์ concurrency 8):

| แถว | ก่อน | หลัง | สิ่งที่แก้ |
|---|---|---|---|
| search | 64.8 req/s, p50 103.6 ms | 1,055 req/s, p50 6.5 ms | ตาราง FTS5 แบบ trigram สำหรับคำค้น 3 ตัวอักษรขึ้นไป + ตาราง `entries` แบบ rowid (เดิม `WITHOUT ROWID` สแกน `instr` ช้ากว่า ~6 เท่า) + จำ realpath ของราก |
| search 200,000 ไฟล์ (เรียกตรง) | 134 ms | 0.05–5 ms (คำค้น 1–2 ตัวอักษร 23 ms) | เหมือนข้างบน |
| zip (ไฟล์ข้อความ 200 × 40 KB / 6 × 3 MB) | 295 ms / 687 ms | 184 ms / 331 ms | deflate ระดับ 1 แทน 3: ไฟล์ใหญ่กว่า 0.3–1.6% (ระดับอื่นนอกจาก 6 zip.js ใช้ deflate ของตัวเอง ส่วนระดับ 6 ของ CompressionStream ช้ากว่าระดับ 1) |
| upload 100 MB | 117–141 MB/s | ไม่เปลี่ยน | โปรไฟล์ชี้ที่การเขียนไฟล์ใหม่ลงดิสก์ (`dd` ไฟล์ใหม่ขนาดเท่ากัน 136–160 MB/s) ไม่มี fsync/แฮชใน path นี้ และงานอื่นต่อชังก์รวม <0.2 ms จึงไม่แก้ |

`zip-200` ของ bench (ไฟล์ละ 1.6 KB) ไม่เปลี่ยน (11.1 → 11.2 req/s): เวลาไปกับ stream ต่อไฟล์ใน zip.js (~0.3 ms) ไม่ใช่ deflate
ลองอ่านไฟล์เล็กเข้าหน่วยความจำ และบีบเองด้วย `Bun.deflateSync` แล้วส่งต่อ (`passThrough`) แล้ว: ช้ากว่า (90 กับ 62 ms) หรือไฟล์ใหญ่ขึ้น 34% จึงไม่ใช้
การสร้างดัชนีครั้งแรกช้าลง (200,000 ไฟล์: 6 → 15 วินาที ในเบื้องหลัง) เพราะต้องเขียนดัชนี trigram ด้วย

## รันด้วย Docker และย้ายเครื่อง

```bash
cp .env.example .env     # แก้ ADMIN_PASSWORD ถ้าต้องการ
docker compose up -d --build
docker compose logs file-center   # ดูรหัสผ่าน admin ที่สุ่มให้ครั้งแรก
```

ข้อมูลทั้งหมดอยู่ในโฟลเดอร์ `./data` ข้างไฟล์ `docker-compose.yml` เท่านั้น:

- `data/storage/` ไฟล์ที่อัปโหลด
- `data/system/` ผู้ใช้ การตั้งค่า โลโก้ ประวัติ ถังขยะ session และไฟล์อัปโหลดที่ยังไม่เสร็จ (เป็นไฟล์ JSON ธรรมดา ไม่มีฐานข้อมูลแยก)

**ย้ายไปเครื่อง server ใหม่:** `docker compose down` ที่เครื่องเดิม → คัดลอก **ทั้งโฟลเดอร์โปรเจกต์** (รวม `data/` และ `.env`) ไปเครื่องใหม่ → `docker compose up -d --build`
ไม่ต้องแก้ค่าใดๆ ผู้ใช้ รหัสผ่าน ไฟล์ ถังขยะ และประวัติจะอยู่ครบ ผู้ที่ login อยู่ยัง login ต่อได้ ข้อมูลไม่มีพาธเครื่องเดิมฝังอยู่
(ควร `down` ก่อนคัดลอกเพื่อให้ไฟล์ข้อมูลนิ่ง และเครื่องใหม่ต้องมี Docker กับ Docker Compose v2)

ค่าเริ่มต้นของ `docker-compose.yml` เปิดพอร์ตให้เข้าได้จากเครื่อง server เท่านั้น (`127.0.0.1:3000`)
ถ้าต้องการให้เครื่องอื่นในวง LAN เข้าตรงได้ ให้ตั้ง `BIND_ADDRESS=0.0.0.0` ใน `.env`

### แอปในคอนเทนเนอร์ไม่ได้รันเป็น root

แอปทำงานเป็นผู้ใช้ `bun` (uid 1000 ของอิมเมจ `oven/bun`) ถ้ามีช่องโหว่ในแอป ผู้โจมตีจะไม่ได้สิทธิ์ root ในคอนเทนเนอร์
ตอนเริ่ม `scripts/docker-entrypoint.sh` เริ่มเป็น root ก่อน ถ้า `./data` (หรือโฟลเดอร์ชั้นแรกในนั้น) ยังไม่เป็นของ `bun` จะเปลี่ยนเจ้าของให้ (`chown -R`) **ครั้งเดียว** หลังอัปเกรดจากเวอร์ชันที่รันเป็น root
(ข้อมูลมากอาจใช้เวลาสักครู่ในการเริ่มครั้งนั้น) แล้วจึงสลับเป็น `bun` และเริ่ม launcher การอัปเดตและรีสตาร์ตผ่านหน้าเว็บเขียนเฉพาะใน `/data` จึงใช้ได้ตามเดิม
บนเครื่อง host ไฟล์ใน `./data` จะเป็นของ uid 1000 (ใช้ `sudo` ถ้าต้องจัดการไฟล์เหล่านั้นด้วยบัญชีอื่น)

ตรวจบนเครื่อง server หลังอัปเกรด:

```bash
docker compose up -d --build
docker compose top file-center                                  # คอลัมน์ UID ของ bun src/launcher.ts และ src/index.ts ต้องเป็น 1000 (หรือชื่อผู้ใช้ uid 1000 ของเครื่อง host) ไม่ใช่ root
docker compose exec file-center grep -E '^(Uid|Gid)' /proc/1/status   # ต้องเป็น 1000
ls -ln data                                                     # storage และ system เป็นของ 1000
```

แล้วเปิดหน้าเว็บ อัปโหลดไฟล์หนึ่งไฟล์ ดาวน์โหลดกลับ และลบลงถังขยะ ให้ทำได้ตามปกติ
(`docker compose exec file-center id` จะแสดง root เพราะ `exec` เปิดโปรเซสใหม่ด้วยผู้ใช้ตั้งต้นของคอนเทนเนอร์ ซึ่งต้องเป็น root เพื่อเปลี่ยนเจ้าของ `./data` ตอนเริ่ม
ไม่ได้บอกว่าแอปรันเป็นใคร ให้ดูจาก `top` หรือ `/proc/1/status` ตามด้านบน)

**ทางหนีไฟ:** ถ้ามีปัญหาเรื่องสิทธิ์ไฟล์ (เช่น `./data` อยู่บน NFS ที่ไม่ยอมให้ `chown`) ให้ใส่ `FC_RUN_AS_ROOT=true` ใน `.env` แล้ว `docker compose up -d` แอปจะรันเป็น root เหมือนเดิม

### ตั้งค่าความปลอดภัยของคอนเทนเนอร์

อิมเมจใช้ฐาน `oven/bun:1.4.2-slim` (เล็กกว่าฐานเต็มราว 70 MB; จำนวนแพ็กเกจ Debian ที่ `dpkg -l | wc -l` นับได้เท่ากับฐานเต็มคือ 85 บรรทัด
เพราะฐานทั้งสองมีชุดแพ็กเกจเดียวกัน ที่ลดคือขนาด ไม่ใช่จำนวนแพ็กเกจ) ไม่ใช้ distroless เพราะ entrypoint ต้องมี shell ทำ `chown` ครั้งเดียวและ `setpriv`
`docker-compose.yml` ของบริการ `file-center` ตั้งไว้ดังนี้ (`scripts/ci-docker.sh` ตรวจทุกข้อกับคอนเทนเนอร์จริง):

| ค่า | ทำอะไร | ถ้า host ใช้ไม่ได้ |
|---|---|---|
| `read_only: true` + `tmpfs: /tmp` | ระบบไฟล์ของอิมเมจเขียนไม่ได้ เขียนได้เฉพาะ `/data` (ข้อมูล และเวอร์ชันที่อัปเดตจากเว็บใน `/data/system/app` จึงอัปเดตได้ตามเดิม) กับ `/tmp` ในหน่วยความจำ 256 MB | ลบสองบรรทัดนี้ (ถ้าเพิ่ม volume ที่แอปต้องเขียน เช่น `BACKUP_DIR=/backups` ก็ต้องเป็น volume ที่เขียนได้อยู่แล้ว) |
| `cap_drop: [ALL]` + `cap_add` | `CHOWN` เปลี่ยนเจ้าของ `./data` ของการติดตั้งเก่า, `SETUID` และ `SETGID` ใช้ใน `setpriv` ลดจาก root เป็น `bun`, `DAC_OVERRIDE` อ่านโฟลเดอร์ใน `./data` ที่เป็นของผู้ใช้อื่นและปิดสิทธิ์ไว้ (และเขียน `./data` ตอน `FC_RUN_AS_ROOT=true`) หลังลดเป็น `bun` แล้วแอปไม่เหลือสิทธิ์ใด (`CapEff` ใน `/proc/1/status` เป็น 0) | ลบ `cap_drop` และ `cap_add` ถ้า host (เช่น NAS บางรุ่น) ไม่รองรับ |
| `security_opt: no-new-privileges:true` | โปรเซสในคอนเทนเนอร์ขอสิทธิ์เพิ่มผ่าน setuid ไม่ได้ | ลบบรรทัดนั้น |
| `mem_limit` / `pids_limit` | จำกัดหน่วยความจำ (2g) และจำนวนโปรเซส (512) ปรับได้ด้วย `FC_MEMORY_LIMIT` / `FC_PIDS_LIMIT` ใน `.env` | ตั้งค่าให้สูงขึ้นถ้าเก็บไฟล์ใหญ่มากหรือมีผู้ใช้พร้อมกันมาก (แอปถูกฆ่าเมื่อเกิน `mem_limit`) |

ตรวจบนเครื่อง server: `docker compose exec file-center touch /app/x` ต้องล้มเหลว (`Read-only file system`) และ `docker compose exec file-center grep -E 'CapEff|NoNewPrivs' /proc/1/status` ต้องได้ `0000000000000000` กับ `1`

## อัปเดตระบบจากหน้าเว็บ (ไม่ต้อง FTP ไม่ต้องปิดระบบ)

ผู้ดูแลระบบอัปเดตโค้ดได้เองที่เมนู **อัปเดตระบบ** โดยลากไฟล์แพ็กเกจ `.zip` ใส่ในหน้านั้น ไม่ต้องเข้าเครื่อง server และไม่ต้องรัน `docker compose` อีก

**สร้างแพ็กเกจ** (บนเครื่องที่มีโค้ด):

```bash
# 1) เพิ่มเลข "version" ใน package.json (ระบบรับเฉพาะเวอร์ชันที่ใหม่กว่าที่ใช้อยู่)
bun run package --notes "สิ่งที่เปลี่ยน"     # ได้ dist-update/file-center-<version>.zip (ราว 1 MB)
```

**ติดตั้ง:** เมนู อัปเดตระบบ → ลากไฟล์ `.zip` มาวาง → ระบบตรวจไฟล์ในแพ็กเกจ (ยังไม่รันโค้ดใด ๆ ของแพ็กเกจ) → ใส่รหัสผ่านของคุณยืนยัน → กด **ติดตั้งและรีสตาร์ต** ระบบจะลองเปิดเวอร์ชันใหม่แยกต่างหากก่อน ถ้าเปิดไม่ขึ้นจะไม่ติดตั้ง

- ระบบรีสตาร์ตเฉพาะโปรเซสของแอปประมาณ 2–5 วินาที คอนเทนเนอร์และ Cloudflare Tunnel ไม่ดับ ผู้ใช้ที่ login อยู่ยัง login ต่อได้ ข้อมูลและไฟล์ไม่ถูกแตะต้อง (การอัปโหลดไฟล์ที่กำลังส่งอยู่จะลองส่งชิ้นส่วนใหม่เอง)
- **ย้อนกลับอัตโนมัติ:** ถ้าเวอร์ชันใหม่เปิดไม่ขึ้นหรือล้มภายในไม่กี่วินาทีหลังติดตั้ง `launcher` จะกลับไปใช้เวอร์ชันก่อนหน้าเอง และหน้าอัปเดตจะบอกสาเหตุ นอกจากนี้ย้อนกลับด้วยมือได้ (เก็บ 2 เวอร์ชันล่าสุด และเวอร์ชันที่มากับอิมเมจ)
- **ความปลอดภัย:** เฉพาะ admin, โค้ดของแพ็กเกจไม่ถูกรันจนกว่าจะใส่รหัสผ่านซ้ำ (ทุกครั้งที่ติดตั้ง/ย้อนกลับ) (ใส่ผิดซ้ำจะถูกล็อกเหมือนการ login), ทุกไฟล์ในแพ็กเกจต้องตรง `manifest.json` (ขนาดและ SHA-256) ไม่มีไฟล์เกิน ไม่มี symlink หรือพาธ `../`, และบันทึกลงประวัติการใช้งานทุกครั้ง
  แพ็กเกจคือโค้ดที่จะรันบนเซิร์ฟเวอร์ ให้อัปโหลดเฉพาะแพ็กเกจที่คุณสร้างเองหรือเชื่อถือได้ ถ้าไม่ต้องการฟีเจอร์นี้ตั้ง `WEB_UPDATE=false`
- เวอร์ชันที่ติดตั้งผ่านเว็บเก็บใน `data/system/app/` (อยู่ใน volume จึงรอดการรีสตาร์ตคอนเทนเนอร์) ถ้าภายหลังสร้างอิมเมจใหม่ด้วย `docker compose up -d --build` แล้วเวอร์ชันในอิมเมจ **ใหม่กว่า** เวอร์ชันที่อัปเดตไว้ ระบบจะใช้เวอร์ชันในอิมเมจ
- `launcher` (`src/launcher.ts`) เป็นส่วนที่อยู่ในอิมเมจและอัปเดตผ่านเว็บไม่ได้ ถ้าต้องแก้ส่วนนี้ต้อง build อิมเมจใหม่
- **ครั้งแรกที่เปิดใช้ฟีเจอร์นี้** ต้องสร้างอิมเมจใหม่หนึ่งครั้ง (`docker compose up -d --build`) เพื่อให้มี launcher หลังจากนั้นอัปเดตผ่านเว็บได้ตลอด

### ลายเซ็นแพ็กเกจ (บังคับ)

**ระบบติดตั้งเฉพาะแพ็กเกจที่เซ็นแล้ว** (ทั้งไฟล์ที่อัปโหลดและที่ดึงจาก `UPDATE_SOURCE`) ถ้าไม่เซ็น ใครที่ได้ทั้ง session ของ admin และรหัสผ่าน admin ไปก็ติดตั้งโค้ดอะไรก็ได้ แต่เมื่อบังคับลายเซ็น แม้บัญชี admin ถูกยึดไปก็ติดตั้งโค้ดอื่นไม่ได้ ระบบฝังกุญแจสาธารณะของ File Center ไว้ใน `src/update-key.ts` จึงติดตั้งรุ่นทางการที่เซ็นแล้วได้ทันทีโดยไม่ต้องตั้งอะไร กุญแจส่วนตัวของรุ่นทางการไม่อยู่ใน repository

- **ผู้ออกรุ่น (File Center):** เซ็นตอนเผยแพร่ด้วย `bun run release --sign <ไฟล์กุญแจส่วนตัว> --push` (ไม่ใส่ `--sign` ระบบไม่ยอมเผยแพร่ ต้องใส่ `--unsigned` ให้ชัดเจนเท่านั้น)
- **สร้างแพ็กเกจเอง:** สร้างกุญแจของคุณเองตามขั้นตอนด้านล่างแล้วตั้ง `UPDATE_PUBLIC_KEY` (กุญแจนี้ใช้แทนกุญแจที่ฝังมา)
- **ปิดการบังคับ:** `UPDATE_ALLOW_UNSIGNED=true` รับแพ็กเกจที่ไม่เซ็นด้วย (แพ็กเกจที่เซ็นมายังต้องตรวจผ่าน) เสี่ยง: ใครที่ได้ session และรหัสผ่านของ admin จะติดตั้งโค้ดของตัวเองบนเซิร์ฟเวอร์ได้ ระบบจะเตือนตอนเริ่มระบบ ในหน้าภาพรวมและหน้าอัปเดต และบันทึกการติดตั้งแพ็กเกจที่ไม่เซ็นเป็น `update-apply-unsigned`
- **อัปเกรดจากรุ่นเก่า:** เซิร์ฟเวอร์รุ่น 1.6.0 และเก่ากว่ารับ 1.7.0 ที่เซ็นแล้วได้ตามปกติ ตั้งแต่ 1.7.0 เป็นต้นไปติดตั้งได้เฉพาะแพ็กเกจที่เซ็น
- หน้าอัปเดตบอกล่วงหน้าก่อนดาวน์โหลดว่าเวอร์ชันล่าสุดใน `latest.json` เซ็นหรือไม่ ถ้าไม่เซ็นจะแจ้งว่า "จะถูกปฏิเสธ"

1. **สร้างกุญแจครั้งเดียว** บนเครื่องที่ใช้สร้างแพ็กเกจ (ไม่ใช่เครื่อง server):
   ```bash
   bun run package --gen-key ~/file-center-keys
   ```
   ได้ไฟล์กุญแจส่วนตัว `~/file-center-keys/update-signing.key` (อ่านได้เฉพาะเจ้าของ) และ public key หนึ่งบรรทัดที่แสดงบนหน้าจอ
   ระบบไม่เขียนทับไฟล์กุญแจที่มีอยู่แล้ว
2. **เก็บกุญแจส่วนตัวไว้นอก server** ห้ามวางในโฟลเดอร์โปรเจกต์บน server ห้าม commit และควรสำรองไว้ที่ปลอดภัย ถ้ากุญแจหายต้องสร้างใหม่แล้วเปลี่ยน `UPDATE_PUBLIC_KEY` (ต้องเข้าเครื่อง server) ถ้ากุญแจหลุด ให้สร้างใหม่และเปลี่ยนทันที
3. **ตั้งค่าบน server** ใส่ public key ใน `.env` แล้วรีสตาร์ต (`docker compose up -d`):
   ```env
   UPDATE_PUBLIC_KEY=MCowBQYDK2VwAyEA...
   ```
   ถ้าค่าผิด ระบบยังเปิดใช้งานได้ตามปกติ แต่จะแจ้งใน log และไม่รับแพ็กเกจใด ๆ จนกว่าจะแก้ค่า
4. **สร้างแพ็กเกจแบบเซ็น** ทุกครั้งที่อัปเดต:
   ```bash
   bun run package --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน"
   ```
   ในแพ็กเกจจะมี `manifest.sig` (ลายเซ็นของ `manifest.json` ซึ่งมี SHA-256 ของทุกไฟล์) ระบบตรวจลายเซ็นตอนอัปโหลดและตรวจซ้ำตอนติดตั้ง
   แพ็กเกจที่ไม่มีลายเซ็น เซ็นด้วยกุญแจอื่น หรือถูกแก้หลังเซ็น จะถูกปฏิเสธ

ถ้าไม่ตั้ง `UPDATE_PUBLIC_KEY` ระบบใช้กุญแจของ File Center ที่ฝังมา (แพ็กเกจที่เซ็นด้วยกุญแจอื่นจะถูกปฏิเสธ)

### เผยแพร่อัปเดตใน git และให้ server ตรวจหาเอง

**เผยแพร่** (บนเครื่องที่มีโค้ด ทุกครั้งที่ออกเวอร์ชันใหม่):

```bash
# เพิ่ม "version" ใน package.json แล้ว commit ให้เรียบร้อยก่อน
bun run release --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน" --push
```

- สร้างแพ็กเกจด้วย `scripts/package.ts` แล้ว commit ลง branch `updates` (branch ที่มีแต่แพ็กเกจ ไม่มีโค้ด สร้างให้เองถ้ายังไม่มี) พร้อม `SHA256SUMS`, แถวใหม่ในตารางของ `README.md` และ `latest.json` (เวอร์ชันล่าสุด ที่ server อ่าน)
- ไม่ยอมทำงานถ้ามีไฟล์ที่ยังไม่ได้ commit (แพ็กเกจต้องตรงกับ commit ที่ระบุ) หรือ version ไม่ใหม่กว่าทุกเวอร์ชันที่มีใน `updates` แล้ว
- ไม่ใส่ `--push` = commit ไว้ในเครื่องเท่านั้น ตรวจแล้วค่อย `git push origin updates` เอง ใช้ `--skip-web` ถ้า build หน้าเว็บไว้แล้ว
- branch ปัจจุบันที่ทำงานอยู่ไม่ถูกแตะต้อง (ทำใน git worktree ชั่วคราวแล้วลบทิ้งเสมอ)

**ตรวจหาอัปเดตจาก GitHub (เปิดอยู่แล้วตั้งแต่ 1.7.1):** `.env.example` ใส่ `UPDATE_SOURCE` ของรุ่นทางการไว้ให้แล้ว (ตั้งแต่ 1.7.2) ส่วน `.env` ที่มีอยู่ก่อนไม่ถูกแก้ แต่ถ้าไม่มีบรรทัดนี้ server ก็ใช้รุ่นทางการที่ `https://raw.githubusercontent.com/RockZa27/file-center/updates` ปลอดภัยเพราะติดตั้งได้เฉพาะแพ็กเกจที่เซ็นด้วยกุญแจของ File Center ถ้าออกรุ่นเอง ให้ชี้ไปที่ branch `updates` ของคุณ ถ้าไม่ต้องการให้ server ติดต่อ GitHub เลย ให้ตั้ง `off` แล้วรีสตาร์ต (`docker compose up -d`):

```env
UPDATE_SOURCE=https://raw.githubusercontent.com/<owner>/<repo>/updates
# หรือปิด
UPDATE_SOURCE=off
```

หน้าอัปเดตจะมีปุ่มตรวจหาเวอร์ชันใหม่ ถ้ามีเวอร์ชันใหม่กว่า กดดาวน์โหลดแล้ว server
ดึงไฟล์มาเอง ตรวจ SHA-256 กับ `latest.json` แล้วตรวจแพ็กเกจแบบเดียวกับไฟล์ที่ลากมาวางทุกอย่าง การติดตั้งยังต้องใส่รหัสผ่านซ้ำเหมือนเดิม

- **ตรวจเองเบื้องหลัง:** server อ่านเฉพาะ `latest.json` ราว 1 นาทีหลังเริ่มระบบและวันละครั้ง (ไม่ดาวน์โหลดหรือติดตั้งอะไรเอง) ถ้ามีเวอร์ชันใหม่กว่า
  หน้าภาพรวมของ admin เตือน `update.available` พร้อม `{ version }` และส่งการแจ้งเตือนหนึ่งครั้งต่อเวอร์ชันใหม่ (ถ้าตั้งไว้ ดู การแจ้งเตือน) ผลเก็บในหน่วยความจำ เริ่มระบบใหม่ก็ตรวจใหม่
- **อัปเดตในขั้นตอนเดียว:** `POST /api/admin/update/fetch-and-apply` `{ password }` ตรวจรหัสผ่านก่อน (ล็อกเมื่อผิดซ้ำเหมือน `/apply` และยังไม่ดาวน์โหลดอะไร)
  แล้วทำ `/check` → `/fetch` → `/apply` ต่อกันโดยไม่ข้ามการตรวจใด ๆ: ต้องใหม่กว่าที่ใช้อยู่, SHA-256 และขนาดตรง `latest.json`, ตรวจไฟล์ในแพ็กเกจแบบเดียวกับที่อัปโหลด,
  ลายเซ็น, ลองเปิดเวอร์ชันใหม่แยกต่างหาก แล้วจึงรีสตาร์ต ตอบ `{ ok, version, restarting }`
  ถ้าขั้นใดล้มเหลว คำตอบบอกขั้นนั้นใน `params.step` (`check` / `fetch` / `stage` / `apply`) และไม่มีแพ็กเกจค้างอยู่ ประวัติการใช้งานบันทึก `update-fetch` และ `update-apply` เหมือนทำทีละขั้น

#### ช่องทางเบตา (เวอร์ชัน `x.y.z-beta.N`, ตั้งแต่ 1.8.0)

เบตาคือเวอร์ชันทดลองที่ออกก่อนรุ่นปกติ (เช่น `1.9.0-beta.1` < `1.9.0-beta.2` < `1.9.0` ตามลำดับ semver) **ยังไม่เสถียรและอาจมีข้อบกพร่อง
หรือทำให้ระบบใช้งานไม่ได้** ใช้เมื่อต้องการลองของใหม่เท่านั้น ไม่ควรใช้กับเซิร์ฟเวอร์ที่คนอื่นพึ่งพาอยู่ ถ้าจะลองให้สำรองข้อมูลก่อน

- **เผยแพร่:** ตั้ง `version` เป็น `x.y.z-beta.N` แล้วสั่ง `bun run release --beta --sign <กุญแจ> [--push]` ได้ไฟล์ `latest-beta.json` (รูปแบบเดียวกับ `latest.json` เพิ่ม `"channel": "beta"`) และแถวในตาราง README ของ branch `updates` ที่ติดป้าย "เบตา" โดย **ไม่แตะ `latest.json`** (server รุ่น 1.7.2 และเก่ากว่าอ่านแต่ `latest.json` จึงไม่เห็นเบตา)
  รุ่นปกติไม่รับ version `-beta` (ต้องใช้ `--beta`) และ `--beta` ไม่รับ version ปกติ เบตาต้องใหม่กว่า **ทุกเวอร์ชัน** ที่เผยแพร่แล้ว (ปกติและเบตา) ส่วนรุ่นปกติต้องใหม่กว่าทุก **รุ่นปกติ** (จึงออก `1.9.0` ต่อจาก `1.9.0-beta.2` ได้) ต้องเซ็นเสมอเหมือนรุ่นปกติ
- **หน้าอัปเดต:** `GET /api/admin/update/check` ตอบ `beta` เพิ่ม: `{ version, notes, size, signed, builtAt }` หรือ `null` เมื่อไม่มี `latest-beta.json`, ไม่ใหม่กว่าเวอร์ชันที่ใช้อยู่ หรือไม่ใหม่กว่ารุ่นปกติล่าสุด (`latest`/`newer`/`refused` เหมือนเดิม และเบตาที่ `signed: false` จะถูกปฏิเสธเมื่อ `signatureRequired`)
- **ติดตั้ง:** `POST /api/admin/update/fetch` และ `/fetch-and-apply` รับ `channel: "stable" | "beta"` (ค่าเริ่มต้น `stable`) ถ้า `channel: "beta"` ต้องส่ง `acceptBetaRisk: true` ด้วย ไม่งั้นตอบ 400 `update.beta-not-accepted` (ตรวจก่อนถามรหัสผ่านและก่อนดาวน์โหลด) ที่เหลือเหมือนรุ่นปกติทุกอย่าง: รหัสผ่าน, SHA-256, ขนาด, ลายเซ็น (ไม่มีข้อยกเว้นสำหรับเบตา) ประวัติการใช้งานบันทึก `update-apply-beta` เพิ่มเมื่อติดตั้งเบตา
- **เบื้องหลังไม่เกี่ยว:** การตรวจรายวัน คำเตือน `update.available` และการแจ้งเตือนอ่านเฉพาะ `latest.json` ไม่มีการเสนอหรือแจ้งเบตา
- **ขณะใช้เบตา:** `GET /api/admin/status` มีคำเตือน `update.on-beta` พร้อม `{ version }` และถ้ามีรุ่นปกติที่ใหม่กว่า (รวมถึงรุ่นปกติของ x.y.z เดียวกัน เช่น `1.9.0` หลัง `1.9.0-beta.2`) จะเสนอตามปกติ
- **กลับไปรุ่นปกติ:** (1) ติดตั้งรุ่นปกติถัดไปเมื่อออกแล้ว (จากหน้าอัปเดตหรืออัปโหลดแพ็กเกจรุ่นปกติ ต้องใหม่กว่าที่ใช้อยู่) หรือ (2) ย้อนกลับด้วย `POST /api/admin/update/rollback` `{ dir, password }` ไปเวอร์ชันที่ใช้ก่อนหน้า (ระบบเก็บ 2 เวอร์ชันล่าสุดใน `history` ของ `GET /api/admin/update`) หรือ `dir: "builtin"` สำหรับเวอร์ชันที่มากับอิมเมจ หน้าอัปเดตไม่รับแพ็กเกจที่ไม่ใหม่กว่า จึง **ติดตั้งรุ่นเก่ากว่าด้วยการอัปโหลดไม่ได้** การย้อนกลับเปลี่ยนเฉพาะโค้ด ไม่ย้อนข้อมูล (ผู้ใช้ ไฟล์ การตั้งค่า) ที่เบตาเขียนไว้แล้ว จึงควรสำรองข้อมูลก่อนลองเบตา

- ใช้ได้กับ **repo สาธารณะ** เท่านั้น (server ดาวน์โหลดโดยไม่มีรหัสผ่านหรือ token) repo ส่วนตัวให้ดาวน์โหลดไฟล์ .zip เองแล้วลากมาวางแทน
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) และไม่ตามการ redirect ค่าอื่นระบบยังเปิดได้ แต่จะเตือนใน log และปิดการตรวจหาอัปเดตไว้
- **ลายเซ็นบังคับ:** server จะติดตั้งโค้ดที่ดึงมาจากอินเทอร์เน็ต SHA-256 ใน `latest.json` บอกได้แค่ว่าไฟล์ไม่เสียระหว่างทาง
  แต่บอกไม่ได้ว่าใครสร้าง ใครที่แก้ branch `updates` ได้ (หรือบัญชี GitHub ถูกยึด) ก็เปลี่ยนทั้งแพ็กเกจและ `latest.json` ได้ มีแต่ลายเซ็นที่กันกรณีนี้

## ใช้งานผ่านโดเมนด้วย Cloudflare Tunnel

Cloudflare Tunnel ให้คนภายนอกเข้าผ่านโดเมน (เช่น `https://files.example.com`) ได้โดย **ไม่ต้องเปิดพอร์ตที่เราเตอร์และไม่ต้องมี IP จริง**
เพราะคอนเทนเนอร์ `cloudflared` เป็นฝ่ายต่อออกไปหา Cloudflare เอง และ Cloudflare ทำ HTTPS ให้

1. **นำโดเมนเข้า Cloudflare** ที่ [dash.cloudflare.com](https://dash.cloudflare.com) เพิ่มโดเมน แล้วเปลี่ยน nameserver ที่ผู้ให้บริการโดเมนเป็นของ Cloudflare
   รอจนสถานะโดเมนเป็น Active (ไม่กี่นาทีถึงหลายชั่วโมง)
2. **สร้าง tunnel** ที่ Zero Trust (one.dash.cloudflare.com) > Networks > Tunnels > Create a tunnel > เลือก Cloudflared > ตั้งชื่อ เช่น `file-center`
   หน้าถัดไปเลือก Docker แล้วคัดลอก **โทเคน** (ข้อความยาวหลัง `--token`) ไม่ต้องรันคำสั่งที่หน้านั้นให้
3. **ตั้งค่า `.env`** (คัดลอกจาก `.env.example` ถ้ายังไม่มี) ให้มีค่าเหล่านี้:
   ```env
   COMPOSE_PROFILES=tunnel
   TUNNEL_TOKEN=โทเคนที่คัดลอกมา
   SECURE_COOKIE=true
   TRUST_PROXY=cloudflare
   BIND_ADDRESS=127.0.0.1
   ```
4. **เริ่มระบบ** `docker compose up -d --build` แล้วดูว่า tunnel ในหน้า Zero Trust ขึ้นสถานะ Healthy
5. **ผูกโดเมนกับระบบ** ในหน้า tunnel > Public Hostname (หรือ Published application routes) > Add
   - Subdomain: `files` · Domain: โดเมนของคุณ
   - Service Type: `HTTP` · URL: `file-center:3000` (ชื่อคอนเทนเนอร์ ไม่ใช่ localhost)

   Cloudflare สร้าง DNS ให้อัตโนมัติ เปิด `https://files.โดเมนของคุณ` ได้ทันที
6. **ตั้งค่าที่แนะนำใน Cloudflare** (หน้าโดเมน)
   - SSL/TLS > Edge Certificates: เปิด Always Use HTTPS และตั้ง Minimum TLS Version เป็น 1.2
   - **ห้ามสร้าง Cache Rule แบบ "Cache Everything"** กับโดเมนนี้ เพราะจะทำให้ไฟล์ส่วนตัวและ API ถูกเก็บไว้ที่ Cloudflare
     (ระบบตั้ง `Cache-Control` ให้เองแล้ว: ไฟล์หน้าเว็บใน `/assets/` cache ได้ ส่วนไฟล์ที่ดาวน์โหลดและ API ไม่ถูก cache)
   - ถ้าต้องการชั้นป้องกันเพิ่มสำหรับผู้ดูแล ใช้ Cloudflare Access ครอบพาธ `/admin` และ `/api/admin` ได้

ข้อควรรู้เมื่อใช้ผ่าน Cloudflare
- Cloudflare แพ็กเกจ Free/Pro รับคำขอได้ไม่เกิน 100 MB ต่อครั้ง ระบบอัปโหลดแบ่งส่งทีละ 8 MB จึงอัปโหลดไฟล์ใหญ่ได้ตามปกติ (อย่าตั้ง `UPLOAD_CHUNK_SIZE` เกิน 100 MB)
- Cloudflare ตัดคำขอที่เซิร์ฟเวอร์ตอบช้ากว่าประมาณ 100 วินาที (หน้าเว็บจะได้ error 524) การบีบอัด/แตก zip ที่ใหญ่มากอาจเจอกรณีนี้
  แต่งานยังทำต่อจนเสร็จที่เซิร์ฟเวอร์ รอสักครู่แล้วรีเฟรชหน้า (วัดจริง: บีบอัดไฟล์ 5 GB ใช้ ~24 วินาที แตก ~26 วินาที
  เพราะไฟล์ใหญ่กว่า 1 MB ที่บีบอัดไม่ลง เช่น วิดีโอ จะถูกเก็บใน zip แบบไม่บีบอัด)
- ข้อกำหนดของ Cloudflare จำกัดการใช้ CDN แบบไม่เสียเงินเพื่อเผยแพร่วิดีโอหรือไฟล์ขนาดใหญ่ในปริมาณมาก ถ้าจะใช้แจกไฟล์ใหญ่จำนวนมาก ควรอ่านข้อกำหนดก่อน
- โทเคนใน `.env` คือกุญแจของ tunnel ใครได้ไปก็ต่อเข้าโดเมนนี้ได้ ห้ามแชร์ ถ้าหลุดให้ Refresh token ในหน้า tunnel
- ถ้าเปิด `BIND_ADDRESS=0.0.0.0` คู่กับ `TRUST_PROXY=cloudflare` คนในวง LAN ที่เข้าตรงจะปลอม IP ของตัวเองได้ (ไม่กระทบสิทธิ์ แต่กระทบการล็อกและประวัติ)
- **reverse proxy อื่น (1Panel/OpenResty, nginx, Caddy):** ทุกคำตอบของ `/api/*` มีหัว `Cache-Control: no-store` (ตั้งแต่ 1.7.1) proxy ที่ทำตามหัวนี้จะไม่เก็บไว้ ถ้าเปิดแคชแบบบังคับใน proxy ให้ยกเว้น `/api/` หรือปิดแคชของไซต์นี้ ไม่อย่างนั้นรายการไฟล์จะไม่อัปเดต (เช่น อัปโหลดโฟลเดอร์แล้วไม่ขึ้นในรายการ) และข้อมูลส่วนตัวของผู้ใช้คนหนึ่งอาจถูกส่งให้อีกคน

## ผ่าน 1Panel / nginx แล้วอัปโหลดหรือดาวน์โหลดช้า

ถ้าเปิดแอปตรง ๆ (`http://<เครื่อง>:<PORT>`) เร็วปกติ แต่ผ่านโดเมนแล้วช้า สาเหตุมักอยู่ที่ reverse proxy ไม่ใช่ตัวแอป
ค่าเริ่มต้นของ nginx/OpenResty (1Panel) พักทั้งตัวไฟล์ที่ส่งขึ้นและที่ส่งลงไว้ในหน่วยความจำหรือไฟล์ชั่วคราวก่อนส่งต่อ และจำกัดขนาดคำขอไว้ที่ 1 MB
ในหน้าตั้งค่าไซต์ของ 1Panel (เว็บไซต์ > ไซต์ > การตั้งค่า > ไฟล์ตั้งค่า) หรือในไฟล์ `server { }` ของ nginx ให้ตั้งดังนี้

```nginx
client_max_body_size 0;          # ไม่จำกัดขนาด (แอปจำกัดเองด้วย UPLOAD_MAX_SIZE)
location / {
    proxy_pass http://127.0.0.1:<PORT>;
    proxy_http_version 1.1;
    proxy_request_buffering off; # ส่งชิ้นอัปโหลดต่อทันที ไม่พักก่อน
    proxy_buffering off;         # ส่งไฟล์ดาวน์โหลดให้ผู้ใช้ทันที ไม่พักก่อน
    proxy_max_temp_file_size 0;  # ไม่เขียนไฟล์ชั่วคราวลงดิสก์ของ proxy
    proxy_read_timeout 3600s;    # zip ใหญ่และขั้นตอน "ประกอบไฟล์" ใช้เวลานานได้
    proxy_send_timeout 3600s;
}
```

- เปิด **HTTP/2** ที่ไซต์ (ใน 1Panel: ตั้งค่า HTTPS > เปิด HTTP/2) เบราว์เซอร์จะส่งหลายชิ้นพร้อมกันบนการเชื่อมต่อเดียวได้ดีกว่า HTTP/1.1
- **อย่าเพิ่มหัว `Cache-Control` หรือกฎแคชให้ `/api`** แอปตั้งหัวที่ถูกต้องให้เองอยู่แล้ว (ดูหมายเหตุเรื่อง proxy อื่นในหัวข้อ Cloudflare Tunnel ด้านบน)
- ตั้งแต่ 1.9.1 แอปรอคำขอที่เงียบได้นานสุด 255 วินาที (เดิม 30 วินาที) การรวมชิ้นส่วนของไฟล์ใหญ่และ zip ขนาดใหญ่จึงไม่ถูกตัดกลางคัน
- **Cloudflare แบบเมฆส้ม (proxied) ทำให้ไฟล์ใหญ่ช้าได้** ทราฟฟิกอาจถูกส่งอ้อมผ่านประเทศอื่นก่อนถึงเครื่องคุณ และแพ็กเกจ Free/Pro รับคำขอได้ไม่เกิน 100 MB ต่อครั้ง
  ถ้าจะส่งไฟล์ใหญ่บ่อย ๆ ให้ใช้โดเมนที่ตั้งเป็น **เมฆเทา (DNS only)** หรือใช้ Tailscale เข้าเครื่องโดยตรงแทน

### วัดว่าช้าที่ตรงไหน

ลองดาวน์โหลดไฟล์ใหญ่ไฟล์เดียวสามทาง (ไฟล์ในพื้นที่ public ที่ผู้ใช้ guest ดาวน์โหลดได้ หรือใส่คุกกี้ `-b 'fc_sid=...'` ของคุณ) ดูค่าความเร็วเป็นไบต์ต่อวินาที

```bash
# 1) ตัวแอปโดยตรง
curl -o /dev/null -w '%{speed_download}\n' 'http://127.0.0.1:<PORT>/api/download?space=public&path=/<ไฟล์>'

# 2) ผ่าน proxy บนเครื่องเดียวกัน (ไม่ผ่านอินเทอร์เน็ต)
curl -o /dev/null -w '%{speed_download}\n' --resolve <โดเมน>:443:127.0.0.1 'https://<โดเมน>/api/download?space=public&path=/<ไฟล์>'

# 3) ผ่านโดเมนจริง (รวม Cloudflare และเส้นทางอินเทอร์เน็ต)
curl -o /dev/null -w '%{speed_download}\n' 'https://<โดเมน>/api/download?space=public&path=/<ไฟล์>'
```

- ข้อ 1 ช้า: ปัญหาอยู่ที่ดิสก์หรือเครื่อง
- ข้อ 1 เร็วแต่ข้อ 2 ช้า: ปัญหาอยู่ที่ตั้งค่า proxy ด้านบน
- ข้อ 2 เร็วแต่ข้อ 3 ช้า: ปัญหาอยู่ที่เส้นทางอินเทอร์เน็ตหรือ Cloudflare (ลองเมฆเทา/Tailscale)

## เมนู คู่มือ และการแนะนำการใช้งาน

- **เมนูข้าง** แบ่งเป็นหมวด ได้แก่ ไฟล์, การแชร์, จัดการ (admin/manager) และระบบ (admin)
- **หน้า "ระบบ"** รวม ตั้งค่า, สำรองข้อมูล, อัปเดต, บันทึก และถังขยะระบบ ไว้เป็นแท็บ
  ลิงก์เดิมอย่าง `/admin/backup` ยังเปิดได้ และจะเปิดแท็บที่ตรงกัน
- **ธีมและภาษา** อยู่ในเมนูผู้ใช้ (มุมขวาบน) และในหน้าบัญชี แท็บ "การแสดงผล"
- **ผู้ใช้ใหม่** เข้าสู่ระบบครั้งแรกจะเห็นหน้าต้อนรับ และเลือกเริ่มทัวร์ที่ชี้จุดบนหน้าจอได้ ทัวร์แยกตามสิทธิ์ user / manager / admin
- **หลังอัปเดตระบบ** ผู้ใช้เดิมจะเห็น popup "มีอะไรใหม่" เฉพาะเรื่องที่เพิ่มหลังเวอร์ชันที่เคยเห็น
  กด "พาไปดู" เพื่อไปที่จุดนั้นได้ และ popup จะขึ้นครั้งเดียว
- **คู่มือการใช้งาน** (`/help`, เมนูล่างสุด หรือปุ่ม ? บนหัวหน้าจอ) มีหัวข้อค้นหาได้ ปุ่ม "แสดงให้ดู" เริ่มทัวร์ใหม่ และดูประวัติ "มีอะไรใหม่" ได้ทุกเวอร์ชัน
- **สถานะที่ server เก็บ** อยู่ใน `DATA_DIR/guide.json` (API `GET/PUT /api/me/guide`)
  - ตอนอัปเดตเป็น 1.12 ครั้งแรก ผู้ใช้ที่มีอยู่แล้วจะนับว่าเห็นถึง 1.11.0
  - ผู้ใช้ที่สร้างหลังจากนั้นจะได้ทัวร์เต็ม

## ดูและแก้ไฟล์ในหน้าเว็บ (ไม่ต้องมีเซิร์ฟเวอร์เพิ่ม)

- **ดูตัวอย่าง:** `.docx` (ตาราง รูป หัว/ท้ายกระดาษ) · `.xlsx` `.xlsm` `.xls` `.ods` (แยกชีต แถวแรกค้างไว้ด้านบน ตัวเลขและวันที่จัดรูปแบบ แสดง 1,000 แถวแรกของแต่ละชีต)
  · `.pptx` (สไลด์แบบอ่านอย่างเดียว) ตัวอ่านแต่ละแบบโหลดเมื่อเปิดไฟล์ชนิดนั้นครั้งแรกเท่านั้น ไฟล์ใหญ่กว่า 20 MB ให้ดาวน์โหลดแทน
  ไม่มีสิ่งใดในไฟล์ถูกรัน (ไม่อ่าน macro, HTML ที่ได้จากไฟล์ผ่านการกรองก่อนแสดง, ลิงก์ได้เฉพาะ http(s)/mailto/tel)
- **แก้ไข (ผู้มีสิทธิ์ `write`):** โค้ดและข้อความมีเลขบรรทัดและสีตามภาษา · Markdown แก้คู่กับตัวอย่างที่แสดงผลทันที (บนมือถือเรียงบนลงล่าง)
  · `.csv` แก้เป็นตาราง เพิ่ม/ลบแถวและคอลัมน์ได้ บันทึกกลับด้วยตัวคั่นและการขึ้นบรรทัดแบบเดิม · `Ctrl/⌘+S` บันทึก
- **มีคนบันทึกไปก่อน:** การบันทึกส่ง `expectedMtime` ไปด้วย ถ้าไฟล์ถูกบันทึกจากที่อื่นหลังจากเปิด (409 `files.changed-elsewhere`)
  จะให้เลือก "โหลดฉบับของเขา" หรือ "บันทึกทับ" (ยืนยันอีกครั้งก่อนเขียนทับ)

(`.doc` `.xls` `.ppt` แบบเก่าเปิดดูได้อย่างเดียว) **ปิดไว้โดยค่าเริ่มต้น** จะเปิดเมื่อตั้งค่าครบเท่านั้น
เมื่อเปิดใช้ เมนูของไฟล์และหน้าดูตัวอย่างมีปุ่ม "แก้ไขด้วย Office" (หรือ "เปิดด้วย Office" สำหรับไฟล์ที่ดูได้อย่างเดียว) ตัวแก้ไขเปิดเต็มจอ
ปิดแล้วกลับมาที่โฟลเดอร์ และรอจนฉบับใหม่มาถึง (document server ส่งมาภายในไม่กี่วินาทีหลังปิด) เมื่อไม่ได้ตั้งค่า ปุ่มนี้ไม่แสดงและใช้การดูในหน้าเว็บตามด้านบน

- **ทรัพยากร:** document server ใช้ RAM ราว 2–4 GB (ขั้นต่ำ 2 GB + swap แนะนำ 4 GB) และดิสก์ราว 3 GB สำหรับอิมเมจ ครั้งแรกที่เริ่มใช้เวลา 1–2 นาทีก่อนพร้อมใช้งาน
- **รุ่นฟรีจำกัด 20 การเชื่อมต่อพร้อมกัน** (นับทุกแท็บที่เปิดเอกสารอยู่ ทั้งดูและแก้) เกินนั้นผู้ใช้คนถัดไปจะเปิดเอกสารไม่ได้จนกว่าจะมีคนปิด

**เปิดใช้งาน (Docker):** เพิ่มใน `.env` แล้ว `docker compose up -d`

```env
# ถ้าใช้ tunnel อยู่แล้ว: COMPOSE_PROFILES=tunnel,office
COMPOSE_PROFILES=office
# สร้างด้วย  openssl rand -hex 32  (ไม่ตั้งหรือสั้นกว่า 32 ตัวอักษร = ปิด)
OFFICE_JWT_SECRET=ค่าที่สร้างได้
# ที่อยู่ของ document server ที่ "เบราว์เซอร์" เปิดได้
OFFICE_URL=http://localhost:8080
# ที่อยู่ที่ document server ใช้เรียก File Center (ชื่อคอนเทนเนอร์ ไม่ใช่ localhost)
OFFICE_INTERNAL_URL=http://file-center:3000
# ที่อยู่ที่ File Center ใช้ดาวน์โหลดไฟล์ที่บันทึก (ไม่ตั้ง = OFFICE_URL)
OFFICE_SERVER_INTERNAL_URL=http://onlyoffice
```

- `OFFICE_URL` ต้องเป็น `https://` (ยกเว้น `http://localhost` / `127.0.0.1` ใช้ในเครื่องเดียว) ค่าไม่ถูกต้องระบบยังเปิดได้ แต่จะเตือนใน log และปิดการแก้ไขเอกสารไว้
- คอนเทนเนอร์ `onlyoffice` เปิดพอร์ตที่ `127.0.0.1:8080` เท่านั้น (เปลี่ยนด้วย `OFFICE_PORT`) และได้ `JWT_SECRET` จาก `OFFICE_JWT_SECRET` เดียวกันอัตโนมัติ
- **ผ่าน Cloudflare Tunnel ต้องมี hostname ที่สอง** เพราะเบราว์เซอร์ของผู้ใช้โหลดโปรแกรมแก้ไขจาก document server โดยตรง: ในหน้า tunnel > Public Hostname > Add
  Subdomain `office` · Service `HTTP` · URL `onlyoffice:80` แล้วตั้ง `OFFICE_URL=https://office.โดเมนของคุณ` (ไม่ต้องเปิดพอร์ตเพิ่ม)
- รันด้วย bun โดยตรง (ไม่ใช้ Docker): ติดตั้ง document server เอง เปิด JWT ด้วยความลับเดียวกัน และตั้ง `OFFICE_INTERNAL_URL` เป็นที่อยู่ที่เครื่องนั้นเรียกถึง File Center ได้

**ทำงานอย่างไร:** หน้าเว็บขอ `POST /api/office/config` `{ space, path, mode: "edit" | "view" }` (ต้องเข้าสู่ระบบ ดูต้องมีสิทธิ์ `read` + `download` แก้ต้องมี `write` ด้วย
ไฟล์ไม่เกิน `OFFICE_MAX_SIZE` ค่าเริ่มต้น 100 MB) ได้ `{ apiUrl, config }` ซึ่งเป็น config ของ ONLYOFFICE ที่เซ็นด้วย `OFFICE_JWT_SECRET` (`config.token`)
แล้ว document server ติดต่อ File Center เอง ไม่ใช้ cookie ของผู้ใช้: ดาวน์โหลดไฟล์จาก `GET /api/office/file/:token` และส่งไฟล์ที่บันทึกกลับมาทาง `POST /api/office/callback/:token`
`GET /api/session` บอกผู้ที่เข้าสู่ระบบใน `config.office: { enabled, edit: [...], view: [...] }` ว่าเปิดไฟล์นามสกุลไหนได้

- **บันทึก:** เมื่อทุกคนปิดเอกสาร (หรือกดบันทึกแบบ force save) document server ส่งไฟล์ใหม่มา ระบบเก็บ **ฉบับเดิมเป็นเวอร์ชันของไฟล์ก่อน** (กู้คืนได้ที่ `/api/versions`; ถ้าปิดเวอร์ชันด้วย `VERSIONS_KEEP=0` จะย้ายไปถังขยะแทน)
  แล้ววางไฟล์ใหม่แทนที่ในครั้งเดียว (ไม่มีช่วงที่ไฟล์เขียนไม่ครบ) บันทึก `office-save` ในประวัติการใช้งาน และ `office-open` ทุกครั้งที่เปิด
- **ความปลอดภัย:** ลิงก์ที่ให้ document server มีโทเคนที่ File Center เซ็นด้วยกุญแจของตัวเอง (`office-links.key` ใน `DATA_DIR`) ระบุไฟล์ ผู้ใช้ โหมด และหมดอายุใน 24 ชั่วโมง
  ทุกครั้งที่ใช้ตรวจสิทธิ์ของผู้ใช้ใหม่ (ถูกถอนสิทธิ์ `write` แล้วบันทึกไม่ได้ ลิงก์แบบดูบันทึกไม่ได้เลย) document server ต้องส่ง JWT ที่เซ็นด้วย `OFFICE_JWT_SECRET` ทุกคำขอ
  ไฟล์ที่บันทึกดาวน์โหลดจาก origin ของ document server (`OFFICE_SERVER_INTERNAL_URL` / `OFFICE_URL`) เท่านั้น ไม่ตาม redirect จำกัดขนาดตาม `OFFICE_MAX_SIZE` และเวลา
  และ `Content-Security-Policy` ของหน้าเว็บเพิ่ม origin ของ `OFFICE_URL` ใน `script-src`, `frame-src`, `connect-src` เฉพาะเมื่อเปิดใช้งาน

| `ALERT_LANG` | `th` | ภาษาของการแจ้งเตือน `th` หรือ `en` |
| `ALERT_ERRORS_PER_HOUR` | 20 | แจ้งเตือนเมื่อมี error มากกว่านี้ในหนึ่งชั่วโมงที่ผ่านมา |
| `PUBLIC_URL` | ว่าง | ที่อยู่ที่คนเปิด File Center เช่น `https://files.example.com` ใช้สร้างลิงก์ในอีเมล (ต้องมีเมื่อเปิดอีเมล) ไม่เอามาจากหัว `Host` ของคำขอ |
| `SMTP_HOST` / `SMTP_PORT` | ว่าง (ปิด) / 587 | เซิร์ฟเวอร์อีเมลสำหรับส่งการแจ้งเตือนส่วนตัว (ดู การแจ้งเตือนส่วนตัว) |
| `SMTP_SECURE` | `starttls` | `starttls` (พอร์ต 587), `tls` (พอร์ต 465) หรือ `none` (ใช้ได้กับ `SMTP_HOST` ที่เป็นเครื่องนี้เท่านั้นเมื่อมีรหัสผ่าน) |
| `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | ว่าง | บัญชีเข้าสู่เซิร์ฟเวอร์อีเมล (ตั้งคู่กัน) และผู้ส่ง เช่น `File Center <files@example.com>` |
| `LINE_CHANNEL_TOKEN` / `LINE_CHANNEL_SECRET` | ว่าง (ปิด) | LINE Messaging API: Channel access token (ส่งข้อความ) และ Channel secret (ตรวจลายเซ็น webhook) |
| `LINE_GROUP_ID` | ว่าง | กลุ่ม LINE ที่รับการแจ้งเตือนระบบของผู้ดูแล (ไม่บังคับ) |
| `LINE_API_BASE` | ว่าง | **ไว้ทดสอบเท่านั้น** ชี้ไปที่เซิร์ฟเวอร์จำลองบนเครื่องนี้ (`http://127.0.0.1:<พอร์ต>`) ค่าอื่นถูกเมินและใช้ `https://api.line.me` เสมอ |
| `TRUST_PROXY` | `false` | ที่มาของ IP ผู้ใช้: `cloudflare` = หัว `CF-Connecting-IP` (Cloudflare Tunnel), `true` = ค่าสุดท้ายของ `X-Forwarded-For` (nginx/Caddy ของคุณเอง), `false` = ไม่มี proxy |

## ความปลอดภัยเพิ่มเติม

- **หัว HTTP:** หน้าเว็บและไฟล์ JS/CSS ของหน้าเว็บส่ง `Content-Security-Policy` (โหลดสคริปต์ได้เฉพาะจากเว็บนี้เอง และจาก `OFFICE_URL` เมื่อเปิด ONLYOFFICE) และ `Permissions-Policy` (ปิดกล้อง ไมโครโฟน ตำแหน่ง)
  ไฟล์ที่ดาวน์โหลดและโลโก้ใช้ policy ของตัวเองที่เข้มกว่า (`sandbox`) ไม่ถูกแทนที่ เมื่อ `SECURE_COOKIE=true` ทุกคำตอบมี `Strict-Transport-Security: max-age=31536000` ด้วย
- **เลขเวอร์ชัน:** `GET /api/health` ตอบแค่ `{ "status": "ok" }` เว้นแต่คำขอมาจากเครื่อง server เอง (ที่อยู่ของการเชื่อมต่อเป็น loopback และไม่มีหัว `X-Forwarded-For` / `CF-Connecting-IP` ที่ proxy ใส่มา) หรือจาก admin ที่เข้าสู่ระบบ
  ซึ่งได้ `version`, `release`, `boot`, `time` ตามเดิม (launcher และหน้าอัปเดต/กู้คืนใช้ค่าเหล่านี้) ส่วน `GET /api/session` ส่ง `config.version` ให้เฉพาะผู้ที่เข้าสู่ระบบ
- **รหัสผ่าน:** รหัสผ่านใหม่ (สร้างผู้ใช้, admin ตั้งให้, เปลี่ยนเอง) ต้องยาวอย่างน้อย 10 ตัวอักษร ห้ามมีชื่อผู้ใช้อยู่ในรหัส (ไม่สนตัวพิมพ์เล็ก/ใหญ่) ห้ามเป็นรหัสที่ใช้กันบ่อย (100 อันดับแรก และรหัสยอดนิยมที่ยาว 10 ตัวขึ้นไป เช่น `password123`, `1q2w3e4r5t` ใน `src/common-passwords.ts`)
  และห้ามเป็นตัวอักษรเดียวซ้ำกัน (`aaaaaaaaaa`) หรือเรียงตามแป้นพิมพ์/ตัวเลข/ตัวอักษร ทั้งไปและกลับ (`1234567890`, `0987654321`, `abcdefghij`, `qwertyuiop`, `asdfghjkl;`)
  รหัสผ่านเดิมที่ตั้งไว้ก่อนหน้ายังเข้าสู่ระบบได้ตามปกติ `GET /api/session` บอกความยาวขั้นต่ำใน `config.passwordMinLength`
- **ขีดจำกัดของคำขอ:** รายการในคำขอเดียว (`items` ของ batch, zip, ลบ, คัดลอก, ย้าย) ไม่เกิน 2,000 ชื่อ เกินแล้วตอบ 400 `files.bad-count` ชื่อซ้ำนับเป็นรายการเดียว และเช็กว่ามีอยู่จริงแบบ async
  คำขอ JSON ใหญ่เกิน 1 MB ตอบ 413 `request.too-big` ก่อนอ่านเนื้อหา (ยกเว้น `PUT /api/content` ที่ส่งข้อความได้ถึง 2 MB) ส่วนอัปโหลดชิ้นส่วนใช้ขีดจำกัดของตัวเอง
- **เปลี่ยนรหัสผ่าน:** `POST /api/password` ใส่รหัสผ่านปัจจุบันผิดนับรวมในตัวนับเดียวกับการยืนยันรหัสผ่านก่อนทำงานอันตราย (`auth.confirm-locked` 429 พร้อมแจ้งเตือน)
- **บันทึก `login-failed`:** เขียนไม่เกินนาทีละครั้งต่อ IP + ชื่อผู้ใช้ พร้อมจำนวนครั้ง กันบันทึกกิจกรรมถูกท่วม
- **อัปโหลดของผู้เยี่ยมชม:** ถ้าเปิดสิทธิ์ `upload` ให้ผู้เยี่ยมชม ผู้เยี่ยมชมทุกคนใช้โควตารวมกันวันละ `GUEST_UPLOAD_DAILY_BYTES` (ค่าเริ่มต้น 1 GB, `0` = ห้ามอัปโหลด)
  ระบบนับขนาดไฟล์ตั้งแต่ตอนเริ่มอัปโหลด (อัปโหลดพร้อมกันหลายไฟล์จึงเกินโควตาไม่ได้) และคืนให้เมื่อยกเลิกหรือไม่อัปโหลดจนเสร็จ (ถูกลบตาม `UPLOAD_STALE_HOURS`)
  เกินโควตาจะได้ 429 ยอดที่ใช้เก็บใน `guest-uploads.json` ใน `DATA_DIR` จึงไม่หายเมื่อรีสตาร์ต และเริ่มนับใหม่ทุกวัน (ตามเวลาเครื่อง) ผู้ที่เข้าสู่ระบบไม่ถูกจำกัด

## อุปกรณ์ที่เข้าสู่ระบบและการยืนยันสองขั้นตอน (2FA)

- **อุปกรณ์:** `GET /api/sessions` แสดงอุปกรณ์ที่เข้าสู่ระบบอยู่ของตัวเอง (`id`, `ip`, `ua`, `created`, `seen`, `current`) เรียงใหม่สุดก่อน session ที่สร้างก่อนมีรายการนี้แสดง `ip`/`ua` เป็น `unknown` และไม่มีใครถูกออกจากระบบเพราะการอัปเกรด
  `DELETE /api/sessions/:id` ออกจากระบบอุปกรณ์นั้น (ถ้าเป็นเครื่องที่ใช้อยู่ก็เท่ากับออกจากระบบ), `POST /api/sessions/revoke-others` เก็บไว้เฉพาะเครื่องนี้ admin ดูและเพิกถอนทุกอุปกรณ์ของผู้ใช้ได้ที่ `GET /api/admin/users/:username/sessions` และ `POST .../sessions/revoke` (การเพิกถอนนี้ **ลบรหัสผ่านแอป WebDAV ของผู้ใช้ด้วย** คำตอบมี `appPasswords` = จำนวนที่ลบ และบันทึกในประวัติการใช้งาน)
- **เปิด 2FA (TOTP, RFC 6238):** ใช้กับแอป authenticator ทั่วไป (รหัส 6 หลัก เปลี่ยนทุก 30 วินาที ยอมรับรหัสก่อนและหลังหนึ่งช่วง)
  `POST /api/2fa/setup { password }` ได้ `{ secret, uri }` (uri เป็น `otpauth://` ที่ใช้ชื่อแอปจากหน้าตั้งค่าเป็น issuer) → `POST /api/2fa/enable { code }` ได้ `{ backupCodes }` 10 รหัส (`xxxx-xxxx`) **แสดงครั้งเดียว** และอุปกรณ์อื่นของผู้ใช้จะถูกออกจากระบบ
  ปิดด้วย `POST /api/2fa/disable { password, code }` ขอรหัสสำรองชุดใหม่ด้วย `POST /api/2fa/backup-codes { password, code }` (`code` เป็นรหัสจากแอปหรือรหัสสำรองก็ได้) ใส่รหัสผิดซ้ำจะถูกล็อกเหมือนการใส่รหัสผ่านผิด
- **เข้าสู่ระบบ:** ผู้ใช้ที่เปิด 2FA ใส่รหัสผ่านถูกแล้วจะ **ยังไม่ได้ session** ได้เพียง `{ twoFactor: true, ticket }` (ticket ใช้ได้ครั้งเดียว 5 นาที ผูกกับผู้ใช้และ IP) แล้วส่ง `POST /api/login/2fa { ticket, code }` รหัสผิดซ้ำถูกล็อกตาม `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_SECONDS` และแจ้งเตือนผู้ดูแล
  รหัส TOTP ใช้ได้ครั้งเดียว (ใช้ซ้ำไม่ได้แม้ยังอยู่ในช่วงเวลา) รหัสสำรองใช้ได้ครั้งเดียวแล้วถูกลบ
- **ความลับของ 2FA:** เก็บใน `users.json` แบบเข้ารหัส (AES-256-GCM) ด้วยกุญแจ `secret.key` ใน `DATA_DIR` (สร้างเองครั้งแรกที่ใช้ สิทธิ์ `0600`) ส่วนรหัสสำรองเก็บเฉพาะค่าแฮช
  **ไฟล์สำรองข้อมูลไม่มี `secret.key`** (ถ้าอยู่ในไฟล์เดียวกับ `users.json` ใครได้ไฟล์สำรองไปก็ถอดความลับ 2FA ได้) ให้เก็บสำเนา `secret.key` แยกไว้ที่ปลอดภัยเอง
  **ถ้าติดตั้งเครื่องใหม่ ต้องวาง `secret.key` เดิมไว้ใน `DATA_DIR` เองจึงจะใช้ 2FA เดิมได้** ถ้าไม่มีกุญแจนี้รหัส 2FA ของทุกคนใช้ไม่ได้ ให้ล้างด้วย `bun src/cli.ts reset-2fa <user>` แล้วให้แต่ละคนเปิด 2FA ใหม่
- **ลืมโทรศัพท์และรหัสสำรอง:** admin รีเซ็ตให้ที่ `POST /api/admin/users/:username/2fa/reset { password }` (ใส่รหัสผ่านของ admin เอง) หรือที่เครื่อง server:
  ```bash
  bun src/cli.ts reset-2fa <ชื่อผู้ใช้>         # ปิด 2FA ของผู้ใช้และออกจากระบบทุกอุปกรณ์
  bun src/cli.ts sessions-revoke <ชื่อผู้ใช้>   # ออกจากระบบทุกอุปกรณ์ และลบรหัสผ่านแอป WebDAV ของผู้ใช้ (บอกจำนวนในผลลัพธ์)
  docker compose exec file-center bun src/cli.ts reset-2fa admin   # แบบ Docker
  ```
  คำสั่งทำงานกับ `DATA_DIR` เดียวกับแอป เขียนประวัติการใช้งาน (ผู้ใช้ `cli`) และจบด้วยรหัส 1 ถ้าไม่พบผู้ใช้ **ไม่ต้องรีสตาร์ตแอป:** คำสั่งแตะไฟล์ `cli-changed` ใน `DATA_DIR` เมื่อเสร็จ แอปที่เปิดอยู่เห็นแล้วอ่าน `users.json` และ `sessions.json` ใหม่ในคำขอถัดไป
  (ไฟล์นี้ไม่ถูกสำรอง)

## Log ของระบบ

error และเหตุการณ์สำคัญของระบบเขียนลงไฟล์ ไม่หายไปพร้อมคอนเทนเนอร์ ผู้ดูแลดูได้จากหน้าเว็บโดยไม่ต้องเข้าเครื่อง server

- `logs/system.log` ใน `DATA_DIR` บรรทัดละหนึ่งรายการแบบ JSON `{ ts, level, event, detail }` (`level` = `info` / `warn` / `error`) และยังพิมพ์ออก stdout (`docker compose logs`) เหมือนเดิม
  มี error ที่ไม่มีใครดักไว้ (`unhandledRejection` บันทึกแล้วทำงานต่อ, `uncaughtException` บันทึกแล้วปิดโปรเซสให้ launcher เริ่มใหม่) และ error ระหว่างตอบคำขอ (500), สำรอง/กู้คืนข้อมูลล้มเหลว, เขียนไฟล์ข้อมูลไม่ได้ ฯลฯ
- `logs/launcher.log` เขียนโดย launcher: เริ่มระบบ, รีสตาร์ต, ย้อนกลับเวอร์ชัน, ระบบหยุดทำงาน (crash)
- `logs/access.log` เฉพาะเมื่อตั้ง `ACCESS_LOG=true` (ปิดไว้โดยค่าเริ่มต้น)
- ทุกไฟล์หมุนเมื่อใหญ่ถึง `LOG_MAX_BYTES` (`system.log` → `system.log.1` → ...) เก็บไว้ `LOG_MAX_FILES` ไฟล์ ส่วนประวัติการใช้งาน `audit.log` หมุนแบบเดียวกันที่ 10 MB × 10 ไฟล์
- **ไม่มีความลับใน log:** ไม่บันทึกรหัสผ่าน, cookie, CSRF token, โทเคนใน `/api/batch/:token`, ในลิงก์แชร์ (`/api/s/:token`, `/s/:token`) และในลิงก์ของ ONLYOFFICE (`/api/office/file/:token`, `/api/office/callback/:token`), รหัสการอัปโหลด และ query string ของ URL (ตัดออกก่อนเขียน ทั้งในไฟล์และ stdout)
  ข้อยกเว้นเดียวคือรหัสผ่าน admin ที่สุ่มให้ตอนเริ่มครั้งแรก ซึ่งแสดงบน stdout เท่านั้น ไม่ลงไฟล์
- หน้าภาพรวม (`GET /api/admin/status`) เตือน "มี error N รายการใน 24 ชั่วโมงที่ผ่านมา" เมื่อมี error (และส่งการแจ้งเตือนเมื่อเกิน `ALERT_ERRORS_PER_HOUR` ต่อชั่วโมง ดู การแจ้งเตือน)
- `system.log` ปัจจุบันรวมอยู่ในไฟล์สำรองข้อมูลด้วย

## การแจ้งเตือน

ระบบส่งข้อความสั้น ๆ ถึงผู้ดูแลทาง Discord, Slack, Telegram หรือ webhook ใด ๆ ที่รับ JSON เมื่อมีเรื่องที่ต้องดู:

- สำรองข้อมูลไม่สำเร็จ (ทั้งอัตโนมัติและที่กดเอง) พร้อมสาเหตุ
- error มากกว่า `ALERT_ERRORS_PER_HOUR` (ค่าเริ่มต้น 20) ในหนึ่งชั่วโมงที่ผ่านมา (ตรวจทุก 5 นาที)
- บัญชีหรือลิงก์แชร์ถูกล็อกเพราะใส่รหัสผ่านผิดซ้ำ: เข้าสู่ระบบ, ยืนยันรหัสผ่านก่อนติดตั้งอัปเดต/กู้คืน, ปลดล็อกลิงก์แชร์ (บอกชื่อผู้ใช้หรือรหัสลิงก์ และ IP แบบเดียวกับประวัติการใช้งาน)
- ดิสก์เหลือน้อยขั้นวิกฤต (เกณฑ์เดียวกับคำเตือนในหน้าภาพรวม ต่ำกว่า 5%) (ตรวจทุก 5 นาที)
- มีเวอร์ชันใหม่ที่ `UPDATE_SOURCE` (หนึ่งครั้งต่อเวอร์ชัน)

ตั้งใน `.env` แล้วรีสตาร์ต (`docker compose up -d`):

```env
ALERT_WEBHOOK_URL=https://discord.com/api/webhooks/<id>/<token>
ALERT_WEBHOOK_KIND=discord        # slack: URL ของ Incoming Webhook, json: ส่ง { event, code, message, params, lang, version, time }
# Telegram: ALERT_WEBHOOK_KIND=telegram, ALERT_WEBHOOK_URL=https://api.telegram.org/bot<token>/sendMessage, ALERT_TELEGRAM_CHAT_ID=<chat id>
ALERT_LANG=th
```

- แต่ละเรื่องส่งไม่เกินชั่วโมงละครั้ง ส่งเบื้องหลัง รอไม่เกิน 10 วินาที ไม่ตาม redirect ส่งไม่สำเร็จแค่บันทึก `alert-failed` (warn) ใน log ไม่ทำให้คำขอใดช้าหรือล้มเหลว
- ข้อความมาจากรายการข้อความ (`src/messages.ts`) ตาม `ALERT_LANG` และผ่านการตัดความลับแบบเดียวกับ log: ไม่มีรหัสผ่าน โทเคน หรือ cookie
  ชื่อที่ผู้เยี่ยมชมพิมพ์มา (เช่น ชื่อผู้ใช้ที่ login ผิด) เรียก `@everyone` ใน Discord หรือ `<!channel>` ใน Slack ไม่ได้
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) URL ของ webhook และ Telegram มีโทเคนอยู่ในตัว หน้าเว็บและ log จึงแสดงแค่ชื่อโฮสต์
- `GET /api/admin/alerts` ตอบ `{ enabled, kind, host, lastSent: { <เรื่อง>: เวลา } }` · `POST /api/admin/alerts/test` ส่งข้อความทดสอบทันที ตอบ `{ ok: true }` หรือ error ที่บอกสาเหตุ
  (`admin.alert-off`, `admin.alert-status`, `admin.alert-timeout`, `admin.alert-unreachable`) และบันทึก `alert-test` ในประวัติการใช้งาน (เฉพาะ admin)

## การแจ้งเตือนส่วนตัว (กระดิ่ง อีเมล LINE)

ต่างจาก "การแจ้งเตือน" ของผู้ดูแลด้านบน อันนี้ส่งถึงผู้ใช้แต่ละคน (ตั้งแต่ 1.10) เห็นเฉพาะของตัวเอง เก็บไว้ที่ `data/notifications.json` คนละไม่เกิน 100 รายการ (เก่าสุดหลุดก่อน)
ระบบเก็บแค่ชนิดกับค่าที่เกี่ยวข้อง ข้อความเขียนตอนอ่านตามภาษาของผู้อ่าน และไม่มีโทเคนของลิงก์แชร์ รหัสผ่าน หรือลิงก์ลับอยู่ในข้อความใด ๆ (ลิงก์ในข้อความเป็นพาธในแอป เช่น `/links`, `/files?path=...`)

| ชนิด | ส่งเมื่อ |
|---|---|
| `upload-received` | มีคนอัปโหลดไฟล์ผ่านลิงก์รับไฟล์ของฉันเสร็จ (บอกเฉพาะเจ้าของลิงก์) |
| `link-expiring` | ลิงก์แชร์ของฉันจะหมดอายุภายใน 24 ชั่วโมง (ตรวจรายชั่วโมง ครั้งเดียวต่อลิงก์ ลิงก์ที่ตั้งไว้ 1 วันไม่แจ้ง เพราะเจ้าของรู้อยู่แล้ว) |
| `link-limit-reached` | ลิงก์แชร์ของฉันถูกดาวน์โหลดครบจำนวนที่ตั้งไว้ |
| `quota-low` | พื้นที่ของฉันใช้เกิน 90% ของโควตา (ครั้งเดียวจนกว่าจะต่ำกว่า 90% แล้วเกินอีก) |
| `folder-shared` | มีคนแชร์โฟลเดอร์ให้ฉัน (แชร์ให้กลุ่ม = สมาชิกทุกคนยกเว้นผู้แชร์) |
| `group-added` | ฉันถูกเพิ่มเข้ากลุ่ม (ลิงก์ `/groups/<id>`; เปลี่ยนสิทธิ์ในกลุ่มไม่แจ้ง) |
| `system-alert` | (admin) สิ่งเดียวกับที่ส่งไป webhook ของผู้ดูแล: สำรองข้อมูลล้มเหลว, error มาก, บัญชีถูกล็อก, ดิสก์วิกฤต, มีเวอร์ชันใหม่ ชั่วโมงละครั้งต่อเรื่อง แม้ไม่ได้ตั้ง `ALERT_WEBHOOK_URL` |

ผู้ใช้เลือกต่อชนิดและต่อช่องทาง (`web` กระดิ่ง · `email` · `line`) ค่าเริ่มต้นเปิดเฉพาะกระดิ่ง ส่งทางอีเมลและ LINE เป็นงานเบื้องหลัง ไม่ทำให้คำขอใดช้า ลองใหม่ได้ 3 ครั้งแล้วเลิก (บันทึก `notify-delivery-failed` ใน log โดยไม่มีที่อยู่อีเมลหรือโทเคน)
คิวอยู่ในหน่วยความจำ รีสตาร์ตแล้วข้อความที่ยังไม่ได้ส่งหายไป (กระดิ่งยังอยู่)

### อีเมล

```env
PUBLIC_URL=https://files.example.com   # ใช้สร้างลิงก์ยืนยันในอีเมล
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=starttls                   # หรือ tls (พอร์ต 465) / none (เฉพาะเซิร์ฟเวอร์ในเครื่องนี้)
SMTP_USER=files@example.com
SMTP_PASS=รหัสผ่านหรือ app password
SMTP_FROM=File Center <files@example.com>
```

- ไม่ตั้ง `SMTP_HOST` = ไม่ส่งอีเมล ค่าที่ใช้ไม่ได้ ระบบยังเปิดได้แต่ปิดอีเมลและเตือนใน log ตอนเริ่ม
- ใช้ SMTP client ในตัว (`src/mail.ts`, ไม่มีไลบรารีเพิ่ม): EHLO, STARTTLS หรือ TLS ทันที, AUTH PLAIN/LOGIN, ตรวจใบรับรองของเซิร์ฟเวอร์ รหัสผ่านส่งผ่านการเข้ารหัสเท่านั้น (หรือไปยังเครื่องนี้)
  หัวจดหมายกัน CR/LF (ที่อยู่หรือหัวเรื่องที่มีขึ้นบรรทัดใหม่ถูกปฏิเสธ) หัวเรื่องภาษาไทยเข้ารหัส RFC 2047 เนื้อความ UTF-8 แบบ base64
- ผู้ใช้ตั้งอีเมลที่ `PUT /api/me/email` ระบบส่งลิงก์ยืนยัน (โทเคนสุ่ม เก็บแบบแฮช ใช้ได้ 24 ชั่วโมง ใช้ได้ครั้งเดียว) **ก่อนยืนยัน ไม่มีจดหมายอื่นถูกส่งไปที่อยู่นั้น**
- จำกัดต่อผู้ใช้: แจ้งเตือนไม่เกิน 20 ฉบับต่อชั่วโมง และลิงก์ยืนยันไม่เกิน 1 ฉบับต่อ 2 นาที (โควตาของอีเมลยืนยันแยกจากอีเมลแจ้งเตือน แจ้งเตือนท่วมแล้วก็ไม่กินโควตาของการยืนยัน) การอัปโหลดผ่านลิงก์รับไฟล์เดียวกันภายใน 10 นาทีรวมเป็นรายการเดียวในระฆัง (ยังไม่อ่าน: `params.n` = จำนวนไฟล์, `size` = ขนาดรวม, `file` = ไฟล์ล่าสุด) และส่งอีเมล/LINE ไม่เกิน 1 ครั้งต่อลิงก์ต่อ 10 นาที ชื่อไฟล์จากผู้เยี่ยมชมถูกตัดเหลือ 80 ตัวอักษรในข้อความ

### LINE

LINE Notify เลิกให้บริการแล้ว ระบบจึงใช้ LINE Messaging API (บอท) ส่งข้อความ:

1. ไปที่ [LINE Developers Console](https://developers.line.biz/console/) สร้าง Provider แล้วสร้างช่องทาง **Messaging API** (ต้องมี LINE Official Account)
2. แท็บ **Messaging API** กด Issue ที่ *Channel access token (long-lived)* ใส่ใน `LINE_CHANNEL_TOKEN` และแท็บ **Basic settings** คัดลอก *Channel secret* ใส่ใน `LINE_CHANNEL_SECRET`
3. ที่ **Webhook URL** ใส่ `https://<โดเมนของคุณ>/api/line/webhook` (ต้องเป็น https ที่ LINE เรียกถึงได้ เช่นผ่าน Cloudflare Tunnel) กด Verify แล้วเปิด **Use webhook**
   ปิด *Auto-reply messages* และ *Greeting messages* ที่ LINE Official Account Manager เพื่อไม่ให้ตอบซ้ำ
4. เพิ่มบอทเป็นเพื่อนด้วย QR code ในแท็บ Messaging API
5. (ไม่บังคับ) ส่งการแจ้งเตือนระบบของ admin เข้ากลุ่ม: เชิญบอทเข้ากลุ่ม แล้วใส่ group id ใน `LINE_GROUP_ID` (ได้จาก `source.groupId` ของ event ที่ webhook รับ)

ผู้ใช้เชื่อมบัญชีเอง: `POST /api/me/line/link` ได้รหัส 6 หลัก ใช้ได้ 10 นาที → ส่งรหัสนั้นให้บอทในแชต → webhook จับคู่ LINE ของผู้ส่งกับบัญชี (บอทตอบกลับ) · `DELETE /api/me/line` ยกเลิก (บล็อกหรือลบบอทก็ยกเลิกให้)
webhook รับเฉพาะคำขอที่ลายเซ็น `X-Line-Signature` (HMAC-SHA256 ด้วย Channel secret) ถูกต้อง นอกนั้น 401 ไม่ต้องมี CSRF token เพราะไม่มี session · เดารหัสผิด 5 ครั้งจาก LINE เดียวจะถูกเมิน
ที่อยู่ปลายทางคงที่ที่ `https://api.line.me` ไม่มีทางให้ผู้ใช้กำหนด host
ข้อความ LINE ถึงผู้ใช้แต่ละคนไม่เกิน 30 ข้อความต่อชั่วโมง (ที่เหลือยังอยู่ในระฆัง)

### API (ต้องเข้าสู่ระบบ ผู้เยี่ยมชมได้ 401)

| | |
|---|---|
| `GET /api/me/notifications?unreadOnly=true` | `{ items: [{ id, kind, at, read, text, params, link }], unread }` ใหม่สุดก่อน `text` ตามภาษาของคำขอ (`X-Lang`) `unread` นับทั้งหมด ไม่ขึ้นกับ `unreadOnly` |
| `POST /api/me/notifications/read` | `{ ids?: string[] }` ไม่ใส่ = ทั้งหมด → `{ ok, unread }` |
| `DELETE /api/me/notifications/:id` | ลบของตัวเอง ของคนอื่นหรือไม่มี → 404 `notify.not-found` |
| `GET /api/me/notify-prefs` | `{ lang, email: { enabled, address, verified }, line: { enabled, linked }, events: { <ชนิด>: { web, email, line } } }` |
| `PUT /api/me/notify-prefs` | `{ lang?: "th"\|"en", events?: { <ชนิด>: { web?, email?, line? } } }` เปลี่ยนเฉพาะที่ส่ง → ตอบเหมือน GET ชนิดไม่รู้จัก 400 `notify.bad-kind` |
| `PUT /api/me/email` · `DELETE /api/me/email` | `{ address }` → `{ address, verified: false }` และส่งลิงก์ยืนยัน (400 `notify.bad-address`, 409 `notify.email-off`, 429 `notify.verify-too-soon` / `notify.mail-limit`) |
| `GET /api/me/email/verify?token=` | ลิงก์ในอีเมล: เปิดจากโปรแกรมอีเมลได้ redirect ไป `/?emailVerified=1` (หรือ `=0` ถ้าโทเคนใช้ไม่ได้) ถ้าเรียกด้วย fetch (มีหัว `X-Lang` หรือ `Accept: application/json`) ได้ JSON `{ ok, username }` หรือ 400 `notify.bad-token` |
| `POST /api/me/line/link` · `DELETE /api/me/line` | `{ code, expiresAt, ttlSeconds }` (409 `notify.line-off` ถ้ายังไม่ตั้ง LINE) · ยกเลิกการเชื่อม |
| `POST /api/line/webhook` | สำหรับ LINE เท่านั้น (ลายเซ็น ไม่ใช่ session) |

หน้าเว็บควรถามรายการแบบ `?unreadOnly=true` ทุก 30-60 วินาทีขณะแท็บเปิดอยู่ (และเมื่อกลับมาที่แท็บ) แล้วโหลดรายการเต็มเมื่อเปิดกระดิ่ง ปลายทางนี้บีบอัดผลตอบได้เพราะไม่มีความลับในนั้น

## สิทธิ์

บทบาท (รหัสที่เก็บ → ชื่อที่แสดง): `admin` → "ผู้ดูแลระบบสูงสุด" (Super admin) เห็นทุกโฟลเดอร์ (ข้อมูลเดิมไม่ต้องย้าย) /
`manager` → "ผู้ดูแล" (Admin) / `user` เห็นเฉพาะโฟลเดอร์ส่วนตัว (admin เลือกได้ ค่าเริ่มต้น `/users/<ชื่อผู้ใช้>`) /
ผู้เยี่ยมชมเห็นเฉพาะโฟลเดอร์สาธารณะ (`storage/public`)

| ทำอะไรได้ | ผู้เยี่ยมชม | user | manager | admin |
|---|---|---|---|---|
| ไฟล์ของตัวเอง + โฟลเดอร์สาธารณะ ตามสิทธิ์ที่ได้รับ | สาธารณะเท่านั้น | ใช่ | ใช่ (เหมือน user ไม่เห็นทั้ง storage) | ทั้ง storage ทุกสิทธิ์ |
| `GET /api/admin/users` (รายการผู้ใช้ทุกคน มี `manageable`) | - | - | ใช่ | ใช่ |
| สร้าง/แก้/ลบ ผู้ใช้ · รีเซ็ตรหัสผ่าน · 2FA · ดู/เพิกถอนอุปกรณ์ | - | - | เฉพาะผู้ใช้ที่ `manageable` | ทุกคน |
| กำหนดบทบาท `manager`/`admin` | - | - | ไม่ได้ | ได้ |
| ดูไฟล์ของผู้ใช้ (`space=user:<ชื่อ>`) | - | - | อ่านอย่างเดียว เฉพาะ `manageable` | อ่านอย่างเดียว ทุกคน |
| ภาพรวม `GET /api/admin/status` | - | - | ฉบับย่อ | ฉบับเต็ม |
| ประวัติการใช้งาน `GET /api/admin/activity` | - | - | เฉพาะของตัวเองและผู้ใช้ที่ `manageable` | ทั้งหมด |
| ลิงก์แชร์ `GET /api/admin/shares` + ยกเลิก `DELETE /api/shares/:id` | - | - | เฉพาะลิงก์ของผู้ใช้ที่ `manageable` (ดูลิงก์ซ้ำ `.../link` ไม่ได้) | ทั้งหมด |
| ตั้งค่า โลโก้ อัปเดต สำรอง/กู้คืน log การแจ้งเตือน ถังขยะ `admin/folders` | - | - | 403 | ใช่ |

กฎของ manager (ตรวจที่ server ทุกคำสั่ง):
- `manageable` = บทบาท `user` และโฟลเดอร์คือ `/users/<ชื่อผู้ใช้>` พอดี (ผู้ใช้ที่ admin ชี้ไปโฟลเดอร์อื่น/โฟลเดอร์ร่วม จัดการได้เฉพาะ admin) admin: ทุกคนเป็น `manageable`
- สร้าง/เลื่อนเป็น `manager` หรือ `admin` ไม่ได้ (403 `admin.role-not-allowed`) แตะ manager/admin หรือตัวเอง (รวมการเปลี่ยนบทบาทของตัวเองและการลบตัวเอง) ได้ 403 `admin.not-manageable` ผู้ใช้ที่ไม่มีอยู่ 404
- โฟลเดอร์ของผู้ใช้ที่ manager สร้างถูกบังคับเป็น `/users/<ชื่อ>` (ค่า `homedir` ที่ส่งมาถูกเมิน) `permissions` (ของโฟลเดอร์ตัวเอง) ให้ได้ทุกอย่าง และตั้ง `quotaBytes` ได้
- `publicPermissions` ให้ได้ไม่เกินของ manager เอง (ไม่งั้น 403 `admin.public-perms-exceed`) ค่าที่ผู้ใช้คนนั้นมีอยู่แล้วส่งกลับมาซ้ำได้
- ต้องใส่รหัสผ่านซ้ำเมื่อรีเซ็ต 2FA เหมือน admin (รหัสผ่านของ manager เอง)
- สร้างผู้ใช้ได้เฉพาะเมื่อ `/users/<ชื่อ>` ยังไม่มีอยู่ในดิสก์ (ไม่สนตัวพิมพ์เล็กใหญ่ ว่างหรือไม่ก็ตาม) และไม่ซ้อน/ซ้ำกับโฟลเดอร์ของบัญชีอื่น ไม่งั้น 409 `admin.home-exists` (กันการยึดโฟลเดอร์ที่ admin แชร์ไว้หรือที่เหลือจากผู้ใช้ที่ถูกลบ) และจัดการผู้ใช้ได้เฉพาะเมื่อไม่มีบัญชีอื่นใช้โฟลเดอร์เดียวกัน อยู่ในนั้น หรืออยู่เหนือมัน
- ตั้งรหัสผ่านใหม่ให้ผู้ใช้ (`PUT /api/admin/users/:username` พร้อม `password`) ต้องส่ง `confirmPassword` เป็นรหัสผ่านของ manager เอง (ผิด 403) ผู้ใช้ต้องเปลี่ยนรหัสผ่านเมื่อเข้าสู่ระบบครั้งหน้า และบันทึกเป็น `user-password-reset`
- `GET /api/admin/users` ของบัญชีที่จัดการไม่ได้ตอบเพียง `{ username, name, role, manageable: false }`
- การเปิดดูโฟลเดอร์ในพื้นที่ `user:<ชื่อ>` (`list`, `search`) บันทึกเป็น `browse` (ซ้ำโฟลเดอร์เดิมภายใน 1 นาทีบันทึกครั้งเดียว)
- admin คนสุดท้ายลบหรือลดบทบาทไม่ได้ (400 `admin.last-admin`)

หน้าเว็บของ manager (ชื่อที่แสดง: "ผู้ดูแล" / Admin, admin = "ผู้ดูแลระบบสูงสุด" / Super admin): เมนูมีเฉพาะ ผู้ใช้ ประวัติการใช้งาน ลิงก์ที่แชร์ และภาพรวมฉบับย่อ
(ไม่มี ตั้งค่า อัปเดต สำรองข้อมูล บันทึกระบบ ถังขยะ) แถวผู้ใช้ที่ `manageable: false` แสดงเป็นอ่านอย่างเดียวพร้อมป้าย "จัดการไม่ได้" ปุ่ม "ดูไฟล์" เปิด `/admin/users/<ชื่อ>/files`
(ตัวเดียวกับหน้าไฟล์ แต่ซ่อนทุกปุ่มที่เขียนได้ตามสิทธิ์ที่ `list` ตอบกลับ) ฟอร์มผู้ใช้ของ manager เลือกได้เฉพาะบทบาท "ผู้ใช้" ไม่มีช่องโฟลเดอร์ และติ๊กสิทธิ์โฟลเดอร์สาธารณะได้เท่าที่ manager มีเอง
ปุ่มส่งออก CSV ของประวัติการใช้งานและการคัดลอก/เปิดลิงก์ของคนอื่นเป็นของ admin เท่านั้น

### ดูไฟล์ของผู้ใช้แบบอ่านอย่างเดียว (`space=user:<ชื่อผู้ใช้>`)

ใช้ route ไฟล์เดิมทั้งหมดโดยส่ง `space=user:ubob` (ชื่อไม่สนตัวพิมพ์): `GET /api/list` · `/folders` · `/search` · `/content` · `/download` (รวม `inline=1`) · `POST /api/batch` + `GET /api/batch/:token` · `GET /api/versions...`
สิทธิ์ใน space นี้มีเพียง `read, download, batchdownload, zip` (คำตอบของ `/api/list` มี `permissions`) คำสั่งเขียนทุกตัว (mkdir, newfile, PUT content, rename, copy, move, delete, zip, unzip, upload, shares, office, favorites) ได้ 403 รวมถึงการคัดลอกออกจาก space นี้ไปโฟลเดอร์ตัวเอง
ถ้า manager ไม่มีสิทธิ์จัดการเจ้าของ (ไม่มีผู้ใช้ เป็น manager/admin โฟลเดอร์ไม่ใช่ `/users/<ชื่อ>`) หรือเป็น user/ผู้เยี่ยมชม ได้ 403 (ผู้เยี่ยมชม 401) path ที่หลุดออกนอกโฟลเดอร์นั้นได้ 400/403 เหมือน space ปกติ
ทุกการอ่านที่มีผลกับไฟล์ถูกบันทึกในประวัติการใช้งาน: `download` (รวมพรีวิว), `download-zip`, และ `view` (อ่านไฟล์ข้อความ `GET /api/content`) โดย `detail` บอก `user:<ชื่อ>` (การดูรายการและค้นหาไม่บันทึก) ไฟล์ที่เปิดไม่ถูกจำใน "ล่าสุด"/"รายการโปรด"

`GET /api/admin/status` ของ manager ตอบเฉพาะ `{ reduced: true, users, storage: { size }, stale, warnings }` (`users` และ `storage` นับเฉพาะผู้ใช้ที่ manageable ส่วน `size` คือพื้นที่ที่โฮมของพวกเขาใช้) และ `warnings` มีได้เพียง `admin.default-password` นับเฉพาะผู้ใช้ที่ manageable) ไม่มีเวอร์ชัน เวลาทำงาน ดิสก์ สำรองข้อมูล ถังขยะ หรือข้อมูลอัปเดต ของ admin ตอบเหมือนเดิมพร้อม `reduced: false`
ชื่อผู้ใช้ `guest` (ไม่สนตัวพิมพ์เล็ก/ใหญ่) สงวนไว้ เพราะไฟล์ที่ผู้เยี่ยมชมอัปโหลดและประวัติของผู้เยี่ยมชมใช้ชื่อนี้ สร้างบัญชีชื่อนี้ไม่ได้ (บัญชีเดิมที่ชื่อนี้อยู่แล้วไม่ถูกเปลี่ยนชื่อ)

สิทธิ์ที่กำหนดได้: `read` ดูรายการ · `download` · `batchdownload` ดาวน์โหลดหลายไฟล์เป็น zip · `upload` ·
`write` สร้าง/แก้ไข/เปลี่ยนชื่อ/คัดลอก/ย้าย/ลบ · `zip` บีบอัดและแตกไฟล์ · `share` สร้างลิงก์แชร์ (ต้องมี `download` ในพื้นที่เดียวกันด้วย)

`share` เป็นสิทธิ์ใหม่ บัญชีเดิมยังไม่มี ผู้ดูแลต้องให้เองที่หน้าผู้ใช้ (admin แชร์ได้เสมอ ผู้เยี่ยมชมแชร์ไม่ได้ไม่ว่าตั้งสิทธิ์ผู้เยี่ยมชมไว้อย่างไร)

ผู้ใช้แต่ละคนมีชุดสิทธิ์ 2 ชุดแยกกัน คือในโฟลเดอร์ของตัวเอง และในโฟลเดอร์สาธารณะ ส่วนสิทธิ์ของผู้เยี่ยมชมตั้งที่หน้า "ตั้งค่า"
สิทธิ์ถูกตรวจที่ server ทุกคำสั่ง ไม่ใช่แค่ซ่อนปุ่มในหน้าเว็บ

## โควตาพื้นที่ต่อผู้ใช้

admin กำหนดโควตาให้ผู้ใช้แต่ละคนได้ที่ `POST /api/admin/users` และ `PUT /api/admin/users/:username` ด้วย `quotaBytes` (จำนวนไบต์เต็ม 0 ถึง 2^50,
`0` หรือไม่ตั้ง = ไม่จำกัด) ค่านี้แสดงใน `GET /api/admin/users` ด้วย

- **นับอะไร:** เฉพาะโฟลเดอร์ของผู้ใช้เอง (space `home`) **ถังขยะอยู่นอกโฟลเดอร์นั้น จึงไม่นับ** ลบไฟล์แล้วพื้นที่ว่างคืนทันที
  แต่กู้คืนจากถังขยะก็นับกลับเข้าไปใหม่และอาจถูกปฏิเสธถ้าเต็ม โฟลเดอร์สาธารณะไม่มีโควตา และ admin (ที่โฟลเดอร์คือทั้ง storage) ไม่ถูกจำกัดแม้ตั้ง `quotaBytes`
- **ตรวจที่ไหน:** ตอนเริ่มอัปโหลด, `PUT /api/content` (นับเฉพาะส่วนที่ใหญ่ขึ้น), `/api/zip`, `/api/unzip` (งบไบต์ที่แตกได้ลดลงเหลือเท่าที่โควตาเหลือ),
  `/api/copy`, การบันทึกจาก ONLYOFFICE (นับส่วนที่ใหญ่ขึ้นของไฟล์ และเวอร์ชันเดิมที่เก็บไว้), การกู้คืนจากถังขยะ, และอัปโหลดผ่านลิงก์รับไฟล์ (นับกับเจ้าของลิงก์)
  การย้ายภายในโฟลเดอร์เดียวกันไม่เปลี่ยนยอด เต็มแล้วได้ **507** `quota.exceeded` พร้อม `params: { used, quota }` (ไบต์)
- **นับอย่างไร:** นับด้วยการเดินโฟลเดอร์ (ไม่เกิน 1,000,000 รายการ ถ้าเกินถือว่าเต็ม) เก็บผลไว้ 60 วินาทีต่อผู้ใช้ และนับใหม่ทันทีหลังลบ
  งานที่กำลังเขียนอยู่จองพื้นที่ไว้ก่อนในจังหวะเดียวกับที่ตรวจ ส่งหลายคำขอพร้อมกันจึงแย่งไบต์สุดท้ายไม่ได้ และคืนที่จองเมื่อยกเลิก ล้มเหลว หรือถูกลบเพราะค้างนาน (`UPLOAD_STALE_HOURS`)
- ผู้ใช้ดูยอดของตัวเองได้ที่ `GET /api/me/usage` → `{ used, quota, counting }` (`quota` 0 = ไม่จำกัด `counting` เป็น true ขณะกำลังนับครั้งแรกและยังไม่มีตัวเลข)

## ลิงก์แชร์

ผู้ที่เข้าสู่ระบบส่งลิงก์ให้คนที่ไม่มีบัญชีดาวน์โหลดไฟล์หรือโฟลเดอร์หนึ่งรายการได้ (ต้องมีสิทธิ์ `share` และ `download` ในพื้นที่ที่รายการนั้นอยู่)

ในหน้าเว็บ: เมนู "แชร์ลิงก์" ของไฟล์/โฟลเดอร์ (หรือแถบเครื่องมือเมื่อเลือกรายการเดียว) เลือกอายุ 1/7/30 วัน รหัสผ่าน และจำนวนครั้งได้
แล้วคัดลอกลิงก์ · หน้า "ลิงก์ที่แชร์" แสดงลิงก์ของฉันพร้อมสถานะ ปุ่ม "คัดลอกลิงก์" (กลับมาคัดลอกซ้ำได้ตั้งแต่ 1.8.1) และปุ่มยกเลิก (admin เปิดสวิตช์ดูของทุกคนได้)
· ผู้รับเปิดลิงก์ `/s/<token>` ได้โดยไม่ต้องเข้าสู่ระบบ (ลิงก์โฟลเดอร์เปิดดูโฟลเดอร์ย่อยและดาวน์โหลดเป็น zip ได้)

- สร้าง: `POST /api/shares` `{ space, path, days, password?, maxDownloads? }` อายุ `days` เป็น 1, 7 หรือ 30 วัน (ไม่เกิน `SHARE_MAX_DAYS`)
  รหัสผ่านไม่บังคับ (อย่างน้อย 6 ตัวอักษร) `maxDownloads` ไม่ใส่ = ไม่จำกัด ตอบ `{ share, token, url }`
  `shares.json` (ใน `DATA_DIR`) เก็บ SHA-256 ของโทเคนไว้หาลิงก์ และเก็บตัวโทเคนแบบเข้ารหัส (AES-256-GCM ด้วย `secret.key` แบบเดียวกับ secret ของ 2FA) ไว้ให้คัดลอกซ้ำ
  ไฟล์ `shares.json` หลุดไปอย่างเดียวจึงใช้เปิดลิงก์ไม่ได้ (`secret.key` ไม่ลงไฟล์สำรอง) รหัสผ่านเก็บแบบ hash เหมือนรหัสผ่านผู้ใช้
- ลิงก์ของฉัน `GET /api/shares` (มี `linkAvailable`) · คัดลอกซ้ำ `GET /api/shares/:id/link` → `{ token, url }` (เจ้าของหรือ admin เฉพาะลิงก์ที่ยังใช้งานได้ บันทึก `share-link-view` ลิงก์ที่สร้างก่อน 1.8.1 หรือหลังกู้คืนข้อมูลบนเครื่องที่ `secret.key` ต่างไป ตอบ 409 `share.link-unavailable`) · ยกเลิก `DELETE /api/shares/:id` (เจ้าของหรือ admin) · admin ดูทั้งหมดที่ `GET /api/admin/shares` (ไม่มี hash ในคำตอบ)
- ใช้ลิงก์ (ไม่ต้องเข้าสู่ระบบ): `GET /api/s/:token` ตอบ `{ name, type, size, expiresAt, needsPassword, entries? }` (ลิงก์โฟลเดอร์ดูข้างในได้ด้วย `?path=`
  ไม่มีทางออกนอกโฟลเดอร์ที่แชร์ และไม่แสดง/ไม่ตาม symlink) · `POST /api/s/:token/unlock` `{ password }` ตั้ง cookie อายุ 1 ชั่วโมงที่ใช้ได้กับลิงก์นั้นลิงก์เดียว
  (ไม่ต้องมี CSRF token) ใส่ผิด 5 ครั้งล็อกลิงก์นั้นสำหรับ IP นั้น 15 นาที · `GET /api/s/:token/download?path=` ส่งไฟล์ (หัวเดียวกับ `/api/download`) หรือโฟลเดอร์/โฟลเดอร์ย่อยเป็น zip
- `maxDownloads` นับเฉพาะการดาวน์โหลดที่ส่งครบ ครั้งละหนึ่ง ระหว่างดาวน์โหลดจองที่ไว้ (เริ่มพร้อมกันหลายครั้งก็เกินไม่ได้) ยกเลิกกลางทางไม่นับ
  ลิงก์ที่จำกัดจำนวนครั้งส่งทั้งไฟล์เสมอ (ไม่รับ `Range`) ลิงก์ไม่จำกัดรับ `Range` ได้ และนับเฉพาะครั้งที่ได้ทั้งไฟล์
- ลิงก์หยุดทำงานเมื่อ: หมดอายุ, ถูกยกเลิก, ดาวน์โหลดครบจำนวน, รายการถูกลบ/ย้าย/เปลี่ยนชนิด, เจ้าของถูกลบ (ลิงก์ถูกยกเลิกด้วย สร้างบัญชีชื่อเดิมใหม่ก็ไม่กลับมา)
  หรือเจ้าของไม่มีสิทธิ์ `share`/`download` ในพื้นที่นั้นแล้ว ทุกกรณีตอบ 404 `share.not-found` แบบเดียวกัน ผู้เดาลิงก์จึงไม่ได้ข้อมูลอะไร
- ประวัติการใช้งานบันทึก `share-create`, `share-download`, `share-revoke` พร้อมพาธ (ไม่บันทึกโทเคน) ลิงก์ที่หมดอายุถูกลบออกจาก `shares.json` ตอนเริ่มระบบและวันละครั้ง

### ลิงก์รับไฟล์ (ให้คนนอกอัปโหลดเข้าโฟลเดอร์)

`POST /api/shares` ใส่ `kind: "upload"` ได้เฉพาะ **โฟลเดอร์** และต้องมีสิทธิ์ `share` กับ `upload` ในพื้นที่นั้น (ลิงก์ที่ไม่มี `kind` คือลิงก์ดาวน์โหลดเหมือนเดิมทุกประการ)
ตัวเลือก (ไม่บังคับทั้งหมด): `maxFileBytes` (ไม่เกิน `UPLOAD_MAX_SIZE`), `maxFiles`, `maxTotalBytes` (ไม่เกิน 2^50), `note` (ข้อความถึงผู้อัปโหลด ไม่เกิน 500 ตัวอักษร แสดงเป็นข้อความธรรมดา),
`days` และ `password` เหมือนลิงก์ดาวน์โหลด (cookie ปลดล็อกและการล็อกเมื่อใส่ผิดเหมือนเดิม) สิทธิ์ของเจ้าของถูกตรวจใหม่ทุกครั้งที่ใช้ลิงก์ ถ้าเสียสิทธิ์ `share`/`upload` ลิงก์หยุดทันที

- `GET /api/s/:token` ของลิงก์รับไฟล์ตอบชื่อโฟลเดอร์ ข้อจำกัด note จำนวนที่รับแล้ว และ `mine` (ไฟล์ที่ผู้เยี่ยมชมคนนี้ส่งเอง) **ไม่เคยแสดงของที่อยู่ในโฟลเดอร์**
  เส้นทางดาวน์โหลดปฏิเสธลิงก์รับไฟล์ และเส้นทางอัปโหลดปฏิเสธลิงก์ดาวน์โหลด (404 เหมือนกรณีอื่น)
- ส่งไฟล์: `POST /api/s/:token/upload` `{ name, size }` → `{ id, chunkSize, total }` · `PUT /api/s/:token/upload/:id/:n` · `POST /api/s/:token/upload/:id/complete` · `DELETE /api/s/:token/upload/:id`
  ไฟล์ลงตรงในโฟลเดอร์ที่แชร์ (ผู้ส่งเลือกโฟลเดอร์ย่อยไม่ได้) ชื่อผ่านการตรวจชื่อปกติ ชื่อซ้ำได้ชื่อใหม่ เช่น `a (1).pdf` **ไม่เขียนทับ**
- งานอัปโหลดผูกกับลิงก์นั้นและกับผู้เยี่ยมชมคนนั้นด้วย cookie สุ่ม `fc_visitor` (HttpOnly, SameSite=Strict, ใช้ได้เฉพาะ path ของลิงก์) คนอื่นหรือลิงก์อื่นเพิ่มชิ้นส่วน จบ หรือยกเลิกไม่ได้
  เพราะไม่มี session จึงไม่ต้องใช้ CSRF token สำหรับ 4 เส้นทางนี้ (ระบุใน `src/context.ts`)
- ไบต์นับกับโควตาของเจ้าของลิงก์ (ถ้าลิงก์อยู่ใน home) และกับข้อจำกัดของลิงก์ โดยจองตั้งแต่ประกาศไฟล์ จำกัดอัปโหลดค้างพร้อมกัน 5 งานต่อลิงก์ และ 3 งานต่อ IP
  ลิงก์ที่ไม่ได้กำหนดข้อจำกัดใช้ค่าเริ่มต้น `UPLOAD_REQUEST_MAX_FILE` / `UPLOAD_REQUEST_MAX_TOTAL` ลิงก์ในพื้นที่ public หรือของผู้ใช้ที่ไม่มีโควตา (รวมผู้ดูแล) นับกับโควตารายวันของผู้เยี่ยมชม (`GUEST_UPLOAD_DAILY_BYTES`) เหมือนการอัปโหลดแบบไม่ล็อกอิน
  งานที่ประกาศแล้วแต่ไม่มีชิ้นใหม่เกิน `UPLOAD_REQUEST_IDLE_MINUTES` ถูกลบและคืนที่ว่างของลิงก์ ประวัติการใช้งานบันทึก `share-upload` (เจ้าของ รหัสลิงก์ ชื่อไฟล์ ขนาด) ลิงก์เก็บแค่แฮชของ cookie ผู้ส่ง ไม่เก็บตัว cookie

## ถังขยะของผู้ใช้เอง

การลบยังย้ายไปถังขยะกลางเหมือนเดิม (admin ดูและกู้คืนได้ที่ `/api/admin/trash`) แต่แต่ละรายการจดเพิ่ม `owner` (ผู้ใช้ที่โฟลเดอร์ของเขาเก็บรายการนั้นอยู่; `null` = โฟลเดอร์สาธารณะหรือที่อื่น) และ `space` (`home` / `public` / `other`)
รายการเก่าที่ไม่มีสองค่านี้หา `owner` จาก `originalPath` ตอนอ่าน (ไม่นับบัญชีที่สร้างหลังเวลาที่รายการถูกลบ) เมื่อลบบัญชีผู้ใช้ รายการในถังขยะที่เป็นของเขาหรือที่เขาลบ (`owner`, `deletedBy`) จะถูกเปลี่ยนเป็นชื่อ `~<ชื่อ>@<เวลา>` ซึ่งไม่มีบัญชีไหนใช้ได้ (`~` ใช้ในชื่อผู้ใช้ไม่ได้) บัญชีใหม่ชื่อเดิมจึงไม่เห็น เหลือเฉพาะ admin ที่ `/api/admin/trash` ผู้ใช้เห็นได้เฉพาะ

- รายการที่ **ตัวเองเป็นเจ้าของ** (ลบโดยใครก็ตาม รวมถึงผู้รับแชร์ที่ลบในโฟลเดอร์ที่ได้รับ) หรือ
- รายการที่ **ตัวเองลบ** และที่เดิมยังอยู่ใน space ที่ตัวเองเขียนได้ตอนนี้ (home, โฟลเดอร์สาธารณะที่มี `write`, โฟลเดอร์ที่ได้รับสิทธิ์ `edit`)

| | |
|---|---|
| `GET /api/me/trash` | `{ items: [{ id, name, type, size, deletedAt, deletedBy, owner, space, path, restorable }], retentionDays }` `space`/`path` คือที่ที่จะกู้คืนไป (ใน space ของผู้เรียก) เป็น `null` และ `restorable: false` ถ้ากลับไปที่เดิมไม่ได้แล้ว (เช่นโฟลเดอร์ home ถูกย้าย) |
| `POST /api/me/trash/:id/restore` | กู้คืนไปที่เดิม ชื่อซ้ำได้ชื่อใหม่ (`name (1).ext`) เวอร์ชันเก่ากลับมาด้วย นับโควตาเหมือนการเขียนอื่น (507 `quota.exceeded`) ตอบ `{ ok, restoredTo, space, path }` ที่เดิมอยู่นอกพื้นที่ของผู้เรียก หรือไม่มี `write` ที่นั่น = 403 `trash.cannot-restore-here` |
| `DELETE /api/me/trash/:id` | ลบถาวร (ไม่ต้องใส่รหัสผ่าน) ตอบ `{ ok, removed: 1 }` ลบถาวรได้เฉพาะเจ้าของรายการ (รายการในโฟลเดอร์สาธารณะ/ที่อื่นที่ไม่มีเจ้าของ: คนที่ลบ) ผู้รับแชร์ที่ลบในโฟลเดอร์ของคนอื่นกู้คืนได้แต่ลบถาวรไม่ได้ = 403 `trash.cannot-purge` |
| `DELETE /api/me/trash` | ล้างถังขยะของตัวเอง ตอบ `{ ok, removed }` (นับเฉพาะรายการที่ลบถาวรได้ตามข้างบน) |

รายการที่ไม่ใช่ของผู้เรียกตอบ 404 เหมือนรหัสที่ไม่มีอยู่ ประวัติการใช้งานมี `trash-restore-own` และ `trash-delete-own`
`POST /api/delete` ที่ส่ง `withTrash: true` ตอบ `trashed: [{ path, id }]` เพิ่ม (หน้าเว็บใช้ทำปุ่ม "เลิกลบ" ที่เรียก restore ทันที; ไม่ส่งก็ได้คำตอบเดิม `{ done, failed }`)

## แชร์โฟลเดอร์ให้ผู้ใช้อื่นในระบบ (grants)

เจ้าของโฟลเดอร์ (ต้องมีสิทธิ์ `share` ใน home) เลือกโฟลเดอร์ของตัวเองให้ผู้ใช้อีกคนเปิดได้ เก็บใน `DATA_DIR/grants.json` ผู้รับเปิดผ่าน space `grant:<id>` ที่ใช้กับ `/api/list`, `/api/download`, `/api/upload` ฯลฯ ได้เหมือน space อื่น โดยราก (`/`) คือโฟลเดอร์ที่แชร์

- `perms: "view"` = `read`, `download`, `batchdownload`, `zip` · `"edit"` = view + `write`, `upload` ไม่มี `share` เสมอ (ผู้รับแชร์ต่อไม่ได้)
- เปิดได้เฉพาะผู้รับ (`to`) คนที่สามและเจ้าของเองได้คำตอบเหมือนรหัสที่ไม่มีอยู่ (403) สิทธิ์ตรวจใหม่ทุกครั้งที่ใช้: ถ้าเจ้าของหรือผู้รับถูกลบ เจ้าของไม่มี `share` แล้ว โฟลเดอร์ home ของเจ้าของถูกย้าย หรือโฟลเดอร์หายไป ถูกย้ายออก กลายเป็นไฟล์หรือลิงก์ สิทธิ์นั้นใช้ไม่ได้ทันที (ลบผู้ใช้ลบสิทธิ์ที่ให้และได้รับออกจากไฟล์ด้วย)
- ที่ที่ผู้รับเขียนนับโควตาของ **เจ้าของ** ไม่ใช่ของผู้รับ ของที่ผู้รับลบเข้าถังขยะของเจ้าของ (ผู้รับกู้คืนได้เองตราบที่ยังมีสิทธิ์ `edit`)
- การเปิดดูโฟลเดอร์ของผู้รับแชร์ลงประวัติ `browse` (ครั้งเดียวต่อนาทีต่อโฟลเดอร์) ส่วนดาวน์โหลด/เปิดอ่านลงประวัติพร้อม `detail` = space

| | |
|---|---|
| `POST /api/grants` `{ space: "home", path, to, perms }` | ให้สิทธิ์ (ต้องมี `share` ที่ home; `path` เป็นโฟลเดอร์จริงใน home ไม่ใช่ `/` ไม่ใช่ลิงก์) ตอบ `{ ok, created, grant }` ซ้ำ (เจ้าของ+โฟลเดอร์+ผู้รับ เดียวกัน) = แก้ `perms` (`created: false`) · จำกัด 30 ครั้งต่อนาทีต่อคน (429 `grants.create-rate`) เพื่อไม่ให้ใช้เดาชื่อผู้ใช้ · 400 `grants.to-self` / `grants.folder-only` / `grants.too-many` · 404 `admin.user-not-found` / `files.folder-not-found` |
| `GET /api/grants/mine` | `{ items: [{ id, path, name, to, toName, perms, createdAt, active }] }` สิทธิ์ที่ฉันให้ (`path` สัมพันธ์กับ home; `active: false` = ใช้ไม่ได้แล้ว ควรให้ลบ) |
| `GET /api/grants/to-me` | `{ items: [{ id, space, name, owner, ownerName, perms, createdAt }] }` โฟลเดอร์ที่ได้รับและใช้ได้อยู่ (ไม่มีพาธของเจ้าของ) |
| `PATCH /api/grants/:id` `{ perms }` | เจ้าของเท่านั้น (คนอื่น 404) |
| `DELETE /api/grants/:id` | เจ้าของยกเลิก หรือผู้รับออกจากการแชร์ (คนอื่น 404) |
| `GET /api/users/lookup?q=` | เลือกผู้รับ: ต้องเข้าสู่ระบบและมี `share` (admin ได้) `q` อย่างน้อย 3 ตัวอักษร (400 `grants.query-short`, `params.min` = 3) ค้นจากชื่อผู้ใช้และชื่อที่แสดง ตอบ `{ users: [{ username, name }] }` ไม่เกิน 10 คน ไม่รวมตัวเอง ไม่ระบุบัญชี admin/manager ให้ผู้ใช้ทั่วไป (ผู้ใช้ทั่วไปแชร์ให้เจ้าหน้าที่ได้โดยพิมพ์ชื่อผู้ใช้เต็มใน `POST /api/grants`) ไม่มีข้อมูลอื่น จำกัด 20 ครั้งต่อนาทีต่อคน (429 `grants.lookup-rate`) |

ประวัติการใช้งานมี `grant-create`, `grant-update`, `grant-delete` ในโค้ด `onGrantCreated(grant)` ใน `src/grants.ts` เรียกทุกครั้งที่สร้างสิทธิ์ใหม่ (ไม่รวมการแก้) โมดูลอื่น (เช่นการแจ้งเตือน) เพิ่มฟังก์ชันใน `grantCreatedListeners` เพื่อรับรู้

## WebDAV: เปิดไฟล์เป็นไดรฟ์ในเครื่อง (Windows, macOS, มือถือ, rclone)

File Center เปิด WebDAV ที่ `/dav/` ให้โปรแกรมในเครื่องใช้ไฟล์เหมือนไดรฟ์ธรรมดา (เปิด แก้ บันทึก ลาก วาง) โดยผ่านกติกาเดียวกับหน้าเว็บทุกอย่าง: สิทธิ์ของผู้ใช้ โควตา ถังขยะ (ลบผ่าน WebDAV ไปอยู่ในถังขยะของเจ้าของ) และเวอร์ชันของไฟล์ (บันทึกทับแล้วเก็บของเดิมไว้ ตามค่า `VERSIONS_KEEP`) ปิดทั้งหมดได้ด้วย `WEBDAV=off` (ทุกพาธใต้ `/dav` ตอบ 404 ส่วนหน้าเว็บและ API ไม่เปลี่ยน)

### รหัสผ่านแอป (app password)

WebDAV **ไม่รับรหัสผ่านบัญชีและไม่อ่าน cookie ของหน้าเว็บ** รับเฉพาะ Basic auth แบบ `ชื่อผู้ใช้:รหัสผ่านแอป` รหัสผ่านแอปทำเองได้ที่ API ด้านล่าง (ต้องใส่รหัสผ่านบัญชีอีกครั้ง) ทีละเครื่อง ทีละแอป และเพิกถอนทีละอันได้โดยไม่กระทบรหัสผ่านบัญชีหรือเครื่องอื่น

- รูปแบบ `fc-` ตามด้วยตัวอักษรและตัวเลขสุ่ม 32 ตัว **แสดงครั้งเดียวตอนสร้าง** ระบบเก็บเฉพาะแฮช (argon2id) ใน `DATA_DIR/app-passwords.json` แม้แต่ผู้ดูแลระบบก็ดูรหัสไม่ได้
- ขอบเขต (`scope`): `read` = ดูและดาวน์โหลดเท่านั้น · `readwrite` = ตามสิทธิ์ของบัญชี ขอบเขตเป็นได้แค่ตัดสิทธิ์ ไม่เพิ่มสิทธิ์เกินที่บัญชีมี
- สร้างได้คนละ 20 อัน รหัสที่ใช้เข้าได้ไม่ผ่านการยืนยันสองขั้นตอน (2FA) เพราะเป็นรหัสสุ่มแยกต่างหากที่ใช้ได้กับ WebDAV อย่างเดียว เข้า API หรือหน้าเว็บด้วยรหัสนี้ไม่ได้
- **ลบหมดทุกอัน** เมื่อบัญชีถูกลบ เมื่อผู้ใช้เปลี่ยนรหัสผ่าน และเมื่อผู้ดูแลตั้งรหัสผ่านใหม่ให้ (ลบรหัสแล้วใช้ไม่ได้ทันที)
- รหัสผิดซ้ำถูกล็อกเหมือนหน้าเข้าสู่ระบบ (ต่อ IP + ชื่อผู้ใช้ ตาม `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_SECONDS` และต่อ IP ตาม `LOGIN_ADDRESS_MAX_ATTEMPTS`) ตอบ 401 พร้อม `WWW-Authenticate: Basic realm="File Center", charset="UTF-8"` เมื่อโดนล็อกตอบ 429 พร้อม `Retry-After`
- บัญชีที่ยังต้องเปลี่ยนรหัสผ่านเริ่มต้น (`must-change-password`) ใช้ WebDAV ไม่ได้จนกว่าจะเปลี่ยน
- บันทึกการใช้ล่าสุด (`lastUsedAt`, `lastIp`) ไม่เกินนาทีละครั้ง การสร้าง ลบ อัปโหลด แก้ไข สร้างโฟลเดอร์ ลบ ย้าย และคัดลอกลงประวัติการใช้งาน (`detail` ขึ้นต้นด้วย `WebDAV`; อัปโหลดทับไฟล์เดิมซ้ำ ๆ ลงบรรทัดเดียวต่อนาทีต่อไฟล์)

| | |
|---|---|
| `GET /api/me/app-passwords` | `{ items: [{ id, name, scope, hint, createdAt, lastUsedAt, lastIp }], max: 20, enabled }` (`hint` คือ `fc-` กับอักขระ 8 ตัวแรกของรหัส ไว้แยกว่าอันไหน ไม่ใช่ตัวรหัส; `enabled: false` = `WEBDAV=off`) |
| `POST /api/me/app-passwords` `{ name, scope, password }` | `name` 1–60 ตัวอักษร · `scope` = `read` / `readwrite` · `password` = รหัสผ่านบัญชีของคุณตอนนี้ ตอบ `{ id, name, scope, hint, createdAt, lastUsedAt, lastIp, secret }` **`secret` มีเฉพาะคำตอบนี้ครั้งเดียว** · 403 `auth.wrong-password` / 429 `auth.confirm-locked` (นับรวมกับการยืนยันรหัสผ่านอื่น) · 400 `auth.app-password-bad-name` / `auth.app-password-bad-scope` / `auth.app-password-limit` |
| `DELETE /api/me/app-passwords/:id` | ลบอันของตัวเอง (ของคนอื่น = 404 `auth.app-password-not-found`) |

`GET /api/session` มี `config.webdav` (true/false) สำหรับผู้ที่เข้าสู่ระบบแล้ว ให้หน้าเว็บรู้ว่าจะแสดงส่วนนี้หรือไม่

### โครงสร้างโฟลเดอร์ใน `/dav/`

| พาธ | คืออะไร |
|---|---|
| `/dav/home/` | โฟลเดอร์ของตัวเอง (admin = ที่เก็บไฟล์ทั้งหมด) |
| `/dav/public/` | โฟลเดอร์สาธารณะ (มีเมื่อบัญชีนี้มีสิทธิ์ใช้) |
| `/dav/shared/<ชื่อโฟลเดอร์>/` | โฟลเดอร์ที่ผู้ใช้อื่นแชร์ให้ (grants) ชื่อซ้ำกันต่อท้าย ` (2)`, ` (3)` ตามลำดับที่แชร์ ถ้าไม่มีใครแชร์ให้ โฟลเดอร์นี้ไม่ปรากฏ |

ทุกพาธถูกแปลงเป็น (space, พาธใน space) แล้วผ่าน `accessFor` และ `resolveIn` เหมือน API เสมอ: สิทธิ์ `read` `download` `write` `upload` ตามจริงของ space นั้น (แชร์แบบ `view` = อ่านอย่างเดียว) และโควตา/ถังขยะนับตามเจ้าของ space เหมือนในหน้าเว็บ การเขียนทับ ย้าย คัดลอก และลบ ทำได้เฉพาะในโฟลเดอร์จริง ไม่ใช่โฟลเดอร์จัดกลุ่ม (`/dav/`, `/dav/shared/`) พาธที่มี `..`, `\`, `%2f` หรือ NUL ถูกปฏิเสธ

**ผู้พัฒนา:** โมดูลอื่นเพิ่มโฟลเดอร์ใน `/dav/` ได้ด้วย `registerDavSpace(ชื่อ, user => space | null)` (หนึ่งโฟลเดอร์ = หนึ่ง space) หรือ `registerDavFolder(ชื่อ, user => [{ name, space }])` (โฟลเดอร์ที่รวมหลาย space เช่น กลุ่มผู้ใช้: `registerDavFolder('groups', user => groupsOf(user).map(g => ({ name: g.name, space: \`group:${g.id}\` })))`) ใน `src/webdav.ts` ชื่อถูกทำให้ปลอดภัยและไม่ซ้ำให้ ถ้าไม่มี entry โฟลเดอร์นั้นไม่ปรากฏ สิทธิ์ทุกอย่างมาจาก `accessFor(user, space)`

### เชื่อมต่อจากเครื่องต่าง ๆ

ใช้ที่อยู่ `https://files.example.com/dav/home/` (แทนด้วยโดเมนของคุณ) ชื่อผู้ใช้คือชื่อบัญชี รหัสผ่านคือรหัสผ่านแอป **ควรใช้ผ่าน HTTPS เสมอ** (Basic auth ส่งรหัสไปตรง ๆ) ดู [Cloudflare Tunnel](#ใช้งานผ่านโดเมนด้วย-cloudflare-tunnel)

- **Windows** (เปิดใน File Explorer > This PC > Map network drive): ใส่ `https://files.example.com/dav/home` เลือก "Connect using different credentials" แล้วกรอกชื่อผู้ใช้กับรหัสผ่านแอป หรือใช้คำสั่ง `net use Z: https://files.example.com/dav/home /user:alice fc-xxxxxxxx...`
  - บริการ **WebClient** ต้องทำงาน (Services > WebClient > Start, Startup type = Automatic) ถ้าไม่มีบริการนี้ (Windows Server) ต้องติดตั้งฟีเจอร์ "WebDAV Redirector" ก่อน

### ข้อจำกัดที่ควรรู้

- **Cloudflare (แพ็กเกจ Free และ Pro) ตัดคำขอที่ใหญ่เกิน 100 MB** WebDAV ส่งไฟล์ทั้งไฟล์ในคำขอเดียว (หน้าเว็บแบ่งเป็นชิ้นตาม `UPLOAD_CHUNK_SIZE` จึงไม่โดน) อัปโหลดไฟล์เกิน 100 MB ผ่านโดเมนที่ผ่าน Cloudflare จึงล้มเหลว ให้อัปโหลดจากในวง LAN ด้วยที่อยู่ตรงของเครื่อง (`http://<ip>:3000/dav/...`) ผ่านโดเมนที่ไม่ผ่านพร็อกซีของ Cloudflare หรืออัปโหลดผ่านหน้าเว็บ การดาวน์โหลดไม่ติดขีดจำกัดนี้
- ขนาดไฟล์สูงสุดต่อไฟล์คือ `UPLOAD_MAX_SIZE` · ไฟล์ถูกเขียนลงโฟลเดอร์ชั่วคราวแล้วย้ายเข้าที่ในครั้งเดียว ไฟล์ที่ส่งไม่ครบ/ขาดกลางทางไม่ทิ้งไฟล์ค้าง (ใช้ได้ทั้งแบบมีและไม่มี `Content-Length`) และใช้หน่วยความจำคงที่ไม่ว่าไฟล์ใหญ่แค่ไหน
- ขนาดคำขอ: Bun รับเนื้อหาคำขอได้สูงสุดเท่า `UPLOAD_MAX_SIZE` เพื่อให้ `PUT` ของ WebDAV ไหลลงดิสก์ได้ทั้งไฟล์ ส่วนเส้นทางอื่นทั้งหมด (`/api/...`) ยังรับได้เท่าเดิมคือ 2 ชิ้นอัปโหลด + 1 MB (`UPLOAD_CHUNK_SIZE`×2 + 1 MB) และ JSON ไม่เกิน 1 MB: เกินแล้วตอบ 413 `request.too-big` ทันที ทั้งแบบมี `Content-Length` และแบบส่งเป็นท่อน (chunked) ที่ระบบนับไบต์ระหว่างรับ
- `PROPFIND` รองรับ `Depth: 0` และ `1` เท่านั้น (`infinity` ตอบ 403) · `PROPFIND` ขอ property ได้ไม่เกิน 50 ชื่อต่อคำขอ (เกิน → 400 `files.dav-too-many-props`) และโฟลเดอร์ที่มี 100,000 รายการขึ้นไป (ปรับได้ด้วย `WEBDAV_MAX_ITEMS`) ใน `Depth: 1` ตอบ **507** พร้อมเนื้อหา `<D:error><D:number-of-matches-within-limits/></D:error>` ทั้งก้อน (ไม่ตัดครึ่ง เพราะไคลเอนต์จะเข้าใจว่าครบ) ชื่อ property ที่ไม่รู้จัก (รวม `__proto__`, `constructor`) ตอบ 404 ในคำตอบตามปกติ · `PROPPATCH` ตั้งเวลาแก้ไขล่าสุดได้ (`getlastmodified`, `lastmodified` ของ rclone/ownCloud, `Win32LastModifiedTime`) รับแต่ไม่เก็บค่า `Win32*` อื่น ๆ และปฏิเสธ property อื่นทั้งหมด (ไม่มี dead properties) · `PUT` รองรับ `If-Match` / `If-None-Match` และ `X-OC-Mtime`
- **lock ไม่บังคับ:** `LOCK`/`UNLOCK` แจก token ให้ (ไม่เกิน 1 ชั่วโมง) และเก็บไว้ในหน่วยความจำเท่านั้น เพื่อให้ Windows Explorer, Finder และ Office ยอมเขียนไฟล์ แต่ไม่ได้กันไม่ให้คนอื่นเขียนทับไฟล์ที่ล็อกอยู่ และรีสตาร์ตแล้ว lock หายหมด (ผ่าน litmus ชุด `basic` 16/16 และ `copymove` 13/13 ส่วนชุด `locks` และ `props` ที่ตรวจการบังคับ lock และ dead properties ไม่ผ่านตามที่ออกแบบไว้)
- `GET` ที่โฟลเดอร์ตอบ 405 (ใช้ `PROPFIND`)
## กลุ่ม (โฟลเดอร์ร่วมของสมาชิก)

admin สร้างกลุ่มและเพิ่มสมาชิก ทุกกลุ่มมีโฟลเดอร์ `<storage>/groups/<id>` (สร้างพร้อมกลุ่ม `id` สุ่มเป็นตัวพิมพ์เล็กและตัวเลข) และ space `group:<id>` ที่ใช้กับ `/api/list`, `/api/download`, `/api/upload` ฯลฯ ได้เหมือน space อื่น ข้อมูลกลุ่มเก็บใน `DATA_DIR/groups.json`: `{ id, name, members: [{ username, perms }], quotaBytes, createdAt, createdBy }`

- **สิทธิ์:** `view` = `read`, `download`, `batchdownload`, `zip` · `edit` = view + `write`, `upload` ไม่มี `share` เสมอ: **ยังไม่มีลิงก์แชร์ออกจากโฟลเดอร์กลุ่ม** (`POST /api/shares` ตอบ 403) admin เข้าได้ทุกกลุ่มด้วยสิทธิ์เต็ม (เห็นเป็น `/groups/<id>` ใต้ `/` ของตัวเองด้วย) สมาชิกถูกตรวจใหม่ทุกคำขอ ถอดสมาชิกหรือลบกลุ่ม = เข้าไม่ได้ทันที (ถึงอัปโหลดที่ประกาศไว้แล้วก็หยุดที่ chunk ถัดไป) คนนอกกลุ่มได้คำตอบเหมือนรหัสที่ไม่มีอยู่ (403)
- **ชื่อกลุ่ม** 1–64 ตัวอักษร ไม่ซ้ำ (ไม่สนตัวพิมพ์) ไม่มี `/` `\` หรืออักขระควบคุม และไม่ใช่จุดล้วน (`.`, `..` — เพราะเป็นชื่อโฟลเดอร์ใน WebDAV; กลุ่มเก่าที่ชื่อแบบนี้แสดงเป็น `_` ใน `/dav/groups/`) เปลี่ยนชื่อได้ id และโฟลเดอร์ไม่เปลี่ยน
- **โควตา:** `quotaBytes` ของกลุ่ม (0 = ไม่จำกัด) นับจากทั้งโฟลเดอร์กลุ่มรวมเวอร์ชันเก่าของไฟล์ อัปโหลด บันทึก คัดลอก แตก zip และกู้คืนจากถังขยะนับกับ **กลุ่ม** ไม่ใช่โควตาส่วนตัวของสมาชิก เต็มแล้ว 507 `quota.exceeded` (ข้อยกเว้น: admin ที่เขียนผ่าน `/` ของตัวเองไม่ผ่าน space ของกลุ่ม จึงไม่ถูกจำกัด และการบันทึกจาก ONLYOFFICE ในโฟลเดอร์กลุ่มยังไม่นับกับกลุ่ม)
- **ถังขยะ:** ของที่ลบจากโฟลเดอร์กลุ่มเป็นของกลุ่ม (`owner` = `group:<id>`) สมาชิกที่มีสิทธิ์ `edit` ทุกคนเห็นใน `GET /api/me/trash` (มี `group: { id, name }`) และกู้คืนได้ แต่ลบถาวรได้เฉพาะคนที่ลบรายการนั้น (คนอื่น 403 `trash.cannot-purge`) หรือ admin จากถังขยะของ admin สมาชิกที่เป็น `view` ไม่เห็นถังขยะของกลุ่ม ลบกลุ่ม = ย้ายโฟลเดอร์ทั้งโฟลเดอร์ไปถังขยะของ admin (ไม่ลบถาวร กู้คืนกลับเป็นโฟลเดอร์ `/groups/<id>` ได้ แต่กลุ่มไม่กลับมา) รายการในถังขยะที่เคยเป็นของกลุ่มจะเห็นเฉพาะ admin
- **โฟลเดอร์บ้านห้ามอยู่ใน `/groups`:** admin ตั้ง `homedir` ของผู้ใช้เป็น `/groups` หรือข้างในไม่ได้ (400 `admin.home-in-groups`) และ `canManage`/การตรวจโฟลเดอร์ซ้อนกันถือว่าที่นั่นเป็นของกลุ่ม
- **แชร์โฟลเดอร์ให้กลุ่ม:** `POST /api/grants` ใส่ `toGroup: <id>` แทน `to` (ใส่ทั้งสองหรือไม่ใส่เลย = 400 `grants.to-one`) ผู้ใช้ที่มี `share` แชร์ให้ **กลุ่มที่ตัวเองเป็นสมาชิก** ได้ (admin ให้กลุ่มไหนก็ได้) กลุ่มอื่น/ไม่มี = 404 `groups.not-found` สมาชิกทุกคนเห็นใน `GET /api/grants/to-me` (ยกเว้นเจ้าของเอง) ผู้ที่เป็นสมาชิก `view` ได้ไม่เกิน `view` แม้แชร์แบบ `edit` สมาชิกที่ถูกถอดหรือกลุ่มที่ถูกลบ = เสียสิทธิ์ทันที (ลบกลุ่ม = ลบสิทธิ์ที่ให้กลุ่มนั้นด้วย) สมาชิก **ออกจากการแชร์ของกลุ่มเองไม่ได้** (`DELETE /api/grants/:id` ของผู้รับกลุ่ม = 404) เฉพาะเจ้าของยกเลิกได้ เจ้าของเห็นใน `/api/grants/mine` พร้อม `toGroup` และ `toGroupName` (`to` เป็น `null`)
- **ผู้ดูแล (manager)** จัดการกลุ่มไม่ได้ ยกเว้นเพิ่ม/ถอด/เปลี่ยนสิทธิ์สมาชิกที่เป็น "ผู้ใช้ทั่วไปที่ตัวเองดูแล" (`canManage`) ในกลุ่มที่ตัวเองเป็นสมาชิกอยู่ และให้สิทธิ์ได้ไม่เกินของตัวเอง (สมาชิก `view` ให้ได้แค่ `view`) สร้าง/แก้/ลบกลุ่มไม่ได้ ไม่เห็นกลุ่มที่ตัวเองไม่ได้อยู่ (404)
- ผู้ใช้ที่ถูกลบจะถูกถอดจากทุกกลุ่ม (บัญชีใหม่ชื่อเดิมไม่ได้ที่เดิมคืน) การเปิดดูโฟลเดอร์กลุ่มลงประวัติ `browse` (ครั้งเดียวต่อนาทีต่อโฟลเดอร์) เหมือน space ของคนอื่น
- ไฟล์สำรองมี `groups.json` แต่การกู้คืนจากหน้าเว็บยังคืนเฉพาะ `users.json`, `settings.json`, `branding/` (กลุ่มคือโฟลเดอร์ใน `storage/` กับรายชื่อสมาชิก ต้องกู้คู่กันด้วยมือ)

| | |
|---|---|
| `GET /api/groups/mine` | `{ items: [{ id, name, perms, space, quotaBytes, used }] }` กลุ่มที่ฉันเป็นสมาชิก (admin ที่ไม่ได้เป็นสมาชิกไม่อยู่ในนี้) |
| `GET /api/groups/lookup?q=` | เลือกกลุ่มตอนแชร์: ต้องมี `share` (admin ได้) `q` ไม่ใส่ = ทั้งหมด ตอบ `{ groups: [{ id, name }] }` เฉพาะกลุ่มของฉัน (admin: ทุกกลุ่ม) ไม่เกิน 20 |
| `GET /api/admin/groups` | admin: ทุกกลุ่ม · manager: เฉพาะกลุ่มที่เป็นสมาชิก `{ items: [{ id, name, space, quotaBytes, used, createdAt, createdBy, members: [{ username, name, perms }] }] }` |
| `POST /api/admin/groups` `{ name, quotaBytes? }` | admin เท่านั้น ตอบ `{ ok, group }` · 400 `groups.bad-name` · 409 `groups.name-taken` · 400 `admin.bad-quota` |
| `PATCH /api/admin/groups/:id` `{ name?, quotaBytes? }` | admin เท่านั้น ตอบ `{ ok, group }` · 404 `groups.not-found` |
| `DELETE /api/admin/groups/:id` `{ password }` | admin เท่านั้น ต้องใส่รหัสผ่านตัวเองซ้ำ (403 `auth.wrong-password`, 429 `auth.confirm-locked`) |
| `PUT /api/admin/groups/:id/members` `{ username, perms: "view"\|"edit" }` | เพิ่มสมาชิกหรือเปลี่ยนสิทธิ์ ตอบ `{ ok, added, member }` · 404 `admin.user-not-found` · manager: 403 `groups.not-manageable` |
| `DELETE /api/admin/groups/:id/members/:username` | ถอดสมาชิก · 404 `groups.member-not-found` |

ประวัติการใช้งานมี `group-create`, `group-update`, `group-delete`, `group-member-add` (รวมเปลี่ยนสิทธิ์), `group-member-remove` และ `browse`/`download`/`view` ใน space `group:<id>` โมดูลอื่น (เช่น WebDAV) ใช้ `groupSpacesOf(user)` จาก `src/groups.ts` ได้: คืน `[{ name, space }]` ของกลุ่มที่ผู้ใช้เป็นสมาชิก แล้วเรียก `accessFor(user, space)` ตามปกติ

## ค้นหาไฟล์

`GET /api/search?space=home&q=report` หาจากชื่อไฟล์/โฟลเดอร์ (ตัวพิมพ์เล็กใหญ่ไม่ต่างกัน) ใต้ `path` ที่ระบุ เฉพาะภายในพื้นที่ของผู้เรียกที่มีสิทธิ์ `read`
ตัวกรองเพิ่มเติม (ไม่ใส่ = ไม่กรอง):

| พารามิเตอร์ | ความหมาย |
|---|---|
| `type` | `file` หรือ `dir` |
| `ext` | นามสกุลคั่นด้วย `,` เช่น `pdf,docx` (ไม่สนตัวพิมพ์ ใส่จุดหน้าได้) |
| `from` / `to` | วันที่แก้ไขล่าสุด แบบ ISO (`2024-03-01` หรือ `2024-03-01T08:00:00Z`) `to` แบบมีแต่วันที่รวมทั้งวัน |
| `minSize` / `maxSize` | ขนาดเป็นไบต์ (โฟลเดอร์นับเป็น 0) |
| `sort` / `order` | `name` (ค่าเริ่มต้น) `mtime` `size` / `asc` (ค่าเริ่มต้น) `desc` |
| `limit` | จำนวนสูงสุดที่ตอบ ค่าเริ่มต้น 200 มากสุด 500 |

ตอบ `{ results, truncated, indexed }` ค่า filter ที่ผิดตอบ 400 (`files.bad-filter`)

ระบบเก็บ**ดัชนีค้นหา**ไว้ที่ `DATA_DIR/search.db` (SQLite) สร้างในเบื้องหลังตอนเริ่ม (ไม่บล็อกคำขออื่น ไม่ตามลิงก์) สแกนใหม่ทุก `SEARCH_RESCAN_MINUTES` นาที
และอัปเดตทันทีหลังอัปโหลด สร้างโฟลเดอร์/ไฟล์ แก้ไข เปลี่ยนชื่อ ย้าย คัดลอก ลบ/ถังขยะ กู้คืน และแตก zip
ระหว่างที่ดัชนียังสร้างไม่เสร็จ `/api/search` เดินดิสก์เองและตอบ `indexed: false` (ช้ากว่า และหยุดที่ 50,000 รายการ)
ไฟล์นี้สร้างใหม่ได้เสมอ: ถ้าเสียหายหรือเป็นสคีมาเก่าระบบลบแล้วสร้างใหม่เอง จึงไม่ถูกรวมในการสำรองข้อมูล
(`search.db` ของ 1.7.x ก็นับเป็นสคีมาเก่า: ถูกสร้างใหม่ในเบื้องหลังพร้อมตาราง `entries_fts` ระหว่างนั้นค้นหาด้วยการเดินดิสก์ `indexed: false`)
คำค้นตั้งแต่ 3 ตัวอักษรใช้ตาราง `entries_fts` (FTS5 `trigram`) หาแถวที่เป็นไปได้ก่อน คำค้นใส่เป็น phrase ใน `"..."` โดยเติม `"` เป็น `""` และส่งเป็นพารามิเตอร์ จึงไม่มีทางถูกอ่านเป็นไวยากรณ์ FTS
แถวที่ได้ยังถูกตรวจด้วย `instr` กับชื่อจริงอีกครั้ง; คำค้น 1–2 ตัวอักษร หรือคำค้นที่พบเกิน 1,000 แถว ใช้ `instr` เรียงตามชื่อเหมือนเดิม

## ภาพตัวอย่าง (thumbnail) และดูรายการในไฟล์ zip

### ภาพตัวอย่างฝั่งเซิร์ฟเวอร์

หน้ารายการไฟล์แสดงภาพเล็กของรูป, หน้าแรกของ PDF และเฟรมหนึ่งของวิดีโอ แทนไอคอนได้ สร้างโดย **เครื่องมือของระบบในอิมเมจ Docker** (ไม่ใช่ไลบรารีในแอป):

| ชนิด | นามสกุล | เครื่องมือ (แพ็กเกจ Debian) |
|---|---|---|
| รูป | jpg jpeg png webp gif (เฟรมแรก) bmp tif tiff และ heic heif avif ถ้า libvips ในเครื่องอ่านได้ | `vipsthumbnail` + `vipsheader` (`libvips-tools`) |
| PDF | pdf (หน้าแรก) | `pdftoppm` (`poppler-utils`) |
| วิดีโอ | mp4 m4v mov 3gp webm mkv avi mpg mpeg wmv flv (เฟรมที่ 1 วินาที ถ้าคลิปสั้นกว่านั้นใช้เฟรมแรก) | `ffmpeg` |

**หลังอัปเดตจากหน้าเว็บ ให้รัน `docker compose up -d --build` หนึ่งครั้ง** เพื่อให้อิมเมจมีเครื่องมือเหล่านี้: การอัปเดตจากหน้าเว็บส่งเฉพาะโค้ดของแอป ไม่ส่งโปรแกรมของระบบ ถ้าไม่มีเครื่องมือ (หรืออิมเมจเก่า) ระบบไม่พัง หน้าเว็บแค่แสดงไอคอนเหมือนเดิม (`GET /api/thumbs/status` บอกว่าชนิดไหนทำได้) `docker compose build` ใช้ฐาน Debian และลงเครื่องมือด้วย `apt-get` (ปิดได้ด้วย `--build-arg THUMB_TOOLS=false` เฉพาะเครื่องที่เข้า mirror ของ Debian ไม่ได้) 

**ขนาดอิมเมจ:** เครื่องมือทั้งหมดเพิ่มพื้นที่ราว 500 MB (ประมาณ: libvips-tools + poppler-utils + ฟอนต์ ≈ 155 MB, ffmpeg ≈ 350 MB) ถ้าไม่ต้องการภาพตัวอย่างของวิดีโอ ตั้ง `THUMB_VIDEO=false` ใน `.env` แล้ว `docker compose up -d --build` อิมเมจจะไม่มี ffmpeg (`/api/thumbs/status` จะรายงาน `video: false`)

**ทำไมใช้โปรแกรมของระบบ ไม่ใช้ไลบรารี `sharp`:** `sharp` ใช้งานได้ใน Bun (วัดแล้ว: jpg 4000×3000 → 256 px ใน ~60 ms, ติดตั้ง ~19 MB) แต่เป็น native addon ที่ต้องอยู่ใน `node_modules` ของอิมเมจ ขณะที่การอัปเดตจากหน้าเว็บส่งแต่ `server.js` ที่รวมไลบรารีไว้แล้ว addon จึงไม่ถูกส่งไปด้วยและโหลดไม่ได้หลังอัปเดต ส่วน `vipsthumbnail` เป็นโพรเซสแยก (ถ้าไฟล์ทำให้มันค้างหรือพัง กระทบแค่โพรเซสนั้น และฆ่าทิ้งเมื่อหมดเวลาได้) เร็วใกล้เคียงกัน (~120–200 ms ต่อรูป jpg 4000×3000) และถ้าไม่มีก็แค่ปิดภาพตัวอย่างโดยแอปไม่พัง

- `GET /api/thumb?space=&path=&size=256|1024` (ต้องมีสิทธิ์ `read`; `size` ไม่ใส่ = 256 · **`size=1024` ต้องมี `read` + `download`** ผู้ที่อ่านได้อย่างเดียวได้ 256 เท่านั้น 1024 → 403 · เปิดดูใน `space=user:<ชื่อ>` / grant / กลุ่ม บันทึก `browse` ในประวัติการใช้งาน (ไฟล์ละครั้งต่อนาที) เหมือนการเปิดดูโฟลเดอร์) ตอบ `image/webp` (PDF เป็น `image/jpeg`) ด้านยาวไม่เกิน `size` พิกเซล ไม่ขยายรูปเล็ก มี `ETag` (คีย์ของแคช) และ `Cache-Control: private, max-age=86400` ส่ง `If-None-Match` ได้ 304
  ลิงก์แชร์โฟลเดอร์: `GET /api/s/:token/thumb?path=&size=` ตรวจเหมือนดาวน์โหลดของลิงก์นั้น (รหัสผ่าน, ต้องอยู่ในโฟลเดอร์ที่แชร์, ไม่ตามลิงก์ symlink) แต่ **ไม่นับเป็นการดาวน์โหลด** (ลิงก์ที่ใช้ครบจำนวนครั้งแล้ว หมดอายุ หรือถูกเพิกถอน ตอบ 404 `share.not-found` เหมือนเส้นทางอื่น ลิงก์ดาวน์โหลดทุกอันขอ 1024 ได้)
- ตอบ 404 `thumb.unavailable` เมื่อไม่มีเครื่องมือ, ชนิดไฟล์ไม่รองรับ, สร้างไม่ได้ (ไฟล์เสีย, หมดเวลา) หรือเพิ่งล้มเหลว (ไม่ลองซ้ำ 5 นาที) · 422 `thumb.too-big` ไฟล์รูปเกิน 500 MB หรือเกิน 100 ล้านพิกเซล (อ่านขนาดก่อนสร้าง) · 503 `thumb.busy` พร้อม `Retry-After: 3` เมื่อคิวสร้างเต็ม
- `GET /api/thumbs/status` (ต้องเข้าสู่ระบบ) → `{ "image": true, "pdf": true, "video": false }` หน้าเว็บใช้ตัดสินว่าจะขอภาพหรือแสดงไอคอน
- **ความปลอดภัย:** เครื่องมือรันเป็นโพรเซสลูกด้วยอาร์กิวเมนต์แบบอาร์เรย์ (ไม่ผ่าน shell) สภาพแวดล้อมขั้นต่ำ (ไม่มีความลับของแอป) ตัดทิ้งเมื่อเกิน 10 วินาที (ฆ่าเฉพาะตัวนั้น) พร้อมกันได้ 2 งาน คิวรอ 16 งาน เกินนั้นตอบ 503 ทันที เครื่องมือไม่เคยได้พาธที่ผู้ใช้ตั้งชื่อ: ระบบสร้าง symlink ชื่อเรียบ ๆ ใน `DATA_DIR/thumbs/tmp` ชี้ไปไฟล์จริง (ชื่อเช่น `-x[page=2].png` จึงไม่ถูกอ่านเป็นตัวเลือก) `VIPS_BLOCK_UNTRUSTED=1` กัน libvips ส่งไฟล์ที่ไม่ใช่รูปจริงให้ ImageMagick/rsvg/poppler ffmpeg ถูกกำหนดตัวอ่านตามนามสกุลและเปิดเฉพาะโปรโตคอล `file` (playlist ที่ตั้งชื่อ `.mp4` จึงไม่ถูกตามไปยังไฟล์หรือ URL อื่น) และทุกเส้นทางผ่านการตรวจสิทธิ์ + `resolveIn` เหมือนการดาวน์โหลด
- **แคช:** `DATA_DIR/thumbs/<sha1(พาธ|ขนาด|mtime|ขนาดไฟล์)>.webp` (PDF เป็น `.jpg`) ไฟล์ที่แก้ไขแล้วได้ภาพใหม่เอง ตัดให้ไม่เกิน `THUMB_CACHE_MAX_MB` (1024 MB) ทุกชั่วโมง ลบอันที่ใช้ล่าสุดนานที่สุดก่อน (ทุกครั้งที่มีคนขอ ระบบ touch เวลาของไฟล์) **ไม่อยู่ในไฟล์สำรอง** สร้างใหม่ได้เสมอ ปิดทั้งหมดด้วย `THUMBNAILS=off`

### ดูรายการในไฟล์ zip โดยไม่แตกไฟล์

- `GET /api/archive/list?space=&path=` (ต้องมี `read` + `download`) → `{ entries: [{ name, dir, size, compressed, modified, encrypted }], truncated }` อ่านเฉพาะสารบัญท้ายไฟล์ (central directory) ไม่แตกอะไรลงดิสก์ รองรับ ZIP64 และชื่อภาษาไทย (UTF-8) `name` คือพาธเต็มในไฟล์ zip (โฟลเดอร์ลงท้าย `/`) `modified` เป็น ms สูงสุด 10,000 รายการ เกินนั้น `truncated: true` ไม่ใช่ zip หรืออ่านไม่ได้ → 400 `archive.not-zip` (ดูจากเนื้อไฟล์ ไม่ใช่นามสกุล) **ไม่รองรับ .rar และ .7z**
  **กัน zip ที่สารบัญใหญ่เกิน:** zip.js อ่านสารบัญทั้งก้อนเข้าหน่วยความจำก่อนคืนรายการแรก ระบบจึงอ่าน EOCD (และ ZIP64 EOCD) ที่ท้ายไฟล์ก่อน ถ้าสารบัญใหญ่เกิน 64 MB หรือมีเกิน 100,000 รายการ → 413 `archive.directory-too-big` โดยไม่เปิดไฟล์ · เปิดดูพร้อมกันได้ 4 งาน (ทั้งรายการและดึงรายการเดียว รวมลิงก์แชร์) งานที่เกิน → 503 `archive.busy` พร้อม `Retry-After: 3` ตอนหารายการใน zip หยุดที่ 100,000 รายการ
- `GET /api/archive/file?space=&path=&entry=&inline=1` (ต้องมี `read` + `download`) ส่งรายการเดียวแบบสตรีม (ไม่มี Range) `entry` ต้องตรงกับชื่อในสารบัญ ชื่อที่มี `..` ขึ้นต้นด้วย `/` มี `\` หรือ NUL → 400 `archive.bad-entry` · ไม่พบหรือเป็นโฟลเดอร์ → 404 `archive.entry-not-found` · เข้ารหัสด้วยรหัสผ่าน → 422 `archive.encrypted` · อ่านไม่ได้ (วิธีบีบอัดที่ไม่รองรับ) → 422 `archive.damaged`
  **กัน zip bomb:** ขนาดที่ประกาศเกิน `UPLOAD_MAX_SIZE` หรือ (เกิน 100 MB และบีบอัดเกิน 100:1) → 413 `archive.too-big` ก่อนแตกแม้แต่ไบต์เดียว ระหว่างส่งนับไบต์จริงและตัดทิ้งถ้าเกินขนาดที่ประกาศ (และ zip.js ตรวจ CRC)
  `Content-Type` ตามนามสกุล, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (เว้น PDF ที่เปิดในแท็บ เหมือน `/api/download`) และเปิดในแท็บ (`inline=1`) ได้เฉพาะรูป (ไม่รวม svg), PDF และ `.txt` ที่เหลือเป็น `attachment` เสมอ บันทึกในประวัติการใช้งานเป็น `download` (รายการละครั้งต่อนาที) และ `browse` เมื่อผู้ดูแลเปิดดูใน `space=user:<ชื่อ>`
- ลิงก์แชร์โฟลเดอร์ (ลิงก์ดาวน์โหลดเท่านั้น): `GET /api/s/:token/archive/list?path=` และ `GET /api/s/:token/archive/file?path=&entry=` ตรวจเหมือนดาวน์โหลดของลิงก์ (รหัสผ่าน, อยู่ในโฟลเดอร์ที่แชร์) การเอารายการออกจาก zip **นับเป็นการดาวน์โหลดของลิงก์หนึ่งครั้ง** (ลิงก์ที่จำกัดจำนวนครั้งจึงเลี่ยงด้วยการเปิดทีละรายการใน zip ไม่ได้) ส่วนการดูรายการไม่นับ

## ตรวจคุณภาพอัตโนมัติ (CI)

GitHub Actions (`.github/workflows/qa.yml`) ทำงานทุก push และ pull request ไม่ใช้ secret:

| งาน | ตรวจอะไร |
|---|---|
| `qa` | `bun run qa`: build หน้าเว็บ, typecheck, เทสต์ทั้งหมดพร้อม coverage (รันซ้ำเฉพาะที่ล้มเพื่อหาเทสต์ที่ไม่นิ่ง), ทุก route ที่แก้ข้อมูลต้องมีในรายการเทสต์, งบประมาณใน `qa/thresholds.json` ผลอยู่ใน artifact `qa-results` |
| `seeded` | (เฉพาะ push เข้า `main` และสั่งเอง) `bun run qa:seed check`: ใส่บั๊กที่รู้ตัวลงไปแล้วดูว่าเทสต์จับได้ |
| `docker` | `scripts/ci-docker.sh`: build อิมเมจจริง รันบน volume ว่าง ตรวจว่าแอปรันเป็น uid 1000 และไฟล์ใน `/data` เป็นของ 1000, อัปโหลดแบบแบ่งชิ้นแล้วดาวน์โหลดกลับ (ต้องตรงกันทุกไบต์), ติดตั้งแพ็กเกจอัปเดต 99.0.0 ผ่านหน้าอัปเดตแล้วรอรีสตาร์ต, `FC_RUN_AS_ROOT=true` ต้องรันเป็น uid 0, ระบบไฟล์ root อ่านอย่างเดียว (เขียนนอก `/data` ต้องล้ม), `CapEff` ของ PID 1 เป็น 0, ตั้ง `no-new-privileges` แล้ว และ volume เก่าที่เป็นของ root ถูกเปลี่ยนเจ้าของได้ด้วยสิทธิ์ที่เหลือ |
| `security` | ตรวจช่องโหว่ (ดูหัวข้อถัดไป) ผลอยู่ใน artifact `security-results` |

เทสต์ทั้งหมดต้องผ่านบน runner ธรรมดา (ไม่ใช่ root ไม่มี Chromium) รันสคริปต์ Docker บนเครื่องตัวเอง (ต้องมี Docker และ Bun):

```bash
bash scripts/ci-docker.sh
```

สร้างคอนเทนเนอร์ volume และอิมเมจชั่วคราว (ชื่อขึ้นต้น `fc-ci-`) บนพอร์ตสุ่มของ `127.0.0.1` แล้วลบทิ้งเมื่อจบ ไม่ว่าผ่านหรือไม่
ถ้าเครือข่ายผ่านพร็อกซีที่แทรก CA ของตัวเอง ให้ชี้ `FC_CI_CA_BUNDLE=/path/ca.crt` เพื่อให้ขั้นตอน build อิมเมจเชื่อ CA นั้น

### ตรวจช่องโหว่ใน CI

งาน `security` ใน `.github/workflows/qa.yml` ตรวจสามอย่าง และ **ล้มเฉพาะช่องโหว่ระดับ HIGH หรือ CRITICAL ที่มีเวอร์ชันแก้แล้ว** (`ignore-unfixed`):

1. `bun audit --audit-level=high` ตรวจแพ็กเกจจาก `bun.lock` กับฐานข้อมูล advisory
2. Trivy `fs` บนโค้ด: ช่องโหว่ของแพ็กเกจ, ความลับที่หลุดในไฟล์, และการตั้งค่าผิดของ `Dockerfile` (Trivy ไม่ตรวจ `docker-compose.yml` ส่วนค่า hardening ของ compose ตรวจโดย `scripts/ci-docker.sh`)
3. Trivy `image` บนอิมเมจที่ build จาก `Dockerfile`: แพ็กเกจ Debian ของฐานและแพ็กเกจในอิมเมจ

**อ่านผล:** เปิด log ของ step `Trivy repository` / `Trivy image` จะเห็นตาราง (แพ็กเกจ, CVE, เวอร์ชันที่ติดตั้ง, เวอร์ชันที่แก้แล้ว) แก้โดยอัปเดตแพ็กเกจ (`bun update <ชื่อ>`) หรือเปลี่ยนแท็กฐานอิมเมจเป็นรุ่นใหม่
ไฟล์ SARIF ของทุกระดับ (รวม LOW/MEDIUM และที่ยังไม่มีเวอร์ชันแก้) อยู่ใน artifact `security-results` เปิดดูได้ด้วยโปรแกรมอ่าน SARIF
ถ้าต้องยอมรับข้อยกเว้นจริง ๆ ใส่ ID ใน `.trivyignore` โดย **ต้องมีบรรทัดคอมเมนต์บอกเหตุผลอยู่เหนือทุกรายการ** (เทสต์ตรวจข้อนี้) ตอนนี้มีรายการเดียวคือ `DS-0002` (ไม่มี `USER` ใน Dockerfile เพราะ entrypoint ต้องเริ่มเป็น root เพื่อ chown ครั้งเดียวแล้วลดเป็น `bun`)
งานนี้ต้องดาวน์โหลดฐานข้อมูล Trivy จึงต้องมีอินเทอร์เน็ต และยืนยันผลจริงได้บน GitHub Actions เท่านั้น

**ผลสแกนครั้งแรก (รอบ 9):** โค้ดและแพ็กเกจ npm ไม่พบช่องโหว่; อิมเมจพบ 17 รายการ (HIGH 14, CRITICAL 3) ทั้งหมดอยู่ในแพ็กเกจ Debian ของฐาน (perl-base, pcre2, sqlite, openssl, gzip) และมีรุ่นแก้แล้ว — `Dockerfile` จึงลงอัปเดตความปลอดภัยของ Debian (`apt-get upgrade`) ใน stage ที่ใช้รันทุกครั้งที่ build (ปิดได้ด้วย `--build-arg APT_UPGRADE=false` เฉพาะเครื่องที่เข้า mirror ของ Debian ไม่ได้ เช่น `FC_CI_NO_APT=1 bash scripts/ci-docker.sh`) ควร build อิมเมจใหม่เป็นระยะ (`docker compose build --pull`) เพื่อรับอัปเดตล่าสุด

## สำรองและกู้คืนข้อมูลระบบ

ถ้าดิสก์เสีย บัญชีผู้ใช้ รหัสผ่าน และการตั้งค่าจะหายทั้งหมด ระบบจึงสำรองข้อมูลระบบให้เองทุกวัน

- **สำรองอะไรบ้าง:** หนึ่งครั้ง = ไฟล์เดียว `file-center-backup-YYYYMMDD-HHMMSS.zip` (เวลาของเครื่อง server) มี `users.json` (ผู้ใช้และรหัสผ่านที่เข้ารหัสแล้ว), `settings.json`, `groups.json` (กลุ่มและสมาชิก), `branding/` (โลโก้), `logs/audit.log`, `logs/system.log` และ `backup.json` (`{ version, createdAt, includesFiles }`)
  ไม่รวม `app-passwords.json` (รหัสผ่านแอปของ WebDAV เป็นข้อมูลรับรอง จึงเจตนาไม่ใส่ในไฟล์สำรอง: หลังกู้คืนผู้ใช้ต้องสร้างรหัสผ่านแอปใหม่เอง) ไม่รวม session, ถังขยะ, ไฟล์อัปโหลดที่ยังไม่เสร็จ, แคชภาพตัวอย่าง (`thumbs/`), เวอร์ชันที่อัปเดตผ่านเว็บ log เก่าที่หมุนไฟล์แล้ว (`audit.log.N`, `system.log.N`), `access.log` และ `launcher.log`
  ไฟล์ที่ผู้ใช้อัปโหลด (`storage`) ไม่รวมโดยค่าเริ่มต้นเพราะอาจใหญ่มาก เปิดได้ในหน้าสำรองข้อมูล (หรือ `BACKUP_INCLUDE_FILES=true`) ไฟล์จะอยู่ในโฟลเดอร์ `storage/` ของ zip (ระบบตรวจพื้นที่ว่างก่อนตาม `MIN_FREE_SPACE`)
  **ถ้ารวมไฟล์ ไฟล์สำรองแต่ละชุดจะใหญ่เท่ากับพื้นที่เก็บไฟล์ทั้งหมด** (ไฟล์ rar, zip, วิดีโอบีบอัดไม่ลงอีก) แนะนำให้เก็บแค่ 1–2 ชุด และชี้ `BACKUP_DIR` ไปดิสก์อีกลูก
  `backup.json` ใน zip บอกขนาดแต่ละส่วนด้วย (`parts.data`, `parts.logs`, `parts.storage` แต่ละส่วนมี `files`, `size` ก่อนบีบ, `compressed` หลังบีบ) ไฟล์สำรองของเวอร์ชันก่อน 1.10 ไม่มีส่วนนี้ (รายการตอบ `parts: null`) และกู้คืนได้ตามเดิม
- **ตั้งค่าจากหน้าเว็บ** (หน้าสำรองข้อมูล, `PUT /api/admin/backups/settings`) ค่าที่ตั้งเก็บใน `settings.json` ส่วน `BACKUP_HOUR`, `BACKUP_KEEP`, `BACKUP_INCLUDE_FILES` เป็นเพียงค่าเริ่มต้นเมื่อยังไม่เคยตั้งในหน้าเว็บ
  - **การบีบอัด** `compression`: `fast` (ระดับ 1), `balanced` (6), `smallest` (9, ค่าเริ่มต้น) ไฟล์ที่บีบอยู่แล้ว (zip, rar, jpg, mp4, pdf, docx ...) เก็บตามเดิมไม่บีบซ้ำ ส่วนการดาวน์โหลด zip ของผู้ใช้ยังใช้ระดับ 1 เหมือนเดิม
    ตัวอย่างวัดจริง: log และ json รวม 10 MB บีบได้ 1.30 MB (ระดับ 1, 0.12 วินาที) / 0.96 MB (ระดับ 6, 0.09 วินาที) / 0.91 MB (ระดับ 9, 0.39 วินาที)
  - **ตารางเวลา** `schedule` (เวลาตามเครื่อง server ไม่ใช่เวลาของเบราว์เซอร์ หน้าเว็บแสดงเขตเวลาของ server): `{ "mode": "off" }` · `{ "mode": "daily", "time": "03:00" }` · `{ "mode": "weekly", "days": [1, 4], "time": "03:00" }` (0=อาทิตย์ ... 6=เสาร์) · `{ "mode": "interval", "hours": 12 }` (1–168)
    ระบบตรวจทุกนาที daily/weekly เริ่มภายใน 1 ชั่วโมงหลังเวลาที่ตั้ง และข้ามถ้ามีชุดล่าสุดอายุไม่ถึง 20 ชั่วโมง; ตารางที่เพิ่งบันทึกไม่ย้อนไปรันเวลาที่ผ่านไปแล้ว; ชุดที่ล้มเหลวนับเป็นความพยายามครั้งล่าสุด จึงไม่ลองซ้ำทุกนาที
  - **จำนวนชุดที่เก็บ** `keep`: 1–30
  - **รวมไฟล์** `includeFiles`: เปิดต้องใส่รหัสผ่านซ้ำ (`password`) ปิดไม่ต้อง
- **เมื่อไหร่:** ตามตารางเวลาข้างบน (ค่าเริ่มต้น: ทุกวันตี 3 ตาม `BACKUP_HOUR`) และทันทีที่ครั้งล่าสุดที่สำเร็จเก่ากว่า 2 วัน (เช่น เปิดระบบครั้งแรก หรือเครื่องปิดอยู่ตอนถึงเวลา) ไม่เกินชั่วโมงละครั้ง ตารางที่ห่างกันมากกว่านั้น (รายสัปดาห์) ใช้ 2 เท่าของช่วงห่างแทน ถ้าตารางเป็น `off` จะไม่สำรองอัตโนมัติเลย
  สำเร็จแล้วจะลบไฟล์ที่เก่าที่สุดให้เหลือตามจำนวนที่เก็บ ระหว่างเขียนไฟล์ชื่อจะลงท้าย `.partial` จึงไม่มีไฟล์ที่เขียนไม่ครบปนอยู่ในรายการ
- **ตรวจพื้นที่ดิสก์ก่อนสำรอง** (ทั้งสำรองเองและอัตโนมัติ): ประมาณขนาด = ข้อมูลระบบ + (ถ้ารวมไฟล์) ขนาด `storage` โดยถือว่าบีบไม่ได้เลย ต้องมีที่ว่างใน `BACKUP_DIR` อย่างน้อย ประมาณการ × 1.05 + 1 GB
  ถ้าไม่พอ ระบบลบไฟล์สำรองเก่าที่สุดทีละไฟล์แล้วตรวจใหม่ **โดยไม่ลบชุดล่าสุด** ถ้ายังไม่พอจะไม่เริ่มสำรอง บันทึกสถานะ `backup.no-space` (ตอบ 507) และส่งการแจ้งเตือน
  ระหว่างเขียน ตรวจที่ว่างทุกๆ 256 MB ที่อ่าน ถ้าเหลือต่ำกว่า 1 GB จะหยุด ลบไฟล์ `.partial` และบันทึกสถานะ `backup.aborted-no-space`
  `GET /api/admin/backups/estimate` ตอบ `{ estimate, free, needed, ok, parts: { data, logs, storage } }`
- **เก็บที่ไหน:** `BACKUP_DIR` ค่าเริ่มต้นคือโฟลเดอร์ `backups` ข้าง `DATA_DIR` (Docker: `./data/backups`) ซึ่งอยู่บนดิสก์เดียวกับข้อมูล
  **ถ้าดิสก์นั้นเสีย ไฟล์สำรองก็หายไปด้วย** ควรชี้ไปดิสก์อื่น เช่น ใน Docker เพิ่ม volume `- /mnt/backup-disk/file-center:/backups` ใน `docker-compose.yml` แล้วตั้ง `BACKUP_DIR=/backups` ใน `.env`
  หรือดาวน์โหลดไฟล์สำรองเก็บไว้นอกเครื่องเป็นระยะ (หน้ารายการสำรองข้อมูลจะเตือนเมื่อยังอยู่ดิสก์เดียวกัน)
- **ผลการสำรอง** เขียนลง `data/backup-status.json` ทุกครั้ง หน้าภาพรวมแสดงผลและเตือนเมื่อล้มเหลวหรือเก่าเกิน 2 วัน:
  ```json
  { "status": "ok", "lastSuccess": "2026-10-08T20:00:00.000Z", "lastAttempt": "2026-10-08T20:00:00.000Z", "message": "สำรองข้อมูลสำเร็จ", "file": "file-center-backup-20261009-030000.zip", "size": 48213 }
  ```
  (`status` เป็น `"ok"` หรือ `"failed"`; เมื่อล้มเหลว `lastSuccess` ยังเป็นเวลาที่สำเร็จครั้งล่าสุด)
- **กู้คืน** (`POST /api/admin/backups/restore`) เฉพาะ admin และต้องใส่รหัสผ่านซ้ำเหมือนการติดตั้งอัปเดต (ใส่ผิดซ้ำจะถูกล็อก) ระบบจะ
  1) สำรองสถานะปัจจุบันไว้ก่อนหนึ่งไฟล์ (ถ้ากู้ผิดไฟล์ก็กู้กลับจากไฟล์นี้ได้) 2) ตรวจว่า `users.json` ในไฟล์สำรองอ่านได้และมีผู้ดูแลระบบอย่างน้อยหนึ่งคน
  3) แทนที่ `users.json`, `settings.json` และ `branding/` แล้ว 4) รีสตาร์ตแอปผ่าน launcher (ต้องเริ่มด้วย `bun start` หรือ Docker) ผู้ที่ login อยู่ยัง login ต่อได้ถ้าบัญชีมีอยู่ในไฟล์สำรอง
  ไฟล์ใน `storage` **ไม่ถูกกู้คืนจากหน้าเว็บ** แม้ไฟล์สำรองจะรวมไว้ ให้แตก `storage/` จาก zip ด้วยมือเมื่อต้องการ
- **ดิสก์เสียทั้งลูก:** ติดตั้งระบบใหม่ เริ่มระบบหนึ่งครั้งแล้วหยุด จากนั้นแตก `users.json`, `settings.json` และ `branding/` จากไฟล์สำรองลงใน `DATA_DIR` (Docker: `data/system/`) แล้วเริ่มระบบอีกครั้ง

## API โดยสรุป

ทุกคำสั่งที่เปลี่ยนข้อมูลต้องส่งหัว `X-CSRF-Token` ที่ได้จาก `GET /api/session` ผิดพลาดตอบเป็น `{ "error": "ข้อความ", "code": "fs.bad-name", "params": {} }`

- `code` คงที่ไม่เปลี่ยนตามภาษา (รายการทั้งหมดอยู่ใน `src/messages.ts` แบ่งตามหมวด เช่น `auth.locked`, `files.name-taken`) ส่วน `params` คือค่าที่เติมในข้อความ เช่น `{ "seconds": 30 }`
- `error` เป็นภาษาไทยหรืออังกฤษตามคำขอ: หัว `X-Lang: th` หรือ `en` ก่อน ถ้าไม่มีใช้คุกกี้ `fc_lang` (`th`/`en` ที่หน้าเว็บตั้งตามภาษาที่เลือก)
  ถ้าไม่มีใช้ `Accept-Language` ของเบราว์เซอร์ ถ้าไม่ระบุเลยเป็นภาษาไทย
  คำเตือนในหน้าภาพรวม (`warnings` ของ `GET /api/admin/status`) มี `code`, `message` และ `params` แบบเดียวกัน ส่วน log และประวัติการใช้งานยังเป็นภาษาไทยเสมอ
- ลิงก์ดาวน์โหลดที่เบราว์เซอร์เปิดในแท็บ (`/api/download`, `/api/batch/:token`, `/api/admin/logs/download`, `/api/admin/activity/export`,
  `/api/admin/backups/:name/download`, `/api/s/:token/download`) ถ้าล้มเหลวจะได้หน้า HTML สั้น ๆ แทน JSON: รหัสสถานะเดิม ข้อความตามภาษา รหัส และลิงก์กลับหน้าหลัก
  (นับเป็นการเปิดในแท็บเมื่อมี `Sec-Fetch-Mode: navigate` หรือ `Accept` มี `text/html` และไม่มีหัว `X-Lang`) การเรียกด้วย fetch ยังได้ JSON เหมือนเดิม
- รหัสเดิมที่หน้าเว็บใช้อยู่ไม่เปลี่ยน: `csrf`, `must-change-password`, `disk-full`, `not-supervised` และคำเตือน `errors`

## ต่างจาก FileGator ต้นแบบอย่างไร

- ไม่มีการ `chmod` ผ่านหน้าเว็บ (ไม่มีความหมายบน Windows/Docker)
- รหัสผ่านเก็บด้วย argon2id ผู้ใช้เดิมจาก FileGator ย้ายมาไม่ได้ ต้องสร้างใหม่ (ตามที่ตั้งใจไว้ว่าเริ่มใหม่ทั้งหมด)
- API เป็น REST (`/api/...`) ไม่ใช้รูปแบบ `/?r=/route`
- ไฟล์ที่ซ้ำชื่อตอนอัปโหลดจะถูกตั้งชื่อใหม่ เช่น `report (1).pdf` ไม่เขียนทับ
- session ของผู้เยี่ยมชมอยู่ในหน่วยความจำและมีเพดาน ส่วน session ของผู้ที่เข้าสู่ระบบเก็บในดิสก์ จึงอยู่รอดหลังรีสตาร์ต

## ข้อจำกัดที่ควรรู้

- ทดสอบบน Linux และด้วย Docker Desktop บน Windows แล้ว แต่การรันด้วย Bun บน Windows โดยตรง (ไม่ผ่าน Docker) ยังไม่ได้ทดสอบ (พาธ, `statfs`, ชื่อไฟล์ต้องห้ามของ Windows)
- ชื่อไฟล์ที่ไม่ใช่ ASCII ส่งไปในหัว `Content-Disposition` ตามมาตรฐาน RFC 6266 (`filename*=UTF-8''...`) ควรลองดาวน์โหลดไฟล์ชื่อไทยในเบราว์เซอร์ที่ใช้จริงอีกครั้ง
- ชื่อไฟล์/โฟลเดอร์ห้ามมีอักขระ `\ / : * ? " < > |` (เพื่อให้ย้ายข้ามระบบปฏิบัติการได้) และยาวได้ไม่เกิน 255 ไบต์ ซึ่งเท่ากับภาษาไทยประมาณ 85 ตัวอักษร
  (ชื่อที่ยาวเกินในไฟล์ zip จะถูกตัดให้สั้นลงโดยคงนามสกุลไว้)
- ผู้ใช้ที่ได้รหัสผ่านเริ่มต้นจากระบบต้องเปลี่ยนรหัสผ่านก่อน จึงจะเรียก API อื่นได้ (server บังคับ ไม่ใช่แค่หน้าเว็บ)
- โฟลเดอร์ระบบ `/public` และ `/users` คัดลอกได้ แต่ลบ ย้าย หรือเปลี่ยนชื่อไม่ได้
- **จำนวนและขนาดไฟล์ในหน้าภาพรวมอาจช้ากว่าความจริงได้ราวหนึ่งนาที** ระบบนับไฟล์อยู่เบื้องหลัง (ไม่ให้ผู้ใช้คนอื่นต้องรอ) และแสดงผลที่นับไว้ล่าสุดทันที
  `GET /api/admin/status` ตอบ `stale: true` เมื่อตัวเลขเก่ากว่าหนึ่งนาทีและกำลังนับใหม่ ครั้งแรกหลังติดตั้งที่ยังไม่เคยนับเลยจะได้ `storage: null` (เปิดหน้าใหม่อีกครั้งเมื่อนับเสร็จ)
  ผลที่นับเก็บไว้ใน `stats-cache.json` ใน `DATA_DIR` หลังรีสตาร์ตจึงเห็นตัวเลขล่าสุดทันที
- ค้นหาไฟล์ตามชื่อโดยเดินดูโฟลเดอร์ตอนค้นหา ไม่มีดัชนี จึงช้าลงถ้ามีไฟล์หลักแสนไฟล์ขึ้นไป (จำกัดที่ 50,000 รายการต่อการค้นหา)
  การค้นหาและการคัดลอกทำทีละชุดสลับกับคำขออื่น ผู้ใช้คนอื่นจึงไม่ต้องรอ
- การคัดลอกข้ามลิงก์ (symlink) ไปเสมอ ไม่ตามลิงก์และไม่คัดลอกตัวลิงก์ ถ้าคัดลอกไม่สำเร็จกลางทาง (เช่น ดิสก์เต็ม) ส่วนที่คัดลอกไปแล้วจะถูกลบออก
