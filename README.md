# File Center (ElysiaJS)

[![qa](https://github.com/RockZa27/file-center/actions/workflows/qa.yml/badge.svg)](https://github.com/RockZa27/file-center/actions/workflows/qa.yml)

ระบบฝากและแจกจ่ายไฟล์บนเว็บ เขียนใหม่ทั้งหมดด้วย **ElysiaJS + Bun** (backend) และ **Vue 3 + Naive UI** (frontend)
ออกแบบให้ใช้งานและหน้าตาใกล้เคียง File Center ที่สร้างต่อจาก FileGator แต่ไม่ได้ใช้โค้ดหรือข้อมูลเดิมเลย

- **ผู้เยี่ยมชม** เปิดเว็บแล้วดาวน์โหลดไฟล์ในโฟลเดอร์สาธารณะได้ทันที (ปิดได้จากหน้าตั้งค่า)
- **ผู้ใช้** เข้าสู่ระบบแล้วจัดการไฟล์ในโฟลเดอร์ของตัวเอง และใช้โฟลเดอร์สาธารณะตามสิทธิ์ที่ได้รับ
- **ผู้ดูแลระบบ** จัดการไฟล์ทั้งหมด ผู้ใช้ สิทธิ์ ดูสุขภาพระบบ ประวัติการใช้งาน ถังขยะ และตั้งค่าเว็บ

## เริ่มใช้งาน

ต้องมี [Bun](https://bun.sh) 1.1 ขึ้นไป

```bash
bun install
bun run build      # คอมไพล์หน้าเว็บ (ถ้าไม่มี Node ในเครื่องให้ใช้: bun --bun run build)
bun start          # เปิดที่ http://localhost:3000 (เริ่มผ่าน launcher เพื่อให้อัปเดตจากหน้าเว็บได้)
```

ครั้งแรกระบบสร้างบัญชี `admin` ให้และ **แสดงรหัสผ่านที่สุ่มไว้ในหน้าจอ** (จะบังคับให้เปลี่ยนทันทีที่เข้าสู่ระบบ)
หรือกำหนดเองด้วย `ADMIN_PASSWORD=...` ก่อนเริ่มครั้งแรก

ระหว่างพัฒนา:

```bash
bun run dev        # API ที่ :3000 + หน้าเว็บ (Vite, hot reload) ที่ :5173
bun test           # ทดสอบ API และระบบอัปเดต (SLOW_TESTS=1 bun test เพิ่มเทสต์ zip ขนาด 4.4 GB)
bun run typecheck
```

## รันด้วย Docker และย้ายเครื่อง

```bash
cp .env.example .env     # แก้ ADMIN_PASSWORD ถ้าต้องการ
docker compose up -d --build
docker compose logs file-center   # ดูรหัสผ่าน admin ที่สุ่มให้ครั้งแรก
```

ข้อมูลทั้งหมดอยู่ในโฟลเดอร์ `./data` ข้างไฟล์ `docker-compose.yml` เท่านั้น:

- `data/storage/` ไฟล์ที่อัปโหลด
- `data/system/` ผู้ใช้ การตั้งค่า โลโก้ ประวัติ ถังขยะ session และไฟล์อัปโหลดที่ยังไม่เสร็จ (เป็นไฟล์ JSON ธรรมดา ไม่มีฐานข้อมูลแยก)

**ย้ายไปเครื่อง server ใหม่:** `docker compose down` ที่เครื่องเดิม → คัดลอก **ทั้งโฟลเดอร์โปรเจกต์** (รวม `data/` และ `.env`) ไปเครื่องใหม่ → `docker compose up -d --build`
ไม่ต้องแก้ค่าใดๆ ผู้ใช้ รหัสผ่าน ไฟล์ ถังขยะ และประวัติจะอยู่ครบ ผู้ที่ login อยู่ยัง login ต่อได้ ข้อมูลไม่มีพาธเครื่องเดิมฝังอยู่
(ควร `down` ก่อนคัดลอกเพื่อให้ไฟล์ข้อมูลนิ่ง และเครื่องใหม่ต้องมี Docker กับ Docker Compose v2)

ค่าเริ่มต้นของ `docker-compose.yml` เปิดพอร์ตให้เข้าได้จากเครื่อง server เท่านั้น (`127.0.0.1:3000`)
ถ้าต้องการให้เครื่องอื่นในวง LAN เข้าตรงได้ ให้ตั้ง `BIND_ADDRESS=0.0.0.0` ใน `.env`

### แอปในคอนเทนเนอร์ไม่ได้รันเป็น root

แอปทำงานเป็นผู้ใช้ `bun` (uid 1000 ของอิมเมจ `oven/bun`) ถ้ามีช่องโหว่ในแอป ผู้โจมตีจะไม่ได้สิทธิ์ root ในคอนเทนเนอร์
ตอนเริ่ม `scripts/docker-entrypoint.sh` เริ่มเป็น root ก่อน ถ้า `./data` (หรือโฟลเดอร์ชั้นแรกในนั้น) ยังไม่เป็นของ `bun` จะเปลี่ยนเจ้าของให้ (`chown -R`) **ครั้งเดียว** หลังอัปเกรดจากเวอร์ชันที่รันเป็น root
(ข้อมูลมากอาจใช้เวลาสักครู่ในการเริ่มครั้งนั้น) แล้วจึงสลับเป็น `bun` และเริ่ม launcher การอัปเดตและรีสตาร์ตผ่านหน้าเว็บเขียนเฉพาะใน `/data` จึงใช้ได้ตามเดิม
บนเครื่อง host ไฟล์ใน `./data` จะเป็นของ uid 1000 (ใช้ `sudo` ถ้าต้องจัดการไฟล์เหล่านั้นด้วยบัญชีอื่น)

ตรวจบนเครื่อง server หลังอัปเกรด:

```bash
docker compose up -d --build
docker compose top file-center                                  # คอลัมน์ UID ของ bun src/launcher.ts และ src/index.ts ต้องเป็น 1000 (หรือชื่อผู้ใช้ uid 1000 ของเครื่อง host) ไม่ใช่ root
docker compose exec file-center grep -E '^(Uid|Gid)' /proc/1/status   # ต้องเป็น 1000
ls -ln data                                                     # storage และ system เป็นของ 1000
```

แล้วเปิดหน้าเว็บ อัปโหลดไฟล์หนึ่งไฟล์ ดาวน์โหลดกลับ และลบลงถังขยะ ให้ทำได้ตามปกติ
(`docker compose exec file-center id` จะแสดง root เพราะ `exec` เปิดโปรเซสใหม่ด้วยผู้ใช้ตั้งต้นของคอนเทนเนอร์ ซึ่งต้องเป็น root เพื่อเปลี่ยนเจ้าของ `./data` ตอนเริ่ม
ไม่ได้บอกว่าแอปรันเป็นใคร ให้ดูจาก `top` หรือ `/proc/1/status` ตามด้านบน)

**ทางหนีไฟ:** ถ้ามีปัญหาเรื่องสิทธิ์ไฟล์ (เช่น `./data` อยู่บน NFS ที่ไม่ยอมให้ `chown`) ให้ใส่ `FC_RUN_AS_ROOT=true` ใน `.env` แล้ว `docker compose up -d` แอปจะรันเป็น root เหมือนเดิม

### ตั้งค่าความปลอดภัยของคอนเทนเนอร์

อิมเมจใช้ฐาน `oven/bun:1.4.2-slim` (เล็กกว่าฐานเต็มราว 70 MB; จำนวนแพ็กเกจ Debian ที่ `dpkg -l | wc -l` นับได้เท่ากับฐานเต็มคือ 85 บรรทัด
เพราะฐานทั้งสองมีชุดแพ็กเกจเดียวกัน ที่ลดคือขนาด ไม่ใช่จำนวนแพ็กเกจ) ไม่ใช้ distroless เพราะ entrypoint ต้องมี shell ทำ `chown` ครั้งเดียวและ `setpriv`
`docker-compose.yml` ของบริการ `file-center` ตั้งไว้ดังนี้ (`scripts/ci-docker.sh` ตรวจทุกข้อกับคอนเทนเนอร์จริง):

| ค่า | ทำอะไร | ถ้า host ใช้ไม่ได้ |
|---|---|---|
| `read_only: true` + `tmpfs: /tmp` | ระบบไฟล์ของอิมเมจเขียนไม่ได้ เขียนได้เฉพาะ `/data` (ข้อมูล และเวอร์ชันที่อัปเดตจากเว็บใน `/data/system/app` จึงอัปเดตได้ตามเดิม) กับ `/tmp` ในหน่วยความจำ 256 MB | ลบสองบรรทัดนี้ (ถ้าเพิ่ม volume ที่แอปต้องเขียน เช่น `BACKUP_DIR=/backups` ก็ต้องเป็น volume ที่เขียนได้อยู่แล้ว) |
| `cap_drop: [ALL]` + `cap_add` | `CHOWN` เปลี่ยนเจ้าของ `./data` ของการติดตั้งเก่า, `SETUID` และ `SETGID` ใช้ใน `setpriv` ลดจาก root เป็น `bun`, `DAC_OVERRIDE` อ่านโฟลเดอร์ใน `./data` ที่เป็นของผู้ใช้อื่นและปิดสิทธิ์ไว้ (และเขียน `./data` ตอน `FC_RUN_AS_ROOT=true`) หลังลดเป็น `bun` แล้วแอปไม่เหลือสิทธิ์ใด (`CapEff` ใน `/proc/1/status` เป็น 0) | ลบ `cap_drop` และ `cap_add` ถ้า host (เช่น NAS บางรุ่น) ไม่รองรับ |
| `security_opt: no-new-privileges:true` | โปรเซสในคอนเทนเนอร์ขอสิทธิ์เพิ่มผ่าน setuid ไม่ได้ | ลบบรรทัดนั้น |
| `mem_limit` / `pids_limit` | จำกัดหน่วยความจำ (2g) และจำนวนโปรเซส (512) ปรับได้ด้วย `FC_MEMORY_LIMIT` / `FC_PIDS_LIMIT` ใน `.env` | ตั้งค่าให้สูงขึ้นถ้าเก็บไฟล์ใหญ่มากหรือมีผู้ใช้พร้อมกันมาก (แอปถูกฆ่าเมื่อเกิน `mem_limit`) |

ตรวจบนเครื่อง server: `docker compose exec file-center touch /app/x` ต้องล้มเหลว (`Read-only file system`) และ `docker compose exec file-center grep -E 'CapEff|NoNewPrivs' /proc/1/status` ต้องได้ `0000000000000000` กับ `1`

## อัปเดตระบบจากหน้าเว็บ (ไม่ต้อง FTP ไม่ต้องปิดระบบ)

ผู้ดูแลระบบอัปเดตโค้ดได้เองที่เมนู **อัปเดตระบบ** โดยลากไฟล์แพ็กเกจ `.zip` ใส่ในหน้านั้น ไม่ต้องเข้าเครื่อง server และไม่ต้องรัน `docker compose` อีก

**สร้างแพ็กเกจ** (บนเครื่องที่มีโค้ด):

```bash
# 1) เพิ่มเลข "version" ใน package.json (ระบบรับเฉพาะเวอร์ชันที่ใหม่กว่าที่ใช้อยู่)
bun run package --notes "สิ่งที่เปลี่ยน"     # ได้ dist-update/file-center-<version>.zip (ราว 1 MB)
```

**ติดตั้ง:** เมนู อัปเดตระบบ → ลากไฟล์ `.zip` มาวาง → ระบบตรวจไฟล์ในแพ็กเกจ (ยังไม่รันโค้ดใด ๆ ของแพ็กเกจ) → ใส่รหัสผ่านของคุณยืนยัน → กด **ติดตั้งและรีสตาร์ต** ระบบจะลองเปิดเวอร์ชันใหม่แยกต่างหากก่อน ถ้าเปิดไม่ขึ้นจะไม่ติดตั้ง

- ระบบรีสตาร์ตเฉพาะโปรเซสของแอปประมาณ 2–5 วินาที คอนเทนเนอร์และ Cloudflare Tunnel ไม่ดับ ผู้ใช้ที่ login อยู่ยัง login ต่อได้ ข้อมูลและไฟล์ไม่ถูกแตะต้อง (การอัปโหลดไฟล์ที่กำลังส่งอยู่จะลองส่งชิ้นส่วนใหม่เอง)
- **ย้อนกลับอัตโนมัติ:** ถ้าเวอร์ชันใหม่เปิดไม่ขึ้นหรือล้มภายในไม่กี่วินาทีหลังติดตั้ง `launcher` จะกลับไปใช้เวอร์ชันก่อนหน้าเอง และหน้าอัปเดตจะบอกสาเหตุ นอกจากนี้ย้อนกลับด้วยมือได้ (เก็บ 2 เวอร์ชันล่าสุด และเวอร์ชันที่มากับอิมเมจ)
- **ความปลอดภัย:** เฉพาะ admin, โค้ดของแพ็กเกจไม่ถูกรันจนกว่าจะใส่รหัสผ่านซ้ำ (ทุกครั้งที่ติดตั้ง/ย้อนกลับ) (ใส่ผิดซ้ำจะถูกล็อกเหมือนการ login), ทุกไฟล์ในแพ็กเกจต้องตรง `manifest.json` (ขนาดและ SHA-256) ไม่มีไฟล์เกิน ไม่มี symlink หรือพาธ `../`, และบันทึกลงประวัติการใช้งานทุกครั้ง
  แพ็กเกจคือโค้ดที่จะรันบนเซิร์ฟเวอร์ ให้อัปโหลดเฉพาะแพ็กเกจที่คุณสร้างเองหรือเชื่อถือได้ ถ้าไม่ต้องการฟีเจอร์นี้ตั้ง `WEB_UPDATE=false`
- เวอร์ชันที่ติดตั้งผ่านเว็บเก็บใน `data/system/app/` (อยู่ใน volume จึงรอดการรีสตาร์ตคอนเทนเนอร์) ถ้าภายหลังสร้างอิมเมจใหม่ด้วย `docker compose up -d --build` แล้วเวอร์ชันในอิมเมจ **ใหม่กว่า** เวอร์ชันที่อัปเดตไว้ ระบบจะใช้เวอร์ชันในอิมเมจ
- `launcher` (`src/launcher.ts`) เป็นส่วนที่อยู่ในอิมเมจและอัปเดตผ่านเว็บไม่ได้ ถ้าต้องแก้ส่วนนี้ต้อง build อิมเมจใหม่
- **ครั้งแรกที่เปิดใช้ฟีเจอร์นี้** ต้องสร้างอิมเมจใหม่หนึ่งครั้ง (`docker compose up -d --build`) เพื่อให้มี launcher หลังจากนั้นอัปเดตผ่านเว็บได้ตลอด

### เซ็นแพ็กเกจ (แนะนำ)

ถ้าไม่เซ็น ใครที่ได้ทั้ง session ของ admin และรหัสผ่าน admin ไปก็ติดตั้งโค้ดอะไรก็ได้ เมื่อตั้ง `UPDATE_PUBLIC_KEY` ระบบจะรับเฉพาะแพ็กเกจที่เซ็นด้วยกุญแจส่วนตัวของคุณ แม้บัญชี admin ถูกยึดไปก็ติดตั้งโค้ดอื่นไม่ได้

1. **สร้างกุญแจครั้งเดียว** บนเครื่องที่ใช้สร้างแพ็กเกจ (ไม่ใช่เครื่อง server):
   ```bash
   bun run package --gen-key ~/file-center-keys
   ```
   ได้ไฟล์กุญแจส่วนตัว `~/file-center-keys/update-signing.key` (อ่านได้เฉพาะเจ้าของ) และ public key หนึ่งบรรทัดที่แสดงบนหน้าจอ
   ระบบไม่เขียนทับไฟล์กุญแจที่มีอยู่แล้ว
2. **เก็บกุญแจส่วนตัวไว้นอก server** ห้ามวางในโฟลเดอร์โปรเจกต์บน server ห้าม commit และควรสำรองไว้ที่ปลอดภัย ถ้ากุญแจหายต้องสร้างใหม่แล้วเปลี่ยน `UPDATE_PUBLIC_KEY` (ต้องเข้าเครื่อง server) ถ้ากุญแจหลุด ให้สร้างใหม่และเปลี่ยนทันที
3. **ตั้งค่าบน server** ใส่ public key ใน `.env` แล้วรีสตาร์ต (`docker compose up -d`):
   ```env
   UPDATE_PUBLIC_KEY=MCowBQYDK2VwAyEA...
   ```
   ถ้าค่าผิด ระบบยังเปิดใช้งานได้ตามปกติ แต่จะแจ้งใน log และไม่รับแพ็กเกจใด ๆ จนกว่าจะแก้ค่า
4. **สร้างแพ็กเกจแบบเซ็น** ทุกครั้งที่อัปเดต:
   ```bash
   bun run package --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน"
   ```
   ในแพ็กเกจจะมี `manifest.sig` (ลายเซ็นของ `manifest.json` ซึ่งมี SHA-256 ของทุกไฟล์) ระบบตรวจลายเซ็นตอนอัปโหลดและตรวจซ้ำตอนติดตั้ง
   แพ็กเกจที่ไม่มีลายเซ็น เซ็นด้วยกุญแจอื่น หรือถูกแก้หลังเซ็น จะถูกปฏิเสธ

ถ้าไม่ตั้ง `UPDATE_PUBLIC_KEY` ระบบรับทั้งแพ็กเกจที่เซ็นและไม่เซ็น (แต่ตรวจลายเซ็นไม่ได้เพราะไม่มีกุญแจ)

### เผยแพร่อัปเดตใน git และให้ server ตรวจหาเอง

**เผยแพร่** (บนเครื่องที่มีโค้ด ทุกครั้งที่ออกเวอร์ชันใหม่):

```bash
# เพิ่ม "version" ใน package.json แล้ว commit ให้เรียบร้อยก่อน
bun run release --sign ~/file-center-keys/update-signing.key --notes "สิ่งที่เปลี่ยน" --push
```

- สร้างแพ็กเกจด้วย `scripts/package.ts` แล้ว commit ลง branch `updates` (branch ที่มีแต่แพ็กเกจ ไม่มีโค้ด สร้างให้เองถ้ายังไม่มี) พร้อม `SHA256SUMS`, แถวใหม่ในตารางของ `README.md` และ `latest.json` (เวอร์ชันล่าสุด ที่ server อ่าน)
- ไม่ยอมทำงานถ้ามีไฟล์ที่ยังไม่ได้ commit (แพ็กเกจต้องตรงกับ commit ที่ระบุ) หรือ version ไม่ใหม่กว่าทุกเวอร์ชันที่มีใน `updates` แล้ว
- ไม่ใส่ `--push` = commit ไว้ในเครื่องเท่านั้น ตรวจแล้วค่อย `git push origin updates` เอง ใช้ `--skip-web` ถ้า build หน้าเว็บไว้แล้ว
- branch ปัจจุบันที่ทำงานอยู่ไม่ถูกแตะต้อง (ทำใน git worktree ชั่วคราวแล้วลบทิ้งเสมอ)

**เปิดให้ server ตรวจหาอัปเดต:** ตั้งใน `.env` แล้วรีสตาร์ต (`docker compose up -d`):

```env
UPDATE_SOURCE=https://raw.githubusercontent.com/<owner>/<repo>/updates
```

หน้าอัปเดตจะมีปุ่มตรวจหาเวอร์ชันใหม่ ถ้ามีเวอร์ชันใหม่กว่า กดดาวน์โหลดแล้ว server
ดึงไฟล์มาเอง ตรวจ SHA-256 กับ `latest.json` แล้วตรวจแพ็กเกจแบบเดียวกับไฟล์ที่ลากมาวางทุกอย่าง การติดตั้งยังต้องใส่รหัสผ่านซ้ำเหมือนเดิม

- **ตรวจเองเบื้องหลัง:** server อ่านเฉพาะ `latest.json` ราว 1 นาทีหลังเริ่มระบบและวันละครั้ง (ไม่ดาวน์โหลดหรือติดตั้งอะไรเอง) ถ้ามีเวอร์ชันใหม่กว่า
  หน้าภาพรวมของ admin เตือน `update.available` พร้อม `{ version }` และส่งการแจ้งเตือนหนึ่งครั้งต่อเวอร์ชันใหม่ (ถ้าตั้งไว้ ดู การแจ้งเตือน) ผลเก็บในหน่วยความจำ เริ่มระบบใหม่ก็ตรวจใหม่
- **อัปเดตในขั้นตอนเดียว:** `POST /api/admin/update/fetch-and-apply` `{ password }` ตรวจรหัสผ่านก่อน (ล็อกเมื่อผิดซ้ำเหมือน `/apply` และยังไม่ดาวน์โหลดอะไร)
  แล้วทำ `/check` → `/fetch` → `/apply` ต่อกันโดยไม่ข้ามการตรวจใด ๆ: ต้องใหม่กว่าที่ใช้อยู่, SHA-256 และขนาดตรง `latest.json`, ตรวจไฟล์ในแพ็กเกจแบบเดียวกับที่อัปโหลด,
  ลายเซ็นเมื่อตั้ง `UPDATE_PUBLIC_KEY`, ลองเปิดเวอร์ชันใหม่แยกต่างหาก แล้วจึงรีสตาร์ต ตอบ `{ ok, version, restarting }`
  ถ้าขั้นใดล้มเหลว คำตอบบอกขั้นนั้นใน `params.step` (`check` / `fetch` / `stage` / `apply`) และไม่มีแพ็กเกจค้างอยู่ ประวัติการใช้งานบันทึก `update-fetch` และ `update-apply` เหมือนทำทีละขั้น

- ใช้ได้กับ **repo สาธารณะ** เท่านั้น (server ดาวน์โหลดโดยไม่มีรหัสผ่านหรือ token) repo ส่วนตัวให้ดาวน์โหลดไฟล์ .zip เองแล้วลากมาวางแทน
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) และไม่ตามการ redirect ค่าอื่นระบบยังเปิดได้ แต่จะเตือนใน log และปิดการตรวจหาอัปเดตไว้
- **แนะนำให้เซ็นแพ็กเกจและตั้ง `UPDATE_PUBLIC_KEY` ด้วย:** server จะติดตั้งโค้ดที่ดึงมาจากอินเทอร์เน็ต SHA-256 ใน `latest.json` บอกได้แค่ว่าไฟล์ไม่เสียระหว่างทาง
  แต่บอกไม่ได้ว่าใครสร้าง ใครที่แก้ branch `updates` ได้ (หรือบัญชี GitHub ถูกยึด) ก็เปลี่ยนทั้งแพ็กเกจและ `latest.json` ได้ มีแต่ลายเซ็นที่กันกรณีนี้

## ใช้งานผ่านโดเมนด้วย Cloudflare Tunnel

Cloudflare Tunnel ให้คนภายนอกเข้าผ่านโดเมน (เช่น `https://files.example.com`) ได้โดย **ไม่ต้องเปิดพอร์ตที่เราเตอร์และไม่ต้องมี IP จริง**
เพราะคอนเทนเนอร์ `cloudflared` เป็นฝ่ายต่อออกไปหา Cloudflare เอง และ Cloudflare ทำ HTTPS ให้

1. **นำโดเมนเข้า Cloudflare** ที่ [dash.cloudflare.com](https://dash.cloudflare.com) เพิ่มโดเมน แล้วเปลี่ยน nameserver ที่ผู้ให้บริการโดเมนเป็นของ Cloudflare
   รอจนสถานะโดเมนเป็น Active (ไม่กี่นาทีถึงหลายชั่วโมง)
2. **สร้าง tunnel** ที่ Zero Trust (one.dash.cloudflare.com) > Networks > Tunnels > Create a tunnel > เลือก Cloudflared > ตั้งชื่อ เช่น `file-center`
   หน้าถัดไปเลือก Docker แล้วคัดลอก **โทเคน** (ข้อความยาวหลัง `--token`) ไม่ต้องรันคำสั่งที่หน้านั้นให้
3. **ตั้งค่า `.env`** (คัดลอกจาก `.env.example` ถ้ายังไม่มี) ให้มีค่าเหล่านี้:
   ```env
   COMPOSE_PROFILES=tunnel
   TUNNEL_TOKEN=โทเคนที่คัดลอกมา
   SECURE_COOKIE=true
   TRUST_PROXY=cloudflare
   BIND_ADDRESS=127.0.0.1
   ```
4. **เริ่มระบบ** `docker compose up -d --build` แล้วดูว่า tunnel ในหน้า Zero Trust ขึ้นสถานะ Healthy
5. **ผูกโดเมนกับระบบ** ในหน้า tunnel > Public Hostname (หรือ Published application routes) > Add
   - Subdomain: `files` · Domain: โดเมนของคุณ
   - Service Type: `HTTP` · URL: `file-center:3000` (ชื่อคอนเทนเนอร์ ไม่ใช่ localhost)

   Cloudflare สร้าง DNS ให้อัตโนมัติ เปิด `https://files.โดเมนของคุณ` ได้ทันที
6. **ตั้งค่าที่แนะนำใน Cloudflare** (หน้าโดเมน)
   - SSL/TLS > Edge Certificates: เปิด Always Use HTTPS และตั้ง Minimum TLS Version เป็น 1.2
   - **ห้ามสร้าง Cache Rule แบบ "Cache Everything"** กับโดเมนนี้ เพราะจะทำให้ไฟล์ส่วนตัวและ API ถูกเก็บไว้ที่ Cloudflare
     (ระบบตั้ง `Cache-Control` ให้เองแล้ว: ไฟล์หน้าเว็บใน `/assets/` cache ได้ ส่วนไฟล์ที่ดาวน์โหลดและ API ไม่ถูก cache)
   - ถ้าต้องการชั้นป้องกันเพิ่มสำหรับผู้ดูแล ใช้ Cloudflare Access ครอบพาธ `/admin` และ `/api/admin` ได้

ข้อควรรู้เมื่อใช้ผ่าน Cloudflare
- Cloudflare แพ็กเกจ Free/Pro รับคำขอได้ไม่เกิน 100 MB ต่อครั้ง ระบบอัปโหลดแบ่งส่งทีละ 8 MB จึงอัปโหลดไฟล์ใหญ่ได้ตามปกติ (อย่าตั้ง `UPLOAD_CHUNK_SIZE` เกิน 100 MB)
- Cloudflare ตัดคำขอที่เซิร์ฟเวอร์ตอบช้ากว่าประมาณ 100 วินาที (หน้าเว็บจะได้ error 524) การบีบอัด/แตก zip ที่ใหญ่มากอาจเจอกรณีนี้
  แต่งานยังทำต่อจนเสร็จที่เซิร์ฟเวอร์ รอสักครู่แล้วรีเฟรชหน้า (วัดจริง: บีบอัดไฟล์ 5 GB ใช้ ~24 วินาที แตก ~26 วินาที
  เพราะไฟล์ใหญ่กว่า 1 MB ที่บีบอัดไม่ลง เช่น วิดีโอ จะถูกเก็บใน zip แบบไม่บีบอัด)
- ข้อกำหนดของ Cloudflare จำกัดการใช้ CDN แบบไม่เสียเงินเพื่อเผยแพร่วิดีโอหรือไฟล์ขนาดใหญ่ในปริมาณมาก ถ้าจะใช้แจกไฟล์ใหญ่จำนวนมาก ควรอ่านข้อกำหนดก่อน
- โทเคนใน `.env` คือกุญแจของ tunnel ใครได้ไปก็ต่อเข้าโดเมนนี้ได้ ห้ามแชร์ ถ้าหลุดให้ Refresh token ในหน้า tunnel
- ถ้าเปิด `BIND_ADDRESS=0.0.0.0` คู่กับ `TRUST_PROXY=cloudflare` คนในวง LAN ที่เข้าตรงจะปลอม IP ของตัวเองได้ (ไม่กระทบสิทธิ์ แต่กระทบการล็อกและประวัติ)

## ดูและแก้ไฟล์ในหน้าเว็บ (ไม่ต้องมีเซิร์ฟเวอร์เพิ่ม)

- **ดูตัวอย่าง:** `.docx` (ตาราง รูป หัว/ท้ายกระดาษ) · `.xlsx` `.xlsm` `.xls` `.ods` (แยกชีต แถวแรกค้างไว้ด้านบน ตัวเลขและวันที่จัดรูปแบบ แสดง 1,000 แถวแรกของแต่ละชีต)
  · `.pptx` (สไลด์แบบอ่านอย่างเดียว) ตัวอ่านแต่ละแบบโหลดเมื่อเปิดไฟล์ชนิดนั้นครั้งแรกเท่านั้น ไฟล์ใหญ่กว่า 20 MB ให้ดาวน์โหลดแทน
  ไม่มีสิ่งใดในไฟล์ถูกรัน (ไม่อ่าน macro, HTML ที่ได้จากไฟล์ผ่านการกรองก่อนแสดง, ลิงก์ได้เฉพาะ http(s)/mailto/tel)
- **แก้ไข (ผู้มีสิทธิ์ `write`):** โค้ดและข้อความมีเลขบรรทัดและสีตามภาษา · Markdown แก้คู่กับตัวอย่างที่แสดงผลทันที (บนมือถือเรียงบนลงล่าง)
  · `.csv` แก้เป็นตาราง เพิ่ม/ลบแถวและคอลัมน์ได้ บันทึกกลับด้วยตัวคั่นและการขึ้นบรรทัดแบบเดิม · `Ctrl/⌘+S` บันทึก
- **มีคนบันทึกไปก่อน:** การบันทึกส่ง `expectedMtime` ไปด้วย ถ้าไฟล์ถูกบันทึกจากที่อื่นหลังจากเปิด (409 `files.changed-elsewhere`)
  จะให้เลือก "โหลดฉบับของเขา" หรือ "บันทึกทับ" (ยืนยันอีกครั้งก่อนเขียนทับ)

## แก้ไขเอกสาร office ด้วย ONLYOFFICE Docs

เปิดและแก้ไฟล์ `.docx` `.xlsx` `.pptx` `.odt` `.ods` `.odp` `.csv` `.txt` ในเบราว์เซอร์ได้ด้วย ONLYOFFICE Docs (Community Edition ฟรี) ซึ่งรันเป็นคอนเทนเนอร์แยก
(`.doc` `.xls` `.ppt` แบบเก่าเปิดดูได้อย่างเดียว) **ปิดไว้โดยค่าเริ่มต้น** จะเปิดเมื่อตั้งค่าครบเท่านั้น
เมื่อเปิดใช้ เมนูของไฟล์และหน้าดูตัวอย่างมีปุ่ม "แก้ไขด้วย Office" (หรือ "เปิดด้วย Office" สำหรับไฟล์ที่ดูได้อย่างเดียว) ตัวแก้ไขเปิดเต็มจอ
ปิดแล้วกลับมาที่โฟลเดอร์ และรอจนฉบับใหม่มาถึง (document server ส่งมาภายในไม่กี่วินาทีหลังปิด) เมื่อไม่ได้ตั้งค่า ปุ่มนี้ไม่แสดงและใช้การดูในหน้าเว็บตามด้านบน

- **ทรัพยากร:** document server ใช้ RAM ราว 2–4 GB (ขั้นต่ำ 2 GB + swap แนะนำ 4 GB) และดิสก์ราว 3 GB สำหรับอิมเมจ ครั้งแรกที่เริ่มใช้เวลา 1–2 นาทีก่อนพร้อมใช้งาน
- **รุ่นฟรีจำกัด 20 การเชื่อมต่อพร้อมกัน** (นับทุกแท็บที่เปิดเอกสารอยู่ ทั้งดูและแก้) เกินนั้นผู้ใช้คนถัดไปจะเปิดเอกสารไม่ได้จนกว่าจะมีคนปิด

**เปิดใช้งาน (Docker):** เพิ่มใน `.env` แล้ว `docker compose up -d`

```env
# ถ้าใช้ tunnel อยู่แล้ว: COMPOSE_PROFILES=tunnel,office
COMPOSE_PROFILES=office
# สร้างด้วย  openssl rand -hex 32  (ไม่ตั้งหรือสั้นกว่า 32 ตัวอักษร = ปิด)
OFFICE_JWT_SECRET=ค่าที่สร้างได้
# ที่อยู่ของ document server ที่ "เบราว์เซอร์" เปิดได้
OFFICE_URL=http://localhost:8080
# ที่อยู่ที่ document server ใช้เรียก File Center (ชื่อคอนเทนเนอร์ ไม่ใช่ localhost)
OFFICE_INTERNAL_URL=http://file-center:3000
# ที่อยู่ที่ File Center ใช้ดาวน์โหลดไฟล์ที่บันทึก (ไม่ตั้ง = OFFICE_URL)
OFFICE_SERVER_INTERNAL_URL=http://onlyoffice
```

- `OFFICE_URL` ต้องเป็น `https://` (ยกเว้น `http://localhost` / `127.0.0.1` ใช้ในเครื่องเดียว) ค่าไม่ถูกต้องระบบยังเปิดได้ แต่จะเตือนใน log และปิดการแก้ไขเอกสารไว้
- คอนเทนเนอร์ `onlyoffice` เปิดพอร์ตที่ `127.0.0.1:8080` เท่านั้น (เปลี่ยนด้วย `OFFICE_PORT`) และได้ `JWT_SECRET` จาก `OFFICE_JWT_SECRET` เดียวกันอัตโนมัติ
- **ผ่าน Cloudflare Tunnel ต้องมี hostname ที่สอง** เพราะเบราว์เซอร์ของผู้ใช้โหลดโปรแกรมแก้ไขจาก document server โดยตรง: ในหน้า tunnel > Public Hostname > Add
  Subdomain `office` · Service `HTTP` · URL `onlyoffice:80` แล้วตั้ง `OFFICE_URL=https://office.โดเมนของคุณ` (ไม่ต้องเปิดพอร์ตเพิ่ม)
- รันด้วย bun โดยตรง (ไม่ใช้ Docker): ติดตั้ง document server เอง เปิด JWT ด้วยความลับเดียวกัน และตั้ง `OFFICE_INTERNAL_URL` เป็นที่อยู่ที่เครื่องนั้นเรียกถึง File Center ได้

**ทำงานอย่างไร:** หน้าเว็บขอ `POST /api/office/config` `{ space, path, mode: "edit" | "view" }` (ต้องเข้าสู่ระบบ ดูต้องมีสิทธิ์ `read` + `download` แก้ต้องมี `write` ด้วย
ไฟล์ไม่เกิน `OFFICE_MAX_SIZE` ค่าเริ่มต้น 100 MB) ได้ `{ apiUrl, config }` ซึ่งเป็น config ของ ONLYOFFICE ที่เซ็นด้วย `OFFICE_JWT_SECRET` (`config.token`)
แล้ว document server ติดต่อ File Center เอง ไม่ใช้ cookie ของผู้ใช้: ดาวน์โหลดไฟล์จาก `GET /api/office/file/:token` และส่งไฟล์ที่บันทึกกลับมาทาง `POST /api/office/callback/:token`
`GET /api/session` บอกผู้ที่เข้าสู่ระบบใน `config.office: { enabled, edit: [...], view: [...] }` ว่าเปิดไฟล์นามสกุลไหนได้

- **บันทึก:** เมื่อทุกคนปิดเอกสาร (หรือกดบันทึกแบบ force save) document server ส่งไฟล์ใหม่มา ระบบเก็บ **ฉบับเดิมเป็นเวอร์ชันของไฟล์ก่อน** (กู้คืนได้ที่ `/api/versions`; ถ้าปิดเวอร์ชันด้วย `VERSIONS_KEEP=0` จะย้ายไปถังขยะแทน)
  แล้ววางไฟล์ใหม่แทนที่ในครั้งเดียว (ไม่มีช่วงที่ไฟล์เขียนไม่ครบ) บันทึก `office-save` ในประวัติการใช้งาน และ `office-open` ทุกครั้งที่เปิด
- **ความปลอดภัย:** ลิงก์ที่ให้ document server มีโทเคนที่ File Center เซ็นด้วยกุญแจของตัวเอง (`office-links.key` ใน `DATA_DIR`) ระบุไฟล์ ผู้ใช้ โหมด และหมดอายุใน 24 ชั่วโมง
  ทุกครั้งที่ใช้ตรวจสิทธิ์ของผู้ใช้ใหม่ (ถูกถอนสิทธิ์ `write` แล้วบันทึกไม่ได้ ลิงก์แบบดูบันทึกไม่ได้เลย) document server ต้องส่ง JWT ที่เซ็นด้วย `OFFICE_JWT_SECRET` ทุกคำขอ
  ไฟล์ที่บันทึกดาวน์โหลดจาก origin ของ document server (`OFFICE_SERVER_INTERNAL_URL` / `OFFICE_URL`) เท่านั้น ไม่ตาม redirect จำกัดขนาดตาม `OFFICE_MAX_SIZE` และเวลา
  และ `Content-Security-Policy` ของหน้าเว็บเพิ่ม origin ของ `OFFICE_URL` ใน `script-src`, `frame-src`, `connect-src` เฉพาะเมื่อเปิดใช้งาน

## ความปลอดภัยเพิ่มเติม

- **หัว HTTP:** หน้าเว็บและไฟล์ JS/CSS ของหน้าเว็บส่ง `Content-Security-Policy` (โหลดสคริปต์ได้เฉพาะจากเว็บนี้เอง และจาก `OFFICE_URL` เมื่อเปิด ONLYOFFICE) และ `Permissions-Policy` (ปิดกล้อง ไมโครโฟน ตำแหน่ง)
  ไฟล์ที่ดาวน์โหลดและโลโก้ใช้ policy ของตัวเองที่เข้มกว่า (`sandbox`) ไม่ถูกแทนที่ เมื่อ `SECURE_COOKIE=true` ทุกคำตอบมี `Strict-Transport-Security: max-age=31536000` ด้วย
- **เลขเวอร์ชัน:** `GET /api/health` ตอบแค่ `{ "status": "ok" }` เว้นแต่คำขอมาจากเครื่อง server เอง (ที่อยู่ของการเชื่อมต่อเป็น loopback และไม่มีหัว `X-Forwarded-For` / `CF-Connecting-IP` ที่ proxy ใส่มา) หรือจาก admin ที่เข้าสู่ระบบ
  ซึ่งได้ `version`, `release`, `boot`, `time` ตามเดิม (launcher และหน้าอัปเดต/กู้คืนใช้ค่าเหล่านี้) ส่วน `GET /api/session` ส่ง `config.version` ให้เฉพาะผู้ที่เข้าสู่ระบบ
- **รหัสผ่าน:** รหัสผ่านใหม่ (สร้างผู้ใช้, admin ตั้งให้, เปลี่ยนเอง) ต้องยาวอย่างน้อย 10 ตัวอักษร ห้ามมีชื่อผู้ใช้อยู่ในรหัส (ไม่สนตัวพิมพ์เล็ก/ใหญ่) ห้ามเป็นรหัสที่ใช้กันบ่อย (100 อันดับแรก และรหัสยอดนิยมที่ยาว 10 ตัวขึ้นไป เช่น `password123`, `1q2w3e4r5t` ใน `src/common-passwords.ts`)
  และห้ามเป็นตัวอักษรเดียวซ้ำกัน (`aaaaaaaaaa`) หรือเรียงตามแป้นพิมพ์/ตัวเลข/ตัวอักษร ทั้งไปและกลับ (`1234567890`, `0987654321`, `abcdefghij`, `qwertyuiop`, `asdfghjkl;`)
  รหัสผ่านเดิมที่ตั้งไว้ก่อนหน้ายังเข้าสู่ระบบได้ตามปกติ `GET /api/session` บอกความยาวขั้นต่ำใน `config.passwordMinLength`
- **อัปโหลดของผู้เยี่ยมชม:** ถ้าเปิดสิทธิ์ `upload` ให้ผู้เยี่ยมชม ผู้เยี่ยมชมทุกคนใช้โควตารวมกันวันละ `GUEST_UPLOAD_DAILY_BYTES` (ค่าเริ่มต้น 1 GB, `0` = ห้ามอัปโหลด)
  ระบบนับขนาดไฟล์ตั้งแต่ตอนเริ่มอัปโหลด (อัปโหลดพร้อมกันหลายไฟล์จึงเกินโควตาไม่ได้) และคืนให้เมื่อยกเลิกหรือไม่อัปโหลดจนเสร็จ (ถูกลบตาม `UPLOAD_STALE_HOURS`)
  เกินโควตาจะได้ 429 ยอดที่ใช้เก็บใน `guest-uploads.json` ใน `DATA_DIR` จึงไม่หายเมื่อรีสตาร์ต และเริ่มนับใหม่ทุกวัน (ตามเวลาเครื่อง) ผู้ที่เข้าสู่ระบบไม่ถูกจำกัด

## อุปกรณ์ที่เข้าสู่ระบบและการยืนยันสองขั้นตอน (2FA)

- **อุปกรณ์:** `GET /api/sessions` แสดงอุปกรณ์ที่เข้าสู่ระบบอยู่ของตัวเอง (`id`, `ip`, `ua`, `created`, `seen`, `current`) เรียงใหม่สุดก่อน session ที่สร้างก่อนมีรายการนี้แสดง `ip`/`ua` เป็น `unknown` และไม่มีใครถูกออกจากระบบเพราะการอัปเกรด
  `DELETE /api/sessions/:id` ออกจากระบบอุปกรณ์นั้น (ถ้าเป็นเครื่องที่ใช้อยู่ก็เท่ากับออกจากระบบ), `POST /api/sessions/revoke-others` เก็บไว้เฉพาะเครื่องนี้ admin ดูและเพิกถอนทุกอุปกรณ์ของผู้ใช้ได้ที่ `GET /api/admin/users/:username/sessions` และ `POST .../sessions/revoke`
- **เปิด 2FA (TOTP, RFC 6238):** ใช้กับแอป authenticator ทั่วไป (รหัส 6 หลัก เปลี่ยนทุก 30 วินาที ยอมรับรหัสก่อนและหลังหนึ่งช่วง)
  `POST /api/2fa/setup { password }` ได้ `{ secret, uri }` (uri เป็น `otpauth://` ที่ใช้ชื่อแอปจากหน้าตั้งค่าเป็น issuer) → `POST /api/2fa/enable { code }` ได้ `{ backupCodes }` 10 รหัส (`xxxx-xxxx`) **แสดงครั้งเดียว** และอุปกรณ์อื่นของผู้ใช้จะถูกออกจากระบบ
  ปิดด้วย `POST /api/2fa/disable { password, code }` ขอรหัสสำรองชุดใหม่ด้วย `POST /api/2fa/backup-codes { password, code }` (`code` เป็นรหัสจากแอปหรือรหัสสำรองก็ได้) ใส่รหัสผิดซ้ำจะถูกล็อกเหมือนการใส่รหัสผ่านผิด
- **เข้าสู่ระบบ:** ผู้ใช้ที่เปิด 2FA ใส่รหัสผ่านถูกแล้วจะ **ยังไม่ได้ session** ได้เพียง `{ twoFactor: true, ticket }` (ticket ใช้ได้ครั้งเดียว 5 นาที ผูกกับผู้ใช้และ IP) แล้วส่ง `POST /api/login/2fa { ticket, code }` รหัสผิดซ้ำถูกล็อกตาม `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_SECONDS` และแจ้งเตือนผู้ดูแล
  รหัส TOTP ใช้ได้ครั้งเดียว (ใช้ซ้ำไม่ได้แม้ยังอยู่ในช่วงเวลา) รหัสสำรองใช้ได้ครั้งเดียวแล้วถูกลบ
- **ความลับของ 2FA:** เก็บใน `users.json` แบบเข้ารหัส (AES-256-GCM) ด้วยกุญแจ `secret.key` ใน `DATA_DIR` (สร้างเองครั้งแรกที่ใช้ สิทธิ์ `0600`) ส่วนรหัสสำรองเก็บเฉพาะค่าแฮช
  **ไฟล์สำรองข้อมูลไม่มี `secret.key`** (ถ้าอยู่ในไฟล์เดียวกับ `users.json` ใครได้ไฟล์สำรองไปก็ถอดความลับ 2FA ได้) ให้เก็บสำเนา `secret.key` แยกไว้ที่ปลอดภัยเอง
  **ถ้าติดตั้งเครื่องใหม่ ต้องวาง `secret.key` เดิมไว้ใน `DATA_DIR` เองจึงจะใช้ 2FA เดิมได้** ถ้าไม่มีกุญแจนี้รหัส 2FA ของทุกคนใช้ไม่ได้ ให้ล้างด้วย `bun src/cli.ts reset-2fa <user>` แล้วให้แต่ละคนเปิด 2FA ใหม่
- **ลืมโทรศัพท์และรหัสสำรอง:** admin รีเซ็ตให้ที่ `POST /api/admin/users/:username/2fa/reset { password }` (ใส่รหัสผ่านของ admin เอง) หรือที่เครื่อง server:
  ```bash
  bun src/cli.ts reset-2fa <ชื่อผู้ใช้>         # ปิด 2FA ของผู้ใช้และออกจากระบบทุกอุปกรณ์
  bun src/cli.ts sessions-revoke <ชื่อผู้ใช้>   # ออกจากระบบทุกอุปกรณ์
  docker compose exec file-center bun src/cli.ts reset-2fa admin   # แบบ Docker
  ```
  คำสั่งทำงานกับ `DATA_DIR` เดียวกับแอป เขียนประวัติการใช้งาน (ผู้ใช้ `cli`) และจบด้วยรหัส 1 ถ้าไม่พบผู้ใช้ **ไม่ต้องรีสตาร์ตแอป:** คำสั่งแตะไฟล์ `cli-changed` ใน `DATA_DIR` เมื่อเสร็จ แอปที่เปิดอยู่เห็นแล้วอ่าน `users.json` และ `sessions.json` ใหม่ในคำขอถัดไป
  (ไฟล์นี้ไม่ถูกสำรอง)

## Log ของระบบ

error และเหตุการณ์สำคัญของระบบเขียนลงไฟล์ ไม่หายไปพร้อมคอนเทนเนอร์ ผู้ดูแลดูได้จากหน้าเว็บโดยไม่ต้องเข้าเครื่อง server

- `logs/system.log` ใน `DATA_DIR` บรรทัดละหนึ่งรายการแบบ JSON `{ ts, level, event, detail }` (`level` = `info` / `warn` / `error`) และยังพิมพ์ออก stdout (`docker compose logs`) เหมือนเดิม
  มี error ที่ไม่มีใครดักไว้ (`unhandledRejection` บันทึกแล้วทำงานต่อ, `uncaughtException` บันทึกแล้วปิดโปรเซสให้ launcher เริ่มใหม่) และ error ระหว่างตอบคำขอ (500), สำรอง/กู้คืนข้อมูลล้มเหลว, เขียนไฟล์ข้อมูลไม่ได้ ฯลฯ
- `logs/launcher.log` เขียนโดย launcher: เริ่มระบบ, รีสตาร์ต, ย้อนกลับเวอร์ชัน, ระบบหยุดทำงาน (crash)
- `logs/access.log` เฉพาะเมื่อตั้ง `ACCESS_LOG=true` (ปิดไว้โดยค่าเริ่มต้น)
- ทุกไฟล์หมุนเมื่อใหญ่ถึง `LOG_MAX_BYTES` (`system.log` → `system.log.1` → ...) เก็บไว้ `LOG_MAX_FILES` ไฟล์ ส่วนประวัติการใช้งาน `audit.log` หมุนแบบเดียวกันที่ 10 MB × 10 ไฟล์
- **ไม่มีความลับใน log:** ไม่บันทึกรหัสผ่าน, cookie, CSRF token, โทเคนใน `/api/batch/:token`, ในลิงก์แชร์ (`/api/s/:token`, `/s/:token`) และในลิงก์ของ ONLYOFFICE (`/api/office/file/:token`, `/api/office/callback/:token`), รหัสการอัปโหลด และ query string ของ URL (ตัดออกก่อนเขียน ทั้งในไฟล์และ stdout)
  ข้อยกเว้นเดียวคือรหัสผ่าน admin ที่สุ่มให้ตอนเริ่มครั้งแรก ซึ่งแสดงบน stdout เท่านั้น ไม่ลงไฟล์
- หน้าภาพรวม (`GET /api/admin/status`) เตือน "มี error N รายการใน 24 ชั่วโมงที่ผ่านมา" เมื่อมี error (และส่งการแจ้งเตือนเมื่อเกิน `ALERT_ERRORS_PER_HOUR` ต่อชั่วโมง ดู การแจ้งเตือน)
- `system.log` ปัจจุบันรวมอยู่ในไฟล์สำรองข้อมูลด้วย

## การแจ้งเตือน

ระบบส่งข้อความสั้น ๆ ถึงผู้ดูแลทาง Discord, Slack, Telegram หรือ webhook ใด ๆ ที่รับ JSON เมื่อมีเรื่องที่ต้องดู:

- สำรองข้อมูลไม่สำเร็จ (ทั้งอัตโนมัติและที่กดเอง) พร้อมสาเหตุ
- error มากกว่า `ALERT_ERRORS_PER_HOUR` (ค่าเริ่มต้น 20) ในหนึ่งชั่วโมงที่ผ่านมา (ตรวจทุก 5 นาที)
- บัญชีหรือลิงก์แชร์ถูกล็อกเพราะใส่รหัสผ่านผิดซ้ำ: เข้าสู่ระบบ, ยืนยันรหัสผ่านก่อนติดตั้งอัปเดต/กู้คืน, ปลดล็อกลิงก์แชร์ (บอกชื่อผู้ใช้หรือรหัสลิงก์ และ IP แบบเดียวกับประวัติการใช้งาน)
- ดิสก์เหลือน้อยขั้นวิกฤต (เกณฑ์เดียวกับคำเตือนในหน้าภาพรวม ต่ำกว่า 5%) (ตรวจทุก 5 นาที)
- มีเวอร์ชันใหม่ที่ `UPDATE_SOURCE` (หนึ่งครั้งต่อเวอร์ชัน)

ตั้งใน `.env` แล้วรีสตาร์ต (`docker compose up -d`):

```env
ALERT_WEBHOOK_URL=https://discord.com/api/webhooks/<id>/<token>
ALERT_WEBHOOK_KIND=discord        # slack: URL ของ Incoming Webhook, json: ส่ง { event, code, message, params, lang, version, time }
# Telegram: ALERT_WEBHOOK_KIND=telegram, ALERT_WEBHOOK_URL=https://api.telegram.org/bot<token>/sendMessage, ALERT_TELEGRAM_CHAT_ID=<chat id>
ALERT_LANG=th
```

- แต่ละเรื่องส่งไม่เกินชั่วโมงละครั้ง ส่งเบื้องหลัง รอไม่เกิน 10 วินาที ไม่ตาม redirect ส่งไม่สำเร็จแค่บันทึก `alert-failed` (warn) ใน log ไม่ทำให้คำขอใดช้าหรือล้มเหลว
- ข้อความมาจากรายการข้อความ (`src/messages.ts`) ตาม `ALERT_LANG` และผ่านการตัดความลับแบบเดียวกับ log: ไม่มีรหัสผ่าน โทเคน หรือ cookie
  ชื่อที่ผู้เยี่ยมชมพิมพ์มา (เช่น ชื่อผู้ใช้ที่ login ผิด) เรียก `@everyone` ใน Discord หรือ `<!channel>` ใน Slack ไม่ได้
- รับเฉพาะ `https://` (ยกเว้น `http://127.0.0.1` / `localhost` สำหรับทดสอบ) URL ของ webhook และ Telegram มีโทเคนอยู่ในตัว หน้าเว็บและ log จึงแสดงแค่ชื่อโฮสต์
- `GET /api/admin/alerts` ตอบ `{ enabled, kind, host, lastSent: { <เรื่อง>: เวลา } }` · `POST /api/admin/alerts/test` ส่งข้อความทดสอบทันที ตอบ `{ ok: true }` หรือ error ที่บอกสาเหตุ
  (`admin.alert-off`, `admin.alert-status`, `admin.alert-timeout`, `admin.alert-unreachable`) และบันทึก `alert-test` ในประวัติการใช้งาน (เฉพาะ admin)

## สิทธิ์

บทบาท: `admin` เห็นทุกโฟลเดอร์ / `user` เห็นเฉพาะโฟลเดอร์ส่วนตัว (ผู้ดูแลเลือกได้ ค่าเริ่มต้น `/users/<ชื่อผู้ใช้>`) /
ผู้เยี่ยมชมเห็นเฉพาะโฟลเดอร์สาธารณะ (`storage/public`)
ชื่อผู้ใช้ `guest` (ไม่สนตัวพิมพ์เล็ก/ใหญ่) สงวนไว้ เพราะไฟล์ที่ผู้เยี่ยมชมอัปโหลดและประวัติของผู้เยี่ยมชมใช้ชื่อนี้ สร้างบัญชีชื่อนี้ไม่ได้ (บัญชีเดิมที่ชื่อนี้อยู่แล้วไม่ถูกเปลี่ยนชื่อ)

สิทธิ์ที่กำหนดได้: `read` ดูรายการ · `download` · `batchdownload` ดาวน์โหลดหลายไฟล์เป็น zip · `upload` ·
`write` สร้าง/แก้ไข/เปลี่ยนชื่อ/คัดลอก/ย้าย/ลบ · `zip` บีบอัดและแตกไฟล์ · `share` สร้างลิงก์แชร์ (ต้องมี `download` ในพื้นที่เดียวกันด้วย)

`share` เป็นสิทธิ์ใหม่ บัญชีเดิมยังไม่มี ผู้ดูแลต้องให้เองที่หน้าผู้ใช้ (admin แชร์ได้เสมอ ผู้เยี่ยมชมแชร์ไม่ได้ไม่ว่าตั้งสิทธิ์ผู้เยี่ยมชมไว้อย่างไร)

ผู้ใช้แต่ละคนมีชุดสิทธิ์ 2 ชุดแยกกัน คือในโฟลเดอร์ของตัวเอง และในโฟลเดอร์สาธารณะ ส่วนสิทธิ์ของผู้เยี่ยมชมตั้งที่หน้า "ตั้งค่า"
สิทธิ์ถูกตรวจที่ server ทุกคำสั่ง ไม่ใช่แค่ซ่อนปุ่มในหน้าเว็บ

## โควตาพื้นที่ต่อผู้ใช้

admin กำหนดโควตาให้ผู้ใช้แต่ละคนได้ที่ `POST /api/admin/users` และ `PUT /api/admin/users/:username` ด้วย `quotaBytes` (จำนวนไบต์เต็ม 0 ถึง 2^50,
`0` หรือไม่ตั้ง = ไม่จำกัด) ค่านี้แสดงใน `GET /api/admin/users` ด้วย

- **นับอะไร:** เฉพาะโฟลเดอร์ของผู้ใช้เอง (space `home`) **ถังขยะอยู่นอกโฟลเดอร์นั้น จึงไม่นับ** ลบไฟล์แล้วพื้นที่ว่างคืนทันที
  แต่กู้คืนจากถังขยะก็นับกลับเข้าไปใหม่และอาจถูกปฏิเสธถ้าเต็ม โฟลเดอร์สาธารณะไม่มีโควตา และ admin (ที่โฟลเดอร์คือทั้ง storage) ไม่ถูกจำกัดแม้ตั้ง `quotaBytes`
- **ตรวจที่ไหน:** ตอนเริ่มอัปโหลด, `PUT /api/content` (นับเฉพาะส่วนที่ใหญ่ขึ้น), `/api/zip`, `/api/unzip` (งบไบต์ที่แตกได้ลดลงเหลือเท่าที่โควตาเหลือ),
  `/api/copy`, การบันทึกจาก ONLYOFFICE (นับส่วนที่ใหญ่ขึ้นของไฟล์ และเวอร์ชันเดิมที่เก็บไว้), การกู้คืนจากถังขยะ, และอัปโหลดผ่านลิงก์รับไฟล์ (นับกับเจ้าของลิงก์)
  การย้ายภายในโฟลเดอร์เดียวกันไม่เปลี่ยนยอด เต็มแล้วได้ **507** `quota.exceeded` พร้อม `params: { used, quota }` (ไบต์)
- **นับอย่างไร:** นับด้วยการเดินโฟลเดอร์ (ไม่เกิน 1,000,000 รายการ ถ้าเกินถือว่าเต็ม) เก็บผลไว้ 60 วินาทีต่อผู้ใช้ และนับใหม่ทันทีหลังลบ
  งานที่กำลังเขียนอยู่จองพื้นที่ไว้ก่อนในจังหวะเดียวกับที่ตรวจ ส่งหลายคำขอพร้อมกันจึงแย่งไบต์สุดท้ายไม่ได้ และคืนที่จองเมื่อยกเลิก ล้มเหลว หรือถูกลบเพราะค้างนาน (`UPLOAD_STALE_HOURS`)
- ผู้ใช้ดูยอดของตัวเองได้ที่ `GET /api/me/usage` → `{ used, quota, counting }` (`quota` 0 = ไม่จำกัด `counting` เป็น true ขณะกำลังนับครั้งแรกและยังไม่มีตัวเลข)

## ลิงก์แชร์

ผู้ที่เข้าสู่ระบบส่งลิงก์ให้คนที่ไม่มีบัญชีดาวน์โหลดไฟล์หรือโฟลเดอร์หนึ่งรายการได้ (ต้องมีสิทธิ์ `share` และ `download` ในพื้นที่ที่รายการนั้นอยู่)

ในหน้าเว็บ: เมนู "แชร์ลิงก์" ของไฟล์/โฟลเดอร์ (หรือแถบเครื่องมือเมื่อเลือกรายการเดียว) เลือกอายุ 1/7/30 วัน รหัสผ่าน และจำนวนครั้งได้
แล้วคัดลอกลิงก์ที่แสดงครั้งเดียว · หน้า "ลิงก์ที่แชร์" แสดงลิงก์ของฉันพร้อมสถานะและปุ่มยกเลิก (admin เปิดสวิตช์ดูของทุกคนได้)
· ผู้รับเปิดลิงก์ `/s/<token>` ได้โดยไม่ต้องเข้าสู่ระบบ (ลิงก์โฟลเดอร์เปิดดูโฟลเดอร์ย่อยและดาวน์โหลดเป็น zip ได้)

- สร้าง: `POST /api/shares` `{ space, path, days, password?, maxDownloads? }` อายุ `days` เป็น 1, 7 หรือ 30 วัน (ไม่เกิน `SHARE_MAX_DAYS`)
  รหัสผ่านไม่บังคับ (อย่างน้อย 6 ตัวอักษร) `maxDownloads` ไม่ใส่ = ไม่จำกัด ตอบ `{ share, token, url }` **โทเคนแสดงครั้งเดียวตอนนี้เท่านั้น**
  ระบบเก็บแค่ SHA-256 ของโทเคนใน `shares.json` (ใน `DATA_DIR`) ไฟล์นี้หลุดไปก็ใช้เปิดลิงก์ไม่ได้ รหัสผ่านเก็บแบบ hash เหมือนรหัสผ่านผู้ใช้
- ลิงก์ของฉัน `GET /api/shares` · ยกเลิก `DELETE /api/shares/:id` (เจ้าของหรือ admin) · admin ดูทั้งหมดที่ `GET /api/admin/shares` (ไม่มี hash ในคำตอบ)
- ใช้ลิงก์ (ไม่ต้องเข้าสู่ระบบ): `GET /api/s/:token` ตอบ `{ name, type, size, expiresAt, needsPassword, entries? }` (ลิงก์โฟลเดอร์ดูข้างในได้ด้วย `?path=`
  ไม่มีทางออกนอกโฟลเดอร์ที่แชร์ และไม่แสดง/ไม่ตาม symlink) · `POST /api/s/:token/unlock` `{ password }` ตั้ง cookie อายุ 1 ชั่วโมงที่ใช้ได้กับลิงก์นั้นลิงก์เดียว
  (ไม่ต้องมี CSRF token) ใส่ผิด 5 ครั้งล็อกลิงก์นั้นสำหรับ IP นั้น 15 นาที · `GET /api/s/:token/download?path=` ส่งไฟล์ (หัวเดียวกับ `/api/download`) หรือโฟลเดอร์/โฟลเดอร์ย่อยเป็น zip
- `maxDownloads` นับเฉพาะการดาวน์โหลดที่ส่งครบ ครั้งละหนึ่ง ระหว่างดาวน์โหลดจองที่ไว้ (เริ่มพร้อมกันหลายครั้งก็เกินไม่ได้) ยกเลิกกลางทางไม่นับ
  ลิงก์ที่จำกัดจำนวนครั้งส่งทั้งไฟล์เสมอ (ไม่รับ `Range`) ลิงก์ไม่จำกัดรับ `Range` ได้ และนับเฉพาะครั้งที่ได้ทั้งไฟล์
- ลิงก์หยุดทำงานเมื่อ: หมดอายุ, ถูกยกเลิก, ดาวน์โหลดครบจำนวน, รายการถูกลบ/ย้าย/เปลี่ยนชนิด, เจ้าของถูกลบ (ลิงก์ถูกยกเลิกด้วย สร้างบัญชีชื่อเดิมใหม่ก็ไม่กลับมา)
  หรือเจ้าของไม่มีสิทธิ์ `share`/`download` ในพื้นที่นั้นแล้ว ทุกกรณีตอบ 404 `share.not-found` แบบเดียวกัน ผู้เดาลิงก์จึงไม่ได้ข้อมูลอะไร
- ประวัติการใช้งานบันทึก `share-create`, `share-download`, `share-revoke` พร้อมพาธ (ไม่บันทึกโทเคน) ลิงก์ที่หมดอายุถูกลบออกจาก `shares.json` ตอนเริ่มระบบและวันละครั้ง

### ลิงก์รับไฟล์ (ให้คนนอกอัปโหลดเข้าโฟลเดอร์)

`POST /api/shares` ใส่ `kind: "upload"` ได้เฉพาะ **โฟลเดอร์** และต้องมีสิทธิ์ `share` กับ `upload` ในพื้นที่นั้น (ลิงก์ที่ไม่มี `kind` คือลิงก์ดาวน์โหลดเหมือนเดิมทุกประการ)
ตัวเลือก (ไม่บังคับทั้งหมด): `maxFileBytes` (ไม่เกิน `UPLOAD_MAX_SIZE`), `maxFiles`, `maxTotalBytes` (ไม่เกิน 2^50), `note` (ข้อความถึงผู้อัปโหลด ไม่เกิน 500 ตัวอักษร แสดงเป็นข้อความธรรมดา),
`days` และ `password` เหมือนลิงก์ดาวน์โหลด (cookie ปลดล็อกและการล็อกเมื่อใส่ผิดเหมือนเดิม) สิทธิ์ของเจ้าของถูกตรวจใหม่ทุกครั้งที่ใช้ลิงก์ ถ้าเสียสิทธิ์ `share`/`upload` ลิงก์หยุดทันที

- `GET /api/s/:token` ของลิงก์รับไฟล์ตอบชื่อโฟลเดอร์ ข้อจำกัด note จำนวนที่รับแล้ว และ `mine` (ไฟล์ที่ผู้เยี่ยมชมคนนี้ส่งเอง) **ไม่เคยแสดงของที่อยู่ในโฟลเดอร์**
  เส้นทางดาวน์โหลดปฏิเสธลิงก์รับไฟล์ และเส้นทางอัปโหลดปฏิเสธลิงก์ดาวน์โหลด (404 เหมือนกรณีอื่น)
- ส่งไฟล์: `POST /api/s/:token/upload` `{ name, size }` → `{ id, chunkSize, total }` · `PUT /api/s/:token/upload/:id/:n` · `POST /api/s/:token/upload/:id/complete` · `DELETE /api/s/:token/upload/:id`
  ไฟล์ลงตรงในโฟลเดอร์ที่แชร์ (ผู้ส่งเลือกโฟลเดอร์ย่อยไม่ได้) ชื่อผ่านการตรวจชื่อปกติ ชื่อซ้ำได้ชื่อใหม่ เช่น `a (1).pdf` **ไม่เขียนทับ**
- งานอัปโหลดผูกกับลิงก์นั้นและกับผู้เยี่ยมชมคนนั้นด้วย cookie สุ่ม `fc_visitor` (HttpOnly, SameSite=Strict, ใช้ได้เฉพาะ path ของลิงก์) คนอื่นหรือลิงก์อื่นเพิ่มชิ้นส่วน จบ หรือยกเลิกไม่ได้
  เพราะไม่มี session จึงไม่ต้องใช้ CSRF token สำหรับ 4 เส้นทางนี้ (ระบุใน `src/context.ts`)
- ไบต์นับกับโควตาของเจ้าของลิงก์ (ถ้าลิงก์อยู่ใน home) และกับข้อจำกัดของลิงก์ โดยจองตั้งแต่ประกาศไฟล์ จำกัดอัปโหลดค้างพร้อมกัน 5 งานต่อลิงก์ และ 3 งานต่อ IP
  งานที่ค้างถูกลบตาม `UPLOAD_STALE_HOURS` ประวัติการใช้งานบันทึก `share-upload` (เจ้าของ รหัสลิงก์ ชื่อไฟล์ ขนาด) ลิงก์เก็บแค่แฮชของ cookie ผู้ส่ง ไม่เก็บตัว cookie

## ค้นหาไฟล์

`GET /api/search?space=home&q=report` หาจากชื่อไฟล์/โฟลเดอร์ (ตัวพิมพ์เล็กใหญ่ไม่ต่างกัน) ใต้ `path` ที่ระบุ เฉพาะภายในพื้นที่ของผู้เรียกที่มีสิทธิ์ `read`
ตัวกรองเพิ่มเติม (ไม่ใส่ = ไม่กรอง):

| พารามิเตอร์ | ความหมาย |
|---|---|
| `type` | `file` หรือ `dir` |
| `ext` | นามสกุลคั่นด้วย `,` เช่น `pdf,docx` (ไม่สนตัวพิมพ์ ใส่จุดหน้าได้) |
| `from` / `to` | วันที่แก้ไขล่าสุด แบบ ISO (`2024-03-01` หรือ `2024-03-01T08:00:00Z`) `to` แบบมีแต่วันที่รวมทั้งวัน |
| `minSize` / `maxSize` | ขนาดเป็นไบต์ (โฟลเดอร์นับเป็น 0) |
| `sort` / `order` | `name` (ค่าเริ่มต้น) `mtime` `size` / `asc` (ค่าเริ่มต้น) `desc` |
| `limit` | จำนวนสูงสุดที่ตอบ ค่าเริ่มต้น 200 มากสุด 500 |

ตอบ `{ results, truncated, indexed }` ค่า filter ที่ผิดตอบ 400 (`files.bad-filter`)

ระบบเก็บ**ดัชนีค้นหา**ไว้ที่ `DATA_DIR/search.db` (SQLite) สร้างในเบื้องหลังตอนเริ่ม (ไม่บล็อกคำขออื่น ไม่ตามลิงก์) สแกนใหม่ทุก `SEARCH_RESCAN_MINUTES` นาที
และอัปเดตทันทีหลังอัปโหลด สร้างโฟลเดอร์/ไฟล์ แก้ไข เปลี่ยนชื่อ ย้าย คัดลอก ลบ/ถังขยะ กู้คืน และแตก zip
ระหว่างที่ดัชนียังสร้างไม่เสร็จ `/api/search` เดินดิสก์เองและตอบ `indexed: false` (ช้ากว่า และหยุดที่ 50,000 รายการ)
ไฟล์นี้สร้างใหม่ได้เสมอ: ถ้าเสียหายหรือเป็นสคีมาเก่าระบบลบแล้วสร้างใหม่เอง จึงไม่ถูกรวมในการสำรองข้อมูล

## ตรวจคุณภาพอัตโนมัติ (CI)

GitHub Actions (`.github/workflows/qa.yml`) ทำงานทุก push และ pull request ไม่ใช้ secret:

| งาน | ตรวจอะไร |
|---|---|
| `qa` | `bun run qa`: build หน้าเว็บ, typecheck, เทสต์ทั้งหมดพร้อม coverage (รันซ้ำเฉพาะที่ล้มเพื่อหาเทสต์ที่ไม่นิ่ง), ทุก route ที่แก้ข้อมูลต้องมีในรายการเทสต์, งบประมาณใน `qa/thresholds.json` ผลอยู่ใน artifact `qa-results` |
| `seeded` | (เฉพาะ push เข้า `main` และสั่งเอง) `bun run qa:seed check`: ใส่บั๊กที่รู้ตัวลงไปแล้วดูว่าเทสต์จับได้ |
| `docker` | `scripts/ci-docker.sh`: build อิมเมจจริง รันบน volume ว่าง ตรวจว่าแอปรันเป็น uid 1000 และไฟล์ใน `/data` เป็นของ 1000, อัปโหลดแบบแบ่งชิ้นแล้วดาวน์โหลดกลับ (ต้องตรงกันทุกไบต์), ติดตั้งแพ็กเกจอัปเดต 99.0.0 ผ่านหน้าอัปเดตแล้วรอรีสตาร์ต, `FC_RUN_AS_ROOT=true` ต้องรันเป็น uid 0, ระบบไฟล์ root อ่านอย่างเดียว (เขียนนอก `/data` ต้องล้ม), `CapEff` ของ PID 1 เป็น 0, ตั้ง `no-new-privileges` แล้ว และ volume เก่าที่เป็นของ root ถูกเปลี่ยนเจ้าของได้ด้วยสิทธิ์ที่เหลือ |
| `security` | ตรวจช่องโหว่ (ดูหัวข้อถัดไป) ผลอยู่ใน artifact `security-results` |

เทสต์ทั้งหมดต้องผ่านบน runner ธรรมดา (ไม่ใช่ root ไม่มี Chromium) รันสคริปต์ Docker บนเครื่องตัวเอง (ต้องมี Docker และ Bun):

```bash
bash scripts/ci-docker.sh
```

สร้างคอนเทนเนอร์ volume และอิมเมจชั่วคราว (ชื่อขึ้นต้น `fc-ci-`) บนพอร์ตสุ่มของ `127.0.0.1` แล้วลบทิ้งเมื่อจบ ไม่ว่าผ่านหรือไม่
ถ้าเครือข่ายผ่านพร็อกซีที่แทรก CA ของตัวเอง ให้ชี้ `FC_CI_CA_BUNDLE=/path/ca.crt` เพื่อให้ขั้นตอน build อิมเมจเชื่อ CA นั้น

### ตรวจช่องโหว่ใน CI

งาน `security` ใน `.github/workflows/qa.yml` ตรวจสามอย่าง และ **ล้มเฉพาะช่องโหว่ระดับ HIGH หรือ CRITICAL ที่มีเวอร์ชันแก้แล้ว** (`ignore-unfixed`):

1. `bun audit --audit-level=high` ตรวจแพ็กเกจจาก `bun.lock` กับฐานข้อมูล advisory
2. Trivy `fs` บนโค้ด: ช่องโหว่ของแพ็กเกจ, ความลับที่หลุดในไฟล์, และการตั้งค่าผิดของ `Dockerfile` (Trivy ไม่ตรวจ `docker-compose.yml` ส่วนค่า hardening ของ compose ตรวจโดย `scripts/ci-docker.sh`)
3. Trivy `image` บนอิมเมจที่ build จาก `Dockerfile`: แพ็กเกจ Debian ของฐานและแพ็กเกจในอิมเมจ

**อ่านผล:** เปิด log ของ step `Trivy repository` / `Trivy image` จะเห็นตาราง (แพ็กเกจ, CVE, เวอร์ชันที่ติดตั้ง, เวอร์ชันที่แก้แล้ว) แก้โดยอัปเดตแพ็กเกจ (`bun update <ชื่อ>`) หรือเปลี่ยนแท็กฐานอิมเมจเป็นรุ่นใหม่
ไฟล์ SARIF ของทุกระดับ (รวม LOW/MEDIUM และที่ยังไม่มีเวอร์ชันแก้) อยู่ใน artifact `security-results` เปิดดูได้ด้วยโปรแกรมอ่าน SARIF
ถ้าต้องยอมรับข้อยกเว้นจริง ๆ ใส่ ID ใน `.trivyignore` โดย **ต้องมีบรรทัดคอมเมนต์บอกเหตุผลอยู่เหนือทุกรายการ** (เทสต์ตรวจข้อนี้) ตอนนี้มีรายการเดียวคือ `DS-0002` (ไม่มี `USER` ใน Dockerfile เพราะ entrypoint ต้องเริ่มเป็น root เพื่อ chown ครั้งเดียวแล้วลดเป็น `bun`)
งานนี้ต้องดาวน์โหลดฐานข้อมูล Trivy จึงต้องมีอินเทอร์เน็ต และยืนยันผลจริงได้บน GitHub Actions เท่านั้น

**ผลสแกนครั้งแรก (รอบ 9):** โค้ดและแพ็กเกจ npm ไม่พบช่องโหว่; อิมเมจพบ 17 รายการ (HIGH 14, CRITICAL 3) ทั้งหมดอยู่ในแพ็กเกจ Debian ของฐาน (perl-base, pcre2, sqlite, openssl, gzip) และมีรุ่นแก้แล้ว — `Dockerfile` จึงลงอัปเดตความปลอดภัยของ Debian (`apt-get upgrade`) ใน stage ที่ใช้รันทุกครั้งที่ build (ปิดได้ด้วย `--build-arg APT_UPGRADE=false` เฉพาะเครื่องที่เข้า mirror ของ Debian ไม่ได้ เช่น `FC_CI_NO_APT=1 bash scripts/ci-docker.sh`) ควร build อิมเมจใหม่เป็นระยะ (`docker compose build --pull`) เพื่อรับอัปเดตล่าสุด

## สำรองและกู้คืนข้อมูลระบบ

ถ้าดิสก์เสีย บัญชีผู้ใช้ รหัสผ่าน และการตั้งค่าจะหายทั้งหมด ระบบจึงสำรองข้อมูลระบบให้เองทุกวัน

- **สำรองอะไรบ้าง:** หนึ่งครั้ง = ไฟล์เดียว `file-center-backup-YYYYMMDD-HHMMSS.zip` (เวลาของเครื่อง server) มี `users.json` (ผู้ใช้และรหัสผ่านที่เข้ารหัสแล้ว), `settings.json`, `branding/` (โลโก้), `logs/audit.log`, `logs/system.log` และ `backup.json` (`{ version, createdAt, includesFiles }`)
  ไม่รวม session, ถังขยะ, ไฟล์อัปโหลดที่ยังไม่เสร็จ, เวอร์ชันที่อัปเดตผ่านเว็บ log เก่าที่หมุนไฟล์แล้ว (`audit.log.N`, `system.log.N`), `access.log` และ `launcher.log`
  ไฟล์ที่ผู้ใช้อัปโหลด (`storage`) ไม่รวมโดยค่าเริ่มต้นเพราะอาจใหญ่มาก ตั้ง `BACKUP_INCLUDE_FILES=true` เพื่อรวมไว้ในโฟลเดอร์ `storage/` ของ zip (ระบบตรวจพื้นที่ว่างก่อนตาม `MIN_FREE_SPACE`)
- **เมื่อไหร่:** ทุกวันในชั่วโมง `BACKUP_HOUR` (ค่าเริ่มต้นตี 3) และทันทีที่ครั้งล่าสุดที่สำเร็จเก่ากว่า 2 วัน (เช่น เปิดระบบครั้งแรก หรือเครื่องปิดอยู่ตอนตี 3) ตั้ง `BACKUP_HOUR=off` เพื่อปิดการสำรองอัตโนมัติ
  สำเร็จแล้วจะลบไฟล์ที่เก่าที่สุดให้เหลือ `BACKUP_KEEP` ไฟล์ (ค่าเริ่มต้น 7) ระหว่างเขียนไฟล์ชื่อจะลงท้าย `.partial` จึงไม่มีไฟล์ที่เขียนไม่ครบปนอยู่ในรายการ
- **เก็บที่ไหน:** `BACKUP_DIR` ค่าเริ่มต้นคือโฟลเดอร์ `backups` ข้าง `DATA_DIR` (Docker: `./data/backups`) ซึ่งอยู่บนดิสก์เดียวกับข้อมูล
  **ถ้าดิสก์นั้นเสีย ไฟล์สำรองก็หายไปด้วย** ควรชี้ไปดิสก์อื่น เช่น ใน Docker เพิ่ม volume `- /mnt/backup-disk/file-center:/backups` ใน `docker-compose.yml` แล้วตั้ง `BACKUP_DIR=/backups` ใน `.env`
  หรือดาวน์โหลดไฟล์สำรองเก็บไว้นอกเครื่องเป็นระยะ (หน้ารายการสำรองข้อมูลจะเตือนเมื่อยังอยู่ดิสก์เดียวกัน)
- **ผลการสำรอง** เขียนลง `data/backup-status.json` ทุกครั้ง หน้าภาพรวมแสดงผลและเตือนเมื่อล้มเหลวหรือเก่าเกิน 2 วัน:
  ```json
  { "status": "ok", "lastSuccess": "2026-10-08T20:00:00.000Z", "lastAttempt": "2026-10-08T20:00:00.000Z", "message": "สำรองข้อมูลสำเร็จ", "file": "file-center-backup-20261009-030000.zip", "size": 48213 }
  ```
  (`status` เป็น `"ok"` หรือ `"failed"`; เมื่อล้มเหลว `lastSuccess` ยังเป็นเวลาที่สำเร็จครั้งล่าสุด)
- **กู้คืน** (`POST /api/admin/backups/restore`) เฉพาะ admin และต้องใส่รหัสผ่านซ้ำเหมือนการติดตั้งอัปเดต (ใส่ผิดซ้ำจะถูกล็อก) ระบบจะ
  1) สำรองสถานะปัจจุบันไว้ก่อนหนึ่งไฟล์ (ถ้ากู้ผิดไฟล์ก็กู้กลับจากไฟล์นี้ได้) 2) ตรวจว่า `users.json` ในไฟล์สำรองอ่านได้และมีผู้ดูแลระบบอย่างน้อยหนึ่งคน
  3) แทนที่ `users.json`, `settings.json` และ `branding/` แล้ว 4) รีสตาร์ตแอปผ่าน launcher (ต้องเริ่มด้วย `bun start` หรือ Docker) ผู้ที่ login อยู่ยัง login ต่อได้ถ้าบัญชีมีอยู่ในไฟล์สำรอง
  ไฟล์ใน `storage` **ไม่ถูกกู้คืนจากหน้าเว็บ** แม้ไฟล์สำรองจะรวมไว้ ให้แตก `storage/` จาก zip ด้วยมือเมื่อต้องการ
- **ดิสก์เสียทั้งลูก:** ติดตั้งระบบใหม่ เริ่มระบบหนึ่งครั้งแล้วหยุด จากนั้นแตก `users.json`, `settings.json` และ `branding/` จากไฟล์สำรองลงใน `DATA_DIR` (Docker: `data/system/`) แล้วเริ่มระบบอีกครั้ง

## API โดยสรุป

ทุกคำสั่งที่เปลี่ยนข้อมูลต้องส่งหัว `X-CSRF-Token` ที่ได้จาก `GET /api/session` ผิดพลาดตอบเป็น `{ "error": "ข้อความ", "code": "fs.bad-name", "params": {} }`

- `code` คงที่ไม่เปลี่ยนตามภาษา (รายการทั้งหมดอยู่ใน `src/messages.ts` แบ่งตามหมวด เช่น `auth.locked`, `files.name-taken`) ส่วน `params` คือค่าที่เติมในข้อความ เช่น `{ "seconds": 30 }`
- `error` เป็นภาษาไทยหรืออังกฤษตามคำขอ: หัว `X-Lang: th` หรือ `en` ก่อน ถ้าไม่มีใช้คุกกี้ `fc_lang` (`th`/`en` ที่หน้าเว็บตั้งตามภาษาที่เลือก)
  ถ้าไม่มีใช้ `Accept-Language` ของเบราว์เซอร์ ถ้าไม่ระบุเลยเป็นภาษาไทย
  คำเตือนในหน้าภาพรวม (`warnings` ของ `GET /api/admin/status`) มี `code`, `message` และ `params` แบบเดียวกัน ส่วน log และประวัติการใช้งานยังเป็นภาษาไทยเสมอ
- ลิงก์ดาวน์โหลดที่เบราว์เซอร์เปิดในแท็บ (`/api/download`, `/api/batch/:token`, `/api/admin/logs/download`, `/api/admin/activity/export`,
  `/api/admin/backups/:name/download`, `/api/s/:token/download`) ถ้าล้มเหลวจะได้หน้า HTML สั้น ๆ แทน JSON: รหัสสถานะเดิม ข้อความตามภาษา รหัส และลิงก์กลับหน้าหลัก
  (นับเป็นการเปิดในแท็บเมื่อมี `Sec-Fetch-Mode: navigate` หรือ `Accept` มี `text/html` และไม่มีหัว `X-Lang`) การเรียกด้วย fetch ยังได้ JSON เหมือนเดิม
- รหัสเดิมที่หน้าเว็บใช้อยู่ไม่เปลี่ยน: `csrf`, `must-change-password`, `disk-full`, `not-supervised` และคำเตือน `errors`

## ต่างจาก FileGator ต้นแบบอย่างไร

- ไม่มีการ `chmod` ผ่านหน้าเว็บ (ไม่มีความหมายบน Windows/Docker)
- รหัสผ่านเก็บด้วย argon2id ผู้ใช้เดิมจาก FileGator ย้ายมาไม่ได้ ต้องสร้างใหม่ (ตามที่ตั้งใจไว้ว่าเริ่มใหม่ทั้งหมด)
- API เป็น REST (`/api/...`) ไม่ใช้รูปแบบ `/?r=/route`
- ไฟล์ที่ซ้ำชื่อตอนอัปโหลดจะถูกตั้งชื่อใหม่ เช่น `report (1).pdf` ไม่เขียนทับ
- session ของผู้เยี่ยมชมอยู่ในหน่วยความจำและมีเพดาน ส่วน session ของผู้ที่เข้าสู่ระบบเก็บในดิสก์ จึงอยู่รอดหลังรีสตาร์ต

## ข้อจำกัดที่ควรรู้

- ทดสอบบน Linux และด้วย Docker Desktop บน Windows แล้ว แต่การรันด้วย Bun บน Windows โดยตรง (ไม่ผ่าน Docker) ยังไม่ได้ทดสอบ (พาธ, `statfs`, ชื่อไฟล์ต้องห้ามของ Windows)
- ชื่อไฟล์ที่ไม่ใช่ ASCII ส่งไปในหัว `Content-Disposition` ตามมาตรฐาน RFC 6266 (`filename*=UTF-8''...`) ควรลองดาวน์โหลดไฟล์ชื่อไทยในเบราว์เซอร์ที่ใช้จริงอีกครั้ง
- ชื่อไฟล์/โฟลเดอร์ห้ามมีอักขระ `\ / : * ? " < > |` (เพื่อให้ย้ายข้ามระบบปฏิบัติการได้) และยาวได้ไม่เกิน 255 ไบต์ ซึ่งเท่ากับภาษาไทยประมาณ 85 ตัวอักษร
  (ชื่อที่ยาวเกินในไฟล์ zip จะถูกตัดให้สั้นลงโดยคงนามสกุลไว้)
- ผู้ใช้ที่ได้รหัสผ่านเริ่มต้นจากระบบต้องเปลี่ยนรหัสผ่านก่อน จึงจะเรียก API อื่นได้ (server บังคับ ไม่ใช่แค่หน้าเว็บ)
- โฟลเดอร์ระบบ `/public` และ `/users` คัดลอกได้ แต่ลบ ย้าย หรือเปลี่ยนชื่อไม่ได้
- **จำนวนและขนาดไฟล์ในหน้าภาพรวมอาจช้ากว่าความจริงได้ราวหนึ่งนาที** ระบบนับไฟล์อยู่เบื้องหลัง (ไม่ให้ผู้ใช้คนอื่นต้องรอ) และแสดงผลที่นับไว้ล่าสุดทันที
  `GET /api/admin/status` ตอบ `stale: true` เมื่อตัวเลขเก่ากว่าหนึ่งนาทีและกำลังนับใหม่ ครั้งแรกหลังติดตั้งที่ยังไม่เคยนับเลยจะได้ `storage: null` (เปิดหน้าใหม่อีกครั้งเมื่อนับเสร็จ)
  ผลที่นับเก็บไว้ใน `stats-cache.json` ใน `DATA_DIR` หลังรีสตาร์ตจึงเห็นตัวเลขล่าสุดทันที
- ค้นหาไฟล์ตามชื่อโดยเดินดูโฟลเดอร์ตอนค้นหา ไม่มีดัชนี จึงช้าลงถ้ามีไฟล์หลักแสนไฟล์ขึ้นไป (จำกัดที่ 50,000 รายการต่อการค้นหา)
  การค้นหาและการคัดลอกทำทีละชุดสลับกับคำขออื่น ผู้ใช้คนอื่นจึงไม่ต้องรอ
- การคัดลอกข้ามลิงก์ (symlink) ไปเสมอ ไม่ตามลิงก์และไม่คัดลอกตัวลิงก์ ถ้าคัดลอกไม่สำเร็จกลางทาง (เช่น ดิสก์เต็ม) ส่วนที่คัดลอกไปแล้วจะถูกลบออก
